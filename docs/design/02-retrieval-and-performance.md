# myc — L2: Ретривал и производительность

> Лейн L2 дизайн-сессии. Контекст: `docs/design/00-brief.md`.
> Ответственность лейна: бюджеты §3 брифа должны быть **достижимыми конструктивно**,
> а не декларативными. Всё, что не укладывается в горячий путь, — в фон.

## 1. Решения

| Вопрос | Выбор | Почему | Что отвергли |
|---|---|---|---|
| Форм-фактор CLI | Один бинарь `bun build --compile --minify --bytecode` | Холодный старт < 60 мс достижим только без распаковки/резолва модулей; `--bytecode` снимает парс JS (−8–15 мс) | `bun myc.ts` из исходников (старт 150–300 мс), SEA Node (старт 60–120 мс) |
| Демон | Опциональный `mycd` на unix-сокете, **не требование** | Бриф: «локально без демона». Демон убирает старт и держит модель тёплой, но one-shot CLI обязан укладываться сам | Обязательный демон (нарушает §2), фоновый сервис через systemd/launchd как единственный путь |
| Гибридный ретривал | FTS5(BM25) + dense-вектор + граф-расширение, фьюжн RRF **одним SQL-запросом** | Урок socraticode: один round-trip к БД вместо трёх; RRF не требует калибровки шкал bm25 и косинуса | Три запроса с фьюжном в коде (3× латентность БД), линейная комбинация нормализованных скоров (нестабильна к выбросам bm25) |
| RRF константы | k = 60, w_fts = 1.0, w_vec = 1.0, cut-off источников = 100 | k=60 — стандарт, устойчив; equal weights до появления данных для калибровки | Автовзвешивание по длине запроса в v1 (некалибровано, риск регрессий) |
| Локальные эмбеддинги | ONNX Runtime в процессе Bun; модель по умолчанию `bge-small-en-v1.5` INT8, 384 dim; опция `multilingual-e5-small` INT8 для смешанных ru/en корпусов | 384 dim int8 = 384 Б/узел → полный скан 100k ≈ 5–8 мс; bge-small сильнее MiniLM на ретривале (MTEB), e5-small закрывает русский | float32-модели (4× память и время скана), gte-base/bge-base 768 dim (2–3× латентность при +1–2 п.п. качества) |
| ONNX-рантайм | `onnxruntime-web` (WASM SIMD) внутри бинаря по умолчанию; `onnxruntime-node` (натив) — конфиг-опция | WASM сохраняет однофайловость `--compile`; нативный .node ломает one-binary | Натив по умолчанию (таскать .dylib/.so рядом с бинарём) |
| Фолбэк эмбеддингов | **Никакого молчаливого фолбэка.** Деградация = BM25+граф + флаг `degraded` в каждом ответе и в `myc status` | Ловушка memora: молчаливый TF-IDF наполнял базу мусором | Любой автоматический даунгрейд модели без явного конфига |
| Векторный поиск в SQLite | `sqlite-vec` (vec0), хранение int8 + float32, скан int8 → rerank float32 | sqlite-vec — живой, SIMD, brute-force быстрый до ~100k int8; int8-скан + точный rerank топ-200 даёт ≈ exact-качество | sqlite-vss (заброшен), свой ANN-индекс (не-цель §6), faiss через N-API (ломает one-binary) |
| Векторный поиск в Postgres | `pgvector` HNSW (halfvec), m=16, ef_construction=64, ef_search=40 | При ≥100k HNSW 1–3 мс против 100–300 мс exact-скана; halfvec вдвое меньше памяти индекса | IVFFlat как дефолт (нужен периодический retrain, recall ниже при том же бюджете) |
| Граница embedded/server | SQLite до ~100k узлов и одной машины; Postgres при команде/нескольких машинах/>100k | Brute-force int8 перестаёт влезать в бюджет за 100k; WAL не решает multi-host | Единый бэкенд «всегда Postgres» (ломает $0 и офлайн) |
| Sparse в Postgres | `tsvector` + `ts_rank_cd` как sparse-скор в RRF; опционально ParadeDB `pg_search` (настоящий BM25) | ts_rank_cd не BM25, но как источник рангов для RRF достаточен; pg_search — необязательное усиление | Обязательный pg_search (тяжёлая зависимость для MVP) |
| Запись | Синхронно: insert + FTS + oplog в одной транзакции. Асинхронно: эмбеддинг, absorb, суммаризация | Бюджет записи 5 мс несовместим с эмбеддингом (4–8 мс) и LLM-вызовами | Эмбеддинг на записи (удваивает-траивает бюджет), LLM в горячем пути (запрещено §3) |
| Инвалидация кешей | По монотонному `oplog.seq`: кеш-запись хранит seq, валидация — одним prepared statement (~50 мкс) | Oplog уже нужен L1 для синка; seq-валидация дешевле TTL-угадывания и не протухает | TTL-only (протухшие результаты), инвалидация по таблицам (грубо, ложные промахи) |
| Кросс-процессная координация | Только механизмы SQLite: WAL, `BEGIN IMMEDIATE`, `busy_timeout=5000`, поллинг `meta.last_seq` | Урок socraticode: самопальные файловые локи течут и врут; SQLite уже умеет сериализацию писателей | Lock-файлы рядом с БД, advisory-демоны |
| Ретривал | Бюджетированный: `limit` ≤ 12 (max 100), `char_budget` = 12 000 (max 64 000), `timeout_ms` = 20 локально / 200 сервер | Урок TencentDB: «влить всё» убивает и латентность, и контекст агента | Нелимитированный digest, таймаут только на весь запрос без частичной отдачи |
| Обрезка по бюджету | Двухпроходная сборка: сначала crux всех, потом апгрейд топов до полного текста; резерв 10% под рёбра; никогда не резать посередине узла | Не ломаем смысл: узел либо целиком, либо как summary | Жёсткая обрезка по символам (обрыв предложений) |
| Watch | Дебаунс 2 с (socraticode), очередь с приоритетами, чекпойнты по content-hash | 2 с — проверенный баланс; content-hash пропуски делают рестарт бесплатным | Дебаунс 200 мс (гроздья событий от git checkout), обработка каждого события синхронно |
| Бенчмарки | Nightly-джоб на фиксированном раннере, baseline JSON в репо, фейл при регрессии p95 > 15% или нарушении бюджета §3 | Ловим регрессии до релиза; публикуем честные числа | Бенч на PR (шумно на shared-раннерах), «меряем руками» |

## 2. Спецификация

### 2.1 Горячий путь запроса

Три режима исполнения одного и того же кода:

1. **One-shot CLI** (`myc show x`, `myc prime`, `myc search ...`) — процесс рождается и умирает на запрос.
2. **MCP-сервер** (`myc mcp`) — персистентный процесс, JSON-RPC по stdio. Старт амортизирован хостом агента.
3. **Опциональный демон** (`mycd`) — unix-сокет `.myc/myc.sock`; CLI-диспетчер пробует сокет, при промахе (таймаут коннекта 5 мс) идёт one-shot путём. Демон **никогда не автостартует молча** — только `myc daemon start` или `daemon.autostart = true` в конфиге.

#### Стадии one-shot CLI: `myc show bd-a3f8` (бюджет: cold < 60 мс, сам запрос p99 < 3 мс)

| # | Стадия | Бюджет | Что делаем / что выкинули |
|---|---|---|---|
| 1 | exec + загрузчик ОС | 10–15 мс | Статически слинкованный бинарь `--compile`; никаких dylib, кроме системных |
| 2 | Старт JSC + загрузка байткода | 12–18 мс | `--bytecode` убирает парс ~1.5 МБ JS-бандла; `--minify` уменьшает I/O |
| 3 | Инициализация модуля | 2–4 мс | **Ленивые импорты**: onnx, tokenizer, веб-UI, MCP — `await import()` по месту. В топ-левеле только SQLite, arg-парсер, рендер |
| 4 | Конфиг | 0.5–1 мс | Фиксированные пути `.myc/config.toml` + `~/.config/myc/config.toml`, без glob и без подъёма по дереву выше git-root (git-root кешируется в `.myc/` при `myc init`) |
| 5 | Открытие SQLite + PRAGMA | 2–4 мс | `journal_mode=WAL` уже выставлен при init (не выставляем на каждом старте — это write); на старте только `busy_timeout`, `mmap_size=268435456` (256 МБ), `cache_size=-20000` (20 МБ) |
| 6 | Подготовка statement | 0.2–0.5 мс | Только statements нужного под команду; `show` — один `SELECT ... WHERE id=?` |
| 7 | Запрос | 0.5–2 мс | PK-lookup + индекс по oplog для `recent` |
| 8 | Рендер + write(1) | 0.3–1 мс | Буферизованный вывод одним write; никакого pretty-пейджинга при не-tty |
| — | **Итого типичный** | **30–45 мс** | Запас до 60 мс — под холодный page cache |

Что выкинуто из горячего пути CLI целиком: телеметрия (батч-файл, флашит фоновая запись), проверка обновлений (никогда в горячем пути; фоновый `myc doctor`), DNS/сеть (запрещена §3), загрузка embedding-модели в командах, которые её не зовут.

#### Стадии `myc prime` (бюджет p99 < 30 мс, без холодного старта)

Prime — **набор заранее подготовленных запросов, без эмбеддингов**:

| Стадия | Бюджет |
|---|---|
| (если one-shot: стадии 1–5 из таблицы выше — параллельно с запросами стартовать нельзя, но они и есть «холодный старт < 60 мс») | — |
| Открытие + statements (в MCP/демоне — 0) | 0–4 мс |
| `ready`-очередь (задачи без открытых блокеров, индекс по статусу) | 1–3 мс |
| L3/L2 дайджест скоупа (предвычисленная таблица `digest_cache`, инвалидация по seq) | 0.5–2 мс |
| Закреплённая память + открытые риски (индекс `nodes(pinned, layer)`) | 0.5–2 мс |
| Хвост oplog (последние 20 событий, `seq DESC LIMIT 20`) | 0.3–1 мс |
| Бюджетная сборка + рендер (см. 2.7) | 1–3 мс |
| **Итого warm (MCP/демон)** | **4–13 мс** |

Prime **не** вызывает эмбеддер: семантический поиск в prime не нужен — это детерминированный бутстрап по графу и слоям. Прогрев модели — отдельно (2.6).

#### Гибридный поиск `myc search` (бюджет p99 < 25 мс @ 100k узлов, включая эмбеддинг запроса)

| Стадия | Бюджет | Комментарий |
|---|---|---|
| Токенизация запроса | 0.3–0.8 мс | WASM-токенизатор, загружен с моделью |
| Эмбеддинг запроса (тёплая сессия) | 3–7 мс | bge-small INT8 WASM SIMD, ~30 токенов; кеш по sha1(query) (2.6) |
| Один SQL round-trip: FTS top-100 + vec top-100 + RRF + бусты + фильтры | 6–12 мс | Запрос из 2.2; внутри: FTS 2–4 мс, int8-скан 5–8 мс @100k |
| Rerank float32 топ-200→50 | 0.3–0.8 мс | 200 × 1536 Б — из page cache |
| Граф-расширение 1–2 хопа (15 сидов, потолок веера 64 на хоп, 12 сидов второго) | 1–3 мс | Индекс `edges(src)` (PK), `edges(dst)`; замер: p50 +0.12, p95 +1.71, p99 +1.70 мс на 100k узлов / 320k рёбер (`bench/graph-eval.ts --latency`) |
| Гидратация + бюджетная сборка | 1–3 мс | 12 узлов × ~1 КБ |
| **Итого** | **12–26 мс** | Хвост > 20 мс — когда скан идёт по холодному page cache |

Первая стадия, которую режем под таймаутом: граф-расширение (отдаём без него, флаг `partial`).

### 2.2 Гибридный ретривал и RRF

Формула RRF для узла `d`:

```
score_rrf(d) = Σ_i  w_i / (k + rank_i(d))
  k  = 60                      — константа сглаживания
  w_fts = 1.0, w_vec = 1.0     — веса источников (v1, калибруем бенчем 2.10)
  rank_i = ранг узла в источнике i; отсутствие в источнике → rank = 1000 (штраф)
  cut-off каждого источника: top-100
```

Бусты (мультипликативно, после RRF):

```
boost(d) = (1 + 0.30·[P0] + 0.15·[P1] − 0.10·[P3])
         × (1 + 0.25·exp(−age_days(d)/90))          — свежесть, τ=90 дней
         × layer_w(d)                                — prime-профиль: L3 1.2 / L2 1.1 / L1 1.0 / L0 0.9
final(d) = score_rrf(d) × boost(d)
```

`layer_w` — параметр профиля запроса: `prime`-профиль выше, `deep`-профиль инвертирует (L0/L1 1.15, L3 0.9). Профиль передаётся из CLI/MCP (`--profile prime|deep`, дефолт `balanced`: все 1.0).

**Все семь чисел выше — конфигурация, а не литералы в коде** (`HybridConfig`:
`priorityBoostP0/P1`, `priorityPenaltyP3`, `freshnessAmplitude`,
`freshnessTauDays`, `layerWeights`; секция `[retrieval]` в `workspace.toml`
разбирается `boostSettingsFromToml`). Причина не в гибкости: пока коэффициент
зашит в выражение, точку «бусты выключены» нельзя получить, не правя исходник,
то есть нельзя ИЗМЕРИТЬ, что бусты вообще что-то делают.

**Замер** (memory-vhchz7wzfjh9). Корпус `bench/boost-queries.json`: 25 тем по 3
узла, внутри темы все слова запроса стоят дословно в title каждого из трёх —
BM25 их не разводит, порядок решают ровно бусты. Вектор выключен, limit 10.
Пересчёт — `bun run bench/boost-eval.ts`, результат `bench/boost-eval.json`,
сверка — `packages/retrieval/src/boost.test.ts`.

| | MRR@10 | P@1 |
|---|---|---|
| бусты обнулены (`NO_BOOST_OVERRIDES`) | 0.520 | 0.200 |
| бусты §2.2 | **0.867** | **0.800** |
| сдвиг | **+0.347** | **+0.600** |

По группам (MRR): свежесть 0.400 → 1.000, приоритет 0.400 → 1.000, слой на
бутстрапе (`prime`) 0.800 → 1.000, слой за конкретным фактом (`deep`) 0.400 →
1.000. Пятая группа — контрольная: там правильный ответ старый, P2 и в нижнем
слое, а шум свежий, P0 и L3, и бусты честно **вредят**: 0.600 → 0.333. Это
цена механики, а не её опровержение: платить ею стоит, потому что четыре
группы из пяти выигрывают больше, — но цена названа числом и закреплена
тестом, а не умолчана.

Цена по латентности: `search` p95 7.204 → 7.358 мс, p99 7.964 → 7.958 мс
(`bun run scripts/bench-latency.ts`, бюджет p99 < 25 мс) — разница в пределах
разброса машины между прогонами.

Граф-расширение на 1–2 хопа (после RRF, перед бюджетной сборкой). Реализация —
`packages/retrieval/src/hybrid.ts`, замер — `bench/graph-eval.ts`:

```
seeds = top_15 лексического пула                 # обход идёт В ТОМ ЖЕ round-trip,
                                                 # что и лексика, то есть ДО решения о векторе
expanded = {}
score[s] = final(s) для каждого сида
for hop in 1..graph_max_hops:                    # умолчание 2
  decay = graph_decay_by_hop[hop-1]              # умолчание [0.5, 0.5]
  for v in источники этого хопа:                 # хоп 1 — сиды; хоп 2 — top-12 узлов хопа 1
    for e in edges(v):                           # оба направления, e.weight ≥ 0.3
      n = other_end(e)
      if n уже найден лексикой/вектором: continue
      cand = score[v] × decay × e.weight × type_w[e.type]
      expanded[n] = max(expanded[n], cand); score[n] = expanded[n]
  оставить не больше graph_hop_fanout = 64 узлов этого хопа
result = merge(result, expanded, keep=max_score, cap = 2 × (15 + 12))
```

Три вещи здесь не косметические.

**Затухание перемножается по пути, а не назначается абсолютом на глубину.** Узел
второго хопа платит за оба ребра, по которым до него дошли: при весах рёбер 1.0 и
`[0.5, 0.5]` он получает 0.25 × final(сида) — то же число, что стояло в прежнем
наброске, — но при слабом промежуточном ребре путь дешевеет честно, а не
задним числом.

**Типы рёбер участвуют в весе.** `parent` и `blocks` означают «это про то же
самое», а `mentions` и `touches` — «здесь упомянуто имя»; на втором хопе разница
решающая, потому что через упоминания граф связен почти весь. Умолчание —
единицы, кроме `mentions`/`touches` = 0.5. Замер (`--sweep`): MRR@10 группы
`typed` 0.333 без весов против 0.500 с ними, общий MRR 0.389 → 0.422.

**Цену обхода задаёт конфиг, а не данные.** Два потолка — `graph_hop_fanout` (64
узла на хоп) и `graph_hop2_seeds` (12 узлов первого хопа идут сидами второго) —
существуют потому, что без них стоимость определяется степенью самого связного
узла окрестности: замер на 100k с хабами даёт p95 +1.71 мс с потолками против
+23.42 мс без них при бюджете поиска 25 мс.

Что делает обход, видно в ответе (`mode_used.graph`: глубина, сколько узлов дал
каждый хоп, упёрся ли веер в потолок, сколько дошло до выдачи) и в каждом хите
(`graphDepth`). Это И2: расширение добавляет узлы, в которых НЕТ НИ ОДНОГО СЛОВА
запроса, и пользователь обязан отличать связанное от найденного.

Замер качества (`bench/graph-eval.ts`, корпус `bench/graph-queries.json`:
105 узлов, 60 рёбер, 25 запросов, вектор выключен). В группах `hop1`/`hop2`/`typed`
правильный ответ не содержит ни одного слова запроса — без обхода он не находится
вовсе:

| вариант | MRR@10 | P@1 | найдено |
|---|---|---|---|
| расширение выключено (`graph_max_hops = 0`) | 0.193 | 0.080 | 10/25 |
| один хоп (`graph_max_hops = 1`) | 0.355 | 0.080 | 20/25 |
| 1–2 хопа (умолчание) | **0.422** | 0.080 | 25/25 |

По группам: `hop1` 0.000 → 0.500, `hop2` 0.000 → 0.000 → 0.333 (второй хоп —
отдельный вклад, одним хопом эта группа недостижима), `typed` 0.000 → 0.500,
контроль `lexical` 0.633 без изменений, контроль `distractor` 0.333 → 0.143 —
там обход обязан вредить, и вредит.

P@1 не двигается ни на сотую, и это свойство механизма, а не недоработка замера:
узел из обхода получает долю счёта своего сида (decay < 1) и поэтому НИКОГДА не
встаёт выше него. Обход меняет то, что стоит на местах со второго по десятое, —
MRR@10 это ловит, P@1 по построению не может.

Перекалибровка затухания: `bun run bench/graph-eval.ts --sweep`. На текущем
корпусе d2 в диапазоне 0.1–0.7 неразличим (MRR@10 = 0.422 во всех точках);
разделяется только d2 = 1.0 (0.435), но это отказ от затухания по глубине как
такового. Поэтому взято d2 = d1 = 0.5 — равномерное геометрическое затухание,
самое простое из тех, что перебор не отверг.

Один SQL-запрос (SQLite-диалект). Фильтры скоупа/ACL/слоя **внутри CTE источников** — фильтрация до ранжирования (урок TencentDB), иначе top-100 источника вымывается фильтром:

```sql
WITH params AS (SELECT :now_ms AS now_ms),
fts AS (
  SELECT n.id, rank() OVER (ORDER BY bm25(nodes_fts, 10.0, 1.0, 1.0)) AS r
  FROM nodes_fts f JOIN nodes n ON n.rowid = f.rowid
  WHERE nodes_fts MATCH :q
    AND n.scope IN (SELECT value FROM json_each(:scopes))
    AND n.layer BETWEEN :layer_min AND :layer_max
    AND n.acl_rank <= :caller_rank
  LIMIT 100
),
vec AS (
  SELECT n.id, rank() OVER (ORDER BY v.distance) AS r
  FROM (
    SELECT node_id, distance FROM vec_nodes_i8
    WHERE embedding_i8 MATCH :qvec_i8 AND k = 200
  ) v JOIN nodes n ON n.id = v.node_id
  WHERE n.scope IN (SELECT value FROM json_each(:scopes))
    AND n.layer BETWEEN :layer_min AND :layer_max
    AND n.acl_rank <= :caller_rank
  ORDER BY v.distance LIMIT 100
),
fused AS (
  SELECT coalesce(f.id, v.id) AS id,
         1.0/(60 + coalesce(f.r, 1000)) + 1.0/(60 + coalesce(v.r, 1000)) AS rrf
  FROM fts f FULL OUTER JOIN vec v USING (id)
)
SELECT n.id, n.kind, n.layer, n.priority, n.crux, n.content, n.updated_at,
       f.rrf
       * (1 + 0.30*(n.priority=0) + 0.15*(n.priority=1) - 0.10*(n.priority=3))
       * (1 + 0.25*exp(-((params.now_ms - n.updated_at)/86400000.0)/90.0))
       * (CASE n.layer WHEN 3 THEN 1.2 WHEN 2 THEN 1.1 WHEN 1 THEN 1.0 ELSE 0.9 END)
       AS score
FROM fused f JOIN nodes n ON n.id = f.id, params
ORDER BY score DESC
LIMIT :limit;
```

Rerank float32: vec-CTE отдаёт top-200 по int8; после RRF берём top-50 узлов, дочитываем их float32-вектора (`vec_nodes_f32`) одним `IN (...)`, пересчитываем косинус в коде (50 × 384 FMA — микросекунды), подменяем `rank` vec-источника. Дёшево, поднимает точность int8-скана до ≈ exact.

Postgres-диалект тот же по форме: `nodes_fts` → `tsv @@ plainto_tsquery(:cfg, :q)` со скором `ts_rank_cd`, `vec_nodes_i8 MATCH` → `ORDER BY emb_half <=> :qvec LIMIT 100` (HNSW делает это индексным сканом). Два диалекта генерируются одним билдером запросов — не руками.

### 2.3 Локальные эмбеддинги в процессе Bun

**Модели:**

| Модель | dim | Параметры | INT8 на диске | Query-латентность (M-серия, WASM SIMD) | Когда |
|---|---|---|---|---|---|
| `bge-small-en-v1.5` (default) | 384 | 33M | ~34 МБ | 3–7 мс @ 32 tok | Англоязычные/кодовые корпуса |
| `multilingual-e5-small` (опция) | 384 | 118M | ~118 МБ | 8–15 мс | Смешанные ru/en корпуса |
| API-бэкенд (OpenAI/Anthropic-совместимый) | 1536/1024 | — | — | 80–400 мс (сеть!) | Только явным конфигом `embedder.backend = "openai"` |

Правила:
- Размерность фиксируется на БД при `myc init` (колонка `meta.embed_dim`); смена модели = `myc reembed` (полная переиндексация в фоне, поиск в это время работает по старым векторам + BM25).
- API-бэкенд **не может быть дефолтом** (§3: сеть в горячем пути запрещена, $0). При нём `search` честно выходит за 25 мс — это видно в `myc status` и в ответе (`embed_ms`).
- Квантизация int8 per-vector: `q = round(127 × v / max|v|)`, scale храним рядом (4 Б). Косинус int8≈float32 с rerank-шагом из 2.2.

**Рантайм и пулы:**

```
Embedder
├── query_session  — одна ONNX-сессия на главном потоке, ТОЛЬКО одиночные
│                    тексты (поисковый запрос). Создаётся лениво при первом
│                    search, живёт в процессе. intra_op_threads = 2.
└── batch_pool     — N = clamp(floor(cores/4), 1, 4) воркеров (Worker API),
                     каждый со своей сессией. Только фоновые батчи из
                     embed_queue (до 32 текстов, паддинг до 64 tok,
                     обрезка 512 tok). intra_op_threads = 1.
```

Почему query не через воркер: IPC round-trip Bun Worker = 0.3–1.5 мс и лишний serialized copy Float32Array — на бюджете 25 мс это заметно; главный поток во время query-эмбеддинга всё равно ждёт. Фоновые батчи наоборот обязаны быть вне главного потока, чтобы не блокировать MCP-цикл.

Стоимость одного query-эмбеддинга (bge-small INT8, M-серия): токенизация 0.3–0.8 мс + inference 3–6 мс + mean-pool/нормализация < 0.1 мс = **4–7 мс p50, ≤ 9 мс p99 (тёплая)**. В бюджет 25 мс ложится с запасом 2×. Холодная загрузка модели (первый search процесса): 150–400 мс WASM-инстанцирование + mmap весов — поэтому MCP/демон прогревают её при старте (2.6), а one-shot CLI при `search` показывает её честно в `embed_ms`.

**Громкая деградация (антидот memora):**

- Состояния эмбеддера: `ok` / `degraded(reason)` / `missing`. Причины: `model_not_downloaded`, `backend_unreachable`, `dimension_mismatch`, `load_error`.
- Любое не-`ok` состояние: (1) поле `degraded: {embedder: reason}` в каждом ответе `search`/`prime`; (2) `myc status` печатает его первым блоком и выходит кодом `2` в `--json`-режиме флагом; (3) фоновый индексер **останавливает** наполнение векторов (не пишет мусор), очередь копится с метрикой `embed_queue_depth`.
- Ретривал при деградации: w_vec = 0 (источник исключается из RRF), работают FTS + граф. Это **не** молчаливый фолбэк: пользователь видит деградацию в каждом ответе.
- Запрещено: автоматический даунгрейд модели, подмена API→локальная (и наоборот) без явного конфига, TF-IDF-заглушки.

### 2.4 Векторный поиск внутри БД: ANN против скана

**SQLite + sqlite-vec (embedded):**

```sql
CREATE VIRTUAL TABLE vec_nodes_i8 USING vec0(
  node_id TEXT PRIMARY KEY,
  embedding_i8 int8[384],
  +scope TEXT                       -- auxiliary-фильтр сканом
);
CREATE TABLE vec_nodes_f32 (        -- обычная таблица, blob 1536 Б
  node_id TEXT PRIMARY KEY REFERENCES nodes(id),
  embedding_f32 BLOB NOT NULL
);
```

sqlite-vec — brute-force KNN с SIMD. Издержки скана по int8 384 dim (≈384 Б/вектор, memory-bound):

| Узлов | int8 скан | float32 скан | Вердикт |
|---|---|---|---|
| 10k | 0.5–1 мс | 1.5–3 мс | Exact, даже float32 |
| 100k | 5–8 мс | 15–30 мс | int8-скан + f32-rerank топ-200 (2.2) |
| 1M | 50–100 мс | 150–300 мс | **Вне бюджета** → префильтр по scope/layer до ≤100k кандидатов, иначе Postgres |

Правило: embedded-режим заявляем **до 100k узлов в скоупе поиска**. Глобальный поиск по 1M-репозиторию = server-режим. Это честная граница, а не «потом оптимизируем».

**Postgres + pgvector (server):**

```sql
CREATE EXTENSION vector;
ALTER TABLE nodes ADD COLUMN emb_half halfvec(384);
CREATE INDEX nodes_emb_hnsw ON nodes USING hnsw (emb_half halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);
-- запрос: SET LOCAL hnsw.ef_search = 40;
```

| Размер | HNSW (ef_search=40) | Exact-скан (halfvec) | Recall HNSW |
|---|---|---|---|
| 100k | 1–3 мс | 40–80 мс | ~0.97 |
| 1M | 2–6 мс | 400–800 мс | ~0.96 |

Параметры: `m=16` (больше — память и время билда растут, recall +~1 п.п.), `ef_construction=64` (билд 100k/384d ≈ 1–2 мин), `ef_search=40` — точка, где recall@10 ≈0.97 при 1–3 мс. IVFFlat (`lists=316` для 100k, `probes=10`) — только если HNSW-память критична: recall ~0.90 при том же времени, плюс дрейф при вставках. Где ANN, а где скан: **до 10k — скан везде (SQLite даже без vec0-индекса), 10k–100k — sqlite-vec int8+rerank, ≥100k — HNSW**.

Индексы строятся фоном (2.5): строки с `emb_half IS NULL` видны поиску через BM25, лаг показывается в `/status` как `embed_queue_depth`.

### 2.5 Конвейер индексации

Принцип: **на записи синхронно — почти ничего** (бюджет 5 мс), всё остальное — очереди в той же БД.

Синхронная транзакция записи (`create`/`remember`), один `BEGIN IMMEDIATE`:

```
1. INSERT INTO nodes (...)                       — ~0.5 мс
2. INSERT INTO nodes_fts (rowid, ...)            — ~0.5–1 мс (FTS5 триггером или явно)
3. INSERT INTO embed_queue (node_id, prio=10)    — ~0.1 мс
4. INSERT INTO oplog (seq, op, id, ...)          — ~0.2 мс; seq = nextval
COMMIT                                           — WAL, synchronous=NORMAL: ~1–2 мс
```

Итого 2–4 мс p99. Эмбеддинг, absorb-классификация, суммаризация L0→L1→L2 — только фоном.

Очереди и чекпойнты:

```sql
CREATE TABLE embed_queue (
  node_id     TEXT PRIMARY KEY REFERENCES nodes(id) ON DELETE CASCADE,
  prio        INTEGER NOT NULL DEFAULT 100,   -- 10 = пользовательская запись,
                                              -- 50 = watch, 100 = bulk-import
  enqueued_at INTEGER NOT NULL,
  attempts    INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE index_checkpoint (
  stream     TEXT PRIMARY KEY,                -- 'docs', 'watch', 'import:<uuid>'
  last_id    TEXT NOT NULL,
  last_hash  TEXT NOT NULL,                   -- sha1 контента последнего батча
  updated_at INTEGER NOT NULL
);
```

Фоновый воркер (в том же процессе MCP/демона; для one-shot CLI — `myc index --once` отдельным запуском):

```
loop:
  batch = SELECT node_id FROM embed_queue
          ORDER BY prio, enqueued_at LIMIT 50        — батч 50 (socraticode)
  if empty: sleep 250 мс; continue
  texts = SELECT id, content FROM nodes WHERE id IN batch
          AND sha1(content) != last_hash             — content-hash пропуск
  vectors = batch_pool.embed(texts, batch_size=32)
  BEGIN IMMEDIATE:
    UPSERT vec_nodes_i8/f32; DELETE FROM embed_queue;
    UPDATE index_checkpoint;
  COMMIT                                             — транзакция ≤ 50 мс, чтобы не
  держать писателя (урок socraticode про голодание читателей)
```

Свойства: **инкрементально** (очередь — разница состояний), **возобновляемо** (чекпойнт + content-hash: рестарт воркера повторяет максимум один батч из 50), **приоритетно** (пользовательские `remember` обгоняют bulk-import), **отменяемо** (DELETE из очереди — absorb-джобы отменяются до старта LLM-вызова, урок TencentDB о дешёвой отмене).

**Watch**: watcher (fs events на привязанные доки/артефакты контекста, не на свою БД) → дебаунс 2 с по пути → coalesce до последнего состояния файла → content-hash против `index_checkpoint` → постановка в очередь с prio=50. Git-операции (checkout/rebase) порождают шторм событий: дебаунс + coalesce схлопывают его до одного прохода.

**Branch-aware**: индексные потоки ключуются `(repo, branch)`; узлы несут `scope = repo:branch`. Переключение ветки не переиндексирует мир: watch-шторм после checkout пропускается по content-hash (файл с тем же хешем в другом scope уже имеет вектор — вектор переиспользуется по хешу контента, таблица `content_vectors(hash → vector)`), веточные узлы накапливаются параллельно; merge-конфликтов ID нет за счёт иерархических хеш-ID из beads.

### 2.6 Кеши

| Уровень | Тип | Ключ | Размер | Инвалидация |
|---|---|---|---|---|
| Prepared statements | per-process map | текст SQL | все горячие (~40 шт) | живёт с процессом |
| Результаты поиска | LRU in-process | sha1(norm_query + scopes + layers + limit + vector_mode + **вызывающий** + эффективный конфиг) | 512 записей (~0.7 МиБ) | seq-валидация (ниже) + TTL 60 с |
| Эмбеддинги запросов | LRU in-process | sha1(norm_query) + embed_fingerprint | 1000 записей (float32, ~1.5 МиБ) | отпечаток в ключе (смена модели = другой ключ) |
| Гидратация узлов | LRU in-process | node_id | 4096 записей | точечно по oplog: список узлов, менявшихся после запомненного seq |
| Prime-дайджест | таблица `digest_cache` в БД | (scope, profile) | 1 строка/скоуп | seq на момент сборки; пересборка при расхождении, фоном |
| content_vectors | таблица в БД | sha1(content) | растёт, GC при vacuum | вечная (хеш = содержимое) |

Валидация по seq: каждая кеш-запись хранит `seq_at_read`. На запрос: один prepared statement `SELECT MAX(seq) FROM oplog` — `seq` там INTEGER PRIMARY KEY AUTOINCREMENT, то есть rowid, и MAX берётся одним спуском по правому краю B-дерева. Равен — отдаём кеш; изменился — промах. Кросс-процессно это же работает: демон/MCP читает хвост ИЗ БД, а не из памяти, поэтому запись из one-shot CLI инвалидирует кеши демона. Никаких lock-файлов (урок socraticode). Поллинга по таймеру нет — проверка в начале запроса.

Почему `MAX(oplog.seq)`, а не `myc_meta.last_seq`: last_seq — счётчик ЛОКАЛЬНОГО сайта, а операция, приехавшая репликацией с другого сайта, двигает оплог, не трогая его. Кеш обязан увидеть и её.

Четыре уточнения, без которых кеш поиска молча врёт (реализация — `packages/retrieval/src/cache.ts`, каждое закрыто мутацией в `cache.test.ts`):

1. **Вызывающий — часть ключа.** ACL фильтруется ВНУТРИ SQL, значит один запрос от разных вызывающих даёт разные выдачи. В долгоживущем процессе ключ без `FtsCaller` — это утечка чужих узлов через кеш, а не промах производительности.
2. **Ключ поиска НЕ понижает регистр** (в отличие от ключа эмбеддингов, где вектор от регистра не зависит): `isAnchorToken` разбирает форму токена, и `ENOENT` против `enoent` — разные решения триггера вектора.
3. **Ключ включает эффективный конфиг целиком**, а не перечисленные руками поля: список полей ржавеет при добавлении параметра, и это ржавение молча портит выдачу.
4. **Деградированный ответ не кешируется** (`degraded` непуст или вектор `unavailable`/`degraded`): он верен ровно сейчас, и заморозить его на TTL значит продлить деградацию после того, как она кончилась (И2). Ответ отдаётся, но не запоминается.

Гидратация инвалидируется ТОЧЕЧНО: сверка спрашивает у оплога `SELECT DISTINCT entity_id FROM oplog WHERE seq > ? AND entity = 'node'` и выбрасывает только эти записи. Сбрасывать все 4096 тел из-за одной правки значит получить кеш, который в рабочей сессии (агент пишет и читает вперемешку) не попадает никогда. Запасной путь — полный сброс, когда список длиннее 512 id (bulk-import, merge из сети) или когда seq уехал назад (компакция оплога): там дешевле выбросить всё, и это видно в `cleared`.

Попадание и промах ВИДНЫ в ответе: `mode_used.cache` = `hit` | `miss` | `off` (тот же образец, что `cache hit`/`cache miss` в подвале `myc prime`), а у эмбеддера — `EmbedResult.cached`. При `hit` счётчик `roundTrips` равен 1: единственный statement запроса — чтение хвоста оплога.

Замерено (`bun test packages/retrieval/src/cache.test.ts`, корпус 2000 узлов): промах 1.31 мс против попадания 0.0066 мс — **дешевле в 198 раз**; сессия из 60 запросов без записей даёт 40 попаданий из 60 (все повторы), она же с записью каждые 20 запросов — 24 из 60; полный кеш из 512 ответов по 12 узлов занимает 0.70 МиБ (~1440 Б/запись). Кеш эмбеддингов: попадание 0.0009 мс против 23.3 мс промаха — дешевле в ~26 000 раз при 1.46 МиБ на 1000 векторов. Качество не меняется: `bun run bench/boost-eval.ts --cache` прогоняет тот же корпус с кешем и без, MRR@10 совпадает точно (0.520 → 0.520 без бустов, 0.867 → 0.867 с бустами), рангов разошлось 0.

**Прогрев `myc prime` / старта MCP:**

```
1. open SQLite, PRAGMA mmap/cache
2. SELECT last_seq; прочитать digest_cache по всем активным scope (≤ 5 строк)
3. прогнать prime-запросы (ready/pinned/digest) — наполнить page cache SQLite
4. если режим != one-shot: фоново инстанцировать query_session эмбеддера
   и сделать embed("warmup") — модель тёплая к первому search
5. prepared statements для всех горячих команд
```

One-shot CLI пункт 4 **пропускает** (держим холодный старт < 60 мс; модель грузится только если команда реально `search`).

### 2.7 Бюджетированный ретривал

Параметры каждого ретривал-вызова (CLI/MCP одинаковые):

```
limit        = 12     (max 100)     — узлов в ответе
char_budget  = 12000  (max 64000)   — суммарный объём контента ответа
timeout_ms   = 20     (server: 200) — на стадии после эмбеддинга запроса
```

Сборка ответа (двухпроходная, не ломает смысл):

```
reserve = 0.10 × char_budget                 — под секцию рёбер/источников
pass 1: для каждого кандидата по убыванию score:
          включаем crux (≤ 300 символов, граница — конец предложения)
pass 2: пока бюджет не исчерпан, снизу сверху:
          апгрейдим топовые узлы crux → content целиком (узел либо целиком,
          либо остаётся crux — середины нет)
edges: секция связей ≤ reserve
on timeout: вернуть собранное с partial: true, elapsed_ms, omitted: n
ответ всегда несёт: { items, edges, partial, omitted, elapsed_ms,
                      degraded?, cursor? }  — cursor продолжает выдачу
```

Правила обрезки: узел не режется посередине; crux сам обрезается только по границе предложения; при нулевом остатке бюджета узел уходит в `omitted`, а не в ответ обрывком. `timeout_ms` измеряется монотонными часами между стадиями 2.1; первая жертва — граф-расширение, вторая — pass 2.

### 2.8 Embedded против server

| Аспект | Embedded (SQLite) | Server (Postgres) |
|---|---|---|
| Когда | ≤ 100k узлов, одна машина, $0, офлайн | команда, несколько машин/агентов, > 100k узлов |
| Конкурентность | WAL: N читателей + 1 писатель; писатели сериализуются SQLite; `busy_timeout=5000`, `synchronous=NORMAL`, `BEGIN IMMEDIATE` для записи | Пул соединений: min 2 / max 10 на инстанс myc; statement_timeout 5 с; prepared statements per-connection |
| Sparse | FTS5 `bm25()` | `tsvector`/`ts_rank_cd` (+ опц. pg_search) |
| Векторы | sqlite-vec int8+f32 | pgvector HNSW halfvec |
| Кеш-инвалидация | `meta.last_seq` из БД (кросс-процессно бесплатно) | `LISTEN/NOTIFY` на oplog-агрегат + fallback seq-проверка |
| Миграция | — | `myc export` (JSONL) → `myc import` на сервере; embed_dim обязан совпадать |

Гонки агентов на локальной БД: читатели не блокируются (WAL); писатели ждут ≤ busy_timeout; фоновый индексер держит write-транзакции ≤ 50 мс батчами — p99 записи 5 мс сохраняется даже при идущей индексации. Claim задачи — `UPDATE ... WHERE status='open' RETURNING` в одной транзакции, атомарно в обоих бэкендах (L1 детализирует, здесь важно: без lock-файлов и без «проверил-потом-записал»).

```yaml
      MYC_DB: postgres://myc:${PGPASS}@db:5432/myc
      MYC_EMBEDDER: local          # в процессе; 'sidecar' — только для тяжёлых моделей
    depends_on: [db]
  db:
    image: pgvector/pgvector:pg16-alpine
    volumes: [pgdata:/var/lib/postgresql/data]
  embedder:                        # ОПЦИОНАЛЬНО: внешний embedding-API
    image: myc/embedder:latest     # (tei-совместимый), нужен только при
    profiles: ["heavy-embed"]      # моделях > int8-small или CPU-лимитах myc
```

Холодный старт в контейнере: процесс→`/readyz` ok: **< 3 с** без прогрева модели (она грузится фоном, `/status` показывает `embedder: warming`); с предварительно скачанной моделью и `MYC_WARM_EMBEDDER=1` — до `ready` +1.5–2.5 с. Health-эндпоинты:

- `/healthz` — процесс жив, event loop отвечает (200 всегда, если не дедлок).
- `/readyz` — DB ping < 50 мс, миграции применены; эмбеддер **не** блокирует ready (поиск деградирует, не падает).
- `/status` — полный JSON: версии, `last_seq`, `embed_queue_depth`, состояние эмбеддера (`ok|warming|degraded|missing` + reason), лаги индексера, RSS.

## 4. Риски и что ломается на масштабе

1. **WASM-эмбеддинг медленнее ожиданий на x86 без SIMD128-оптимизаций** → конфиг `embedder.runtime = "native"` (onnxruntime-node) + честное `embed_ms` в ответах; бенч-гейты на двух архитектурах (2.10).
2. **sqlite-vec brute-force за 100k узлов** → жёсткая граница 2.4: префильтр по scope/layer или server-режим. Риск молчаливой деградации латентности закрыт бенчем на 1M (ожидаемый фейл = сигнал перейти на PG).
3. **FTS5 unicode61 без русского стемминга** — «задач/задачи» не сматчатся → опциональный второй FTS-индекс `tokenize='trigram'` для ru-корпусов (конфиг per-scope); sparse-скор тогда берём как max(bm25_unicode, bm25_trigram).
4. **`--bytecode`/`--compile` с нативными зависимостями** (sqlite-vec поставляется как .node) → грузим sqlite-vec как внешний модуль рядом с бинарём ИЛИ статически через bun:sqlite-совместимую сборку; фолбэк — pure-WASM sqlite-vec. Проверяется первым пунктом дорожной карты (spike).
5. **Писатель-голодание при bulk-import 1M** → батч-транзакции ≤ 50 мс + yield между батчами; метрика `writer_wait_ms` в `/status`.
6. **Рост oplog/content_vectors** → `myc gc`: oplog compaction за retain-окном 30 дней, vacuum в maintenance-окне; метрики размера в `/status`.
7. **RRF equal-weights слабо калиброваны** → recall@10 в nightly-бенче ловит регрессию; калибровка весов — отдельная задача после сбора реальных запросов (L4 может помочь данными исходов).
8. **Холодный старт в контейнере с lazy model fetch** → модель как опциональный слой образа + `MYC_WARM_EMBEDDER`; без слоя `/status` честно показывает `warming`.

## 5. Открытые вопросы координатору

1. **L1 (ядро данных):** прошу зарезервировать в схеме: `nodes.layer INTEGER 0..3`, `nodes.priority INTEGER 0..3`, `nodes.scope TEXT`, `nodes.acl_rank INTEGER`, `nodes.crux TEXT` (≤ 300 символов), `nodes.updated_at`, `nodes.rowid↔fts rowid` связь, таблицы `oplog(seq, op, id, ts)`, `meta(last_seq, embed_dim, embed_model)`, `digest_cache(scope, profile, seq, payload)`, `edges(src, dst, type, weight)`. Если L1 называет их иначе — L2 переименует запросы, это дешевле делать сейчас.
2. **L1/L2 граница:** кто владеет миграцией SQLite→Postgres (`myc export/import`)? Предлагаю L1 пишет формат дампа, L2 — бенч объёма/скорости импорта.
3. **L3 (поверхности):** контракт деградации: поле `degraded` и `partial` должны войти в MCP-схемы ответов (`search`, `prime`, `memory_digest`) и в HTTP API — иначе «громкость» не доедет до агента. Также: флаг `--profile prime|balanced|deep` в CLI/тул-параметрах.
4. **L3/L4:** эмбеддинг запроса кешируется по sha1 — L4 (роутинг) может переиспользовать query_session для отпечатков задач? Если да — нужен общий Embedder-интерфейс, предлагаю его владельцем сделать L2, потребителями L3/L4.
5. **Координатору:** подтвердить порог «100k узлов = server» как публичное требование к деплою (входит в README и install-guide).
