# 01a — Валидация DDL §8.1 против реального SQLite (myc-qie.1)

Дата: 2026-09-03. Исполнитель: агент-фактчекер.

**Стенд:** Bun 1.3.14, `bun:sqlite` → **SQLite 3.51.0**, FTS5 включён. macOS arm64 (Apple Silicon).
sqlite-vec **v0.1.9** (бинарь `sqlite-vec-darwin-arm64`) проверялся через Node 24 + better-sqlite3
(SQLite 3.53.4) — причина в п.4: `bun:sqlite` расширения не загружает вовсе.

Итог: DDL §8.1 (кроме блока vec0) накатывается без ошибок и в основном соответствует спеке.
Найдены **одна дыра в триггерах счётчика** (закрыта правкой), **одна фатальная проблема
с доступностью sqlite-vec в bun:sqlite** (не решается на уровне DDL) и **опровергнутые
числа производительности векторного скана** (спека занижает в 3–4 раза).

## 1. Generated-колонки VIRTUAL + частичные индексы

Индекс по VIRTUAL generated-колонке в SQLite 3.51 строится (STORED не нужна) и
реально используется планировщиком. Дословный вывод:

```
EXPLAIN QUERY PLAN SELECT id FROM nodes WHERE g_etype='person' AND kind='entity'
→ SEARCH nodes USING INDEX ix_nodes_etype (g_etype=?)

EXPLAIN QUERY PLAN SELECT id FROM nodes WHERE kind='message' AND g_thread_root='r1' ORDER BY created_at
→ SEARCH nodes USING INDEX ix_nodes_thread (g_thread_root=?)
```

Значения generated-колонок извлекаются корректно (`g_task_type='bug'` из
`{"type":"bug"}`, отсутствующий ключ → NULL, `g_pinned` → 0 через `coalesce`).
Частичный UNIQUE `ux_nodes_content` отвергает дубликат живого узла и принимает
тот же `content_hash` после soft-delete предка — как задумано:

```
T1 dup live rejected: SQLiteError: UNIQUE constraint failed: nodes.scope, nodes.kind, nodes.content_hash
T1 dup after soft-delete: accepted (ok)
```

## 2. Триггеры `open_blockers`

Тест: 12 задач, 1000 случайных мутаций (добавление ребра `blocks`, мягкое
удаление, восстановление, закрытие/переоткрытие источника), после прогона
сверка счётчика с пересчётом из `edges`⋈`nodes`.

**Вариант A (только операции, покрытые спекой: add / softdel / close / reopen):**
`СХОДИТСЯ` — триггеры §8.1.11 корректны, включая подзапрос в `WHEN`
(SQLite 3.51 допускает подзапросы в WHEN-триггере).

**Вариант B (+ восстановление мягко удалённого ребра, deleted_at → NULL):**
`РАСХОДИТСЯ`. В спеке нет триггера на этот переход — ребро возвращается в
пересчёт, но не в счётчик. Минимальный сценарий:

```sql
INSERT INTO edges VALUES ('A','blocks','B', ...);   -- counter(B)=1
UPDATE edges SET deleted_at=2  WHERE src='A' AND dst='B';  -- counter(B)=0
UPDATE edges SET deleted_at=NULL WHERE src='A' AND dst='B';
-- факт: counter(B) = 0, пересчёт = 1
```

**Правка** (внесена в `db/schema.sqlite.sql`): триггер `trg_blk_res`,
зеркальный `trg_blk_del`. После правки вариант B сходится на 1000 мутаций
на двух независимых сидах.

**Жёсткий DELETE** (`DELETE FROM edges`, в т.ч. каскад при `ON DELETE CASCADE`
при purge узла) триггерами не покрыт: после `DELETE` ребра counter(B)=1 при
пересчёте 0. Это соответствует модели «только мягкие удаления» (OR-Set,
§8.1.3), но purge обязан после физического удаления пересчитывать счётчики —
SQL пересчёта дан в комментарии схемы.

## 3. FTS5 с внешним контентом (contentless_delete=1)

SQLite 3.51 поддерживает `contentless_delete` (нужно ≥ 3.43). Полный цикл
проверен триггерами §8.1.5, дословный вывод:

```
T3 match 'алхимия':                    [{"id":"n1"}]
T3 match prefix 'алх*':                [{"id":"n1"}]     -- prefix = '2 3' работает
T3 match tag 'vec':                    [{"id":"n1"}]     -- tags из attrs собираются
T3 после UPDATE title, 'алхимия':      []  'переимен*': [{"id":"n1"}]
T3 после soft-delete, 'переимен*':     []
T3 после restore, 'переимен*':         [{"id":"n1"}]
T3 accessed_at/salience update: fts rows 2 -> 2           -- UPDATE OF не срабатывает, индекс не перестраивается
T3 update body удалённого, 'переимен*': []  'новое': []   -- удалённый не воскресает от UPDATE
T3 после DELETE n2, 'другое':          []
```

`bm25(nodes_fts, 4.0, 1.0, 2.0)` принимается. Замечание: на корпусе из двух
документов bm25 даёт rank 0 для терма, встречающегося в обоих (idf=0) — это
математика bm25, не дефект схемы.

## 4. sqlite-vec

**Доступность в целевом рантайме — отрицательная.** Дословно:

```
db.loadExtension("./vec0.dylib", "sqlite3_vec_init")
→ error: This build of sqlite3 does not support dynamic extension loading (Bun v1.3.14)
```

`bun:sqlite` собран без `SQLITE_ENABLE_LOAD_EXTENSION`. Загрузить sqlite-vec
из кода на Bun невозможно ни в каком виде — весь векторный контур §8.1.6 /
§8.3 / §8.4 (`search_vec`) сейчас неработоспособен на заявленном стеке.
Это блокер уровня архитектуры, а не DDL: варианты — статическая линковка
расширения в форк Bun, отдельный векторный процесс, смена движка БД или
перенос векторов в обычные BLOB-таблицы с собственным сканом.

**Само расширение проверено вне bun** (Node 24 + better-sqlite3, SQLite 3.53.4,
sqlite-vec 0.1.9, darwin-arm64):

- Обе заявленные схемы создаются: `nodes_vec` из §8.1.6 (`FLOAT[384]
  distance_metric=cosine`, два partition key) и `vec_nodes_i8` из §2.4
  (`int8[384]`). `int8[384] distance_metric=cosine` — тоже принимается.
- **int8 и хост-параметры.** Сырой BLOB-параметр длиной 384 байта vec0
  интерпретирует как float32 (длина кратна 4) и отвергает: `Inserted vector
  ... expected to be of type int8, but a float32 vector was provided`.
  Подтип int8 через границу хоста не проходит. Рабочие формы:
  `INSERT ... VALUES (..., vec_int8(?))` для готового int8-блоба (схема
  per-vector квантизации из §2.2) и `vec_quantize_int8(?, 'unit')` для
  квантизации из float32 на стороне SQL. То же для `MATCH`.
- **Auxiliary-колонки не фильтруются в KNN.** Запрос `... WHERE embedding_i8
  MATCH ? AND k=10 AND scope='s1'` к таблице с `+scope TEXT` падает дословно:
  `An illegal WHERE constraint was provided on a vec0 auxiliary column in a
  KNN query.` Комментарий §2.4 «`+scope TEXT` — auxiliary-фильтр сканом»
  неверен: префильтр возможен только по partition key (форма §8.1.6).
- **Производительность** (100k векторов × 384 dim, случайные, квантизация
  per-vector из §2.2; медиана из 30 прогонов после прогрева):

  | Запрос | min | p50 | p90 | Спека |
  |---|---|---|---|---|
  | int8, скан всех 100k, k=10 | 24.74 | **25.55** | 25.87 мс | «5–8 мс @100k» — **не сходится, в 3–4× хуже** |
  | int8, партиция ~20k (`scope='s1'`, partition key), k=10 | 5.02 | **5.12** | 5.24 мс | «~8 мс на партицию 20k» (§13) — сходится |
  | float32, скан 100k, k=10 | 24.53 | **24.92** | 26.18 мс | «15–30 мс» — на нижней границе; int8 **не быстрее** float32 |

  Скан линеен (~0.25 мкс/вектор): 100k ≈ 25 мс, 20k ≈ 5 мс. Вывод §2.4
  «int8 в 3× быстрее float32» на vec0 0.1.9/arm64 не воспроизводится —
  int8 даёт только экономию памяти. Бюджет поиска 25 мс (§12) на скоупе 100k
  не выполняется уже на одном векторном скане; партиции по `(scope, layer)`
  до ≤ 20k векторов — обязательное условие, а не оптимизация.
- **Хранение:** 100k × int8[384] = 40.9 МБ (409 Б/вектор после VACUUM) —
  заявленные «384 Б/узел» близки к факту. Вставка 100k ≈ 1 с.
- **Расхождение между документами:** §8.1.6 (01-doc) описывает `nodes_vec`
  FLOAT[384] с partition keys, §2.4 (02-doc) — `vec_nodes_i8` int8 + aux
  `scope` плюс отдельную `vec_nodes_f32`. Это две разные схемы; нужна
  единая. Факты говорят за: int8[384] + cosine + **partition key** `scope`
  (+ f32-переранжирование из обычной BLOB-таблицы, оно vec0 не нужно).

## 5. План запроса `ready`

Стенд: 1500 узлов (200 целевых + 1300 шума: closed, заблокированные, удалённые,
другой scope, заметки), `ANALYZE` выполнен. Дословный вывод:

```
EXPLAIN QUERY PLAN SELECT id, title, priority, updated_at
  FROM nodes
 WHERE scope = 's' AND kind = 'task' AND status = 'open'
   AND open_blockers = 0 AND deleted_at IS NULL
   AND (lease_expires = 0 OR lease_expires < 999999)
 ORDER BY priority ASC, updated_at ASC LIMIT 20

→ SEARCH nodes USING INDEX ix_nodes_ready (scope=?)
```

Частичный индекс выбран, полного скана нет; предикаты частичного индекса
в точности совпадают с WHERE запроса. Время выполнения на стенде: 0.023 мс.

## 6. CHECK и `json_valid`

Все CHECK отвергают невалидные значения с читаемыми сообщениями:

```
bad kind:       CHECK constraint failed: kind IN ('task','note','doc',...)
bad layer:      CHECK constraint failed: layer BETWEEN 0 AND 3
bad priority:   CHECK constraint failed: priority BETWEEN 0 AND 3
bad acl:        CHECK constraint failed: acl IN ('private','team','restricted','agent')
bad confidence: CHECK constraint failed: confidence BETWEEN 0.0 AND 1.0
invalid JSON attrs: malformed JSON        -- падает на вычислении generated-колонки, раньше CHECK
self-edge:      CHECK constraint failed: src <> dst
FK ghost:       FOREIGN KEY constraint failed
```

Нюанс: `json_valid('"str"')` = 1, поэтому JSON-скаляр в `attrs` проходит CHECK
(хотя модель предполагает объект). Если нужна строгость — добавить
`CHECK (json_type(attrs) = 'object')`. В DDL не вносил: спека этого не требует,
а лишняя строгость может ударить по параллельным агентам. Рекомендация.

## 7. Побочное наблюдение: молчаливый пропуск ошибок в bun:sqlite

`Database.exec()` в Bun 1.3.14 **не бросает ошибку** на `CREATE VIRTUAL TABLE`
с незарегистрированным модулем в середине скрипта — оператор молча пропускается,
остальные выполняются:

```
db.exec("create table a(x); CREATE VIRTUAL TABLE v USING vec0(e FLOAT[384]); create table b(x);")
→ ошибки нет; таблицы a и b созданы, v — нет
```

Тот же оператор отдельно ошибку бросает (`no such module: vec0`). Обычные
ошибки (нет таблицы, дубликат) бросаются корректно. Следствие: накат схемы
обязан идти пооператорно с последующей сверкой `sqlite_master` — зафиксировано
в шапке `db/schema.sqlite.sql`.

## Приёмка

- `db/schema.sqlite.sql` накатывается из чистого файла одной командой
  (`db.exec(файл)`): **21 таблица** (16 базовых + 5 shadow FTS5),
  **33 индекса**, **8 триггеров** (7 спеки + `trg_blk_res`), `journal_mode=wal`.
- Все тесты п.1–3, 5, 6 прогнаны повторно против итогового файла — зелёные.
- Чего проверить **не удалось**: работу vec0 внутри bun:sqlite (расширение
  не загружается средой — проверено отрицательно, не выдаётся за успех) и
  поведение sqlite-vec именно под SQLite 3.51 (бенчмарк снят на 3.53.4;
  скан — собственный SIMD-код расширения, версия SQLite на него не влияет,
  но строго говоря стенд другой).

# Приложение К — проверка координатора

Отчёт выше принят с двумя исправлениями. Замеры ниже сделаны **в целевом
рантайме** (bun 1.3.14 + `bun:sqlite`, SQLite 3.53.4 из Homebrew,
sqlite-vec 0.1.9, darwin-arm64), а не через better-sqlite3.

## К.1 Расширения в bun:sqlite загружаются — вывод §4 неверен

Утверждение «загрузить sqlite-vec из кода на Bun невозможно ни в каком виде»
не подтвердилось. Верно только то, что **встроенная** в Bun сборка SQLite
собрана без `SQLITE_ENABLE_LOAD_EXTENSION`. У Bun есть штатный обход:

```ts
import { Database } from "bun:sqlite";
Database.setCustomSQLite("/opt/homebrew/opt/sqlite/lib/libsqlite3.dylib");
const db = new Database(path);
db.loadExtension("<...>/vec0");        // работает
db.query("select vec_version()").get() // { v: "v0.1.9" }
```

`setCustomSQLite` обязан вызываться **до** открытия первого соединения.
После него `sqlite_version()` = 3.53.4 вместо встроенной 3.51.0.

Это не блокер архитектуры, а требование к рантайму: myc обязан найти или
принести с собой libsqlite3 с поддержкой расширений. Заведена задача
`myc-qie.2`. Форк Bun, отдельный векторный процесс и смена движка — не нужны.

## К.2 int8 быстрее float32 в 18 раз — вывод §4 неверен

Замеры на минимальной таблице `vec0(id integer primary key, emb <тип>[384])`,
100 000 векторов, k=10, 40 прогонов после прогрева:

| Тип | p50 | p95 | Размер файла |
|---|---|---|---|
| int8 | **6.62 мс** | 7.15 мс | 39 МБ |
| float32 | **117.75 мс** | 370.84 мс | 149 МБ |

Заявление «int8 даёт только экономию памяти» ошибочно: разница 18×.
Число спеки «5–8 мс на 100k» **подтверждается**, а не опровергается.

## К.3 Откуда взялось расхождение: цена partition key и aux-колонок

Расхождение между 25.55 мс (отчёт) и 6.62 мс (проверка) объясняется формой
таблицы, а не движком. Та же машина, 100k int8:

| Форма таблицы и запрос | p50 |
|---|---|
| минимальная, скан всех 100k | 6.62 мс |
| `+ 2 partition key + 1 aux`, скан всех 100k **без фильтра** | 29.95 мс |
| `+ 2 partition key + 1 aux`, **с фильтром** `scope=? and layer=?` (~5k) | 1.46 мс |

Отсюда три следствия для схемы:

1. Partition key и aux-колонки стоят примерно **4.5× на нескан-фильтрованном
   запросе**. Платить за них имеет смысл, только если фильтр действительно
   используется.
2. Когда фильтр используется — выигрыш огромен: 1.46 мс против 6.62 мс, и это
   на порядок внутри бюджета.
3. Вывод отчёта «партиции — обязательное условие, а не оптимизация» **верен**,
   но по другой причине: не потому, что скан 100k не укладывается в бюджет
   (укладывается, 6.62 мс), а потому, что без фильтра partition key лишь
   ухудшает результат. Партиционировать и фильтровать — либо не
   партиционировать вовсе.

## К.4 Что из отчёта подтверждено полностью

- Триггер восстановления мягко удалённого ребра (`trg_blk_res`) — настоящая
  дыра в спеке, найдена верно, закрыта верно.
- Обёртка `vec_int8(?)` при вставке и в `MATCH` обязательна: сырой BLOB длиной
  384 vec0 трактует как float32 и отвергает. Проверено дословно.
- Aux-колонки нельзя фильтровать в KNN — комментарий «`+scope` фильтром
  сканом» в 02-документе неверен, префильтр только по partition key.
- Расхождение схем между §8.1.6 (01-документ) и §2.4 (02-документ) реально;
  принимается форма int8[384] + cosine + partition key `(scope, layer)`.
- `Database.exec` молча пропускает `CREATE VIRTUAL TABLE` с неизвестным
  модулем — накат пооператорно со сверкой `sqlite_master` остаётся в силе.

## К.5 Правки в документы

- 02-retrieval-and-performance.md §2.4: «int8 в 3× быстрее float32» → 18×;
  «`+scope` фильтр сканом» → префильтр только по partition key.
- 01-core-data-model.md §8.1.6: схема вектора приводится к int8[384] + cosine
  + partition key `(scope, layer)`.
