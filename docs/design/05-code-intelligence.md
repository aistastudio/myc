# 05. Код-интеллект: свой минимум и внешний graft

Статус: проект, пересмотр инварианта И3. Дата: 2026-09-04.
Источники: `01-core-data-model.md` §7, `03-interfaces-and-integration.md` §7,
`ARCHITECTURE.md` §И3 и S9, задачи вехи M3 (см. §9), замеры этой сессии (§2).

## 0. Решение одним абзацем

Делаем **встроенный текстовый код-интеллект** без AST: якоря по `file:line`, три
уровня протухания, ре-привязка по crux, резолв символа в спан по регулярным
определениям, `fan_in` как число вхождений слова, всё это индексируется в фоне и
живёт в бинаре без единого внешнего пакета. Это закрывает **все восемь задач M3**
и не добавляет к бинарю ни мегабайта. Граф вызовов, ранжированный поиск по коду,
карта репозитория и разбор девяти языков **остаются за graft**, который
подключается как вторая реализация того же интерфейса `CodeIntel` и выбирается
пользователем явно или автоматически. И3 не отменяется, а переформулируется:
запрет «не переписываем graft» сужается до «не пишем AST и граф вызовов»,
а требование «работает без graft» усиливается до «встроенная реализация
обязательна, внешняя опциональна, и отсутствие возможности всегда видно».
Не делаем: tree-sitter в бинаре, LSP, ranked-поиск по коду, repo map, socraticode.

## 1. Почему И3 пересматривается, а не обходится

И3 отвергал **дублирование возможностей**: «код-интеллект — чужая, уже решённая
задача». Довод заказчика другой — **связанность при установке**:

| Факт | Число |
|---|---|
| graft как глобальный npm-пакет | 396 МБ, 18 зависимостей |
| из них `tree-sitter-wasm` | 137 МБ |
| из них `tree-sitter-swift` / `-typescript` / `-kotlin` / `-php` | 73 / 38 / 32 / 23 МБ |
| из них `openai` + `@anthropic-ai/sdk` | 20 + 11 МБ |
| myc, один бинарь `bun build --compile` | 68 МБ |
| холодный старт `myc --version` сегодня | 20 мс (бюджет И1: 60 мс) |

Требовать рядом с 68-мегабайтным бинарём, обещающим «$0 и никакой сети», пакет
с двумя LLM-SDK и 137 МБ wasm-грамматик — противоречие, которое И3 в момент
написания не рассматривал. При этом сама спека якорей (`01` §7.2–7.4) уже
построена так, что graft нужен только на **последнем шаге** ре-привязки, при
резолве `--symbol`, для `callers` и `map`. Всё остальное локально и бесплатно.
Пересмотр честный: мы не выкидываем И3, а проводим границу там, где она
де-факто уже стоит в спеке.

## 3. Вопрос 1. Какой минимум действительно нужен

### 3.1 Что нужно якорям myc

Пройдёмся по восьми задачам M3 и выпишем, какая операция над кодом нужна каждой.

| Задача | Операция над кодом | Нужен AST? |
|---|---|---|
| `memory-3afmdwe7bwyp` таблица anchors, запрос по `file:line` | интервальный индекс в SQLite | нет |
| `memory-ehmatz79210p` трёхуровневый детект протухания | `stat`, blake3 файла, blake3 спана | нет |
| `memory-5c03r9t5n472` ре-привязка после рефакторинга | поиск `crux_norm` в файле и в изменённых файлах, winnowing | нет |
| `memory-g79mpkt53yn3` фоновый `fan_in` | число вхождений слова вне определения | нет (приближение) |
| `memory-5wq6pdexn2wz` адаптер graft вне горячего пути | спавн процесса, кеш, таймаут | нет |
| `memory-rw885z6nvatt` хук post-edit | пометить грязным, выйти | нет |
| `memory-apq1h7wra93w` приёмка M3 «код ↔ знание» | обход рёбер `touches`, якорь ↔ узел | нет |
| `anchor add --symbol` (из `03` §7.4) | символ → `path:span` | **нет, если принять regex-определения** |

Итог числом: **8 из 8 задач M3 закрываются без AST.** Единственное место, где
спека сегодня зовёт graft как обязательный шаг, — `--symbol` без graft уже
описан в `03` §7.4 как «эвристика regex `\b<sym>\b` + выбор наибольшего блока».
Этот документ делает эвристику **штатной** реализацией, а не аварийной.

### 3.2 Что graft даёт сверх этого и кому

| Возможность graft | Кому нужна в myc | Заменяем? |
|---|---|---|
| `callers --depth all`, точный граф вызовов | `myc impact <anchor>`, `close --blast`; человек перед рефакторингом | **нет**. Текстовый `fan_in` — число, не граф |
| `ask "<задача>" --source`, ранжированный поиск по коду | обогащение `digest` в фоне (`03` §7.1) | **нет**. Без graft берём собственные якоря темы |
| `map`, карта репозитория | первичное наполнение L2 при `init` | **нет**. Без graft пропускаем и говорим об этом |
| `skeleton <file>`, API файла с точными спанами | `anchor scan <file>` | частично: regex-определения дают имена и начало, конец спана — по скобочному балансу (§4.3) |
| 9 языков через tree-sitter | пользователи вне TS/JS | см. §5 |
| свежесть по content-hash | у нас своя (`01` §7.2) | уже своё |

Вывод: сверх минимума graft нужен **людям** для навигации и **фоновому
дистиллятору** для обогащения. Ни то ни другое не в горячем пути и не в
приёмке M3. Это и есть граница между «своим» и «внешним».

### 4.2 Выбор: B, с C как необязательной надстройкой, E как второй реализацией

- **A недостаточен**: `--symbol` и `fan_in` не покрыты, а S9 требует число `fan_in`.
- **B покрывает минимум §3.1 целиком** и стоит 0 по бинарю и старту.
- **C бесплатен** и повышает точность пометки exported, но не обязателен для приёмки; включаем как флаг реализации, а не как отдельную задачу.
- **D отвергаем**: он не даёт того, ради чего его стоило бы брать (граф вызовов), а даёт то, что нам не нужно (точные деревья), ценой 3–8 МБ бинаря, 25 мс на инициализацию и постоянной поддержки грамматик. Если понадобятся деревья, это и есть graft.
- **E остаётся**: вторая реализация интерфейса, выбирается пользователем.

### 4.3 Как устроен вариант B

Индекс лежит в SQLite рядом с `anchors`, строится **только в фоне**
(`jobs(kind='code_index')`) и **только для репозиториев, где есть хотя бы один
якорь или явно вызван `myc anchor scan`**. Горячий путь читает готовые столбцы.

```
code_files(repo_id, path, lang, mtime_ms, size_bytes, file_hash, indexed_at)
code_defs (repo_id, path, name, kind, span_start, span_end, exported, PRIMARY KEY(repo_id, path, name, span_start))
code_refs (repo_id, name, n_files, n_hits, computed_at)      -- fan_in по слову
```

- **Определение**: одна регулярка на язык по началу строки
  (`export? default? async? (function|class|interface|type|enum|const|let|var) NAME`),
  для методов класса — отступ + `NAME(` внутри блока класса.
- **Конец спана**: скобочный баланс `{}` от строки определения с пропуском
  строк и комментариев; для языков без фигурных скобок (python) — по отступу.
  Это единственное место, где B «разбирает» код, и оно намеренно тупое:
  ошибка в конце спана не ломает якорь, потому что якорь хранит crux.
- **`fan_in`**: число файлов и вхождений `\bNAME\b` минус строка определения.
  Это **верхняя оценка** реального fan_in (имя может совпадать с другим
  символом). S9 просил число для отпечатка задачи, не граф; в ответе всегда
  помечаем `fan_in_source: 'text' | 'graft'`.
- **Инкрементальность**: `code_files.mtime_ms/size_bytes` как первый уровень,
  `file_hash` как второй, ровно как у якорей (`01` §7.2). Хук post-edit ничего
  не индексирует, только помечает файл грязным (`memory-rw885z6nvatt`).
- **Ре-привязка, шаг (3)** из `01` §7.3 переписывается: вместо «спрашиваем
  graft» — «ищем `crux_norm` по файлам, изменённым с `bound_at`
  (`git diff --name-status -M <git_ref>`) и по `code_defs` с тем же `symbol`».
  Если graft подключён — он идёт четвёртым шагом, после встроенного.

## 5. Вопрос 3. Многоязычность

Сколько нужно myc: **ts, tsx, js, jsx** в первой версии. Основание — не вкус,
а замер §2: в отслеживаемых деревьях заказчика нет ни одного файла на других
языках, а сам myc написан на TypeScript.

Уровни поддержки и что означает «поддерживается»:

| Уровень | Что работает | Языки |
|---|---|---|
| L0 «любой текст» | `file:line`, протухание, ре-привязка по crux, хук post-edit | все файлы без исключения |
| L1 «определения» | `--symbol`, `anchor scan`, `fan_in` | ts, tsx, js, jsx |
| L2 «граф» | `callers`, `map`, ранжированный `ask` | только через graft |

**Критерий добавления десятого языка на уровень L1**: одновременно
(а) в репозитории пользователя, где создан якорь, доля файлов этого языка
превышает 20 % (myc это видит из `code_files` и пишет в `doctor`
«ваш репозиторий на 63 % python, для него доступен только уровень L0»);
(б) есть заявка от пользователя или заказчика; (в) правило определения
укладывается в один regex плюс одно правило границы блока и проходит тот же
приёмочный набор, что у ts. Стоимость добавления по этому критерию — задача на
полдня, не на неделю. Языки с нетривиальной грамматикой определений, где regex
заведомо не удержится (C++ с шаблонами, Scala, Haskell), не добавляются на L1
никогда: для них ответ — graft или L0.

## 6. Вопрос 4. Выбор пользователя

### 6.1 Интерфейс

Один интерфейс, две реализации, одно место выбора.

```ts
type CodeIntelCapability =
  | "anchor"      // file:line, протухание, ре-привязка          — есть всегда
  | "symbol"      // символ → path:span                            — builtin: L1-языки; graft: 9 языков
  | "fan_in"      // число                                          — builtin: текст; graft: граф
  | "callers"     // рёбра вызовов                                  — только graft
  | "search"      // ранжированный поиск по коду                    — только graft
  | "map";        // карта репозитория                              — только graft

interface CodeIntel {
  readonly id: "builtin" | "graft";
  readonly state: "ok" | "missing" | "incompatible" | "stale";
  readonly capabilities: ReadonlySet<CodeIntelCapability>;
  langs(): ReadonlySet<string>;                                   // для symbol/fan_in
  resolveSymbol(repo: RepoId, name: string): Promise<SymbolHit[]>;
  fanIn(repo: RepoId, name: string): Promise<{ n: number; source: "text" | "graph" }>;
  defsOf(repo: RepoId, path: string): Promise<SymbolHit[]>;
  callers?(repo: RepoId, name: string, o?: { depth?: number | "all" }): Promise<CallEdge[]>;
  search?(repo: RepoId, q: string, o?: { limit?: number }): Promise<CodeHit[]>;
  map?(repo: RepoId): Promise<Cluster[]>;
}
```

`GraftAdapter` из `03` §7.2 становится реализацией `CodeIntel` с полным
набором возможностей; `BuiltinCodeIntel` реализует первые три. Всё, что уже
описано про кеш, таймауты и `graph_rev` (`03` §7.3), остаётся внутри
graft-реализации без изменений.

### 6.2 Кто выбирает

Ключ `code_intel` в `.myc/config.json`, четыре значения:

| Значение | Поведение |
|---|---|
| `auto` (умолчание) | graft, если найден и совместим; иначе builtin. Выбор пишется в `.myc/state.json` с 24-часовым кешем детекта (как в `03` §7.4) |
| `graft` | только graft. Если не найден — `state=missing`, все возможности сверх `anchor` недоступны и **это ошибка конфигурации**, `doctor` красный, `exit 5` у команд, которым нужен символ |
| `builtin` | только встроенная, graft не спавнится даже если установлен. Режим для контейнеров и CI |
| `off` | код-интеллекта нет вовсе, работает только уровень `anchor`. Для тех, кому якоря нужны как закладки |

Переключение: `myc config set code_intel builtin`. Правило неудвоения MCP
(`03` §7.1) сохраняется: при `graft` и `auto→graft` myc не проксирует
инструменты graft, а подсказывает их имена.

Важно для приёмки M3 (`memory-apq1h7wra93w`): сценарий «код ↔ знание» обязан
проходить при `builtin` и при `graft`, то есть тест гоняется дважды.

### 6.3 Громкая деградация (И2)

Возможность либо есть, либо её отсутствие видно в трёх местах сразу.

| Где | Что |
|---|---|
| `meta.degraded[]` любой поверхности (CLI JSON, MCP, HTTP) | код `code_intel_builtin` при `auto→builtin` («graft не найден, символы только для ts/tsx/js, callers недоступны»); `code_intel_lang_unsupported` при якоре на файл вне L1; `code_intel_missing` при `graft` без graft; `code_intel_off` при `off` |
| `myc doctor` | строка `code-intel: builtin · языки ts,tsx,js,jsx · индекс 1506 файлов, 260 мс, свежий` либо `code-intel: graft 0.9.2 · кеш-хит 71 %` либо красное `code-intel: graft запрошен, не найден` |
| Ответ команды | `myc anchor of --symbol X` при builtin печатает `WARN callers недоступны (builtin): установите graft или code_intel=auto`; `fan_in` в выдаче всегда с суффиксом источника: `fan_in 12 (text)` |

Пустой выдачи без причины не бывает: если символ не найден, ответ содержит
`searched: {files: N, langs: [...]}`, чтобы было видно, что искали и где.
Обе реализации отсутствовать не могут: builtin вкомпилирован. «Отсутствие
обеих» возможно только как `off`, и это осознанный выбор, отражённый в `doctor`.

## 7. Вопрос 5. Что делать с уже написанным

Через `graft callers --depth all`:

- `probeGraft` (`packages/cli/src/commands/bootstrap.ts:565-577`) вызывается
  из `autoBlocks` (`:637-651`), дальше `buildPrint` и `createBootstrapCommand`;
  тесты `bootstrap.test.ts`.
- `detectGraft` (`packages/cli/src/commands/init.ts:113-120`) вызывается из
  `createInitCommand` (`init.ts:365`); через `makeRegistry` его тянут пять
  тестовых файлов (`bootstrap`, `init`, `memory`, `retrieve.budget`,
  `retrieve.fallback`).

Обе функции сегодня делают одно и то же на разный лад: `existsSync(graft/)` или
`existsSync(graft/INDEX.md)` плюс `Bun.which("graft")`. Изменения:

## 8. Вопрос 6. Судьба И3

И3 сохраняется как запрет на переписывание AST-разбора и графа вызовов и
усиливается требованием обязательной встроенной реализации. Дословная правка
для `ARCHITECTURE.md`, заменить §И3 целиком:

```markdown
### И3. Свой код-интеллект — текстовый и встроенный; AST и граф вызовов — чужие

myc обязан работать с кодом **без единого внешнего пакета**: якоря
(`repo + path + span + blob_hash + текстовый crux`), три уровня детекта
протухания, ре-привязка по crux, резолв символа в спан и `fan_in` символа
реализованы встроенно, на тексте и регулярных определениях, без AST. Это
покрывает всё, что нужно памяти и задачам, и стоит 0 байт в бинаре и 0 мс на
старте: индекс строится только в фоне и только для репозиториев с якорями.

Мы **не пишем** разбор деревьев, граф вызовов, ранжированный поиск по коду,
карту репозитория, LSP и ничего из socraticode. Всё это — вторая реализация
того же интерфейса `CodeIntel`, которую даёт внешний graft; она подключается
адаптером вне горячего пути (40–300 мс на вызов против бюджета recall 25 мс)
и выбирается ключом `code_intel: auto | builtin | graft | off`. Какая
реализация активна и чего она не умеет — видно в `meta.degraded[]`, в
`myc doctor` и в ответе команды (И2). Идею graft «crux — текст, а не номера
строк» мы переносим на свои якоря; сами узлы, рёбра и индекс graft у себя не
храним.
```

Правка строки в реестре рисков (§13), заменить строку «Дублирование graft»:

```markdown
| Дублирование graft | соблазн дописать в builtin разбор деревьев или граф вызовов | И3: builtin ограничен текстом и регулярными определениями; любая возможность уровня «граф» добавляется только как реализация `CodeIntel` через внешний инструмент |
```

Правка `01-core-data-model.md` §7.3 шаг (3) и `03-interfaces-and-integration.md`
§7.4 таблица «без graft» следуют из этого документа; их вносит владелец
спеки после утверждения.

## 9. Вопрос 7. Что НЕ делаем

- **Ранжированный поиск по коду** (`graft ask`): нет. Обогащение `digest`
  кодом без graft ограничено собственными якорями темы.
- **Repo map** (`graft map`): нет. При `init` без graft карта L2 не строится,
  об этом пишется в вывод `init`.
- **Граф вызовов и `callers --depth all`**: нет. `fan_in` из текста — число с
  пометкой источника, не граф.
- **tree-sitter в бинаре**: нет, ни вшитый, ни докачиваемый.
- **LSP-интеграция**: нет.
- **socraticode** и семантический поиск по коду: нет, за пределами задачи.
- **Проксирование MCP-инструментов graft**: нет, правило неудвоения остаётся.
- **Языки вне ts/tsx/js/jsx на уровне L1**: не в первой версии, критерий в §5.

## 11. Открытые вопросы заказчику

1. **Умолчание `auto` или `builtin`?** `auto` даёт лучший результат тем, у кого
   graft уже стоит, но означает, что поведение myc зависит от окружения.
   `builtin` по умолчанию проще объяснить и воспроизвести в контейнере.
   Рекомендация: `auto` на рабочих машинах, `builtin` при обнаружении
   контейнера (`/.dockerenv`, `CI=true`), и это тоже надо утвердить.
2. **Достаточно ли ts/tsx/js/jsx на старте?** Замер §2 говорит да для ваших
   репозиториев; если планируются проекты на Swift/Kotlin, критерий §5 стоит
   пересмотреть заранее, а не по заявке.
3. **Приемлема ли текстовая верхняя оценка `fan_in` для отпечатка задачи в
   рое (S9)?** Она завышает число при совпадении имён. Альтернатива — не
   считать `fan_in` без graft вовсе и держать признак пустым; это честнее, но
   рой теряет признак у всех без graft.
4. **Где живёт код: `packages/anchors` или новый `packages/code-intel`?**
   Инженерно всё равно; вопрос в том, хочет ли заказчик видеть в дереве пакет
   с таким именем после И3.
5. **Надо ли `off`?** Режим дёшев, но это четвёртое состояние, которое надо
   тестировать. Если якоря-закладки без индекса никому не нужны, три режима
   проще.

## 12. Ответы заказчика (2026-09-04)

Пять вопросов §11 закрыты. Решения, принятые к исполнению:

1. **Умолчание — `builtin` везде**, а не `auto`. Довод заказчика прямее моего:
   глобальную зависимость убирают ради воспроизводимости, и `auto` возвращает
   ровно ту болезнь, от которой уходят, — «у меня работает иначе». `auto`
   остаётся как явная опция для тех, у кого graft стоит и кто хочет его
   автоматически. Никакого определения контейнера по `/.dockerenv` и `CI=true`
   не нужно: поведение одинаково всюду по умолчанию, и объяснять нечего.
2. **`fan_in` считаем и помечаем источником.** Колонка `fan_in_source` со
   значением `text` или `graft`. Пустой признак у всех без graft — это потеря
   сигнала у всех, кто в контейнере, то есть у большинства; завышение при
   совпадении имён видно, измеримо (замер в T5) и честно подписано.
3. **ts/tsx/js/jsx на старте достаточно** (решение владельца спеки). Критерий
   §5 применяется к десятому языку по заявке, а не заранее.
4. **Код живёт в новом пакете `packages/code-intel`** (решение владельца спеки).
   `packages/anchors` остаётся про якоря; код-интеллект делает больше, и имя
   `anchors` вводило бы в заблуждение после И3.
5. **Режим `off` сохраняется.** С умолчанием `builtin` он единственный способ
   отключить фоновый индексатор совсем; T7 и так проверяет все четыре режима,
   так что цена — ноль сверх уже запланированного.
