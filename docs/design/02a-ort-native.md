# 02a. Нативный ORT-бэкенд для эмбеддера: исследование с замерами

Задача myc-dze.1. Дата замеров: 2026-09-04, машина координатора (macOS,
darwin/arm64), Bun 1.3.14. Модель: `bge-small-en-v1.5-q8` (INT8, 384 dim),
уложена в `~/.cache/myc/models`. Способ замера — тот же, что в
`packages/embed/src/bench.ts`: та же строка запроса (~30 токенов), та же
область замера (токенизация + inference + CLS-pool + L2), прогрев 10 прогонов,
100 измерений, тёплая сессия.

## 1. Работает ли onnxruntime-node под Bun

**Да.** onnxruntime-node@1.20.1 загружается под Bun 1.3.14 через N-API
(биндинг `bin/napi-v3/darwin/arm64/onnxruntime_binding.node`), сессия
создаётся, inference исполняется, входы/выходы модели совпадают с
WASM-версией. Никаких обходов не потребовалось: `import("onnxruntime-node")`
работает из коробки.

Контроль эквивалентности: вектор нативного бэкенда совпадает с вектором
WASM-бэкенда на том же тексте с косинусом > 0.9999 (тест
`packages/embed/src/ort-native.test.ts`, «вектор совпадает с WASM-бэкендом»).

## 2. Измеренные числа

WASM-база (`bench.ts`, intra_op=1 — конфигурация LocalEmbedder) на этой
машине, два прогона:

| бэкенд | одиночный p50 | одиночный p95 | батч 256 текстов |
|---|---|---|---|
| WASM (onnxruntime-web), 1 поток | 18.6–19.5 мс | 20.5–20.9 мс | 101–128 текстов/с |
| **нативный (onnxruntime-node), 1 поток** | **3.3 мс** | **3.7–3.8 мс** | **290–295 текстов/с** |
| **нативный, 4 потока** | **1.6 мс** | **1.9 мс** | **1065 текстов/с** |

Выигрыш нативного бэкенда против WASM в той же конфигурации (1 поток):
**5.6–5.9× по одиночному запросу, ~2.5× по батчам**. С 4 потоками — до ~12×
по одиночному запросу и ~8× по батчам. В отличие от WASM под JSC, нативный
рантайм реально использует intra_op-потоки.

Спековая цель 4–7 мс на эмбеддинг запроса (решение S31) нативным бэкендом
**достигается даже в однопоточной конфигурации** (p50 3.3 мс, p95 3.8 мс).

Замеры воспроизводятся:

```bash
MYC_EMBED_TEST_MODELS_DIR=$HOME/.cache/myc/models bun packages/embed/src/bench.ts
MYC_EMBED_TEST_MODELS_DIR=$HOME/.cache/myc/models bun packages/embed/src/bench-ort-native.ts
MYC_ORT_THREADS=4 MYC_EMBED_TEST_MODELS_DIR=$HOME/.cache/myc/models bun packages/embed/src/bench-ort-native.ts
```

## 3. Вес, платформы, лицензия

onnxruntime-node@1.20.1, лицензия **MIT**. Пакет целиком весит 180 МБ, но
внутри — бинарники под все платформы; на одну платформу приходится:

| платформа | размер | содержимое |
|---|---|---|
| darwin/arm64 | 24 МБ | libonnxruntime.1.20.1.dylib (24 МБ) + onnxruntime_binding.node (172 КБ) |
| darwin/x64 | 27 МБ | то же |
| linux/x64 | 38 МБ | libonnxruntime*.so + binding |
| linux/arm64 | 26 МБ | то же |
| win32/x64 | 32 МБ | onnxruntime.dll + DirectML.dll + binding |

Дистрибуция по прецеденту S29 (библиотеки рядом с бинарём): на платформу это
+24–38 МБ против 61 МБ самого бинаря myc, т.е. +40–60 % размера дистрибутива.
Существенно дороже, чем libsqlite3+vec0 (2 %), поэтому нативный бэкенд
остаётся **opt-in**: зависимость объявлена `optionalDependencies` пакета
`@myc/embed`, WASM остаётся дефолтом и единственным обязательным бэкендом.
Отсутствие onnxruntime-node (установка с `--no-optional`, неподдерживаемая
платформа) не ломает ничего: ошибка возникает только при явном запросе
нативного бэкенда и формулируется внятно (`getOrtNative()` в
`packages/embed/src/ort-native.ts`).

Замечание по типам: npm-пакет onnxruntime-node объявляет
`"types": "dist/index.d.ts"`, но .d.ts в пакет не входит; локальное
объявление `packages/embed/src/ort-node.d.ts` покрывает используемую часть
API (по образцу существующего `ort-wasm.d.ts`).

## 4. Альтернативы

Не понадобились: основной путь (onnxruntime-node, официальный N-API биндинг
Microsoft к libonnxruntime) работает под Bun и даёт выигрыш кратно больше
двукратного. Из других доступных пакетов: `onnxruntime-react-native` (не
применим), `tensorflow-node` (тяжелее и без выигрыша в переносимости),
сборка candle/tract через FFI (своя сборка нативного кода — против требования
$0 и офлайн). Рассматривать их не имеет смысла, пока onnxruntime-node
покрывает целевые платформы.

## 5. Что сделано

- `packages/embed/src/ort-native.ts` — нативный бэкенд: ленивая загрузка
  onnxruntime-node, создание сессии (CPU-EP, graphOptimizationLevel=all,
  настраиваемые intra_op-потоки), построение int64-фидов BertModel.
- `packages/embed/src/ort-node.d.ts` — локальные типы (см. выше).
- `packages/embed/src/bench-ort-native.ts` — бенч, сравнимый с bench.ts.
- `packages/embed/src/ort-native.test.ts` — тесты на реальной модели
  (пропускаются без модели или без onnxruntime-node, как e2e.test.ts).
- `packages/embed/package.json` — onnxruntime-node@1.20.1 в
  `optionalDependencies`.

Проверки: `bun test` (518 pass, 0 fail), `bun run typecheck` и
`bun run scripts/deps-check.ts` — зелёные.

Не сделано осознанно: подключение нативного бэкенда к `LocalEmbedder`
(переключатель конфигурации) — это следующий шаг отдельной задачей; форма
переключения (явная, WASM дефолтом) заложена в ort-native.ts, а полю
`EmbedFingerprint.provider`/`backend` потребуется отметка о нативном
рантайме.

## Вывод

Нативный путь применим и даёт измеренный выигрыш **5.6× (p50 одиночного
запроса, 1 поток) — до 12× (4 потока)** на той же модели и том же наборе
запросов; спековые 4–7 мс достигаются. Цена — +24–38 МБ нативных бинарников
на платформу при opt-in дистрибуции. Рекомендуется принять бэкенд как opt-in
и завести задачу на подключение его к LocalEmbedder с явным переключателем.
