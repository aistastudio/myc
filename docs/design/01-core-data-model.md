## 1. Решения

| Вопрос | Выбор | Почему | Что отвергли |
|---|---|---|---|
| Форма хранения узлов | **Одна таблица `nodes` + дискриминатор `kind` + `attrs JSON`**; 1:1 расширение только для `anchors` | Все горячие запросы (`prime`, `ready`, гибридный поиск, обход рёбер) — кросс-kind. Один B-tree, один FTS-индекс, один вектор-индекс, один планировщик. Table-per-type превращает поиск в `UNION ALL` по 9 таблицам с 9 FTS+9 vec-сканами | Таблица-на-тип; EAV; отдельная БД на слой |
| Горячие поля | ~30 реальных колонок (включая `assignee`, `lease_*`, `open_blockers`), холодные — в `attrs` | CAS-claim и `ready` не должны трогать JSON. `json_extract` в SQLite ~0.4 мкс/вызов — терпимо для 20 строк, недопустимо для скана 100k | Всё в JSON; всё в колонках |
| Per-kind поля, которым нужен индекс | `GENERATED ALWAYS AS (json_extract(attrs,...)) VIRTUAL` + частичный индекс (SQLite) / expression-index по JSONB (PG) | Даёт индекс без физической колонки и без миграции на каждый новый kind | Добавлять колонку на каждый kind |
| ID | **`myc-` + 12 симв. Crockford base32** (60 бит), канонический и неизменный; **дотовый путь `myc-a3f8.1.2` — вычисляемый ярлык отображения, не хранится** | Хеш-ID переживает мерж веток и офлайн-создание; дотовый путь у beads безопасен только под cell-merge Dolt'а, которого у нас нет | Автоинкремент; UUIDv4 (не читаем); контент-адресация (ID меняется при правке) |
| Короткая форма ID | Префикс ≥ 4 символа, разрешение — **range-scan по PK** (`id >= 'myc-a3f8' AND id < 'myc-a3f9'`), при неоднозначности — ошибка со списком | O(log n), не `LIKE`. Как git-хеши | Отдельная таблица алиасов |
| Транзитивность рёбер | `blocks` — **денормализованный счётчик `open_blockers`** (триггеры); `parent` — материализованное замыкание `parent_closure`; остальное — рекурсивным CTE по требованию | `ready` — самый горячий граф-запрос, он обязан быть одним сканом частичного индекса, а не рекурсией по 100k | Полное замыкание всех типов; всё рекурсивным CTE |
| Слои L0–L3 | Колонка `layer INTEGER 0..3` в `nodes` + частичные индексы по слою. Физически — те же строки | Подъём по слою = вставка нового узла + `derived_from` рёбра, а не миграция между таблицами | Таблица на слой; отдельная БД на L0 |
| Дистилляция L0→L1→L2→L3 | **Асинхронный воркер**, отменяемый, с жёстким бюджетом (≤ 4 LLM-вызова и ≤ 30 с на прогон) | §4 брифа: «асинхронная дистилляция обязана быть отменяемой и дешёвой» | Синхронная дистилляция при записи |
| absorb | **Двухступенчатый: детерминированная ступень A (хеш + косинус + триграммы), опциональная LLM-ступень B** | §3: запись p99 < 5 мс и `$0` без ключа | LLM в горячем пути; чистый TF-IDF |
| Деградация без LLM/эмбеддингов | Кандидаты **не сливаются и не выбрасываются**, а становятся `relates`; статус деградации виден в `myc status`, `myc doctor` и в MCP-ответах (`degraded: [...]`) | Прямо закрываем ловушку memora («молчаливый фолбэк на TF-IDF») | Молчаливый фолбэк |
| Якоря на код | Свои: `repo+path+span+file_hash+span_hash+crux(текст)`; graft — **только внешний резолвер символов**, вызывается вне горячего пути | Бриф §2: свой код-граф не пишем; бриф §4: crux-как-текст переносим на якоря. graft может отсутствовать — якорь обязан жить без него | Хранить у себя копию graft-графа; звать graft на каждый `show` |
| Диалекты | Два рукописных DDL (SQLite + Postgres), **один текст запроса** с плейсхолдерами `?N`, автопереписывание в `$N` для PG, явный override только там, где диалекты реально расходятся (~9 из ~50 запросов) | ORM/квери-билдер стоит аллокаций в горячем пути и прячет план запроса. Запросов мало и они стабильны | Drizzle/Kysely/Prisma; универсальный SQL-подмножество |
| Миграции | Forward-only, целочисленная версия, `schema_migrations` с checksum. **Guard**: БД новее бинаря → жёсткий отказ, exit 3; checksum не сходится → exit 4 | Как в beads: молчаливое открытие чужой схемы — это порча данных на нескольких машинах | Автодаунгрейд; «best effort» открытие |
| Сходимость нескольких агентов/машин | **Оплог + per-field LWW на Hybrid Logical Clock**, add-wins OR-Set для рёбер, G-counter для счётчиков, **lease с epoch** для claim | Векторные часы растут O(числа сайтов) и требуют буфера каузальной доставки; наши поля семантически независимы. Опасны LWW только для claim и множеств — им сделаны отдельные типы | Векторные часы; Dolt; полный CRDT-документ (Automerge/Yjs) на узел |
| Атомарный claim | Одно `UPDATE ... WHERE status='open' AND (lease_expires=0 OR lease_expires<now)` + проверка `changes()==1`. Lease TTL 900 с, продление каждые 300 с | Compare-and-swap одним стейтментом — нет окна между чтением и записью, работает и в SQLite (BEGIN IMMEDIATE), и в PG | `SELECT` → `UPDATE`; блокировки на уровне приложения |
| Экспорт в git | `.myc/graph/nodes-<c>.jsonl` и `edges-<c>.jsonl`, 32 корзины по первому символу ID, строки отсортированы по ID, ключи в стабильном порядке | Одна строка = один узел ⇒ git-дифф читаем, конфликт локален. 32 файла = мерж двух веток почти всегда трогает разные файлы | Один большой JSONL; SQLite-файл в git; Dolt |
| ACL | 4 уровня в колонке `acl` + `owner_id`/`team_id`/`agent_id` + таблица `acl_grants` для `restricted`. Фильтр **компилируется в WHERE каждого ретривального запроса**, до ранжирования | Бриф §4: «фильтрация до ранжирования». Пост-фильтрация после top-k ломает полноту выдачи | Post-filter; ACL на уровне приложения после ранжирования; row-level security только в PG |
| ACL и вектор-индекс | Partition key `(scope, layer)` в vec0 + over-fetch `k' = max(64, 4k)` c ≤ 3 раундами расширения; в локальном одно-пользовательском режиме `acl_enforced=0` и предикат вырезается из SQL целиком | ANN/brute-force индекс не умеет пре-фильтр по произвольному предикату; но 95 % запусков `myc` — локальные, там ACL просто нет | Отдельный вектор-индекс на каждый ACL-класс |
| Удаление | Три уровня: `decay` (тело в холод), `prune` (удалить холодные тела), `purge` (жёсткое удаление + тумбстоун в оплог) | Разные требования: экономия контекста ≠ экономия диска ≠ «удали навсегда у всех» | Только `DELETE`; только soft-delete |

## 2. Единая модель узлов

### 2.1 Почему одна таблица — счётом

Проверяемое обоснование под наши бюджеты (§3 брифа: гибридный поиск по 100k p99 < 25 мс, `prime` p99 < 30 мс):

| Операция | Одна таблица + `kind` | Таблица на тип (9 шт.) |
|---|---|---|
| Гибридный поиск по всем видам | 1 FTS-скан + 1 vec-скан + 1 join | 9 FTS-сканов + 9 vec-сканов + `UNION ALL` + пересортировка; RRF считается над 9 несравнимыми ранжировками |
| `prime` (взять L2/L3 по scope) | 1 частичный индекс `ix_nodes_prime` | 9 индексов, 9 обращений, слияние в приложении |
| Рёбра | `FOREIGN KEY` на одну таблицу, каскад работает | Полиморфный FK невозможен ⇒ целостность только в коде |
| Новый kind | `INSERT` + запись в `attrs` | Миграция: таблица + FTS + vec + триггеры + 5 запросов |
| Сквозной оплог | `entity='node'`, один формат | Тип сущности в каждой операции, 9 применяторов |
| Цена | Разреженные колонки: NULL в SQLite — 1 байт в заголовке записи; в PG — бит в null-bitmap | Плотные строки |

Разреженность — единственная плата, и она измеримо мала: строка `nodes` для `message`
(заполнено 12 из 31 колонки) занимает в SQLite ~140 байт + тело. 100k узлов ≈ 14 МБ
метаданных — целиком помещается в page cache (64 МБ, см. PRAGMA).

**Граница компромисса:** отдельная 1:1 таблица заводится, только если выполнены оба условия —
(а) payload не участвует ни в одном кросс-kind запросе, (б) по нему нужны собственные
структурные индексы. Под это подпадает ровно один kind — `anchor` (таблица `anchors`):
её пишет и перечитывает фоновый ре-биндер по `(repo_id, path)` и `(repo_id, symbol)`,
а поиск по узлам её колонок не касается.

| kind | Обязательные `attrs` | Индексируемые через generated column | Слой по умолчанию |
|---|---|---|---|

| `fragment` | `frag_type` (`claim│plan_item│reference│risk│section`), `ord`, `char_start`, `char_end` | `g_frag_type` | 1 |
| `session` | `agent`, `model`, `started_at`, `ended_at`, `cwd`, `git_head` | — | 0 |
| `message` | `session_id`, `role` (`user│assistant│tool│system`), `ord`, `thread_root`, `tokens_in`, `tokens_out` | `g_session_id`, `g_thread_root` | 0 |
| `entity` | `etype` (`person│repo│service│model│file│lib│term`), `aliases[]`, `canonical` | `g_etype` | 2 |
| `anchor` | всё структурное — в таблице `anchors`; в `attrs` только `note` | — | 1 |

`doc` → фрагменты: фрагмент — отдельный узел `kind='fragment'` с ребром `parent` на `doc`.
Причина: фрагмент — самостоятельная единица ретривала (у него свой вектор, свой ACL
не бывает, но своя salience и свои `evidence`-рёбра), а документ целиком в контекст
почти никогда не вливается.

| kind | Допустимые `status` |
|---|---|

| `note`, `fragment`, `entity`, `skill` | `active`, `superseded`, `retracted` |

| `session` | `open`, `closed` |

Единая семантика «закрыто» для счётчика блокеров: `status IN ('closed','cancelled','superseded','retracted')`.

## 3. Схема ID

### 3.1 Канонический ID

```
id      := prefix "-" body
prefix  := [a-z][a-z0-9]{1,7}          -- по умолчанию "myc", настраивается на граф
body    := 12 символов Crockford base32 (алфавит 0123456789abcdefghjkmnpqrstvwxyz)
```

Генерация (детерминированная функция, без обращения к БД):

```
fn new_id(prefix, site_id, actor, content_hash) -> String:
    seed  = blake3( site_id || 0x1f || actor || 0x1f
                  || u64_be(now_unix_ns()) || 0x1f
                  || random_bytes(8) || 0x1f || content_hash )
    body  = crockford32( seed[0..8] )[0..12]     # 60 бит
    return prefix + "-" + body
```

60 бит ⇒ вероятность хотя бы одной коллизии при 10⁷ узлов ≈ `n²/2N = 10¹⁴ / 2.3·10¹⁸ ≈ 4.3·10⁻⁵`.
Коллизия всё равно детектируется: `INSERT` в PK падает ⇒ перегенерация (до 3 попыток),
при мерже — см. 3.4.

### 3.2 Короткая форма и дотовый путь

Пользователь и агент почти всегда пишут `myc-a3f8`. Разрешение:

```sql
SELECT id FROM nodes
 WHERE id >= :p AND id < :p_succ      -- p_succ = p с инкрементом последнего символа
 LIMIT 2;
```
0 строк → `not found`; 2 строки → `ambiguous prefix, use N chars` со списком;
1 строка → готово. Это range-scan по первичному ключу, ~2 мкс.

**Дотовый путь `myc-a3f8.1.2` — производная величина, а не идентификатор.**
Вычисляется на чтение из цепочки рёбер `parent`:

```
path(n) = if parent(n) is null then short(n)
          else path(parent(n)) + "." + ordinal(n)
ordinal(n) = позиция n среди детей parent(n), сортировка (created_at ASC, id ASC), с 1
```

Принимается на вход наравне с хеш-формой (резолвится через `parent_closure`).
Никогда не пишется в `nodes.id`, в рёбра, в оплог и в JSONL-экспорт.

### 3.3 Почему не автоинкремент

1. **Мерж веток.** Две ветки создали `#41` с разным содержимым. Автоинкремент даёт
   ложное совпадение ключей — самый дорогой класс порчи данных (рёбра одной ветки
   начинают указывать на узлы другой). Хеш-ID даёт непересекающиеся множества.
2. **Офлайн и несколько машин.** Инкремент требует единого аллокатора ⇒ сеть в горячем
   пути записи, что прямо запрещено §3 брифа.
3. **Форвард-референс.** Агент должен уметь построить пакет из 5 задач со связями
   между ними до первой записи в БД. Хеш-ID известен до `INSERT`.
4. **Оплог.** Операция должна быть самодостаточной и переносимой между сайтами;
   ключ-локальный-инкремент к этому непригоден.
5. **JSONL в git.** Пересчёт номеров при ребейзе переписал бы весь файл; при хеш-ID
   дифф трогает только реально изменённые строки.

### 3.4 Поведение при мерже и нескольких агентах

| Ситуация | Что происходит |
|---|---|
| Две ветки создали разные узлы | ID различны с вероятностью 1−4.3·10⁻⁵ ⇒ объединение множеств, ничего не делаем |
| Две ветки правили один узел | Разрешение по полям (§9.2), ID не трогается |
| Реальная коллизия ID при импорте | `myc import` детектирует: PK совпал, `content_hash` разный. Действие: узлу **из импортируемой стороны** назначается новый ID (перегенерация с добавлением `site_id` в seed), все его рёбра и оплог-записи переписываются, в `myc doctor` пишется отчёт. Локальная сторона не трогается — так операция идемпотентна при повторном импорте |
| Иерархия перестроилась (задачу перевесили под другого родителя) | Дотовые пути всех потомков меняются, канонические ID — нет. Ни одно ребро не ломается |
| Несколько агентов в одном процессе/машине | Один `site_id` на БД-реплику, конкуренция снимается транзакцией `BEGIN IMMEDIATE`; ID независимы (в seed входит `random_bytes(8)` + `now_ns`) |

## 4. Типизированные рёбра

Ребро — направленная тройка `(src, type, dst)` с весом. Одно ребро каждого типа
между парой узлов (PK = `(src, type, dst)`); повтор — это обновление веса и тега.

### 4.1 Полная семантика

| Тип | Читается как | Обратное (виртуальное) | Транзитивно | Ациклично (проверяем) | Материализуем | Кто ставит | Что делает в ретривале |
|---|---|---|---|---|---|---|---|
| `blocks` | **src** блокирует **dst** | `blocked_by` | да (для готовности) | да, глубина ≤ 64 | **счётчик `nodes.open_blockers`** | человек/агент | `ready` = `open_blockers=0` |
| `parent` | **src** — ребёнок **dst** | `children` | да | да, глубина ≤ 32 | **`parent_closure(ancestor,descendant,depth)`** | человек/агент/парсер `doc` | поддерево, дотовые пути, наследование `scope`/`acl` |
| `relates` | связано с | `relates` (симметрично) | **нет** | нет | — | absorb, человек | расширение выдачи на 1 хоп, вес = косинус |
| `duplicates` | **src** — дубликат канонического **dst** | `duplicated_by` | да, но **схлопывается**: при вставке путь сжимается до корня | да | путь сжат ⇒ глубина всегда 1 | absorb | `src` скрыт из выдачи, `dst.seen_count++` |
| `supersedes` | **src** заменяет **dst** | `superseded_by` | да (цепочка) | да | **`nodes.head_id`** у всех, кроме головы | absorb, человек | режим `active` показывает только голову |
| `replies_to` | **src** — ответ на **dst** | `replies` | да (тред) | да | `attrs.thread_root` (generated column `g_thread_root`) | слой сообщений | тред целиком одним индекс-сканом |
| `derived_from` | **src** выведен из **dst** | `derives` | да (провенанс) | да | — (обход по требованию, глубина ≤ 8) | дистиллятор, absorb | «покажи источники» для L2/L3; блокирует decay источника |
| `mentions` | **src** упоминает сущность **dst** | `mentioned_by` | **нет** | нет | — | извлекатель сущностей | вход в граф по имени сущности |
| `touches` | **src** привязан к якорю **dst** | `touched_by` | **нет** | нет | — | `myc anchor bind`, агент | код↔память в обе стороны; протухание якоря помечает ребро подозрительным |
| `evidence` | **src** обоснован **dst** (фрагмент/лог/тест) | `evidence_for` | **нет** | нет | — | absorb, агент | пересчёт `confidence`; показ «на чём основано» |
| `contradicts` | **src** противоречит **dst** | `contradicts` (симметрично) | **нет** | нет | — | absorb (класс `contradiction`) | оба узла показываются вместе и помечаются в выдаче |

`contradicts` — единственный тип, добавленный сверх списка beads/memora: классу
`contradiction` из absorb-конвейера (§6.2) нужно куда-то записываться, а `relates`
теряет смысл «конфликт, нужен человек».

### 4.2 Что транзитивно и как именно считается

**Материализовано (пишется в той же транзакции, что и ребро):**

* `blocks` → `nodes.open_blockers`. `ready` становится сканом частичного индекса.
  Стоимость поддержки: 1 `UPDATE` по PK на вставку ребра и на смену статуса
  (амортизированно ≤ 30 мкс). Пересборка при подозрении: `myc doctor --recount`.
* `parent` → `parent_closure`. Вставка ребра `(c → p)` добавляет
  `|ancestors(p)|+1 × |descendants(c)|+1` строк; при глубине ≤ 32 и типичной
  ширине это < 200 строк.
* `supersedes` → `nodes.head_id` (обновляется у всей цепочки за один `UPDATE ... WHERE head_id = old_head`).
* `duplicates` → сжатие пути при вставке: если `dst` уже дубликат, ребро
  переставляется на канонический корень.

**Вычисляется на лету (рекурсивный CTE, лимит глубины в самом запросе):**
`derived_from` (провенанс), полный транзитивный `blocks` (для `myc blame-blockers`),
любые смешанные обходы. Причина: эти запросы вызываются единицами раз за сессию,
а материализация всего замыкания дала бы O(n²) строк на плотном графе.

**Никогда не транзитивно:** `relates`, `mentions`, `touches`, `evidence`, `contradicts`.
Транзитивное замыкание `relates` за 3 хопа на 100k узлах даёт «всё связано со всем»
и делает выдачу бесполезной — расширение ограничено **1 хопом и 12 соседями**
с сортировкой по весу.

### 4.3 Проверка ацикличности (перед вставкой `blocks`/`parent`)

```sql
WITH RECURSIVE reach(id, d) AS (
    SELECT :dst, 0
  UNION
    SELECT e.dst, r.d + 1
      FROM edges e JOIN reach r ON e.src = r.id
     WHERE e.type = :type AND e.deleted_at IS NULL AND r.d < :max_depth
)
SELECT 1 FROM reach WHERE id = :src LIMIT 1;
```
Вернулась строка ⇒ отказ `E_CYCLE` с показом пути. Стоимость на типичном графе
(≤ 64 достижимых) — ~80 мкс, внутри бюджета записи 5 мс.

**Как это реализовано и почему не буквально этим запросом (замер, 2026-09-07).**
`parent` проверяется не обходом, а материализованным замыканием
`parent_closure` — там факт «B уже потомок A» стоит один индексный спуск.
Обход остаётся для `blocks`, у которого транзитивной таблицы нет, и он сделан
BFS по `edges` в коде (`packages/store-sqlite/src/cycle.ts`), а не запросом
выше. Причины — числа на стенде 100 000 узлов / 193 000 рёбер `blocks`:

* CTE выше дедуплицирует пары `(id, глубина)`: узел, достижимый на пяти разных
  глубинах, обходится пять раз. На цепочке из 40 звеньев с ромбами это 0.64 мс
  против 0.07 мс у дедупликации по одному `id`.
* **Предела глубины НЕДОСТАТОЧНО.** Узел с 500 исходящими рёбрами, из которого
  достижимо 20 000 узлов на глубине 40 (предел 64 даже не задет), обходится за
  445 мс — в 89 раз больше бюджета записи. Поэтому у обхода `blocks` ВТОРОЙ
  предел: не более **512 посещённых узлов**. Замеры того же худшего случая:
  без бюджета 445 мс; CTE с бюджетом 4096 — 9.7 мс; BFS с бюджетом 4096 —
  6.0 мс; BFS с бюджетом 512 — **0.13 мс** (2.6 % бюджета записи).
* BFS отдаёт путь цикла даром; CTE потребовал бы второго прохода, а приёмка
  требует назвать ПУТЬ, а не пару концов.

**Два разных отказа, а не один (И2).** Упёршись в предел (глубины или числа
посещённых), проверка не доказала ацикличность — она перестала искать. Поэтому
`precond.cycle` (путь найден, он в сообщении: `dst → … → src → dst`) и
`precond.depth` («искать дальше дороже бюджета записи») — разные новости и
разные коды. Оба отказа откатывают транзакцию целиком: ни проекции, ни оплога.

При **мерже** ацикличность может нарушиться (две стороны добавили встречные рёбра).
Тогда цикл не отвергается (операция уже принята другим сайтом), а помечается:
рёбра цикла получают `attrs.cycle=1`, узлы попадают в `myc doctor`, `ready` считает
такую задачу заблокированной. Разрывает человек.

## 5. Слои L0–L3

### 5.1 Что физически лежит на каждом слое

| Слой | Что это | kind'ы | Тело | FTS | Вектор | Ретеншн тела | Читает `prime`? |
|---|---|---|---|---|---|---|---|
| **L0 conversation** | сырой диалог сессии | `session`, `message` | полностью | **да** | **нет** | 14 суток, дальше в `bodies_cold` | нет |
| **L1 atom** | одно утверждение / одна задача / один фрагмент | `note`, `task`, `fragment`, `doc`, `anchor` | полностью | да | **да** | бессрочно (закрытые задачи сжимаются через 30 суток) | нет (только по запросу) |
| **L2 scenario** | синтез по теме/задаче: «что мы знаем про X» | `note` (`attrs.scenario_key`), `entity` | синтез ≤ 2000 симв. | да | да | бессрочно, перестраивается | **да** |
| **L3 core/persona** | инварианты проекта и предпочтения пользователя | `note`, `skill` | ≤ 400 симв. каждый | да | да | бессрочно | **да, целиком** |

Слой — колонка `nodes.layer`, а не отдельное хранилище. Три причины:
рёбра между слоями (`derived_from`) обязаны быть обычными рёбрами;
`prime` обязан быть **одним** индекс-сканом `ix_nodes_prime`;
подъём по слою не должен быть переносом строки между таблицами (это ломает ID и рёбра).

Жёсткие лимиты (проверяются дистиллятором, превышение — в `myc status`):

* L3: **≤ 64 узла на scope**, суммарно **≤ 8 КБ** текста. При превышении — вытеснение
  по `salience` с понижением в L2 (`layer=2`), не удаление.
* L2: **≤ 512 узлов на scope**. При превышении — слияние двух ближайших по косинусу
  сценариев (порог 0.88) либо понижение хвоста по salience в L1.
* L1: без лимита; управляется decay (§6.4).

### 5.2 Подъём узла по слоям

```
L0 → L1   извлечение атомов из сессии
L1 → L2   кластеризация атомов в сценарий
L2 → L3   продвижение устойчивого сценария в ядро
```

Узел **никогда не меняет слой на месте** (кроме вытеснения L3→L2 и L2→L1, где
меняется только `layer`, но не содержание). Подъём — это **создание нового узла**
верхнего слоя и рёбра `derived_from` на все источники. Так провенанс сохраняется,
источник остаётся адресуемым, а откат дистилляции — это удаление одного узла.

### 5.3 Дистиллятор: кто и когда

Отдельный процесс-воркер (`myc daemon` или короткоживущий `bun` детач из CLI),
берёт задания из таблицы `jobs` (`kind='distill'`).

**Триггеры постановки задания:**

| Триггер | Условие | Приоритет `jobs.priority` |
|---|---|---|
| Закрытие сессии | `session.status → closed` | 3 |
| Накопление атомов | **32** новых L1-узла в scope с прошлой дистилляции | 5 |
| Таймер | **86 400 с** (24 ч) с последнего успешного прогона по scope | 7 |
| Ручной | `myc distill --scope X` | 1 |

**Бюджет одного прогона (жёсткий, прерывание по любому из):**
≤ **4** LLM-вызова, ≤ **30 с** wall-clock, ≤ **12 000** входных токенов,
≤ **256** обрабатываемых узлов.

**Отменяемость.** Перед каждым шагом (и перед каждым LLM-вызовом) воркер читает
`jobs.lease_holder`/`attrs.cancel`. `myc distill --abort` ставит `cancel=1`;
воркер выходит на ближайшей проверке (≤ 250 мс) и откатывает транзакцию.
Аренда задания — 120 с, продлевается каждые 30 с; повисший воркер теряет аренду
и задание подхватывает следующий.

**Алгоритм L0→L1 (извлечение атомов):**

```
distill_atoms(session_id):
    msgs = messages(session_id) where role in ('user','assistant')
    if llm_available:
        for batch in chunks(msgs, 40):                      # ≤ 4 батча ⇒ ≤ 4 вызова
            atoms = llm.extract_atoms(batch)                 # JSON: [{title, body, tags, confidence}]
            for a in atoms: absorb(a, layer=1, source='distill', derived_from=[batch ids])
    else:
        # детерминированный фолбэк, $0
        for m in msgs:
            for s in split_sentences(m.body):
                if matches(s, DECISION_PATTERNS):            # «решили», «выбрали», «не работает», «баг в», TODO:, FIXME:
                    absorb({title: first(s, 120), body: s, confidence: 0.5},
                           layer=1, source='distill-heuristic', derived_from=[m.id])
        mark_degraded('distill.atoms', 'heuristic-only: no LLM key')
```

**Алгоритм L1→L2 (сценарии):**

```
distill_scenarios(scope):
    A = L1-узлы scope, обновлённые с прошлого прогона, лимит 256
    # кластеризация детерминированная и дешёвая — не нужен LLM
    C = agglomerative(A ∪ members_of_existing_L2(scope),
                      metric=cosine, threshold=0.78, max_clusters=64)
    for cluster in C:
        key = stable_key(cluster)                # blake3 отсортированных ID членов ядра
        existing = L2-узел с attrs.scenario_key = key
        text = llm.summarize(cluster) if llm_available
               else template_summary(cluster)    # заголовок кластера + до 8 title'ов + счётчики
        if existing: supersede(existing, text)   # supersedes-ребро, не UPDATE
        else:        create(kind='note', layer=2, attrs.scenario_key=key, body=text,
                            edges=[derived_from → each member])
```

`template_summary` без LLM даёт: `«{topic}: {n} фактов, {k} открытых задач»` + список
до 8 заголовков + даты. Это заведомо хуже LLM-саммари, но **работает и честно
помечено** `attrs.summary_kind='template'`; в `prime` такие узлы отдаются с пометкой.

**Алгоритм L2→L3 (ядро):** промоушен только по детерминированному правилу, без LLM:

```
promote_core(scope):
    for s in L2(scope):
        stable   = age(s) >= 7*86400_000 and supersede_count(s) <= 2
        reused   = s.accessed_at hits >= 5 за 14 суток
        endorsed = exists edge evidence→s  or  s.confidence >= 0.9
        if stable and reused and endorsed and count(L3(scope)) < 64:
            create(kind='note', layer=3, body=first(s.body, 400), derived_from=[s])
```

Человек может продвинуть/понизить вручную (`myc pin <id>` / `myc unpin <id>`) —
ручное решение помечается `attrs.pinned=1` и защищено от автоматического вытеснения.

## 6. Жизненный цикл памяти

### 6.1 `absorb` — общая схема

```
myc remember "..."  /  MCP absorb  /  дистиллятор
        │
        ├── ФАЗА 0  синхронно, ≤ 5 мс, детерминированно, $0
        │     normalize → content_hash → точный дубликат?
        │        да  → seen_count++, updated_at=now, вернуть существующий id
        │        нет → INSERT nodes(status='active', attrs.absorb='pending')
        │               + INSERT jobs(kind='absorb') + INSERT jobs(kind='embed')
        │               вернуть новый id
        │
        ├── ФАЗА A  фон, детерминированно, $0        (после того как готов эмбеддинг)
        │     kNN top-24 по вектору в пределах (scope, layer)  +  FTS top-24
        │     для каждого кандидата: cos, trigram_jaccard
        │        cos ≥ 0.95 и jac ≥ 0.80  → DUPLICATE      (решено без LLM)
        │        0.82 ≤ cos < 0.95        → CANDIDATE      (нужна ФАЗА B)
        │        cos < 0.82               → NEW
        │
        └── ФАЗА B  фон, LLM, опционально
              один вызов, ≤ 600 выходных токенов, таймаут 8 с, 1 ретрай
              вход: новый текст + до 5 кандидатов
              выход: {class: duplicate|update|contradiction|related|new, target_id, reason}
```

Нормализация текста для `content_hash`: NFKC, схлопывание пробелов, обрезка
конечной пунктуации, lowercase. Хеш — blake3-128, hex.

### 6.2 Действия по классу

| Класс | Действие | Рёбра | Побочные эффекты |
|---|---|---|---|
| `duplicate` | канонический = более ранний по `created_at`, при равенстве — с большим `confidence` | `duplicates: new → canonical` (путь сжат) | `canonical.seen_count++`, новый узел `status='superseded'`, `head_id=canonical` |
| `update` | новый узел становится головой | `supersedes: new → old` | `old.status='superseded'`, `old.head_id=new.id` и всей цепочке; рёбра `touches`/`mentions` **копируются** на новый узел |
| `contradiction` | оба узла живут | `contradicts` (двунаправленно записываем одно ребро, читаем симметрично) | `confidence` обоих × 0.7; узел попадает в `myc doctor --conflicts` |
| `related` | ничего не меняем | `relates` с `weight = cos` | — |
| `new` | ничего | — | — |

### 6.3 Supersession и режимы истории

* Цепочка: `A ←supersedes— B ←supersedes— C`. `C.head_id = NULL`, `A.head_id = B.head_id = C.id`.
  Обновление головы — один `UPDATE nodes SET head_id=:new WHERE head_id=:old OR id=:old`.
* **Режим `active` (по умолчанию):** все ретривальные запросы несут `AND head_id IS NULL`.
* **Режим `full_history`:** флаг на узле (`attrs.history_mode='full'`) — тогда узел
  и его предки видимы всегда; или на запросе (`myc search --history`, MCP-параметр
  `include_superseded: true`).
* `myc show <id> --chain` печатает всю цепочку с датами и `reason` из absorb.
* Supersession **никогда не удаляет** — только `purge` удаляет.

### 6.4 Decay и сжатие

Три независимых механизма.

**(1) Salience decay** — непрерывный, детерминированный, без записи:
```
salience(n, t) = base(n) * exp(-(t - accessed_at) / TAU)
TAU = 14 * 86400 * 1000 мс   (14 суток)
base(n) = 1.0 + 0.15*ln(1+seen_count) + 0.30*[layer=3] + 0.15*[layer=2]
          + 0.20*[pinned] + 0.10*ln(1+|edges|)
```
Считается выражением в SQL при ранжировании; материализуется в `nodes.salience`
раз в сутки фоновым `jobs(kind='rescore')` для использования в индексе `ix_nodes_prime`.

**(2) Сжатие закрытых задач:**
```
condition: kind='task' AND status IN ('closed','cancelled')
           AND closed_at < now - 30*86400*1000
           AND compacted_at IS NULL
           AND NOT EXISTS (открытая задача с ребром blocks/parent/relates на неё)
action:    body → bodies_cold (zstd, уровень 6)
           body := summary (≤ 512 симв.), body_cold := 1, compacted_at := now
           FTS-строка перестраивается по summary
```
Саммари: с LLM — 1 вызов на батч из **16** задач; без LLM — детерминированный шаблон
`«{title} [{type}/P{priority}] закрыта {date}. {первые 200 симв. body} … {последние 120 симв.} {список commit/PR из attrs}»`.
Обратимо: `myc uncompact <id>` восстанавливает тело из `bodies_cold`.

**(3) Свёртка старых эпизодов:**
```
condition: kind='session' AND ended_at < now - 14*86400*1000
action:    создать узел kind='note', layer=1, attrs.episode_of=<session_id>
           с дайджестом сессии (LLM: 1 вызов; без LLM: первые/последние 3 сообщения + список
           созданных/закрытых узлов + список изменённых файлов из touches)
           + derived_from на сессию
           тела всех message-узлов → bodies_cold, их FTS-строки удаляются
           сами message-узлы остаются (рёбра replies_to и провенанс не рвём)
```

**Detach-защита:** ни (2), ни (3) не трогают узел, у которого есть ребро
`derived_from` **от** живого L2/L3-узла и который является его единственным
источником — иначе провенанс ядра указывал бы в пустоту.

### 6.5 `prune` и `purge`

| Команда | Что делает | Что остаётся | Оплог |
|---|---|---|---|
| `myc prune` | удаляет строки `bodies_cold` старше **180 суток**; удаляет `oplog` старше **30 суток**, подтверждённый всеми известными пирами; `VACUUM` при фрагментации > 25 % | узлы, рёбра, саммари | не пишется (локальная операция) |
| `myc purge --id X [--cascade]` | физическое `DELETE` узла, его рёбер, вектора, FTS-строки, `bodies_cold`, замыкания | ничего | пишется `op='purge'` — пиры удалят у себя |
| `myc purge --scope X --before T` | то же массово, с обязательным `--yes` | — | пишется |

`purge` необратим и требует подтверждения; `delete` в CLI — это soft-delete
(`deleted_at`), он реплицируется как обычное поле и обратим (`myc restore`).

### 6.6 Что детерминированно, а что требует LLM

| Шаг | Без LLM ($0, офлайн) | С LLM | Как деградирует |
|---|---|---|---|
| Точный дубликат | **полностью** (blake3) | — | — |
| Почти-дубликат | **полностью** (cos ≥ 0.95 ∧ jaccard ≥ 0.80) | — | без эмбеддингов — только FTS-кандидаты + jaccard; порог поднимается до 0.90 |
| Классификация кандидата | нет | да | **все кандидаты → `related`**, ничего не сливается и не выбрасывается |
| Извлечение атомов L0→L1 | паттерны решений/проблем (`DECISION_PATTERNS`) | да | ниже полнота, помечено `source='distill-heuristic'` |
| Кластеризация L1→L2 | **полностью** (агломеративная по косинусу) | — | без эмбеддингов кластеризация по тегам+FTS-триграммам |
| Текст сценария L2 | шаблон | синтез | `attrs.summary_kind='template'`, видно в выдаче |
| Промоушен L2→L3 | **полностью** (правило из 3 условий) | — | — |
| Саммари закрытых задач | шаблон | синтез | `attrs.summary_kind='template'` |
| Извлечение сущностей | регулярки + словарь из `entity`-узлов | NER | ниже полнота |

**Громкая деградация (закрываем ловушку memora).** Таблица `myc_health`:

```sql
CREATE TABLE myc_health (
  component  TEXT PRIMARY KEY,     -- embed | llm | graft | vec_index | fts | sync | distill | absorb
  state      TEXT NOT NULL,        -- ok | degraded | down
  reason     TEXT NOT NULL DEFAULT '',
  since      INTEGER NOT NULL,
  detail     TEXT NOT NULL DEFAULT '{}'
);
```
Правила: (а) `myc status` печатает деградации первым блоком и **красным**;
(б) exit-код `myc status` = 1 при любом `degraded`, 2 при `down`;
(в) каждый MCP-ответ ретривала несёт поле `degraded: ["llm","embed"]`, если оно непусто;
(г) узлы, записанные в деградированном режиме, помечены `attrs.degraded_at`, и
`myc doctor --reprocess` переставляет им задания absorb/embed после восстановления;
(д) **фолбэка «векторы → TF-IDF» не существует**: при недоступности эмбеддингов
поиск честно становится FTS-only и говорит об этом.

## 7. Якоря на код поверх graft

### 7.1 Что храним у себя

Якорь — узел `kind='anchor'` + строка в `anchors`. Содержательное ядро — **crux как
текст** (идея graft, перенесённая на якоря): номера строк протухают при первом же
рефакторинге, текст — нет.

| Поле | Смысл | Как получено |
|---|---|---|
| `repo_id` | стабильный ключ репозитория: `blake3(git remote origin)[0..8]`, иначе `blake3(realpath)` | локально |
| `repo_root` | абсолютный путь на этой машине (не реплицируется, per-site) | локально |
| `path` | путь относительно `repo_root`, всегда POSIX-слэши | локально |
| `lang` | язык по расширению | локально |
| `symbol` | имя символа, если якорь на символ (`Foo.bar`) | от graft или от пользователя |
| `span_start`,`span_end` | строки, 1-based, включительно | локально/graft |
| `file_hash` | blake3 всего файла на момент привязки | локально |
| `span_hash` | blake3 нормализованного текста спана | локально |
| `crux` | **до 400 символов / до 24 строк** самого показательного куска спана (сигнатура + первые непустые строки тела) | локально |
| `crux_norm` | `crux` без комментариев, с нормализованными пробелами и без строковых литералов | локально |
| `fp` | winnowing-фингерпринт спана: k-грамм **5**, окно **4**, **32×u32** | локально |
| `state` | `fresh│drifted│stale│lost` | ре-биндер |
| `drift` | 0..1, сходство при последней ре-привязке | ре-биндер |
| `mtime_ms`,`size_bytes` | для дешёвой проверки | локально |
| `bound_at`,`checked_at` | — | — |
| `git_ref` | `HEAD` sha на момент привязки (если есть git) | локально |

Реплицируется всё, кроме `repo_root` (машинозависим) — на другой машине он
резолвится из `repo_id` через локальный конфиг `myc repo map`.

### 7.2 Детект протухания — три уровня, все локальные

```
check_anchor(a) -> state:
    st = stat(join(repo_root(a.repo_id), a.path))
    # Уровень 1: ~0.05 мс — метаданные
    if st is None:                       return rebind_via_graft(a)      # файл исчез/переехал
    if st.mtime_ms == a.mtime_ms and st.size == a.size_bytes:
        a.checked_at = now;              return 'fresh'
    # Уровень 2: ~0.6 мс/100 КБ — хеш файла
    fh = blake3(read(path))
    if fh == a.file_hash:
        a.mtime_ms = st.mtime_ms;        return 'fresh'                  # touch без изменений
    # Уровень 3: ~3–20 мс — ре-привязка по тексту
    return rebind_local(a, text)
```

Уровень 1 стоит один `stat` — поэтому **`myc show` и `myc prime` могут позволить себе
только его** и только для якорей, реально попавших в выдачу (≤ 12 штук ⇒ ≤ 0.6 мс).
Уровни 2 и 3 — всегда фон (`jobs(kind='anchor_check')`).

### 7.3 Ре-привязка после рефакторинга

```
rebind_local(a, text):
    lines = split_lines(text)
    # (1) точное совпадение нормализованного crux — самый частый случай (код переехал по файлу)
    hit = find_normalized(lines, a.crux_norm)
    if hit: a.span = hit; a.drift = 1.0; return commit(a, 'fresh')

    # (2) нечёткое: winnowing по скользящему окну высоты span_len ± 40 %
    best = argmax over windows w of jaccard(fp(w), a.fp)
    if best.score >= 0.60:
        a.span = best.span; a.drift = best.score
        a.crux = recut_crux(best.span); a.fp = fp(best.span)
        return commit(a, 'drifted')

    # (3) спрашиваем graft — вне горячего пути, с таймаутом
    return rebind_via_graft(a)

rebind_via_graft(a):
    if not graft_available(a.repo_id):
        return commit(a, 'stale')                       # честно: не знаем, где это теперь
    cands = graft_lookup(a)          # см. 7.4, таймаут 200 мс, ≤ 8 вызовов на батч
    for c in cands (по убыванию ранга, ≤ 5):
        s = jaccard(fp(text_of(c)), a.fp)
        if s >= 0.50:
            a.repo/path/span = c; a.drift = s
            a.crux = recut_crux(c); a.fp = fp(c); a.file_hash = blake3(file(c))
            return commit(a, 'drifted')
    return commit(a, 'lost')
```

`commit(a, state)` в одной транзакции: обновляет `anchors`, ставит `nodes.status`,
и если `state ∈ {stale, lost}` — помечает все входящие рёбра `touches`
`attrs.suspect=1`, чтобы ретривал понижал такие результаты и показывал плашку.

Состояния и что с ними делает продукт:

| `state` | Значит | Ретривал | Что показываем |
|---|---|---|---|
| `fresh` | спан совпал | полный вес | `file:line` |
| `drifted` | нашли по тексту в другом месте, `drift ∈ [0.5, 1)` | вес × `drift` | `file:line` + «сдвинулось» |
| `stale` | файл изменился, не нашли, graft недоступен | вес × 0.5 | последний известный `file:line`, «требует проверки» |
| `lost` | не нашли даже через graft | вес × 0.2, не попадает в `prime` | «код удалён или переписан», предложение отвязать |

### 7.4 Что спрашиваем у graft, а что нет

**Спрашиваем (адаптер `GraftAdapter`, все вызовы — вне горячего пути, таймаут 200 мс,
не более 8 вызовов на один батч ре-привязки):**

| Нужда | Вызов | Когда |
|---|---|---|
| Резолв символа в `file:line` | `graft grep "<symbol>"` (исчерпывающий) | `myc anchor add --symbol`, ре-привязка |
| Кандидаты по смыслу | `graft ask "<crux первые 80 симв.>" --source` | ре-привязка, когда символ неизвестен |
| API файла для нарезки якорей | `graft skeleton <file>` | `myc anchor scan <file>` |
| Радиус изменения при правке символа | `graft callers <sym> --depth all` | `myc impact <anchor>` (по требованию пользователя) |
| Ориентация в незнакомом репо | `graft map` | `myc init` в новом репозитории |

**Не спрашиваем никогда:** ничего в `prime`, `show`, `get`, `search`, `ready` —
это внешний процесс, его латентность нам неподконтрольна, а бюджеты §3 — жёсткие.

**Не храним у себя:** graft-узлы, его summary, его рёбра вызовов, его индекс.
Причина: дублирование состояния, которое нужно синхронизировать, а graft уже держит
свежесть по content-hash сам. Кэшируем **только** результат конкретного резолва
на время одного батча (in-memory Map, TTL 60 с).

**Работа без graft.** `graft_available(repo_id)` = существует `<repo_root>/graft/INDEX.md`
и в PATH есть `graft`. Если нет — уровни 1–2 и `rebind_local` работают полностью
(они не зависят от graft), теряется только шаг (3). В `myc_health` пишется
`graft: degraded (not indexed in <repo>)`, `myc doctor` предлагает
`graft init -y --agents claude agents --no-global`.

### 7.5 Двусторонняя связь и триггеры пересканирования

* Память/задача → код: ребро `touches: node → anchor`.
* Код → память: обратный обход `ix_edges_dst`; `myc why <file>:<line>` находит якоря,
  чьи спаны накрывают строку (индекс `ix_anchors_file` + фильтр по спану), и отдаёт
  входящие узлы.

Триггеры пересканирования:

| Триггер | Как детектируем | Стоимость |
|---|---|---|
| Сменился git HEAD | сравниваем `mtime` файла `.git/HEAD` с `myc_meta.git_head_mtime` на старте CLI | ~0.1 мс |
| Явно | `myc anchor check [--repo X]` | — |
| Периодически при открытой сессии | `jobs(kind='anchor_check')` каждые **300 с**, дебаунс изменений файлов **2 с** | фон |
| Файл изменён watcher'ом | опционально, если запущен `myc daemon --watch` | фон |

Батч пересканирования: **≤ 256 якорей** за прогон, приоритет — по `checked_at ASC`
среди `state != 'lost'`.

 AND (SELECT status FROM nodes WHERE id=new.src)
       NOT IN ('closed','cancelled','superseded','retracted')

  UPDATE nodes SET open_blockers = open_blockers + 1 WHERE id = new.dst;
END;

WHEN new.type='blocks' AND old.deleted_at IS NULL AND new.deleted_at IS NOT NULL
 AND (SELECT status FROM nodes WHERE id=new.src)
       NOT IN ('closed','cancelled','superseded','retracted')
BEGIN
  UPDATE nodes SET open_blockers = max(0, open_blockers - 1) WHERE id = new.dst;
END;

CREATE TRIGGER trg_st_close AFTER UPDATE OF status ON nodes
WHEN old.status NOT IN ('closed','cancelled','superseded','retracted')
 AND new.status     IN ('closed','cancelled','superseded','retracted')
BEGIN
  UPDATE nodes SET open_blockers = max(0, open_blockers - 1)
   WHERE id IN (SELECT dst FROM edges
                 WHERE src=new.id AND type='blocks' AND deleted_at IS NULL);
END;

CREATE TRIGGER trg_st_reopen AFTER UPDATE OF status ON nodes
WHEN old.status     IN ('closed','cancelled','superseded','retracted')
 AND new.status NOT IN ('closed','cancelled','superseded','retracted')
BEGIN
  UPDATE nodes SET open_blockers = open_blockers + 1
   WHERE id IN (SELECT dst FROM edges
                 WHERE src=new.id AND type='blocks' AND deleted_at IS NULL);
END;

### 8.3 Где диалекты расходятся

| Аспект | SQLite | PostgreSQL | Как закрываем |
|---|---|---|---|
| Полнотекст | FTS5, отдельная виртуальная таблица, join по `rowid`, ранг `bm25()` | `tsvector` STORED-колонка + GIN, ранг `ts_rank_cd()` | Разные тексты запроса `search_fts` под одним id; наружу — одинаковый `{id, rank}` |
| Вектор | `vec0` виртуальная таблица, join по `node_rowid`, **линейный скан** ⇒ обязательны partition keys | колонка `vector(384)` + HNSW, `<=>` | Разные тексты `search_vec`; `k'` для over-fetch задаётся диалектом (SQLite 4k, PG 2k) |
| JSON | `TEXT` + `json_extract`, virtual generated columns | `JSONB` + `->>`, GIN `jsonb_path_ops` | Хелперы `d.jsonGet(col, path)` в компиляторе запроса |
| Плейсхолдеры | `?1, ?2` | `$1, $2` | Автопереписывание при загрузке (§8.4) |
| Автоинкремент | `INTEGER PRIMARY KEY AUTOINCREMENT` | `GENERATED ALWAYS AS IDENTITY` | Только `jobs` и `oplog`, оба в override-списке |
| Время | `INTEGER` мс | `BIGINT` мс (**не** `timestamptz`) | Одинаковая арифметика, никакого TZ; человеку форматируем в CLI |
| Транзакция записи | `BEGIN IMMEDIATE` (иначе upgrade-deadlock) | `BEGIN` (+ `SELECT ... FOR UPDATE SKIP LOCKED` для батч-claim) | `driver.tx('immediate', fn)` — в PG режим игнорируется |
| Конкурентность записи | один писатель на файл, `busy_timeout 5000` | MVCC | Все записи короткие (< 1 мс); длинных write-транзакций нет by design |
| Частичные индексы | есть | есть | одинаково |
| Рекурсивный CTE | есть | есть | одинаково |
| `max()` над скалярами | `max(a,b)` | `greatest(a,b)` | override |
| Массивы | нет ⇒ JSON-массив | есть, но **не используем** | одинаковая форма данных |
| Upsert | `ON CONFLICT ... DO UPDATE` | то же | одинаково |
| `RETURNING` | есть (≥ 3.35) | есть | одинаково |
| Компрессия тел | zstd в Bun, хранится как `BLOB` | то же, `BYTEA` | одинаково (не полагаемся на TOAST) |
| Изменение схемы | часто требует rebuild-таблицы (12 шагов) | `ALTER TABLE` | Хелпер `rebuildTable()` в раннере миграций |

### 8.4 Слой абстракции запросов в Bun

Не ORM и не квери-билдер. **Реестр запросов**: у каждого запроса есть id, один
текст SQL и — только при реальном расхождении — override для PG.

```ts
// src/db/dialect.ts
export type Dialect = 'sqlite' | 'pg';

/** Единственное автоматическое преобразование: ?N -> $N. */
const toPg = (sql: string) => sql.replace(/\?(\d+)/g, '$$$1');

export interface QuerySpec { sql: string; pg?: string }
export const defineQueries = <T extends Record<string, QuerySpec>>(q: T) => q;

// src/db/queries.ts  (~50 записей; override нужен ~9 из них)
export const Q = defineQueries({
  node_get: { sql:
    `SELECT * FROM nodes WHERE id = ?1 AND deleted_at IS NULL` },

  node_prefix: { sql:
    `SELECT id FROM nodes WHERE id >= ?1 AND id < ?2 AND deleted_at IS NULL LIMIT 2` },

  ready: { sql:
    `SELECT id, title, priority, updated_at
       FROM nodes
      WHERE scope = ?1 AND kind = 'task' AND status = 'open'
        AND open_blockers = 0 AND deleted_at IS NULL
        AND (lease_expires = 0 OR lease_expires < ?2)
        AND {{ACL}}
      ORDER BY priority ASC, updated_at ASC
      LIMIT ?3` },

  claim: { sql:
    `UPDATE nodes
        SET status='in_progress', assignee=?2, lease_holder=?2,
            lease_epoch=lease_epoch+1, lease_expires=?3,
            updated_at=?4, hlc=?5, site_id=?6
      WHERE id=?1 AND status='open' AND deleted_at IS NULL
        AND (lease_expires = 0 OR lease_expires < ?4)
      RETURNING id, lease_epoch` },

  search_fts: {
    sql: `SELECT n.id, bm25(nodes_fts, 4.0, 1.0, 2.0) AS rank
            FROM nodes_fts f JOIN nodes n ON n.rowid = f.rowid
           WHERE nodes_fts MATCH ?1 AND n.scope = ?2 AND n.deleted_at IS NULL
             AND n.head_id IS NULL AND {{ACL}}
           ORDER BY rank LIMIT ?3`,
    pg:  `SELECT n.id, -ts_rank_cd(n.tsv, websearch_to_tsquery('simple', $1)) AS rank
            FROM nodes n
           WHERE n.tsv @@ websearch_to_tsquery('simple', $1)
             AND n.scope = $2 AND n.deleted_at IS NULL
             AND n.head_id IS NULL AND {{ACL}}
           ORDER BY rank LIMIT $3` },

  search_vec: {
    sql: `SELECT n.id, v.distance AS rank
            FROM nodes_vec v JOIN nodes n ON n.rowid = v.node_rowid
           WHERE v.embedding MATCH ?1 AND v.scope = ?2 AND v.layer >= ?3
             AND k = ?4 AND n.deleted_at IS NULL AND {{ACL}}`,
    pg:  `SELECT n.id, (n.embedding <=> $1::vector) AS rank
            FROM nodes n
           WHERE n.scope = $2 AND n.layer >= $3 AND n.embedding IS NOT NULL
             AND n.deleted_at IS NULL AND {{ACL}}
           ORDER BY n.embedding <=> $1::vector LIMIT $4` },
});
```

`{{ACL}}` — единственная подстановка в тексте; её раскрывает `AclCompiler` (§10.2)
в зависимости от принципала, и результат кэшируется вместе с подготовленным
стейтментом. Никаких других конкатенаций SQL в кодовой базе нет — это правило,
проверяемое линтером (`no-raw-sql` кроме `src/db/queries.ts`).

```ts
// src/db/driver.ts
export interface Driver {
  readonly dialect: Dialect;
  one<T>(q: keyof typeof Q, p: unknown[], acl?: AclKey): T | undefined;
  all<T>(q: keyof typeof Q, p: unknown[], acl?: AclKey): T[];
  run(q: keyof typeof Q, p: unknown[], acl?: AclKey): { changes: number };
  tx<T>(mode: 'deferred' | 'immediate', fn: (t: Driver) => T): T;
}
```

*SQLite-драйвер* — `bun:sqlite`, кэш подготовленных стейтментов `Map<string, Statement>`
на **64** записи (ключ = `queryId + '|' + aclKey`), вытеснение LRU.
*PG-драйвер* — `Bun.sql`/`postgres.js`, именованные prepared statements, тот же кэш.

**Гарантия паритета.** Один и тот же поведенческий тест-сьют (~120 кейсов) прогоняется
против обоих драйверов в CI: `bun test --dialect=sqlite` и `--dialect=pg`
(Postgres из `docker compose`). Расхождение результата — падение сборки.
Дополнительно `EXPLAIN`-тесты: для 8 горячих запросов проверяется, что план
использует ожидаемый индекс (SQLite `EXPLAIN QUERY PLAN` содержит имя индекса;
PG `EXPLAIN (FORMAT JSON)` не содержит `Seq Scan` по `nodes`).

### 8.5 Миграции и guard версии схемы

```
migrations/
  0001_init.sql.ts
  0002_anchors_fp.sql.ts
  ...
```
Каждая миграция — TS-модуль `{ version, name, up(driver): void }`, forward-only,
исполняется целиком в одной транзакции. `checksum = blake3(source)`.

```
open_database(path, EXPECTED_SCHEMA):
    db = open(path); apply_pragmas(db)
    have = read_int(myc_meta, 'schema_version', default 0)

    if have > EXPECTED_SCHEMA:
        fatal(exit=3,
          "база записана более новой версией myc (схема {have}, бинарь знает {EXPECTED_SCHEMA}). "
          "Обновите myc: `myc self-update`. Даунгрейд схемы не поддерживается.")

    for m in applied_migrations(db):
        if m.checksum != known_checksum(m.version):
            fatal(exit=4, "миграция {m.version} изменилась после применения — база и бинарь "
                          "разошлись. `myc doctor --schema` покажет расхождение.")

    if have < EXPECTED_SCHEMA:
        if not config.auto_migrate:                 # default: true для sqlite, false для pg
            fatal(exit=5, "нужна миграция {have} -> {EXPECTED_SCHEMA}: `myc migrate`")
        with advisory_lock(db):                     # sqlite: BEGIN IMMEDIATE; pg: pg_advisory_lock(0x6d7963)
            backup_if_sqlite(path)                  # копия <path>.bak-<have> перед первой миграцией
            for m in pending(have, EXPECTED_SCHEMA):
                tx: m.up(db); record(m)
            set(myc_meta, 'schema_version', EXPECTED_SCHEMA)
```

Коды выхода: **3** — БД новее бинаря; **4** — checksum миграции; **5** — нужна миграция,
автомиграция выключена. Все три печатают ровно одну строку с командой-исправлением.

Отдельно версионируется **модель эмбеддингов**: `myc_meta.embed_model` +
`embed_dim`. Смена модели ⇒ размерность вектора и семантика расстояний другие ⇒
`myc doctor` требует `myc reembed` (фоновая перестройка `nodes_vec` батчами по
**256** с чекпойнтом в `jobs.payload`, возобновляемая после падения — приём из socraticode).
До завершения `reembed` векторный поиск помечен `degraded`, но не выключен:
используются только узлы с `attrs.embed_model == current`.

## 9. Оплог, синхронизация и мерж

### 9.1 Почему не векторные часы и не Dolt

| Кандидат | Почему отвергли |
|---|---|
| **Dolt** (как в beads) | Отдельный движок, +~100 МБ бинаря, свой протокол, ломает «SQLite по умолчанию, Postgres для сервера» из §2 |
| **Векторные часы** | Размер часов O(числа сайтов); нужен буфер каузальной доставки; при 20 машинах × 5 агентов часы весят больше полезной нагрузки. Каузальность нам не нужна: у нас нет операций, корректность которых зависит от порядка чужих операций над **другими** полями |
| **Полный CRDT-документ на узел** (Automerge/Yjs) | Нам не нужен конкурентный текстовый редактор. Тела правит один автор за раз; цена — метаданные размером с сам документ |
| **Только «последняя запись победила» по строке** | Теряет параллельные правки разных полей одного узла (один поменял приоритет, другой — тело, и одна правка пропадает) |

**Выбор: гибрид.** Тип разрешения конфликта подобран под каждый класс поля.

| Класс | Тип | Поля |
|---|---|---|
| Скаляр | **LWW-register по полю**, часы = HLC, тайбрейк по `site_id` лексикографически | `title`, `body`, `status` (кроме claim), `priority`, `layer`, `acl`, `owner_id`, `team_id`, `confidence`, `due_at`, `deleted_at`, `attrs.*` (по ключу верхнего уровня) |
| Счётчик | **G-counter** (`counters`, чтение = `SUM`) | `seen_count`, счётчики телеметрии |
| Множество | **OR-Set, add-wins** | `edges`, `acl_grants` |
| Взаимное исключение | **Lease с epoch** | `assignee`, `lease_holder`, `lease_epoch`, `lease_expires`, `status='in_progress'` |
| Неизменяемое | запись-один-раз, конфликт невозможен | `id`, `kind`, `created_at`, `content_hash`, `actor` |

Обоснование add-wins для рёбер: заново потерянную связь дороже обнаружить, чем
лишнюю — удалить. Конкурентные «добавил / удалил» разрешаются в пользу добавления;
удаление, знающее конкретный `add_tag`, побеждает именно то добавление.

### 9.2 Hybrid Logical Clock

```
hlc: 64-битное целое = (ts_ms << 16) | counter
ts_ms   — 48 бит, unix-миллисекунды (хватает до 8919 года)
counter — 16 бит, до 65 536 операций в одну миллисекунду на сайт

now_hlc(state, phys_ms):
    if phys_ms > state.ts:  state.ts = phys_ms; state.ctr = 0
    else:                   state.ctr += 1
    assert state.ctr < 65536          # иначе подождать 1 мс
    return (state.ts << 16) | state.ctr

recv_hlc(state, phys_ms, remote_hlc):
    r_ts, r_ctr = remote_hlc >> 16, remote_hlc & 0xffff
    m = max(state.ts, r_ts, phys_ms)
    if   m == state.ts == r_ts: state.ctr = max(state.ctr, r_ctr) + 1
    elif m == state.ts:         state.ctr += 1
    elif m == r_ts:             state.ctr  = r_ctr + 1
    else:                       state.ctr  = 0
    state.ts = m
    return (state.ts << 16) | state.ctr
```

Защита от съехавших часов: если `r_ts > phys_ms + 300000` (5 мин вперёд) — операция
принимается, но в `myc_health` пишется `sync: degraded (peer clock skew +Xс)`.
`site_id` — UUIDv4, генерируется при `myc init` на **реплику БД**, а не на человека:
две копии базы на одной машине — два сайта.

### 9.3 Применение операции

```
apply_op(op):
    if exists(oplog where op_id = op.op_id): return    # идемпотентность
    insert into oplog(..., origin=0)
    hlc_state = recv_hlc(hlc_state, now_ms(), op.hlc)

    switch op.op:
      'set':                                            # LWW по полю
          cur = field_clock[op.entity_id, op.field]
          if cur is null or (op.hlc, op.site_id) > (cur.hlc, cur.site_id):
              write_field(op.entity_id, op.field, op.value)
              field_clock[op.entity_id, op.field] = (op.hlc, op.site_id)
          # иначе: наша версия новее, молча игнорируем

      'inc':                                            # G-counter
          counters[op.entity_id, op.field, op.site_id] = max(existing, op.value)
          nodes.<field> = (select sum(value) from counters where ...)

      'edge_add':                                       # OR-Set add
          upsert edges(src,type,dst) set add_tag=op.value.tag, deleted_at=null, weight=...
          if exists edge_tombstones(src,type,dst,tag=op.value.tag):
              edges.deleted_at = tombstone.ts          # удаление знало именно этот тег

      'edge_del':
          insert edge_tombstones(src,type,dst,tag=op.value.tag, ...)
          if edges.add_tag == op.value.tag: edges.deleted_at = op.ts_ms
          # если add_tag другой, значит ребро добавлено заново: add wins, не трогаем

      'claim': см. 9.4
      'purge': жёсткое удаление node+edges+vec+fts+cold, тумбстоун в oplog
```

Порядок применения внутри пакета — по `(hlc, site_id)` возрастанию. Каузальная
доставка **не требуется**: LWW и OR-Set коммутативны, G-counter — тоже.
Единственная не-коммутативная операция — `purge`; она применяется последней в пакете
и поглощает все более ранние операции над тем же `entity_id`.

### 9.4 Атомарный claim без гонок

**Локально (много агентов, одна БД):** одна CAS-инструкция, никакого read-modify-write.

```sql
BEGIN IMMEDIATE;
UPDATE nodes
   SET status='in_progress', assignee=?2, lease_holder=?2,
       lease_epoch = lease_epoch + 1,
       lease_expires = ?3,                 -- now + 900000 мс
       updated_at = ?4, hlc = ?5, site_id = ?6
 WHERE id = ?1
   AND deleted_at IS NULL
   AND status = 'open'
   AND open_blockers = 0
   AND (lease_expires = 0 OR lease_expires < ?4)
RETURNING id, lease_epoch;
COMMIT;
```

`changes() == 0` означает, что задачу забрали; берём следующую из `ready`. Окна между
проверкой и записью не существует: условие и запись — один стейтмент, а
`BEGIN IMMEDIATE` берёт write-lock сразу (без него SQLite мог бы уйти в
`SQLITE_BUSY` на upgrade и откатить всю транзакцию).

**Батч:** `myc ready --claim 3` вызывает CAS в цикле по кандидатам, останавливается,
набрав 3 или исчерпав список. В Postgres то же самое делается одним запросом:

```sql
WITH cand AS (
  SELECT id FROM nodes
   WHERE scope=$1 AND kind='task' AND status='open' AND open_blockers=0
     AND deleted_at IS NULL AND (lease_expires=0 OR lease_expires<$4)
   ORDER BY priority, updated_at
   LIMIT $7 FOR UPDATE SKIP LOCKED)
UPDATE nodes n SET status='in_progress', assignee=$2, lease_holder=$2,
       lease_epoch=n.lease_epoch+1, lease_expires=$3, updated_at=$4, hlc=$5, site_id=$6
  FROM cand WHERE n.id = cand.id
RETURNING n.id;
```

**Аренда:** TTL **900 000 мс** (15 мин), продление heartbeat'ом каждые **300 000 мс**
(5 мин) через `myc claim --renew <id>`. Просроченная аренда автоматически
переоткрывает задачу для других (условие `lease_expires < now` в CAS). Отдельного
сборщика не нужно, но `myc doctor` возвращает `status='open'` задачам с
истёкшей арендой старше **3 600 000 мс** (1 ч), чтобы они не висели «в работе» в UI.

**Мерж claim между сайтами:** LWW сюда не годится — офлайновый агент с более
поздними часами «украл» бы задачу у того, кто её уже делает. Правило:

```
merge_claim(local, remote):
    if remote.lease_epoch > local.lease_epoch:  взять remote
    if remote.lease_epoch < local.lease_epoch:  оставить local
    # равные эпохи = настоящая параллельная попытка захвата
    if remote.hlc < local.hlc:                  взять remote     # раньше начал, тот и владелец
    if remote.hlc > local.hlc:                  оставить local
    иначе взять по min(site_id)                                  # детерминированный тайбрейк
    # проигравшему создаётся узел kind='message', acl='agent', чтобы он узнал при синхронизации
```

Эпоха монотонно растёт при каждом успешном захвате, поэтому длинный офлайн-период
не даёт преимущества: пока агент был офлайн, эпоха на сервере ушла вперёд.

### 9.5 Протокол синхронизации

Pull-push поверх HTTP, инициатор — клиент. Сервер (Postgres) — хаб, но не источник
истины: он такой же сайт.

```
POST /v1/sync
  request : { site_id, scopes: [...], have: { <peer_site>: <last_hlc_seen>, ... },
              ops: [ ...локальные операции, не подтверждённые сервером, <= 1000... ] }
  response: { accepted: [op_id...], ops: [ ...операции пиров, которых у нас нет, <= 1000... ],
              watermarks: { <site>: <hlc> }, more: bool }
```

* `have` — **разреженный вектор высоких вод по сайтам**, не векторные часы: он
  используется только для «что мне ещё прислать», а не для упорядочивания.
* Пакет не больше **1000** операций и **4 МБ**; при `more: true` клиент повторяет.
* Клиент применяет пришедшее (§9.3), потом обновляет `sync_state`.
* Периодичность: `myc sync` вручную; фоновым `jobs(kind='sync')` каждые
  **60 000 мс** при наличии `remote` в конфиге; принудительно после `close`/`claim`
  задачи (важные события — с задержкой не более 2 с).
* **Сеть никогда не в горячем пути**: `prime`, `ready`, `show`, `search` читают
  локальную БД и не ждут синхронизации. `myc ready` показывает возраст последней
  синхронизации, если он больше 600 с.

**Без сервера, машина-машина:** `myc sync --export ops.jsonl --since <hlc>` и
`myc sync --import ops.jsonl` — тот же формат операций, перенос любым способом
(git, scp, флешка). Идемпотентно по `op_id`.

**Компактирование оплога:** запись удаляется, если `ts_ms < now - 30*86400*1000`
**и** её `hlc` ниже `min(last_seq_sent)` по всем записям `sync_state`. Состояние при
этом не теряется — оно уже в `nodes`/`edges` вместе с `field_clock`. Сайт, который
проспал больше 30 суток, получает не операции, а **снапшот**
(`GET /v1/snapshot?scope=`), после чего продолжает инкрементально.

### 9.6 JSONL-экспорт для git

```
.myc/
  graph/
    nodes-0.jsonl ... nodes-z.jsonl     # 32 корзины по первому символу body ID
    edges-0.jsonl ... edges-z.jsonl
    anchors.jsonl
  meta.json                             # schema_version, id_prefix, embed_model, exported_at
```

* Одна строка — один узел/ребро. Ключи в **фиксированном алфавитном порядке**,
  числа без экспоненты, строки в NFC, переводы строк внутри тел экранируются.
* Строки внутри файла отсортированы по `id` (для рёбер — по `src,type,dst`),
  поэтому git-дифф показывает ровно изменённые сущности.
* **Не экспортируются:** эмбеддинги (бинарь, шумит в диффе, восстанавливается
  `myc reembed`), FTS-индекс, `parent_closure`, `jobs`, `repo_root`, `bodies_cold`
  (по умолчанию; `--with-bodies` включает как base64+zstd).
* **Экспортируются** `field_clock` и `counters` — в тех же строках, в поле `_clk`.
  Без них мерж деградировал бы до «победил тот, кто позже сделал `git merge`».

Формат строки узла:

```json
{"_clk":{"body":[1727352841001,"s1"],"status":[1727352999002,"s2"]},
 "acl":"team","attrs":{"tags":["db","sqlite"]},"body":"...","confidence":1,
 "content_hash":"9f2c...","created_at":1727352000000,"hlc":1727352999002,
 "id":"myc-a3f8k2mq7xz1","kind":"note","layer":1,"site_id":"s2","status":"active",
 "title":"...","updated_at":1727352999002}
```

**Мерж-драйвер git.** `.gitattributes`:

```
.myc/graph/*.jsonl merge=myc
```

```
git config merge.myc.name "myc graph merge"
git config merge.myc.driver "myc merge-driver %O %A %B %L %P"
```

Драйвер не пытается мержить текст: он парсит три версии, строит операции из
разностей относительно базы `%O` и применяет их правилами §9.1 (per-field LWW по
`_clk`, add-wins для рёбер). Результат детерминирован независимо от того, на какой
машине выполняется мерж. Код выхода всегда 0 — текстовых конфликтов не бывает;
семантические конфликты (`contradicts`, циклы) записываются в граф и попадают
в `myc doctor`.

Импорт: `myc import .myc/graph` идемпотентен, применяет только те строки, чьи
`_clk` новее локальных. Хук `post-merge`/`post-checkout` может звать
`myc import --quiet` автоматически (`myc init --git-hooks`, по умолчанию выключено).

## 10. ACL

### 10.1 Модель

| Уровень | Кто видит | Поля-носители |
|---|---|---|
| `private` | только `owner_id` | `owner_id` |
| `team` | все принципалы с членством в `team_id` | `team_id` |
| `restricted` | только перечисленные в `acl_grants` плюс владелец | `acl_grants` |
| `agent` | только агент `agent_id` **и** владелец сессии, в которой агент работал | `agent_id`, `owner_id` |

Принципал вызова: `Principal { user_id, team_ids: string[], agent_id?, is_local_owner }`.
Определяется в CLI из конфига, в MCP — из сессии, в HTTP — из токена.

Правила распространения:

* Узел, созданный дистилляцией, наследует **самый строгий** ACL среди источников
  (`private` > `agent` > `restricted` > `team`). Иначе L2-сценарий утёк бы приватные факты.
* Фрагмент наследует ACL документа (по ребру `parent`).
* Якорь всегда `team` — он не содержит контента, только координаты; но входящее
  ребро `touches` видно только тем, кому видим его источник.
* Изменение ACL узла — обычное LWW-поле; ужесточение и ослабление равноправны,
  побеждает более позднее. `myc doctor --acl` показывает узлы, у которых ACL
  строже, чем у их L2-потомка: это ошибка распространения.

### 10.2 Фильтрация ДО ранжирования

Предикат компилируется один раз на принципала и подставляется в `{{ACL}}`:

```ts
// src/db/acl.ts
export function compileAcl(p: Principal, alias = 'n'): { sql: string; params: unknown[] } {
  if (!aclEnforced) return { sql: '1=1', params: [] };            // локальный одиночный режим
  const t = p.team_ids;                                            // на практике не больше 8
  return {
    sql: `(
        (${alias}.acl = 'team'       AND ${alias}.team_id  IN (${ph(t.length)}))
     OR (${alias}.acl = 'private'    AND ${alias}.owner_id = ?)
     OR (${alias}.acl = 'agent'      AND (${alias}.agent_id = ? OR ${alias}.owner_id = ?))
     OR (${alias}.acl = 'restricted' AND (
            ${alias}.owner_id = ?
         OR EXISTS (SELECT 1 FROM acl_grants g
                     WHERE g.node_id = ${alias}.id AND g.principal IN (${ph(1 + t.length)}))))
    )`,
    params: [...t, p.user_id, p.agent_id ?? ' ', p.user_id, p.user_id,
             `user:${p.user_id}`, ...t.map(x => `team:${x}`)],
  };
}
```

Ключ кэша стейтмента: `queryId + '|' + aclKey`, где
`aclKey = blake3(user_id + '|' + sorted(team_ids) + '|' + agent_id)[0..8]`.

**Почему до ранжирования, а не после.** При post-filter из top-50 могло уцелеть 3
результата — выдача обеднена не по релевантности, а по случайности. Пре-фильтр
даёт полные top-k среди видимого. Это прямое требование §4 брифа (TencentDB).

### 10.3 Как ACL ложится на индексы

* Три частичных индекса (`ix_nodes_acl_team` / `_own` / `_agent`) делают каждую
  ветку OR индексируемой. SQLite умеет OR-оптимизацию через слияние индексов, но
  выбирает её не всегда — поэтому в горячем `search_fts` предикат применяется
  **после** FTS (FTS уже сузил выдачу до сотен строк), а в `prime`/`ready`/`list` —
  как ведущий предикат по частичному индексу.
* `restricted` через `EXISTS` по `ix_acl_principal` — точечный lookup на кандидата.
  Ограничение: доля `restricted`-узлов должна быть мала (менее 5 %), иначе `EXISTS`
  начинает доминировать. Отслеживается в `myc doctor` (предупреждение при 5 % и выше).
* В **локальном режиме** (`myc_meta.acl_enforced = 0` — значение по умолчанию для
  embedded SQLite) `compileAcl` возвращает `1=1`, и оптимизатор выбрасывает условие
  целиком: ACL не стоит ничего. Флаг включается автоматически при `myc init --team`
  или при работе против сервера.

### 10.4 ACL и векторный поиск

Векторный индекс (линейный скан vec0 и HNSW) не умеет произвольного пре-фильтра:

```
vec_search(q, k, principal):
    k_prime = max(64, 4*k)                # SQLite; для pgvector max(64, 2*k) + iterative scan
    for round in 1..3:
        cand = vec_topk(q, k_prime, partition=(scope, layer_range))   # partition key = честный пре-фильтр
        vis  = filter_by_acl_sql(cand)    # один IN-запрос по PK, предикат тот же
        if len(vis) >= k or len(cand) < k_prime: return vis[:k]
        k_prime *= 4
    mark_degraded('acl.vec_recall', 'over-fetch исчерпан'); return vis[:k]
```

`scope` и `layer` вынесены в **partition key** vec0 именно потому, что это
единственные фильтры, которые векторный индекс применяет честно до поиска;
остальное — over-fetch. В pgvector та же роль у `hnsw.iterative_scan = relaxed_order`
(доступен с 0.8), который делает это внутри движка.

**Утечки через рёбра закрыты явно:**

* Обход рёбер применяет ACL к **обоим** концам.
* `open_blockers` считает и невидимые блокеры — иначе отсутствие блокера было бы
  утечкой факта существования узла. В выдаче: «2 блокера, 1 не виден вам».
* `parent_closure` при обходе фильтруется; невидимый предок обрывает путь,
  дотовый путь тогда показывается от ближайшего видимого предка.
* FTS-сниппеты строятся **только** по прошедшим фильтр строкам.

### 12.1 Разложение по операциям

| Операция | Бюджет §3 | Разложение | Что в фоне |
|---|---|---|---|
| Холодный старт процесса | < 60 мс | Bun-рантайм ~18 мс + загрузка бинаря ~10 мс + `open()` + PRAGMA ~2 мс + загрузка `sqlite-vec` ~4 мс (ленивая: только если запрос векторный) + разбор конфига ~1 мс + компиляция ACL ~0.05 мс | загрузка ONNX-модели эмбеддера (~120 мс) — **только в воркере**, CLI её не трогает |

| `myc show` / `get` | p99 < 3 мс | 1 lookup по PK ~0.02 мс (или range-scan по префиксу ~0.05 мс) + рёбра по `ix_edges_dst`/`ix_edges_type` ~0.1 мс + `bodies_cold` при необходимости ~0.3 мс | `accessed_at` обновляется **отложенно**, батчем раз в 1 000 мс, чтобы не плодить write-транзакции |
| `myc ready` | не задан явно, целимся < 3 мс | 1 скан `ix_nodes_ready`, LIMIT 20, без рекурсии — благодаря `open_blockers` | пересчёт `open_blockers` — в триггерах, амортизированно 30 мкс на запись |
| `myc create` / `remember` | p99 < 5 мс | `BEGIN IMMEDIATE` ~0.1 мс + blake3 ~0.02 мс + `INSERT nodes` ~0.15 мс + FTS-триггер ~0.04 мс + 1–3 `INSERT edges` ~0.1 мс + 2 `INSERT jobs` ~0.06 мс + `COMMIT` (WAL, `synchronous=NORMAL`) ~0.3 мс. | `myc claim` | не задан, целимся < 3 мс | 1 CAS-`UPDATE` + `COMMIT` ~0.5 мс | оплог-запись — в той же транзакции (она дешёвая), синхронизация — в фоне |

### 12.2 Правила, которые держат бюджет

1. **Ни одной сетевой операции** в `prime`, `show`, `get`, `search`, `ready`, `create`,
   `claim`. Проверяется тестом: горячие команды исполняются с замоканным `fetch`,
   который бросает исключение.
2. **Ни одного вызова graft** в горячем пути (§7.4). Тот же приём с моком.
3. **Ни одного `json_extract` в предикате скана.** Всё, что фильтруется, — реальная
   или generated-колонка с индексом. Проверяется `EXPLAIN`-тестами (§8.4).
4. **Ни одной write-транзакции на чтение.** `accessed_at` копится в памяти процесса
   и сбрасывается батчем раз в 1 000 мс или при выходе.
5. **Векторный индекс не обновляется синхронно.** `nodes_vec` пишет только воркер.
6. **Все тяжёлые работы — через `jobs`** с арендой и чекпойнтами: падение воркера
   не теряет работу и не блокирует CLI.
7. **Партиционирование `nodes_vec` по `(scope, layer)`** — единственное, что делает
   линейный скан sqlite-vec совместимым с бюджетом 25 мс на 100k узлов.
8. **Ленивая загрузка расширений.** `sqlite-vec` подгружается только когда запрос
   реально векторный; `myc show` его не грузит.

### 12.3 Где именно тратится латентность и что с этим делать при росте

| Место | При 100k | При 1M | Действие |
|---|---|---|---|
| Линейный скан vec0 | ~8 мс на партицию 20k | ~80 мс — **бюджет пробит** | переход на партиции по `(scope, layer, kind)`; при 1M+ — вынос вектора в PG/HNSW либо int8-квантизация (в 4 раза меньше данных) |
| FTS5 | 1.5 мс | ~4 мс | ок |
| `ix_nodes_ready` | 0.3 мс | 1.2 мс | ок (частичный индекс растёт только с числом открытых задач) |
| `parent_closure` | ~3× числа рёбер | то же | ок; глубина ограничена 32 |
| Размер БД | ~180 МБ с векторами | ~1.8 ГБ | `prune` + int8-квантизация векторов (384×4 → 384×1 байт) |
| Оплог | ~30 МБ/мес на активную команду | — | компактирование 30 суток + снапшоты |

## 13. Риски и что ломается на масштабе

| # | Риск | Когда проявится | Митигация |
|---|---|---|---|
| 1 | **sqlite-vec линейный.** На 1M узлов в одном scope векторный поиск выходит за 25 мс | 1M узлов или один гигантский scope | Партиционирование по `(scope, layer)` уже в схеме; int8-квантизация; порог в `myc doctor` («партиция > 50k векторов»); последний рубеж — Postgres+HNSW, схема к этому готова |
| 2 | **Один писатель в SQLite.** 10 агентов × запись каждые 100 мс = 100 tx/с; при среднем 0.8 мс на транзакцию потолок ~1200 tx/с, но `busy_timeout` 5 с маскирует деградацию | 20+ параллельных агентов на одной БД | Все write-транзакции короткие by design; метрика `write_wait_ms` в `myc doctor`; при устойчивом ожидании > 50 мс — рекомендация переехать на Postgres. Никаких длинных транзакций в коде (линтер: нет `await` внутри `tx()`) |
| 3 | **Триггеры `open_blockers` расходятся с реальностью** при прямых правках БД или багах | редко, но тихо | `myc doctor --recount` пересчитывает; сверка запускается автоматически раз в сутки на 1 % узлов; расхождение — `degraded` в health |
| 4 | **LWW теряет правку.** Два агента одновременно переписали `body` — одна версия исчезает | часто при активной команде | Предыдущее значение всегда есть в оплоге; `myc show --clk <id>` показывает, чья правка проиграла и когда; для `body` при конкурентной правке в течение 60 с создаётся `contradicts`-узел вместо тихой потери |
| 5 | **Дотовые пути нестабильны** при перевешивании родителя — агент, запомнивший `myc-a3f8.1.2`, промахнётся | при реорганизации задач | Дотовый путь — только для отображения; во всех машинных интерфейсах (MCP, HTTP, JSONL) отдаётся канонический ID. CLI при промахе печатает «путь изменился, каноничный ID: …» |
| 6 | **Дистилляция генерирует мусор** без LLM и засоряет L2 | у пользователей без ключа | Шаблонные сценарии помечены `summary_kind='template'`, ранжируются ниже, не продвигаются в L3 (промоушен требует `confidence >= 0.9` или `evidence`), и видны в `myc status` |
| 7 | **Якоря массово «протухают»** после большого рефакторинга или смены ветки | ежедневно | Три уровня проверки, из них два дешёвых; фон, батч 256; `state='stale'` не удаляет знание, а понижает вес. `myc anchor check --repo` после мержа предлагается в `post-merge` хуке |
| 8 | **`restricted` через `EXISTS`** становится доминирующим при высокой доле таких узлов | команда с параноидальными настройками | Предупреждение при 5 %; план B — денормализовать в битовую маску `acl_bits` и покрывающий индекс (миграция готова к добавлению, схема не мешает) |
| 9 | **Расхождение диалектов.** SQL, работающий в SQLite, тихо иначе ведёт себя в PG (NULL-сортировка, деление целых, сравнение строк) | при переезде команды на сервер | Один поведенческий сьют (~120 кейсов) против обоих драйверов в CI + `EXPLAIN`-тесты на 8 горячих запросах |
| 10 | **Оплог растёт быстрее компактирования**, если один пир «пропал» (его `last_seq_sent` не двигается) | ноутбук в отпуске | Пир считается мёртвым после 90 суток без синхронизации и исключается из условия компактирования; при возвращении получает снапшот |
| 11 | **Коллизия ID при импорте** — редкая, но её обработка переписывает рёбра | 4.3·10⁻⁵ на 10⁷ узлов | Детерминированная процедура (§3.4), отчёт в `myc doctor`, тест с искусственно укороченным ID (4 символа) гоняет этот путь регулярно |
| 12 | **Уникальный индекс `ux_nodes_content`** мешает легитимным повторам (два одинаковых `TODO: fix` в разных файлах) | часто у задач | Индекс по `(scope, kind, content_hash)`, а `content_hash` для `task` считается по `title + body + attrs.anchor_ref`; для `message` уникальность отключается (в `content_hash` подмешивается `id` сессии и `ord`) |
| 13 | **`purge` не догоняет пира**, который был офлайн и вернулся со старым состоянием | при удалении по требованию | Тумбстоун `purge` живёт в оплоге 365 суток (дольше обычного компактирования) и переигрывается при возврате |
| 14 | **Рост `parent_closure`** при широких деревьях (эпик на 5 000 задач) | крупный проект | Глубина 32; вставка ребра ограничена 5 000 строк за раз, иначе задание уходит в `jobs`; альтернатива (рекурсивный CTE) остаётся рабочей и включается флагом |

| # | Вопрос | Чей лейн пересекает | Моё предположение (по нему и спроектировано) |
|---|---|---|---|
| 1 | Размерность и модель эмбеддинга | **L2** | 384 (bge-small / MiniLM-класс), cosine. Схема хранит `embed_dim` в `myc_meta`; при другом числе меняется одна строка DDL, но `reembed` обязателен |
