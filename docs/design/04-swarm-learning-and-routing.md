# L4 — Самообучение роя и роутинг моделей

> Лейн L4 проекта myc. Подсистема без аналогов в источниках (§5 брифа), поэтому
> здесь всё спроектировано «от скептика»: каждый механизм сопровождён тем, как
> он может соврать, и как мы это ловим. Остальные лейны: L1 — ядро данных,
> L2 — ретривал, L3 — поверхности. Пересечения вынесены в §5 «Открытые вопросы».

**Что делает подсистема.** Каждая попытка выполнить задачу агентом порождает
телеметрию: отпечаток задачи, модель, усилия, стоимость, время, исход, сигналы
верификации. Из телеметрии выводятся апостериорные оценки «модель × класс
задачи», а `myc route` по ним рекомендует, кому отдать следующую задачу,
оптимизируя Парето-компромисс качество / цена / латентность.

**Чего она не делает.** Не запускает агентов, не выбирает модель принудительно
(рекомендация, которую оркестратор волен проигнорировать), не пишет контент
задач и диффов в общий пул, не обучает нейросети: вся «модель обучения» — это
байесовские счётчики с явными формулами, которые можно пересчитать руками.

## 1. Решения

| Вопрос | Выбор | Почему | Что отвергли |
|---|---|---|---|
| Единица обучения | «Рука» бандита = `(model_id, effort) × task_class` | Достаточно грубая, чтобы набирать статистику; достаточно тонкая, чтобы отличать «Haiku на доках» от «Haiku на миграциях» | Рука = модель без класса (теряет главное: специализацию), рука = модель × полный отпечаток (никогда не наберёт выборку) |
| Таксономия классов | Закрытый детерминированный enum из 2 осей `intent × scope` (7 × 4 = 28 классов) + локальный открытый кластер по эмбеддингу как **признак похожести**, не как ключ приоров | Общие приоры команды требуют стабильного ключа; кластеры по эмбеддингам нестабильны между репозиториями и версиями модели эмбеддингов | Ручные ярлыки (не масштабируется, каждый лепит своё); LLM-классификатор (сеть в горячем пути, $, недетерминизм); только кластеры (несовместимы между командами) |
| Признаки отпечатка | Только то, что считается без LLM за < 5 мс из текста задачи, якорей и графа graft | Бюджет `route` p99 < 10 мс, сеть в горячем пути запрещена | Признаки от LLM («оцени сложность 1–10»): дорого, нестабильно, самореференция (модель оценивает задачу для себя) |
| Модель качества | Бета-распределение на «вероятность приемлемого исхода», обновление дробным весом `q ∈ [0,1]` | Замкнутая форма, пересчитывается из сырых данных за миллисекунды, объяснима пользователю | Логистическая регрессия по признакам (нужны тысячи примеров, не объяснима, дрейфует); GP-бандиты (тяжело) |
| Модель стоимости и латентности | Точечные оценки со сжатием к приору (shrinkage), не сэмплируем | Стоимость и время почти детерминированы при известной модели и размере; их дисперсия не то, что стоит исследовать | Полный байес по стоимости (усложняет без выгоды) |
| Политика | Томпсон-семплинг по качеству + детерминированная функция полезности + принудительное исследование с полом 5 % и потолком 15 % | TS даёт естественное исследование пропорционально неопределённости; пол защищает от «петли невыбора»; потолок ограничивает счёт за исследование | ε-greedy (исследует бессмысленно и равномерно), UCB (детерминирован, при общем пуле все клиенты синхронно бьют в одну руку) |
| Иерархия приоров | 3 уровня: global (зашитый в бинарь) → team (сервер) → local (репозиторий), сжатие по псевдо-счётчикам `κ` | Холодный старт с нуля данных; малые репозитории опираются на команду; большие — на себя | Один общий пул (одна шумная репа отравляет всех); только локальный опыт (первые 100 задач вслепую) |
| Синхронизация с сервером | Клиент отправляет **достаточные статистики** по рукам (суммы весов), не попытки; сервер отдаёт снимок приоров; всё в фоне, не чаще 1 раза в час | Приватность по построению, дешёвый протокол, никакой сети в горячем пути | Отправка сырых попыток (утечка метаданных о репе; больше данных, чем нужно) |
| Отложенные сигналы | Сигналы — отдельная append-only таблица; апостериор — **материализация**, пересчитываемая из сигналов целиком в фоне | Реверт через неделю просто добавляет строку, пересчёт всё учтёт; никаких «отменить прошлое обновление» | Инкрементальные апдейты с компенсацией (ошибки накапливаются, невозможно аудировать) |
| Атрибуция «модель vs постановка» | Три механизма: код причины провала от агента; множественные попытки одной задачи; признак качества спецификации в отпечатке. Спорные исходы получают вес 0.25, а не 0 | Полное исключение спорных исходов создаёт дыру: плохо поставленные задачи — тоже реальность, на которой модели различаются | Игнорировать проблему (шум идёт в приоры); LLM-судья постановки (сеть, $) |
| Оценка эффекта | Логируем пропенсити каждого решения; офлайн IPS/SNIPS + DR; онлайн — 10 % контроль | Без пропенсити никакая офлайн-оценка нечестна; без контроля никакая онлайн-оценка нечестна | «Смотрим, что стало дешевле» (confounding: роутер сам решает, кому какие задачи) |
| Приватность | В общий пул — только enum-признаки, бакеты, солёные хеши, суммы. Список запрещённого — явный, проверяется схемой на сервере | Метаданных достаточно для бандита; контент не нужен математике | Opt-in отправка контента «для лучшей точности» (не нужен, и один включивший ломает обещание команде) |
| Дрейф версий моделей | Рука привязана к `model_id` с версией; новая версия наследует апостериор родителя с половинным весом + экспоненциальное забывание с периодом полураспада 60 дней + CUSUM-детектор смены режима | Приоры протухают тихо; нужен и мягкий перенос, и громкий детектор | Сброс в ноль при новой версии (холодный старт заново), игнорирование версии (старые данные врут) |

## 2. Спецификация

### 2.1 Отпечаток задачи (task fingerprint)

#### 2.1.1 Принцип отбора признаков

Признак попадает в отпечаток, если выполняются все три условия:

1. **Дёшев**: вычисляется из уже имеющихся в myc данных (текст задачи, якоря,
   граф graft, git) без сети и без LLM, суммарно за < 5 мс при тёплом кэше.
2. **Предсказывает**: правдоподобно влияет на то, какая модель справится
   (размер и связность изменения, наличие проверки, язык).
3. **Стабилен между командами**: значение имеет один смысл в любом репозитории,
   иначе признак нельзя класть в ключ общих приоров.

Признаки делятся на **ключевые** (входят в `task_class`, ключ приоров) и
**контекстные** (входят в отпечаток, используются для похожести, поправок
стоимости и отчётов, но не дробят статистику).

#### 2.1.2 Схема отпечатка

```ts
type Intent =
  | "fix"        // исправление дефекта
  | "feature"    // новое поведение
  | "refactor"   // изменение структуры без изменения поведения
  | "test"       // только тесты
  | "docs"       // только документация/комментарии
  | "config"     // конфиги, CI, зависимости, инфраструктура
  | "investigate"; // анализ/ответ на вопрос, без ожидаемого диффа

type Scope =
  | "local"      // 1 файл, blast radius ≤ 3 символа
  | "module"     // 2–5 файлов в одном каталоге верхнего уровня
  | "cross"      // > 5 файлов или ≥ 2 каталогов верхнего уровня
  | "unknown";   // якорей нет, оценить нельзя

type TaskClass = `${Intent}:${Scope}`; // 28 значений, ключ приоров

type SizeBucket = "xs" | "s" | "m" | "l" | "xl";
// ожидаемые строки диффа: xs ≤ 10, s ≤ 50, m ≤ 200, l ≤ 800, xl > 800

type DepthBucket = "d0" | "d1" | "d2" | "d3";
// суммарный fan-in якорных символов по graft callers --depth 1:
// d0 = 0, d1 ≤ 5, d2 ≤ 20, d3 > 20

type CtxBucket = "c0" | "c1" | "c2" | "c3";
// оценка контекста, который агенту придётся прочитать (токены):
// c0 ≤ 4k, c1 ≤ 16k, c2 ≤ 64k, c3 > 64k

interface TaskFingerprint {
  fp_version: 1;
  // --- ключевые (входят в класс) ---
  intent: Intent;
  scope: Scope;
  // --- контекстные ---
  size: SizeBucket;
  depth: DepthBucket;
  ctx: CtxBucket;
  langs: string[];        // до 3 языков по расширениям якорных файлов, ISO-подобные коды: "ts","py","go","rs","java","kt","swift","sql","md","yaml","other"
  has_tests: boolean;     // для якорных путей существует тестовый файл-сосед
  has_criteria: boolean;  // в описании есть чек-лист/критерии приёмки/ожидаемый результат
  new_files: boolean;     // задача подразумевает новые файлы (нет якорей, но есть intent feature/config)
  spec_len: "sl0"|"sl1"|"sl2"; // длина описания в словах: ≤ 20 / ≤ 120 / > 120
  blockers_closed: number; // сколько блокеров было закрыто до ready (0..N, обрезаем на 5)
  prior_attempts: number;  // сколько попыток по этой задаче уже было (0..N, обрезаем на 5)
  domain_hash: string;     // salted hash каталога верхнего уровня самого «тяжёлого» якоря, 8 hex
  repo_hash: string;       // salted hash remote URL, 8 hex
  cluster_id: number | null; // локальный кластер по эмбеддингу текста, см. 2.1.5
}
```

Ключ приоров `arm_key = (model_id, effort, task_class)`. Остальные признаки
не дробят руки: 28 классов × ~6 моделей × 3 уровня усилий = ~500 рук, каждая
из которых имеет шанс набрать хотя бы 10 наблюдений в активной команде за месяц.
Если добавить `size` в ключ, рук станет 2500 и большинство навсегда останутся пустыми.

Вместо дробления ключа `size`, `depth`, `ctx` входят в **поправку стоимости и
латентности** (2.4.3) и в **похожесть** (2.1.5): они хорошо предсказывают
цену и время, но плохо — специализацию модели.

#### 2.1.3 Вычисление intent без ручных ярлыков

Три источника, в порядке убывания приоритета; первый, давший ответ, побеждает:

1. **Тип задачи и явное поле.** Если у задачи (L1) `type = bug` → `fix`.
   Если задача создана с явным `intent` (оркестратор знает, что делает) —
   берём его. Это не «ручной ярлык»: поле необязательное и обычно пустое.
2. **Лексикон глаголов** по заголовку (не описанию: описание шумное).
   Лексикон — таблица из ~180 основ на английском и русском, зашитая в бинарь,
   версионируется `fp_version`. Стемминг: обрезка до 5 символов после
   приведения к нижнему регистру, достаточно для обоих языков.
   Примеры: `fix, bug, crash, broken, regress, исправ, почин, падает, ошибк` →
   `fix`; `add, implement, support, feature, добав, реализ, сдела` → `feature`;
   `refactor, extract, rename, cleanup, simplify, рефакт, вынес, переимен, упрост` →
   `refactor`; `test, spec, coverage, тест, покры` → `test`; `doc, readme,
   comment, докум, описан` → `docs`; `ci, deps, bump, upgrade, config, docker,
   зависим, обнов, конфиг` → `config`; `investigate, why, analyze, explain,
   разобр, почему, выясн, объясн` → `investigate`.
   При конфликте нескольких совпадений — приоритет `fix > config > test > docs > refactor > feature > investigate`
   (дефект важнее всего; `feature` — «остаточный» класс).
3. **Форма ожидаемого изменения по якорям.** Все якоря указывают на тестовые
   файлы → `test`; на `*.md` → `docs`; на конфиги (`*.yaml, *.toml, *.json,
   Dockerfile, *.lock`) → `config`. Иначе `feature`.

Стабильность таксономии обеспечивается не точностью классификатора (она
~80 % на глаз и этого достаточно), а тем, что классификатор **детерминирован,
версионирован и одинаков у всех**. Ошибка классификации — это шум,
одинаковый для всех моделей, он не смещает сравнение моделей между собой.

**Пост-фактум коррекция.** По завершении попытки известна реальная форма
диффа. ~~Мы **не** переписываем `task_class` попытки (ключ должен быть тем, что
видел роутер в момент решения, иначе офлайн-оценка врёт), но пишем
`actual_class` в `outcome`.~~ **Пересмотрено решением S67 (ARCHITECTURE.md
§10):** ключ `task_class` на финише становится классом по ФАКТУ (файлы,
изменившиеся за попытку; без факта — якоря, иначе `unknown`), а то, что
видел роутер (якоря, иначе пути, названные в тексте задачи), хранится в
`swarm_attempt.predicted_class` и не переписывается никогда; источник scope
ключа — в `swarm_attempt.scope_source` (`touched` / `anchors` / `none`).
Матрица ошибок `predicted × actual` для `myc report models --fingerprint`
считается по этой паре колонок; если для intent ошибка > 35 % на 200+
попытках, это сигнал править лексикон в следующем `fp_version`.

#### 2.1.4 Вычисление scope, depth, ctx, size

```
function computeStructural(task, anchors, graft):
  if anchors.length == 0:
    return { scope: "unknown", depth: "d0", ctx: ctxFromText(task), size: sizeFromText(task) }

  files = distinct(anchors.map(a => a.path))
  topdirs = distinct(files.map(firstPathSegment))
  fanIn = 0
  for a in anchors[0:8]:                 // не больше 8 запросов к графу
    r = graft.callers(a.symbol, depth=1, timeout_ms=2)   // адаптер L1/L2
    if r == TIMEOUT: fanIn = null; break
    fanIn += r.count
  scope =
    files.length == 1 and (fanIn ?? 0) <= 3      -> "local"
    files.length <= 5 and topdirs.length == 1     -> "module"
    else                                          -> "cross"
  depth = bucket(fanIn, [0, 5, 20])               // null -> "d0" + флаг graft_timeout в attempt
  ctxTokens = sum(anchors.map(a => a.span_lines)) * 12 + task.description_words * 1.3 + 2000
  ctx = bucket(ctxTokens, [4000, 16000, 64000])
  size = sizeFromText(task) ?? bucket(sum(span_lines), [10, 50, 200, 800])
```

`sizeFromText`: если в описании есть явные подсказки («one-liner», «small»,
«large refactor», «в одну строку», «крупный») — берём их; иначе `null`.
Множитель 12 токенов на строку — эмпирическая константа для кода, 1.3 — для
прозы, 2000 — постоянные накладные (prime, системный промпт).

`has_tests`: для каждого якорного пути ищем в том же каталоге или в
`__tests__/`, `test/`, `tests/`, `spec/` файл с тем же базовым именем и
суффиксом `.test.*`, `.spec.*`, `_test.*`, `test_*`. Проверка — `stat` до 6
кандидатов на файл, кэшируется в L1 по `blob_hash` каталога.

`has_criteria`: регулярка по описанию на `- [ ]`, `acceptance`, `expected`,
`should`, `ожида`, `критер`, `должн`. `true` при ≥ 1 совпадении.

`domain_hash`: `hex(blake3(team_salt || topdir))[0:8]`, где `topdir` — каталог
верхнего уровня якоря с наибольшим span. Соль командная (2.8), так что домены
разных команд несравнимы — и не должны быть.

#### 2.1.5 Похожесть двух задач

Нужна для трёх вещей: (a) `myc route --explain` показывает «похожие прошлые
задачи и чем кончились»; (b) при малой выборке в руке подтягиваем опыт из
**соседних** классов (2.5.3); (c) локальный кластер `cluster_id` — грубый
детектор «мы такое уже делали».

```
sim(a, b) =
    0.35 * [a.intent == b.intent]
  + 0.15 * [a.scope  == b.scope]
  + 0.10 * (1 - |ord(a.size)  - ord(b.size)|  / 4)
  + 0.05 * (1 - |ord(a.depth) - ord(b.depth)| / 3)
  + 0.10 * jaccard(a.langs, b.langs)
  + 0.05 * [a.domain_hash == b.domain_hash]
  + 0.20 * cos(emb(a.title), emb(b.title))        // локальный ONNX-эмбеддинг из L2; если нет — слагаемое = 0.10 (нейтрально)
```

Сумма весов = 1.0. Порог «похожие» = 0.65. `cos` берётся из того же
эмбеддинга заголовка, который L2 уже считает для поиска (асинхронно, при
создании задачи); в горячем пути `route` эмбеддинг **не считаем**: если он ещё
не готов, слагаемое заменяется нейтральным 0.10.

`cluster_id`: онлайн k-means по эмбеддингам заголовков закрытых задач,
`k = clamp(round(sqrt(N / 2)), 4, 64)`, пересчёт в фоне раз в сутки. Кластеры
локальны, в общий пул не уходят, в ключ приоров не входят.

**Соседние классы** для сжатия статистики: `neighbors(intent:scope)` =
тот же intent с соседним scope (`local↔module↔cross`) с весом 0.5, и
`unknown` — сосед всех с весом 0.25.

### 2.2 Схема телеметрии

Хранилище — те же SQLite/Postgres, что и у L1, отдельная группа таблиц с
префиксом `swarm_`. DDL приведён в диалекте SQLite; для Postgres отличия:
`TEXT` → `TEXT`, `INTEGER` время → `BIGINT`, `REAL` → `DOUBLE PRECISION`,
JSON-колонки → `JSONB`, `WITHOUT ROWID` опускается.

```sql
-- Справочник моделей и цен. Цены версионируются датой: попытка считается
-- по строке, действовавшей на attempt.started_at.
CREATE TABLE swarm_model (
  model_id        TEXT PRIMARY KEY,       -- "anthropic/claude-sonnet-5", "openai/gpt-5.4"; всегда с провайдером
  family          TEXT NOT NULL,          -- "claude-sonnet", "gpt" — для наследования приоров между версиями
  version         TEXT NOT NULL,          -- "5", "5.4", "20251001"
  parent_model_id TEXT,                   -- предыдущая версия семейства, для наследования апостериора
  tokens_per_sec  REAL NOT NULL DEFAULT 60, -- для оценки латентности при холодном старте
  active          INTEGER NOT NULL DEFAULT 1,
  created_at      INTEGER NOT NULL        -- unix ms
);

CREATE TABLE swarm_model_price (
  model_id        TEXT NOT NULL REFERENCES swarm_model(model_id),
  valid_from      INTEGER NOT NULL,       -- unix ms
  usd_per_m_in    REAL NOT NULL,          -- $ за 1M входных токенов
  usd_per_m_out   REAL NOT NULL,
  usd_per_m_cache_read  REAL NOT NULL DEFAULT 0,
  usd_per_m_cache_write REAL NOT NULL DEFAULT 0,
  PRIMARY KEY (model_id, valid_from)
);
```

#### 2.2.1 Что пишем когда

| Момент | Кто вызывает | Что пишется | Бюджет |
|---|---|---|---|
| `attempt start` | оркестратор / хук агента / сам агент через MCP | `swarm_attempt` со всеми полями, известными до работы: task, model, effort, fingerprint (пересчитывается здесь же, даже если был `route`, — задача могла измениться), `routed/route_id/propensity` (если `task_id` совпадает с последним `route_decision` не старше 10 минут), `attempt_no`, `parent_attempt` | p99 < 5 мс (запись) + < 5 мс (отпечаток) |
| по ходу | хук агента (Claude Code hooks / opencode plugin / Orca) | `swarm_attempt_event`: `tokens` каждые 30 с или каждые 10 тул-вызовов, `commit` при коммите, `test_run` при запуске тестов, `heartbeat` каждые 60 с | < 2 мс, батчами |
| `attempt finish` | тот же, кто стартовал | статус, `fail_reason`, итоговые токены, время, `diff_*` (считаем `git diff --numstat base..HEAD` сами, если не передали), `commit_shas`, `actual_class`; первые сигналы: `tests`, `lint`, `typecheck`, если агент их гонял | p99 < 5 мс; diff-статистика — в фоне, если > 3 мс |
| позже | git-хуки, CI-хук, сервер, `myc attempt rate`, фоновые сканеры | `swarm_signal` любого вида | фон |
| фон | `swarm.recompute` job | `swarm_outcome`, `swarm_arm` | не в горячем пути |

Попытка без `finish` дольше `attempt.timeout` (по умолчанию 4 ч, по
последнему heartbeat — 30 мин) переводится фоном в `abandoned`. `abandoned`
считается провалом с `attribution = 0.5` (мы не знаем, кто виноват).

#### 2.2.2 Связь попытки с задачей и коммитом

- **С задачей**: `attempt.task_id` + `attempt_no`; при `claim` (L1) оркестратор
  передаёт `attempt_id` в `claim`, чтобы L1 хранил `task.current_attempt`.
- **С коммитом**: два независимых пути, оба нужны.
  1. `attempt finish --commits sha1,sha2` — явный, от оркестратора.
  2. **Git-трейлер** `Myc-Attempt: att_xxx` и `Myc-Task: bd-a3f8.1`, который
     агент добавляет в сообщение коммита (L3 даёт шаблон в `prime`; хук
     `prepare-commit-msg` добавляет автоматически, если известна активная
     попытка). Трейлеры нужны для **отложенных** сигналов: `git log --grep`
     по `This reverts commit <sha>` находит реверты, `git blame` — строки
     нового бага, независимо от того, жив ли оркестратор.
- **С ветвлением**: если попытка шла в ветке, `merged` фиксируется, когда
  `sha` становится достижим из `main` (фоновый скан `git merge-base --is-ancestor`
  раз в 10 минут при активности репозитория, не чаще).

### 2.3 Сигналы исхода и атрибуция

#### 2.3.1 Каталог сигналов

| Сигнал | Откуда | Задержка | Вес `w` | Что означает |
|---|---|---|---|---|
| `tests` | finish / CI-хук | 0 – минуты | 0.6 если `has_tests`, иначе 0.3 (тесты написала та же модель — они подтверждают её же понимание) | доля прошедших |
| `lint`, `typecheck` | finish / CI | 0 | 0.15 каждый | чистота |
| `review_ai` | ревью-агент через MCP | минуты | 0.3 | другая модель одобрила |
| `review_human` | `myc attempt rate`, PR-хук | часы – дни | 0.8 | человек одобрил |
| `merged` | git-скан | часы – дни | 0.5 | приняли в main |
| `reverted` | git-скан | дни – недели | 1.0 | самый сильный негатив |
| `reopened` | L1 хук на смену статуса | дни | 0.7 | не сделано |
| `redone` | `attempt start` с тем же task_id после `succeeded` | часы – дни | 0.8 | переделали |
| `followup_bug` | L1: новая `bug`-задача с якорем в строки коммита попытки (по `blame`, окно 30 дней) | дни – недели | 0.5 | сломало что-то |
| `survived` | синтетический, фоном: `merged` и не `reverted` 14 дней | 14 дней | 0.4 | молчание как слабое согласие |
| `human_rating` | `myc attempt rate <id> <0..1>` | любая | 1.0 | явная оценка |
| `spec_defect` | L1: описание задачи существенно изменено (> 40 % слов) после провальной попытки; или `fail_reason = spec_unclear` подтверждён второй попыткой | дни | — | не сигнал качества, а флаг атрибуции |

Веса — константы `outcome_version = 1`, лежат в коде, не в БД, чтобы отчёт
всегда мог сказать, по какой формуле считался.

#### 2.3.2 Формула качества попытки

Позитивные и негативные сигналы агрегируются **не** средним: один реверт
перевешивает три зелёных прогона тестов. Используем «пессимистичное
взвешенное среднее» с доминированием сильных негативов:

```
signals S = {(kind_i, v_i, w_i)} для попытки, v_i ∈ [0,1]

// 1. Дедупликация: одного вида берём последний по времени (tests могут гоняться много раз)
// 2. Сильный негатив: если есть reverted | reopened | redone | human_rating < 0.3
//    -> q = min(0.15, weighted_mean), confidence = 1.0
// 3. Иначе:
W = Σ w_i
q_raw = Σ (w_i * v_i) / W
confidence = min(1, W / 1.5)        // 1.5 = «тесты + ревью человека» дают полную уверенность
q = q_raw

// 4. Провал по статусу без сигналов:
status ∈ {failed, timeout, abandoned} и S = ∅ -> q = 0.1, confidence = 0.5
// 5. Успех по статусу без сигналов:
status = succeeded и S = ∅ -> q = NULL, confidence = 0   (пока не придёт survived)
```

Зачем `q = 0.1`, а не 0: статус `failed` без сигналов — это ещё и самоотчёт
агента, а агенты склонны как преувеличивать, так и преуменьшать; полный ноль
оставляем для реверта с человеческой оценкой.

#### 2.3.3 Атрибуция: модель или постановка

`attribution ∈ [0,1]` — доля, с которой исход попытки идёт в статистику
**модели**. Остаток идёт в статистику задачи/постановщика (отчёт «какие
задачи проваливаются у всех»), а не в приоры рук.

```
attribution(attempt):
  a = 1.0
  // (a) агент сам сказал, что дело в постановке — верим наполовину
  if attempt.fail_reason == 'spec_unclear':   a = 0.5
  if attempt.fail_reason == 'env_blocked':    a = 0.25   // окружение: почти не вина модели
  if attempt.fail_reason == 'cancelled':      a = 0.0    // не наблюдение вовсе
  // (b) подтверждение другими попытками по той же задаче
  others = attempts(task_id) \ {attempt}, finished
  if others содержит ≥ 1 попытку ДРУГОЙ модели со статусом failed
     и attempt.status == failed:              a = min(a, 0.25)  // все падают -> задача
  if others содержит ≥ 1 попытку с q ≥ 0.7
     и attempt.status == failed:              a = 1.0           // кто-то смог -> модель
  // (c) флаг spec_defect
  if signals содержат spec_defect:            a = min(a, 0.25)
  // (d) переделка: успешную попытку, за которой последовала redone другой моделью,
  //     считаем провалом модели; ту, что переделала — успехом с обычной атрибуцией
  return a
```

Ключевое решение: атрибуция **никогда не обнуляет** наблюдение, кроме
`cancelled`. При `a = 0.25` наблюдение входит с четвертью веса: плохо
поставленные задачи — часть реальности, и модель, которая справляется с ними
чаще, объективно полезнее.

**Признак `spec_len`/`has_criteria`** в отпечатке используется в отчётах:
`myc report tasks --by spec` показывает успех по качеству спецификации, что
даёт команде обратную связь на постановку, отдельно от роутинга.

#### 2.3.4 Отложенные сигналы

Механика проста благодаря материализации: сигнал добавляется строкой,
`swarm.recompute` пересчитывает `outcome` затронутой попытки и все `arm`,
которых она касается. Что нужно, чтобы отложенные сигналы вообще возникали:

- **Скан реверта** (`swarm.scan_git`, фон, при активности репозитория не чаще
  раза в 10 минут, иначе при `prime`): для коммитов попыток за последние 45
  дней проверяем (1) `git log --since=<attempt.finished_at> --grep="This reverts commit <sha>"`,
  (2) исчезновение `sha` из `main` при `git rebase` — тогда ищем по трейлеру
  `Myc-Attempt` в новой истории; если трейлер найден в другом sha — переносим
  `commit_shas`, если нет нигде — `reverted` с `weight = 0.5` (могли сквошить).
- **Скан выживания**: попытки с `merged` и без `reverted` старше 14 дней получают
  `survived`. Один раз, идемпотентно.
- **Скан follow-up багов**: при создании задачи типа `bug` с якорями L1
  вызывает `swarm.blame(anchors)`: `git blame -L` на якорные строки, если
  коммит из `commit_shas` попытки не старше 30 дней — сигнал `followup_bug`.
  Бюджет: асинхронно, `git blame` на ≤ 8 якорей.
- **Переоткрытие**: хук L1 на переход `closed → open` пишет `reopened` для
  последней `succeeded` попытки.

Все сканы записывают `source` и `latency_ms`, чтобы отчёт показывал, сколько
сигналов «дозрело» и с какой задержкой — и, главное, чтобы оценка (2.11) могла
отбросить попытки моложе 14 дней, у которых отложенные сигналы ещё не пришли.

#### 2.3.5 Когда сигнала нет вовсе

Три уровня деградации, явно видимые в `myc report models`:

1. Попытка `succeeded`, ни одного сигнала, коммит есть: ждём `survived` (14
   дней). До тех пор `q = NULL`, в приоры не входит. В отчёте — «pending».
2. Попытка `succeeded`, коммитов нет (например, `investigate`): через 7 дней
   без `reopened`/`redone` — синтетический `survived` с `weight = 0.25`.
   Слабое «никто не пожаловался».
3. Репозиторий вообще без сигналов (нет тестов, нет хуков, нет ревью):
   доля попыток с `confidence < 0.3` > 70 % за 30 дней → статус подсистемы
   `degraded: no_verification_signals`, роутер продолжает работать на командных
   приорах, `myc route` печатает предупреждение, а `myc status` (L3) —
   жёлтый индикатор. Тихой деградации, как у memora, не будет.

### 2.4 Модель стоимости и функция полезности

#### 2.4.1 Прямая стоимость попытки

```
cost_usd(attempt) =
    tokens_in          * p.usd_per_m_in         / 1e6
  + tokens_out         * p.usd_per_m_out        / 1e6
  + tokens_cache_read  * p.usd_per_m_cache_read / 1e6
  + tokens_cache_write * p.usd_per_m_cache_write/ 1e6
где p = строка swarm_model_price с max(valid_from) ≤ attempt.started_at
```

Если рантайм отдал только суммарные токены — кеш считаем нулём и ставим флаг
`extra.cost_estimated = true`. Если рантайм отдал готовую сумму `$` — берём её,
пишем `extra.cost_reported = true`, наше вычисление — рядом для сверки.

#### 2.4.2 Стоимость человеческого вмешательства

```
cost_human_usd(attempt) = human_minutes * config.human_usd_per_hour / 60
human_minutes =
    5   если есть review_human                    // прочитать и одобрить
  + 20  если есть review_human с v < 0.5           // попросить переделать
  + 30  если есть reverted                         // откатить и разобраться
  + 15  если есть reopened
  + 10  если fail_reason == spec_unclear           // переформулировать
  + явно переданные минуты из `myc attempt rate --minutes N`
```

`config.human_usd_per_hour` по умолчанию **60**; пользователь меняет через
`myc config set swarm.human_usd_per_hour 120`. Значение 0 отключает слагаемое
(и роутер тогда честно оптимизирует только токены — это худший режим, отчёт
это подсвечивает).

**Полная стоимость задачи** (для отчётов и оценки, не для руки):
`task_cost = Σ по всем попыткам (cost_usd + cost_human_usd)`. Именно эта
величина — то, что мы обещаем снизить, и именно она фигурирует в 2.11.

#### 2.4.3 Ожидаемая стоимость и латентность руки для конкретной задачи

Стоимость в руке хранится нормированной на размер `m`; для задачи применяем
множители по размеру и контексту:

```
size_mult  = { xs: 0.3, s: 0.55, m: 1.0, l: 2.2, xl: 4.5 }
ctx_mult   = { c0: 0.7, c1: 1.0, c2: 1.6, c3: 2.8 }
effort_mult= { low: 0.6, medium: 1.0, high: 1.8 }   // только для холодного старта; при данных рука уже включает effort

cost_hat(arm, fp) = arm.cost_mean_usd * size_mult[fp.size] * ctx_mult[fp.ctx]
lat_hat(arm, fp)  = arm.lat_mean_ms   * size_mult[fp.size] * ctx_mult[fp.ctx]^0.5
```

Множители — начальные константы; фоновой job раз в неделю переоценивает их
по локальным данным как медианные отношения (`cost | size=l` / `cost | size=m`)
при ≥ 30 наблюдениях в каждой корзине и пишет в `swarm_config`; иначе
остаются константы.

При холодном старте (`cost_mean_usd IS NULL`):
```
cost_mean_usd(cold) = (tokens_in_ref * usd_per_m_in + tokens_out_ref * usd_per_m_out) / 1e6 * effort_mult
tokens_in_ref  = 60_000   // типичная задача размера m: контекст + тул-вызовы
tokens_out_ref = 8_000
lat_mean_ms(cold) = tokens_out_ref * effort_mult / tokens_per_sec * 1000 + 90_000   // 90 с накладных на тулы
```

#### 2.4.4 Функция полезности

```
utility(q, cost, lat; w, ref) =
    w.q * q
  - w.c * (cost / ref.cost_usd)
  - w.l * (lat  / ref.lat_ms)

ref.cost_usd = 2.0     // «средняя задача стоит $2» — масштаб, не цель
ref.lat_ms   = 600_000 // 10 минут
```

Смысл: единица `w.q` — «один гарантированный успех», единица `w.c` — «$2»,
`w.l` — «10 минут». Веса нормируются так, чтобы `w.q + w.c + w.l = 1`.

Профили (пресеты), выбираются `myc config set swarm.profile <name>` или
флагом `myc route --profile`:

| Профиль | w.q | w.c | w.l | Когда |
|---|---|---|---|---|
| `balanced` (по умолчанию) | 0.6 | 0.3 | 0.1 | обычная работа |
| `cheap` | 0.4 | 0.55 | 0.05 | ночные батчи, черновики |
| `quality` | 0.85 | 0.1 | 0.05 | прод, миграции, безопасность |
| `fast` | 0.5 | 0.15 | 0.35 | интерактивная сессия, человек ждёт |

Ручная настройка: `myc config set swarm.weights '{"q":0.7,"c":0.2,"l":0.1}'`.
Веса можно переопределить на уровне задачи: тег `route:quality` у задачи (L1
теги) или поле `task.route_profile`. Отдельно от весов — **жёсткие
ограничения**: `swarm.max_cost_usd` (по умолчанию нет), `swarm.max_latency_ms`,
`swarm.allow_models` / `swarm.deny_models`. Ограничения отсекают кандидатов до
расчёта полезности.

Почему линейная свёртка, а не «настоящее» Парето: пользователю нужен один
ответ. Парето-фронт целиком показываем в `--explain` и в вебе, чтобы человек
видел альтернативы, но выбирает роутер по свёртке. Утилита может быть
отрицательной: это нормально, сравниваем только относительный порядок.

### 2.5 Политика роутинга

#### 2.5.1 Состояние руки и приор

Для каждой руки `(model_id, effort, task_class)` роутер держит Beta(α, β).
Смысл: `q ~ Beta(α, β)` — распределение веры в «долю приемлемых исходов».

Иерархический приор (2.7 описывает, откуда берутся уровни):

```
prior_strength κ_team  = 8     // сколько «псевдонаблюдений» команды видит локальный уровень
prior_strength κ_global= 4     // сколько псевдонаблюдений глобального видит командный

m_global = α_g / (α_g + β_g)                     // среднее глобального (зашитого) приора
α_team_prior = κ_global * m_global;   β_team_prior = κ_global * (1 - m_global)
α_team = α_team_prior + S_team;       β_team = β_team_prior + F_team   // S,F — взвешенные суммы командных наблюдений

m_team = α_team / (α_team + β_team)
α_local_prior = κ_team * m_team;      β_local_prior = κ_team * (1 - m_team)
α_local = α_local_prior + S_local;    β_local = β_local_prior + F_local
```

Роутер использует **локальный** уровень; при `n_eff_local < 3` и наличии
командного — командный; при отсутствии обоих — глобальный.

**Заимствование у соседних классов** (малая выборка): если `n_eff_local < 5`,
добавляем `0.5 * (S, F)` от рук с тем же `(model, effort)` и соседним `scope`
и `0.25 * (S, F)` от `scope = unknown`. Заимствованное не превышает 5
эффективных наблюдений. Это реализуется на этапе материализации `swarm_arm`,
не в горячем пути.

#### 2.5.2 Обновление

Наблюдение — это `outcome` с `q ≠ NULL`:

```
w_obs = confidence * attribution * decay(now - attempt.finished_at)
decay(Δt) = 0.5 ^ (Δt / 60 дней)          // экспоненциальное забывание, полураспад 60 дней
S += w_obs * q
F += w_obs * (1 - q)
```

Так как `swarm_arm` — материализация, «обновление» — это пересчёт сумм по всем
`outcome` руки с учётом текущего `now`. Пересчёт всех рук по 10k попыток —
одна агрегация по индексу `swarm_attempt_arm`, ~20 мс в SQLite; делается в
фоне (2.5.6). Забывание пересчитывается при каждой материализации, поэтому
руки, которые перестали выбирать, **теряют уверенность** со временем — это
один из механизмов против залипания.

Стоимость и латентность: экспоненциально-взвешенные средние по логарифму
(стоимость лог-нормальна):

```
cost_mean_usd = exp( Σ w_i * ln(cost_i / size_mult_i / ctx_mult_i) / Σ w_i )   // нормировано к размеру m
cost_log_var  = взвешенная дисперсия ln(cost)
здесь w_i = decay(...) без confidence: стоимость известна точно даже у попытки без сигналов
```

#### 2.5.3 Выбор руки: Томпсон-семплинг с полом исследования

```
function route(task, profile, constraints, rng):
  fp    = fingerprint(task)                                  // < 5 мс
  arms  = candidateArms(fp.task_class, constraints)          // из кэша swarm_arm, отфильтровано allow/deny/active
  if arms.length == 0: return NO_MODELS

  // 1. Принудительное исследование недообследованных рук
  under = arms.filter(a => a.n_eff < N_MIN)                  // N_MIN = 5
  if under.length > 0 and exploreBudgetAvailable(rng):
      chosen = pickBy(under, a => -a.n_eff)                  // самая пустая
      mode = 'forced'
      goto FINALIZE

  // 2. Контрольная группа для честной оценки (2.11)
  if rng() < P_CONTROL:                                      // P_CONTROL = 0.10 при включённой оценке, иначе 0
      chosen = uniformPick(arms, rng); mode = 'control'
      goto FINALIZE

  // 3. Томпсон-семплинг
  for a in arms:
      a.q_sample = betaSample(a.alpha, a.beta, rng)
      a.cost_hat = cost_hat(a, fp)                           // 2.4.3
      a.lat_hat  = lat_hat(a, fp)
      a.utility  = utility(a.q_sample, a.cost_hat, a.lat_hat, profile.weights)
  arms.sortDesc(utility)
  chosen = arms[0]; alt = arms[1]
  mode = (chosen == argmax по posterior mean, не sample) ? 'exploit' : 'explore'

FINALIZE:
  propensity = estimatePropensity(arms, chosen, fp, profile, rng)   // 2.5.5
  decision = persist route_decision(...)                             // async write, не блокирует ответ
  return Recommendation(chosen, alt, propensity, ...)
```

`exploreBudgetAvailable`: скользящее окно 24 ч по `swarm_route_decision`;
доля `mode ∈ {forced, explore}` не должна превышать `EXPLORE_CAP = 0.15`, при
этом доля `forced` не ниже `EXPLORE_FLOOR = 0.05`, пока есть руки с
`n_eff < N_MIN`. Если доля уже ≥ cap — принудительное исследование
пропускается, работает чистый TS. Если за 24 ч меньше 20 решений — окно
расширяется до последних 20 решений.

**Гарантии против залипания:**

1. TS сам исследует: рука с `α = 2, β = 1` даёт сэмплы на всём [0,1].
2. Пол 5 % принудительного исследования, пока есть руки с `n_eff < 5`.
3. Забывание с полураспадом 60 дней: невыбираемая рука через полгода вернётся
   в состояние `n_eff < 5` и снова попадёт под пол исследования. Это делает
   «петлю невыбора» невозможной по построению: каждая активная модель
   получит хотя бы одну задачу каждого класса примерно раз в 4 месяца.
4. Потолок 15 %: счёт за исследование ограничен.
5. Верхний предел уверенности: при материализации `α + β` обрезаются так,
   чтобы `n_eff ≤ N_MAX = 200` (масштабируем α и β пропорционально). Иначе
   рука с 5000 наблюдений станет дельта-функцией и TS перестанет исследовать
   даже при дрейфе.

#### 2.5.4 Холодный старт при нуле данных

Глобальный приор `swarm_arm(level='global')` зашит в бинарь как JSON и
обновляется с релизами myc. Источник значений — публичные бенчмарки
кодинг-агентов (SWE-bench Verified, Aider polyglot, Terminal-bench) с
экспертной поправкой на класс; **сила приора маленькая**, чтобы реальные
данные быстро его перекрыли:

```
α_g = κ_0 * m_0,  β_g = κ_0 * (1 - m_0),  κ_0 = 4
```

`m_0` — таблица «семейство модели × intent» (scope не различаем на глобальном
уровне, кроме поправки `cross: −0.10`, `unknown: −0.05`):

| family | fix | feature | refactor | test | docs | config | investigate |
|---|---|---|---|---|---|---|---|
| frontier (Opus/Fable-класс, GPT-5.x-high) | 0.75 | 0.70 | 0.70 | 0.80 | 0.90 | 0.75 | 0.80 |
| mid (Sonnet-класс, GPT-5.x-medium) | 0.65 | 0.60 | 0.60 | 0.75 | 0.88 | 0.70 | 0.70 |
| small (Haiku-класс, mini) | 0.40 | 0.35 | 0.35 | 0.60 | 0.80 | 0.55 | 0.50 |
| open/local (без данных) | 0.30 | 0.25 | 0.25 | 0.50 | 0.70 | 0.45 | 0.40 |

Поправка на effort: `high: +0.05`, `low: −0.07`, обрезка в [0.05, 0.95].
Значения намеренно **пессимистичны для дешёвых** моделей: ошибиться в сторону
дорогой модели на первых 5 задачах дешевле, чем в сторону дешёвой (провал +
переделка). После `n_eff = 4` локальных наблюдений приор весит уже половину.

Незнакомая модель (нет в `swarm_model`): `family = 'open/local'`, отчёт
предупреждает «модель без приора, добавьте `myc model add --family mid`».

#### 2.5.5 Пропенсити

Для офлайн-оценки нужна `P(chosen | контекст, политика)`. У TS она не в
замкнутой форме; оцениваем Монте-Карло:

```
estimatePropensity(arms, chosen, fp, profile, rng):
  if mode == 'control': return 1 / arms.length
  if mode == 'forced':  return EXPLORE_FLOOR_SHARE / under.length   // фактическая доля forced за окно / число кандидатов
  hits = 0
  for k in 1..K:                                    // K = 64
      for a in arms: a.s = betaSample(a.alpha, a.beta, rng)
      if argmax(utility(a.s, ...)) == chosen: hits++
  return clamp(hits / K, 0.01, 1.0)                 // пол 0.01: обрезаем веса IPS
```

64 сэмпла × ≤ 20 рук — ~1300 бета-сэмплов, < 1 мс. Пишется в
`route_decision.candidates[].propensity` и в `attempt.propensity`.

#### 2.5.6 Материализация (`swarm.recompute`)

Фоновая задача, запускается: после `attempt finish` (debounce 2 с),
после прихода любого сигнала (debounce 10 с), после `pull` снимка с сервера,
и не реже раза в сутки (забывание). Никогда — в горячем пути `route`.

```
recompute(dirty_attempts | ALL):
  for att in dirty:  outcome[att] = computeOutcome(att)         // 2.3.2, 2.3.3
  for arm in affected_arms(dirty):
      local = aggregate(outcomes where arm, level=local, decay(now))
      team  = snapshot.team[arm]     // как пришло с сервера
      global= builtin[arm]
      swarm_arm[arm] = hierarchical(global, team, local)        // 2.5.1, включая соседей и N_MAX
  bump(arm_cache_version)                                       // процесс route перечитает 500 строк
```

Если myc работает без демона (по умолчанию), кто выполняет фон? Тот же
механизм, что у L1 для эмбеддингов/decay: короткоживущий фоновый процесс,
отпочковывающийся после команды записи, с файловым локом, либо отложенная
работа при следующем `prime`. Пересчёт 500 рук по 10k попыток — ~20–40 мс.

### 2.6 Эскалация и каскад

Каскад: сначала дешёвая рука A, при **обнаруженном** провале — дорогая B.
Ключевое слово — «обнаруженном». Каскад без верификации — это не каскад, а
рулетка: провал A, который никто не заметил, уедет в main.

Обозначения: `p_A` — вероятность приемлемого исхода A (posterior mean, не
сэмпл: решение о каскаде должно быть консервативным); `c_A, c_B` —
ожидаемые стоимости; `d` — вероятность обнаружить провал A до эскалации;
`c_sw` — стоимость переключения (повторный контекст B + человеческое время на
разбор, если провал обнаружил человек).

```
d = 0.9 если fp.has_tests и tests обязательны в finish
    0.6 если только lint/typecheck или review_ai
    0.2 если верификации нет (только самоотчёт агента)

E[cost_cascade] = c_A + (1 - p_A) * d * (c_B + c_sw) + (1 - p_A) * (1 - d) * c_leak
E[cost_direct]  = c_B
где c_leak — ожидаемая цена необнаруженного провала: cost_human(reverted) = 30 мин * human_usd_per_hour / 60 + c_B (всё равно переделывать)

E[q_cascade] = p_A + (1 - p_A) * d * p_B
E[q_direct]  = p_B

E[lat_cascade] = l_A + (1 - p_A) * d * l_B
```

Каскад выбирается, когда `utility(E[q_cascade], E[cost_cascade], E[lat_cascade]) > utility(p_B, c_B, l_B)`.
При чистой стоимости (w.q = 0, w.l = 0) это условие превращается в **порог по p_A**:

```
c_A + (1 - p_A) * [d * (c_B + c_sw) + (1 - d) * c_leak] < c_B
⇔ p_A > 1 - (c_B - c_A) / [d * (c_B + c_sw) + (1 - d) * c_leak]
```

Пример с числами: `c_A = $0.30, c_B = $2.00, c_sw = $0.50, human $60/ч →
c_leak = $30 + $2 = $32`. При `d = 0.9`: знаменатель = 0.9·2.5 + 0.1·32 = 5.45,
порог `p_A > 1 − 1.7/5.45 = 0.69`. При `d = 0.2`: знаменатель = 0.2·2.5 + 0.8·32 = 26.1,
порог `p_A > 0.935` — практически недостижим. То есть **без тестов каскад
почти никогда не оправдан**, и это правильный вывод.

Правила поверх формулы:

- Каскад допускается только при `d ≥ 0.6`.
- Не более одной эскалации (A → B), не A → B → C: третья ступень почти никогда
  не окупается и удваивает латентность.
- `myc route` возвращает `cascade: {first: A, then: B, escalate_if: "tests_fail | fail_reason != spec_unclear"}`;
  запускает ступени оркестратор. Вторая попытка стартует с `parent_attempt = A`,
  при этом A получает сигнал `redone` (weight 0.8) автоматически.
- При `fail_reason == spec_unclear` у A эскалация **не** запускается: B провалится
  по той же причине; вместо этого рекомендация «уточните задачу».

### 2.7 Общие приоры команды

#### 2.7.1 Протокол синхронизации

Клиент → сервер (`POST /v1/swarm/push`, фон, не чаще 1 раза в час, только при
наличии новых `outcome` с `confidence ≥ 0.3`):

```ts
interface SwarmPush {
  proto: 1;
  repo_hash: string;          // salted (соль команды), 8 hex
  fp_version: number;
  outcome_version: number;
  window_from: number; window_to: number;    // unix ms
  arms: Array<{
    model_id: string; effort: string; task_class: string;
    S: number; F: number;     // Σ w·q, Σ w·(1−q) за окно, БЕЗ decay (сервер применит свой)
    n: number;                // число попыток
    cost_log_sum: number; cost_log_sq_sum: number; cost_n: number;   // по нормированной стоимости
    lat_log_sum: number;  lat_log_sq_sum: number;  lat_n: number;
    size_hist: number[5]; ctx_hist: number[4]; langs_hist: Record<string, number>;
  }>;
}
```

Никаких `attempt_id`, `task_id`, sha, путей, текста. Окно — с момента
последнего успешного push; сервер дедуплицирует по `(repo_hash, window_to)`.

Сервер → клиент (`GET /v1/swarm/snapshot?team=...&since=<snapshot_id>`, фон,
раз в час или при `prime`, если снимок старше 6 ч):

```ts
interface SwarmSnapshot {
  snapshot_id: string;        // монотонный
  computed_at: number;
  fp_version: number;
  arms: Array<{ model_id; effort; task_class; alpha; beta; n_eff; n_repos;
                cost_mean_usd; cost_log_var; lat_mean_ms; lat_log_var }>;
  models: SwarmModel[];       // справочник + цены, чтобы клиенты не расходились
  drift_alerts: Array<{ model_id; task_class; since; delta }>;   // 2.9.3
}
```

Снимок кладётся в `swarm_arm(level='team')`, потом `recompute`. Сеть строго
в фоне: `route` никогда не ждёт снимка; при отсутствии сервера работает на
локальном + глобальном.

#### 2.7.2 Агрегация на сервере: устойчивость к шумной репе

Наивная сумма `S, F` по всем репозиториям даёт одной репе с 3000 попыток и
сломанными тестами (все `tests = 0`) власть над командой. Защита в три слоя:

```
aggregateTeam(arm):
  per_repo = { r: (S_r, F_r, n_r) } за скользящее окно 90 дней с decay(60 дней)
  // 1. Потолок вклада одной репы
  W_REPO_MAX = 50                              // эффективных наблюдений на руку за окно
  for r: scale_r = min(1, W_REPO_MAX / (S_r + F_r)); S_r *= scale_r; F_r *= scale_r
  // 2. Робастность: усечённое среднее долей
  rates = { r: S_r / (S_r + F_r) } для реп с S_r + F_r ≥ 3
  if |rates| ≥ 4:
      med = median(rates); mad = median(|rate_r − med|)
      outliers = { r : |rate_r − med| > max(0.25, 3 * 1.4826 * mad) }
      for r in outliers: S_r *= 0.5; F_r *= 0.5; flag(r, arm, 'outlier')
  // 3. Сумма
  S = Σ S_r; F = Σ F_r; n_repos = |per_repo|
  α_team = κ_global * m_global + S;  β_team = κ_global * (1 − m_global) + F
  clamp n_eff ≤ N_MAX (200), как локально
```

Репа с флагом `outlier` на ≥ 3 руках подряд два снимка получает статус
`quarantined` в отчёте админа сервера: её вклад ×0.25, пока флаг не снимут.
Клиенту этой репы приходит `drift_alerts`-запись с `reason: 'your_repo_is_outlier'`,
чтобы владелец проверил свои тесты/хуки — обычно виноваты именно они.

#### 2.7.3 Смешивание уровней

Уже описано в 2.5.1: `global → team → local` через псевдо-счётчики `κ_global = 4`,
`κ_team = 8`. Интуиция: команда «стоит» 8 локальных наблюдений; репозиторий,
накопивший 30 наблюдений в руке, слушает себя на 79 %, команду — на 21 %.
Пустой репозиторий слушает команду полностью. Значения `κ` конфигурируемы
(`swarm.kappa_team`), но менять их без данных не рекомендуется.

### 2.8 Приватность

**По умолчанию и без возможности переключить в общий пул уходят только
метаданные.** Нет флага «отправлять контент для точности»: он не нужен
математике, а его наличие ломает обещание для всей команды.

**Никогда не пишется ни локально в `swarm_*`, ни на сервер:**

- текст задачи (заголовок, описание, комментарии) — в `swarm_*` только
  `task_id` (локально) и производные enum/бакеты;
- содержимое диффа, файлов, промптов, ответов модели, вывода тулов;
- текст ревью, сообщений коммитов (только sha, и только локально);
- пути к файлам (только `domain_hash`, солёный) и имена веток (только hash);
- имена людей, e-mail, имена агентов-сессий (только `agent_runtime` enum);
- имя репозитория и remote URL (только `repo_hash` с командной солью);
- сырые токены/логи API.

**На сервер (2.7.1) не уходит даже то, что есть локально:** ни `attempt_id`,
ни `task_id`, ни `commit_shas`, ни `fingerprint` целиком — только суммы по
рукам и гистограммы бакетов. Сервер валидирует push по JSON-схеме и отвергает
поля вне схемы (`additionalProperties: false`), а не «игнорирует».

**Соль команды** выдаётся сервером при подключении (`myc login`), хранится
локально; без сервера — генерируется локально случайно. Хеши с разной солью
несовместимы, что и требуется.

**Как остаёмся полезными на одних метаданных.** Бандиту нужны ключ руки,
исход и стоимость — всё это метаданные. Похожесть задач (2.1.5) использует
эмбеддинг заголовка, но только **локально** и не пишет его в `swarm_*`.
Единственное, что теряем, — возможность «объяснить», почему модель провалила
конкретную задачу; для этого есть локальный `myc attempt show`, который
джойнит `swarm_attempt` с задачей L1 — на машине пользователя.

`myc report privacy` печатает точный список полей последнего push и пример
записи — чтобы обещание было проверяемым, а не декларативным.

#### 2.10.2 Формат рекомендации

```ts
interface Recommendation {
  route_id: string;
  task_class: TaskClass;
  fingerprint: TaskFingerprint;
  model_id: string;
  effort: "low" | "medium" | "high";
  confidence: number;          // 0..1, см. ниже
  evidence: "none" | "weak" | "ok" | "strong";   // n_eff < 1 / < 5 / < 20 / ≥ 20
  expected: { quality: number; cost_usd: [number, number]; latency_s: [number, number] };
                               // интервалы: 20–80 перцентили по log-var
  mode: "exploit" | "explore" | "forced" | "control" | "cascade";
  alternative?: { model_id; effort; expected; why: "cheaper" | "better" | "faster" };
  cascade?: { first: {model_id; effort}; then: {model_id; effort};
              escalate_if: string; expected_cost_usd: number; detect_prob: number };
  warnings: string[];          // "no verification signals in repo", "model X has no prior", "explore budget exhausted"
  pareto?: Array<{ model_id; effort; quality; cost_usd; latency_s }>;   // при --explain
  similar?: Array<{ task_id; sim; model_id; quality }>;                 // при --explain, только локально
  prior_snapshot: string;
}
```

`confidence` — не «вероятность успеха», а **уверенность в том, что выбор
верный**: доля из 64 МК-сэмплов (2.5.5), в которых выбранная рука была лучшей,
умноженная на `min(1, n_eff / 20)`. Так рука с `n_eff = 2`, выигравшая 60 из
64 сэмплов, покажет `0.09`, а не `0.94`.

### 2.11 Честная оценка: докажем, что роутинг экономит

Цель: оценить `Δ = E[task_cost | routed] − E[task_cost | baseline]` при
`E[quality | routed] ≥ E[quality | baseline] − 0.02`, где `task_cost` — полная
стоимость (токены + человек, 2.4.2). Три метода, результаты показываются
рядом; расходятся — верим худшему.

**A. Онлайн-контроль (главный).** 10 % решений (`mode = 'control'`) выбирают
руку равномерно среди допустимых; ещё один бейзлайн — `baseline_fixed`: рука,
которую команда использовала бы без роутера (`swarm.baseline_model`, по
умолчанию — самая частая рука в `routed = 0` попытках за 90 дней). Сравниваем
routed (`exploit + explore`) против control и против попыток с `routed = 0` на
том же бейзлайне. Учитываются только попытки старше 14 дней (отложенные
сигналы дозрели). Оценка разницы средних с бутстрэп-ДИ 95 % (2000 ресэмплов,
стратификация по `task_class`). Минимальная выборка для вывода: 30 контрольных
и 100 роутед-задач; до этого отчёт пишет «недостаточно данных» с прогрессом.

**B. Офлайн-оценка по логам (IPS/SNIPS + DR).** Для новой политики π' (например,
после смены весов) на исторических решениях с известной пропенсити `p_i`
логирующей политики:

```
IPS   : V̂(π') = (1/N) Σ_i [π'(a_i | x_i) / p_i] · r_i
SNIPS : V̂(π') = Σ_i [π'(a_i|x_i)/p_i] · r_i  /  Σ_i [π'(a_i|x_i)/p_i]
DR    : V̂(π') = (1/N) Σ_i { r̂(x_i, π'(x_i)) + [π'(a_i|x_i)/p_i] · (r_i − r̂(x_i, a_i)) }
где r_i = −task_cost_i + λ · q_i (λ = w.q / w.c · ref.cost_usd — та же свёртка, что в utility),
    r̂(x, a) = прогноз по руке: −cost_hat(a, fp) + λ · posterior_mean(a),
    π'(a|x) считается тем же МК-методом (2.5.5) с 64 сэмплами на текущих приорах,
    веса π'/p обрезаются сверху на 20 (пол пропенсити 0.01 даёт максимум 100; 20 — консервативнее).
```

Ограничения, которые отчёт печатает рядом с числом: (1) оценка валидна только
для рук, у которых `p_i > 0` в логах, — то есть для рук, которые исследование
реально трогало; (2) эффективный размер выборки `ESS = (Σ w_i)² / Σ w_i²`
показывается явно; при `ESS < 30` вывод помечен «ненадёжно».

**C. Реплей по классам.** Для каждого класса: средняя `task_cost` и `q` по
рукам за период (только контроль + `routed = 0`), «оракул» — лучшая рука по
`utility` постфактум. Показываем `regret = utility(oracle) − utility(routed)`
и долю решений, совпавших с оракулом. Это не доказательство экономии (оракул
знает будущее), но диагностика «где роутер систематически промахивается».

**Что считаем успехом на пилоте** (критерий для координатора/заказчика):
за 60 дней на ≥ 300 задачах команды метод A показывает снижение полной
стоимости на успешную задачу ≥ 20 % при неухудшении `q` (95 % ДИ не
пересекает 0), и метод B не противоречит A по знаку. Если нет — подсистема
остаётся в режиме «отчёты без рекомендаций» (`swarm.routing = off`), что тоже
полезно: телеметрия сама по себе показывает команде, куда уходят деньги.

| `attempt event` | < 2 мс | INSERT батчем (хук копит до 10 событий или 5 с) | — |

| `report models` | < 100 мс на 10k попыток | агрегации по индексам | — |

Правила, которые держат бюджет:

1. **`route` читает одну таблицу** (`swarm_arm`) и никогда не трогает
   `swarm_attempt`/`swarm_signal`. Вся тяжесть — в материализации.
2. **Graft с таймаутом 2 мс на вызов и не более 8 вызовов**: при таймауте
   `depth = d0`, `graft_timeout = 1`, рекомендация помечается `warnings:
   ["graph timeout, scope may be underestimated"]`. Лучше грубый отпечаток за
   5 мс, чем точный за 50.
3. **Кэш `swarm_arm` в процессе**: при CLI без демона процесс живёт одну
   команду, поэтому холодная загрузка 500 строк — один `SELECT` по
   `WITHOUT ROWID`-таблице, ~0.3 мс. Для MCP-сервера — версия в `swarm_config`
   (`arm_cache_version`), перечитывание при изменении.
4. **Нет сети в `route`, `start`, `finish`.** Снимок команды — только фоном.
5. **Хранение**: `swarm_attempt_event` — 30 дней, затем удаление (итоги уже в
   `attempt`); `swarm_route_decision.candidates` — 180 дней (нужно для оценки),
   затем обрезка до `chosen/propensity`; `swarm_attempt`/`swarm_signal` — не
   удаляются (при 50 попытках в день это 18k строк в год, ~10 МБ).

## 4. Риски и что ломается на масштабе

1. **Сигналы не приходят.** Самый вероятный сценарий провала: команда не
   ставит хуки, тесты не гоняются, реверты никто не размечает. Тогда 80 %
   попыток «pending», приоры застывают на глобальных, роутер деградирует до
   «выбирай по цене из таблицы бенчмарков». Мы это **показываем**
   (`degraded: no_verification_signals`), но не чиним. Минимально
   необходимая интеграция — git-хуки `prepare-commit-msg` + фоновый скан
   реверта/выживания: они дают `merged/survived/reverted` вообще без участия
   CI и людей, и это должно ставиться `myc init` по умолчанию.
2. **Оркестраторы не вызывают `start/finish`.** Без попыток нет ничего.
   Ставка на хуки Claude Code / плагины opencode / Orca (L3). Если агент
   вызывает MCP-тулы сам — статистика будет с дырами (забыл `finish` → `abandoned`
   через 4 ч → ложный провал с `attribution = 0.5`). Порог `abandoned` по
   heartbeat 30 мин слишком агрессивен для долгих задач без хуков —
   конфигурируемо.
3. **Разреженность рук.** 28 классов × 6 моделей × 3 усилия = 504 руки. В
   команде с 30 задачами в день по 3–4 популярным классам большинство рук
   останется `weak` навсегда. Иерархия и соседи смягчают, но честный ответ:
   роутер полезен в 5–8 самых частых классах, остальное — глобальный приор.
   Возможное упрощение при нехватке данных: схлопнуть `effort` в ключе
   (оставить в поправке стоимости) — 168 рук. Решение отложено до пилота.
4. **Дрейф отпечатка при смене `fp_version`.** Каждое обновление лексикона
   сдвигает классы; сервер держит агрегацию по версиям и взвешивает старые
   0.5 — 60 дней частичной слепоты после каждого обновления. Обновлять
   лексикон не чаще раза в квартал.
5. **Стоимость исследования.** 15 % задач могут уйти не лучшей руке. При
   `quality`-профиле и задачах в проде это чувствительно; поэтому
   `swarm.explore_cap` конфигурируем, а `forced`-исследование **никогда** не
   выбирает руку с `posterior_mean < 0.3` для классов `fix:cross` и
   `config:cross` (правило безопасности, константы в коде).
6. **Пропенсити при внешнем выборе.** Если оркестратор игнорирует
   рекомендацию (`taken = 0`), пропенсити логирующей политики для реально
   запущенной руки неизвестна; такие попытки в офлайн-оценке исключаются, в
   материализации весят 0.5. Если рекомендации игнорируют > 50 % времени,
   оценка B невозможна, и отчёт это скажет.
7. **Сервер и много команд.** Агрегация 2.7.2 — per team; при 100 репах × 500
   рук × 90 дней — 4.5M строк статистик в Postgres, агрегация раз в час
   выполнима (индекс по `(team, arm, window_to)`). Глобальный уровень между
   командами **не** смешиваем в MVP: без opt-in это утечка, с opt-in — новая
   ось шума.
8. **Игра с системой.** Агент, знающий, что его оценивают по `tests`, может
   ослабить тесты. Веса и Гудхарт-отчёт (2.9) — сдерживание, не гарантия.
   Единственное настоящее лекарство — сигналы от человека и реверты; они и
   весят больше всего.
9. **Многопроцессность локально.** Несколько агентов пишут `attempt_event`
   одновременно: SQLite WAL + короткие транзакции; `recompute` под файловым
   локом (тот же механизм, что у L1/L2 для индексации), при занятом локе —
   пропуск, следующий триггер доберёт.
10. **Цены устаревают.** `swarm_model_price` приходит со снимком сервера;
    без сервера — из бинаря myc (обновляется релизами) и `myc model add`.
    Стоимость, посчитанная по устаревшей цене, помечается в отчёте датой
    прайса.

## 5. Открытые вопросы координатору

1. **L1 — ID и oplog.** `attempt_id`/`route_id` должны идти по общей схеме
   ID L1 (ULID-производные?) и попадать в oplog для синхронизации с сервером?
   Предлагаю: `swarm_attempt`, `swarm_signal`, `swarm_route_decision` —
   локальные, **не** реплицируются через oplog L1 (на сервер идут только
   суммы 2.7.1). Нужно подтверждение, что это не ломает модель «один граф».
2. **L1 — хуки статусов задачи.** Нужны события `task.closed → open`
   (сигнал `reopened`), `task.description_changed` с долей изменённых слов
   (флаг `spec_defect`), `task.created(type=bug, anchors)` (скан `followup_bug`),
   и поле `task.current_attempt` при `claim`. Предлагаю единый внутренний
   event-bus L1, на который L4 подписывается.
3. **L1 — якоря и graft-адаптер.** `computeStructural` нуждается в
   `graft.callers(symbol, depth=1)` с **жёстким таймаутом 2 мс** и в
   `span_lines` якоря. Есть ли такой интерфейс у адаптера, или L4 должен
   работать с кэшированным `fan_in` в таблице якорей (предпочтительно: L1
   считает fan-in при обновлении якоря в фоне, L4 читает число)?
4. **L2 — эмбеддинги заголовков.** Похожесть (2.1.5) и `cluster_id`
   используют эмбеддинг заголовка задачи, который L2 считает для поиска.
   Нужен доступ к вектору по `task_id` без пересчёта и признак «ещё не
   готов».
5. **L3 — хуки и MCP-профили.** Кто ставит хуки Claude Code / opencode / Orca,
   вызывающие `attempt start/event/finish`, и git-хук `prepare-commit-msg` с
   трейлерами `Myc-Attempt`/`Myc-Task`? Предлагаю `myc init` ставить git-хуки
   всегда, агентские — по флагу `--agent claude-code|opencode|orca`. Имена
   MCP-тулов (`myc_route`, `myc_attempt_*`) и их распределение по профилям
   agent/leader/full — на согласование с L3.
6. **L3 — `prime`.** В `prime` нужно ≤ 200 токенов подсказки: активная
   попытка (если есть), рекомендация роутера для взятой задачи, инструкция
   ставить трейлеры. Укладывается ли это в бюджет `prime` p99 < 30 мс с учётом
   того, что `route` добавляет ≤ 10 мс? Если нет — `prime` печатает только
   `attempt_id`, а `route` агент вызывает отдельно.
7. **L3/сервер — auth и соль команды.** `myc login` должен возвращать
   `team_salt`; эндпоинты `/v1/swarm/push|snapshot` требуют командного
   токена. Кто владеет схемой аутентификации.
8. **L1 — фоновые задачи без демона.** `recompute`, сканы git и sync полагаются
   на общий механизм фоновой работы L1 (fork после записи / отложенная работа
   в `prime`). Нужна единая очередь фоновых job с приоритетами: эмбеддинги L2
   важнее `recompute` L4.
9. **Заказчику.** Контрольная группа 10 % (`P_CONTROL`) — это осознанная плата
   за доказуемость. Включать по умолчанию или только на пилоте? Моё
   предложение: включена по умолчанию первые 90 дней после `init`, затем
   снижается до 3 %.
10. **Заказчику.** `effort` в ключе руки (504 руки) или в поправке (168)? Первое
    точнее при больших данных, второе быстрее учится. Предлагаю начать с 504 и
    измерить долю `weak`-рук через 30 дней пилота.
