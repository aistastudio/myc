# myc — архитектура

> Статус: черновик координатора. Разделы 6–9 собираются из лейн-документов
> `01`–`04` после завершения дизайн-сессии.

## 1. Тезис

Пять инструментов-источников решают пять кусков одной задачи, и каждый держит
**своё** хранилище:

| Инструмент | Что держит | Чего не знает |
|---|---|---|
| beads | граф задач с зависимостями | какая память объясняет задачу |
| memora | граф фактов и решений | к какой задаче и какому коду он относится |
| TencentDB-Agent-Memory | слои памяти L0–L3, ACL, proxy | про задачи разработки и код проекта |
| graft | граф символов кода, $0, детерминированный | какие решения были приняты про этот символ |
| socraticode | гибридный семантический индекс кода | про работу, память и исходы |

Главная потеря сегодня не в том, что какого-то из этих слоёв нет, а в том, что
**они не связаны**. Агент каждый раз заново склеивает «что делать» ↔ «что мы уже
про это знаем» ↔ «где это в коде» — и платит за склейку контекстом, временем и
деньгами.

**myc — это один граф, один ретривал и четыре проекции над ними:**
задачи, память, якоря кода, телеметрия роя. Связь между проекциями — не интеграция,
а первичный факт схемы.

Пятая проекция — телеметрия роя — замыкает петлю, которой нет ни у одного из
источников: myc видит и постановку задачи, и её исход, и цену исхода, а значит
может отвечать на вопрос «кому отдать следующую такую задачу».

## 2. Три архитектурных инварианта

Это не пожелания, а ограничения, которые имеют право отклонить любую фичу.

### И1. Скорость — ограничение, а не оптимизация

myc стоит в горячем пути агента и вызывается десятки раз за сессию.
Поэтому в горячем пути **запрещены**: сетевые вызовы, вызовы LLM, полные
пересчёты индексов, ожидание фоновой работы.

Запись всегда дешёвая: факт попадает в append-only оплог за один синхронный
шаг, а всё дорогое (эмбеддинги, классификация absorb, суммаризация,
подъём по слоям) делает фоновый дистиллятор. Чтение идёт из материализованных
проекций, а не из свёртки лога.

Бюджеты: `prime` p99 < 30 мс, точечное чтение < 3 мс, гибридный поиск по 100k
узлов < 25 мс, запись < 5 мс, холодный старт < 60 мс.

### И2. $0 и офлайн по умолчанию, деградация — громкая

Без единого API-ключа myc обязан работать полностью: задачи, память, поиск,
якоря, роутинг. LLM добавляет только качество обогащения.

Обратная сторона — правило, нарушение которого убило бы доверие к базе:
**никакого молчаливого фолбэка.** У memora при недоступности эмбеддингов
происходит тихий переход на TF-IDF, и хранилище наполняется мешками ключевых
слов, продолжая выглядеть здоровым. У нас любая деградация ретривала:
(а) помечает затронутые узлы флагом качества, (б) видна в `myc doctor` и в
`/health`, (в) при `--strict` останавливает запись, а не портит её.

### И3. Мы не переписываем graft и socraticode

Код-интеллект — чужая, уже решённая задача. myc хранит **якоря**
(`repo + path + span + blob_hash + текстовый crux`) и умеет детектировать их
протухание, а тяжёлый разбор кода делегирует graft через адаптер.
Идею graft «crux хранится как текст, а не как номера строк — чтобы пережить
рефакторинг» переносим на свои якоря.

## 3. Топология

```
   CLI `myc`        MCP-сервер        HTTP API        Web UI
  ────────────────────────────────────────────────────────────
                      Ядро myc  (Bun + TypeScript)

   ┌─────────┬──────────┬─────────────┬────────────────────┐
   │ Задачи  │  Память  │ Якоря кода  │  Телеметрия роя    │  проекции
   └─────────┴──────────┴─────────────┴────────────────────┘
      Единый граф: узлы + типизированные рёбра + слои L0–L3
  ────────────────────────────────────────────────────────────
      Ретривал:  FTS/BM25 + векторы + расширение по графу
                 → RRF → бюджет (элементы / символы / таймаут)
  ────────────────────────────────────────────────────────────
      Оплог (append-only)  →  материализованные проекции
  ────────────────────────────────────────────────────────────
      SQLite + FTS5 + sqlite-vec   │   PostgreSQL + pgvector
         (embedded, по умолчанию)  │   (сервер, команда)
  ────────────────────────────────────────────────────────────
   Фоновый дистиллятор │ graft-адаптер │ LLM-провайдеры (опц.)
```

Два режима одного бинаря:

- **Embedded** — библиотека внутри процесса CLI/MCP, SQLite в `.myc/`, без демона.
  Это дефолт и это то, что обязано быть быстрым.
- **Server** — `myc serve`, PostgreSQL, воркспейсы, участники, ACL, общие
  приоры роутинга. Клиенты те же CLI и MCP, только с `--remote`.

| `@myc/distiller` | absorb, supersede, decay, подъём L0→L1→L2→L3 |
| `@myc/anchors` | якоря на код, детект протухания, адаптер graft |
| `@myc/swarm` | телеметрия попыток, приоры, политика роутинга |

Правило зависимостей: поверхности зависят от ядра, ядро не знает о поверхностях;
`retrieval` не знает о `distiller`; `swarm` не знает ни о чём, кроме `core`.

## 6. Ядро данных и хранилище

Полностью: [`01-core-data-model.md`](01-core-data-model.md) (1801 строка).

**Одна таблица `nodes` с дискриминатором `kind` и `attrs JSON`**, а не таблица на тип.
Решающий довод — счётом: все горячие запросы (`prime`, `ready`, гибридный поиск,
обход рёбер) кросс-kind, и при table-per-type каждый из них превращается в
`UNION ALL` по девяти таблицам с девятью FTS- и девятью вектор-сканами.
Горячих колонок ~30 (включая `assignee`, `lease_*`, `open_blockers`), холодное —
в `attrs`. Полям, которым нужен индекс, дают `GENERATED ... VIRTUAL` +
частичный индекс: индекс есть, физической колонки и миграции на каждый новый
kind — нет.

**ID:** `<slug>-` + 12 символов Crockford base32 (60 бит), канонический и
неизменный. Дотовый путь `myc-a3f8.1.2` — **вычисляемый ярлык отображения, не
хранимое поле**: у beads он хранимый, но это безопасно только под cell-merge
Dolt'а, которого у нас нет. Короткая форма разрешается range-scan'ом по
первичному ключу (`id >= 'myc-a3f8' AND id < 'myc-a3f9'`), как git-хеши, а не
через `LIKE`.

**Рёбра — 11 типов.** Десять из источников плюс `contradicts`: в absorb-конвейере
memora есть класс «contradiction», но связи, которая бы его выражала, нет —
противоречие помечается и повисает. Транзитивность считается по-разному в
зависимости от того, насколько запрос горячий: `blocks` — денормализованный
счётчик `open_blockers` на триггерах (потому что `ready` обязан быть одним
сканом частичного индекса), `parent` — материализованное замыкание, остальное —
рекурсивным CTE по требованию.

**Слои L0–L3 — колонка `layer`, а не отдельные таблицы.** Подъём по слою есть
вставка нового узла и ребра `derived_from`, а не миграция строки между
хранилищами; история остаётся целой.

**Сходимость команды — оплог с per-field LWW на гибридных логических часах**,
add-wins OR-Set для рёбер, G-counter для счётчиков. Векторные часы отвергнуты:
они растут по числу сайтов и требуют буфера каузальной доставки, а наши поля
семантически независимы. Два места, где LWW опасен, получили отдельные типы:
множества (OR-Set) и claim (**lease с epoch** — CAS одним `UPDATE ... WHERE`
с проверкой `changes()==1`, без окна между чтением и записью).

**Экспорт в git — 32 корзины JSONL** по первому символу ID, строки
отсортированы. Одна строка = один узел: дифф читаем, конфликт локален, а мерж
двух веток почти всегда трогает разные файлы.

## 7. Ретривал и производительность

Полностью: [`02-retrieval-and-performance.md`](02-retrieval-and-performance.md).

**Холодный старт 30–45 мс** на one-shot CLI: `bun build --compile --minify
--bytecode` плюс ленивые импорты. Оба слагаемых обязательны и оба измерены
(S63): без `--bytecode` старт дороже на ~12 мс, со статической регистрацией
команд — ещё на ~3.7 мс. Замер 2026-09-07 на 14 ядрах при load 6.6:
`myc --version` p50 20.1 мс, из них 13.6 мс — неустранимый спавн
скомпилированного bun-бинаря. Демон `mycd` существует, но остаётся опцией —
если он не поднят, CLI откатывается в one-shot за 5 мс. Это и есть техническое
содержание требования «локально без демона».

**`prime` не трогает эмбеддинги вообще** — только детерминированные запросы и
`digest_cache`. Самая горячая команда не зависит от самой дорогой подсистемы.

**Гибридный ретривал — один SQL round-trip.** FTS5 BM25 + плотные векторы +
расширение по графу на 1–2 хопа, слияние RRF (k=60, cut-off 100), фильтрация
scope/ACL **внутри CTE источников**, то есть до ранжирования. Два этапа
точности: int8-скан, затем float32-переранжирование топ-200.

**Эмбеддинги:** bge-small-en-v1.5 INT8, 384 измерения, onnxruntime-web WASM
внутри бинаря. Эмбеддинг запроса — 4–7 мс. Query-сессия на главном потоке,
пул воркеров `clamp(cores/4, 1, 4)` для батчей.

**Граница SQLite → Postgres — около 100k узлов.** sqlite-vec держит int8-скан
за 5–8 мс до этого порога; дальше pgvector HNSW halfvec (m=16,
ef_construction=64, ef_search=40) даёт 1–3 мс на 1M при recall ≈ 0.97.

**Запись — четыре insert'а в одной транзакции, 2–4 мс.** Всё тяжёлое уходит в
очередь: батчи по 50, чекпойнты, пропуски по content-hash, branch-aware
переиспользование векторов по хешу содержимого.

**Инвалидация кешей — по `oplog.seq` одним prepared statement (~50 мкс)**,
кросс-процессно через `myc_meta.last_seq`. Без lock-файлов: socraticode решает
ту же задачу файловыми локами, а нам достаточно монотонного счётчика.

## 8. Поверхности и интеграции

Полностью: [`03-interfaces-and-integration.md`](03-interfaces-and-integration.md) (3051 строка).

**CLI — плоские короткие глаголы**, вложенность не глубже двух уровней,
24 команды, 10 фиксированных кодов выхода. Человеческий вывод — плотный
колоночный текст без рамок, эмодзи и ANSI: его читает модель, а не человек,
и рамки суть чистые потери токенов. Машинный — конверт `{ok,cmd,data,meta,warn}`,
в котором есть куда положить `degraded`, не ломая парсеры.

**MCP — 7 инструментов в профиле `agent`**, 11 в `leader`, 16 в `full`, бюджет
описаний ≤ 1100 токенов. Для сравнения: memora с 43 инструментами платит этот
налог в каждой сессии. Гранулярность выбрана по намерению, а не по CRUD:
`myc_ready{claim:true}` сразу выдаёт и берёт задачу, потому что три round-trip'а
на «взять задачу» — это три инференса.

**`PreCompact` — обязательный хук.** Компакт есть единственный момент, когда
контекст теряется гарантированно; если myc туда не встаёт, он не память, а
записная книжка. Порядок записи важен: сырой эпизод пишется **первым** за 6 мс,
спасательный пакет вторым, дистилляция уходит в фон.

**`post-edit` — fire-and-forget за < 2 мс**: помечает якоря грязными и выходит,
ничего не пересчитывая. Хук стоит в горячем пути редактирования, где любая
работа умножается на сотни правок за сессию.

**graft физически не может стоять в горячем пути**: минимум 40 мс против бюджета
`recall` в 25 мс. Отсюда правило — только фон и явные команды. Плюс правило
неудвоения: если graft уже подключён у хоста как MCP, myc не дублирует его
инструменты.

**Секреты редактируются на записи** (паттерны + энтропия). Хук pre-compact
пишет транскрипты, а `.myc/` лежит рядом с git — без детектора это утечка по
расписанию.

**Proxy-режим делаем, но выключенным по умолчанию**, и инъекция памяти идёт
строго **после** статического префикса промпта: правка начала system-промпта
убивает prompt caching провайдера, и это дороже пользы от самой памяти.

## 9. Самообучение роя и роутинг

Полностью: [`04-swarm-learning-and-routing.md`](04-swarm-learning-and-routing.md).

**Рука бандита = `(model_id, effort) × task_class`.** Класс — закрытый
детерминированный enum `intent × scope` (7 × 4 = 28), а кластер по эмбеддингу
работает признаком похожести, но не ключом приоров: общие приоры команды
требуют стабильного ключа, а кластеры нестабильны между репозиториями и
версиями эмбеддера.

**Томпсон-семплинг** с полом принудительного исследования 5 % и потолком 15 %.
Пол — защита от петли невыбора: модель, которую перестали выбирать, иначе
никогда не наберёт статистики и останется плохой навсегда. Потолок — ограничение
счёта за исследование. UCB отвергнут отдельно: он детерминирован, и при общем
пуле все клиенты синхронно бьют в одну руку.

**Три уровня приоров** — global (зашит в бинарь) → team (сервер) → local
(репозиторий), со сжатием по псевдо-счётчикам. Один общий пул отвергнут:
одна шумная репозитория отравляет всех.

**Отложенные сигналы решены материализацией, а не компенсацией.** Сигналы —
append-only таблица, апостериор пересчитывается из них целиком в фоне. Реверт
через неделю просто добавляет строку; «отменять» прошлое обновление не нужно,
и всё остаётся аудируемым.

Два вывода, меняющих продукт:

- **Каскад «сначала дёшево, при провале дорого» почти никогда не окупается без
  автоверификации** — порог `p_A > 0.93` при разнице качества 0.2. Без тестов
  эскалация дороже прямого запуска сильной модели.
- **Пропенсити логируется на каждое решение.** Без этого офлайн-оценка экономии
  нечестна: роутер сам решает, кому какие задачи, и получается confounding.
  Онлайн — контрольная группа.

**Приватность по построению:** в общий пул уходят только enum-признаки, бакеты,
солёные хеши и суммы достаточных статистик — не попытки и не контент.
Список запрещённого явный и проверяется схемой на сервере.

## 10. Разрешение стыков

Лейны проектировались параллельно и оставили 40 вопросов на границах. Ниже —
координаторские решения; они имеют приоритет над допущениями внутри лейн-документов.

| # | Стык | Решение |
|---|---|---|
| S1 | Формат ID (L1 ↔ L3) | Канон L1: `<slug>-` + 12 Crockford base32. Префикс — slug воркспейса (по умолчанию `myc`), задаётся в `init`. CLI **печатает кратчайший однозначный префикс с полом в 4 символа**, пересчитывая длину на каждую выдачу, как git. Ни один лейн этого не покрывал: L1 отвечал за разбор ввода, L3 — за примеры вывода |
| S2 | Дотовый путь | Вычисляемый ярлык, не хранится. Хранимый ординал потребовал бы централизованного аллокатора, то есть сети в пути записи — прямое нарушение И1 |
| S3 | `oplog.seq` (L1 → L2, L3) | Да, монотонный целочисленный на воркспейс, доступен как `myc_meta.last_seq`. HLC служит разрешению конфликтов, `seq` — локальному порядку. На нём висят инвалидация кешей, `Last-Event-ID` в SSE и `sync --since` |
| S4 | `digest_cache` vs `prime_cache` | Одна таблица `digest_cache(scope, profile, seq, payload)`. `prime` — это `profile='prime'`. Владелец — L2 |
| S5 | Короткий текст узла для сборки выдачи | Новая колонка `nodes.excerpt` (≤ 300 символов, детерминированно из `body` при записи). Отдельно от `anchors.crux_text` — это разные вещи, и одноимённость их бы склеила |

Ленивость платит именно на путях, не исполняющих команду; на `myc show` выигрыш в пределах шума (−0.8 мс), на `--help` она дороже статики на 1.5 мс — за это платит не горячий путь. Сторож `register.test.ts` (S62) остался зелёным и усилен: имя из таблицы обязано совпасть с именем загруженной команды (иначе `myc <имя>` уехал бы на чужой обработчик молча), и в реестре не должно быть команд, которых не производит ни один модуль. (3) `cold_start` сравнивается с линией по **p50**, а не по p95: он единственный меряется спавном процесса и всего 25 раз, и на неизменном бинаре три прогона дали p50 24.07/23.97/25.23 при p95 27.27/31.36/30.99 и p99 29.71/38.49/53.98 — p95 на 25 замерах есть 24-й элемент, то есть один сосед по CPU. Бюджет И1 (p99 < 60 мс) по-прежнему проверяется по p99, хвост не теряется. В базовую линию теперь пишутся `load1` и `cpus`: число без условий замера невоспроизводимо. **Базовая линия не сдвинута** — после (1) и (2) она выполняется: p50 20.10 против 18.23 (+10.3 % при пороге 15 %) на машине, загруженной вдвое сильнее, чем при её снятии |
| S64 | **Комментарий — это один вид узла: `kind='note'`, `layer=1`, `attrs.type='comment'`; нить определяется РЕБРОМ `replies_to`, а не видом** | Три поверхности разошлись независимо и молча (memory-1nh192mztcqy). ИЗМЕРЕНО на рабочей базе 2026-09-07: в нитях 15 реплик — **9** `note` + `attrs.type='comment'` (их писали агенты через MCP `addNote`) и **6** `message` (их писал `myc msg --reply-to`, добавленный днём раньше). `myc show` читал нить по ребру и видел все; веб фильтровал по `kind='message'` (packages/web/src/card.ts) и показывал **ноль из девяти**. Вид выбран `note`, и довод не в имени, а в **контракте слоя** (01-core-data-model.md §2.3, §5.1): `message` — это **L0**, сырой диалог сессии. По проекту тело L0 через **14 суток** уезжает в `bodies_cold`, а его FTS-строки удаляются; в векторный индекс L0 не попадает вовсе; обязательные `attrs` у `message` — `session_id`/`role`/`ord`/`thread_root`, которых у комментария к задаче нет (`messageInput` их и требует); статус допустим ровно один — `active`. Комментарий к задаче — **постоянная история проекта**: 156 комментариев cherry старше двух недель уже в момент ввоза, и их ищут через полгода. `note` L1 хранится бессрочно, индексируется и ищется. **Форму задаёт ОДНА функция ядра** `commentInput` (packages/core/src/memory.ts): её зовут все три писателя — `mcp addNote`, `myc comment`, `import-beads`, — и разойтись им больше нечем. **Миграции нет и не нужно**: девять накопленных узлов уже канонического вида. Шесть `message` остаются как есть — `kind` неизменяем по §2.2, пересоздание стоило бы им id и рёбер, а читаются они и так: читатель идёт по ребру. Повторение перекрыто ограждением: `myc msg --reply-to` на узел, который не `message`/`session`, даёт WARN `comment.kind_wrong` с именем правильной команды. **Читателям запрещён фильтр по виду**: тест смешанной нити держит это числом — 3 реплики по ребру против 1 из 3 по `kind='message'` и 2 из 3 по `kind='note'`; на однородной нити такой тест прошёл бы и на сломанном фильтре |

## 11. Где мы осознанно расходимся с источниками

| Источник | Он делает | Мы делаем | Почему |
|---|---|---|---|
| beads | хранимый иерархический ID | вычисляемый ярлык | хранимый безопасен только под cell-merge Dolt'а |
| beads | Dolt как движок | SQLite/Postgres + оплог на HLC | отдельный движок БД — слишком дорогая зависимость для утилиты в горячем пути |
| memora | тихий фолбэк на TF-IDF | громкая деградация в строке узла | молчаливая порча базы хуже отказа |
| memora | «contradiction» без ребра | 11-й тип ребра `contradicts` | иначе классу absorb некуда писаться |
| memora | 43 MCP-инструмента всегда | 7 / 11 / 16 по профилю | описания инструментов — постоянный налог на каждую сессию |
| TencentDB | proxy как основной путь интеграции | proxy выключен по умолчанию | через него течёт весь трафик; и инъекция ломает prompt caching, если делать её наивно |
| socraticode | Qdrant как зависимость | вектор внутри SQLite/Postgres | лишний сервис в пути установки |
| socraticode | файловые локи для мультипроцессности | монотонный `oplog.seq` | дешевле и без мусора при падении процесса |
| graft | свой код-граф | якоря + адаптер | чужая решённая задача |

## 12. Дорожная карта

| Веха | Содержание | Критерий готовности |
|---|---|---|
| **M0** Ядро и задачи | оплог, граф, SQLite, задачи, `ready`, атомарный claim, CLI, MCP-профиль `agent` | myc полностью заменяет beads в реальном проекте |
| **M1** Память | `remember`, absorb (детерминированная ступень), FTS-поиск, `prime`, хук `PreCompact` | сессия агента переживает компакт без потери решений |
| **M2** Семантика | локальные ONNX-эмбеддинги, гибридный ретривал, RRF, `digest` | поиск по смыслу укладывается в 25 мс на 100k узлов |
| **M3** Код | якоря, трёхуровневый детект протухания, адаптер graft | «покажи решения про этот символ» работает в обе стороны |
| **M4** Команда | сервер, Postgres, воркспейсы, ACL, контейнеры, веб-визуализация | два человека и четыре агента на общей базе |
| **M5** Рой | телеметрия попыток, приоры, `myc route`, git-хуки исходов | офлайн-оценка на пропенсити показывает экономию против фиксированной модели |
| **M6** Дистилляция | подъём L1→L2→L3, skills, proxy-режим | `prime` даёт полезный контекст проекта без ручной работы |

M0–M2 — самостоятельно полезный продукт. Всё после M3 имеет смысл, только если
M0–M2 действительно быстрые: бюджеты §3 брифа проверяются в CI, и их нарушение
ломает сборку.

## 13. Риски

| Риск | Почему серьёзен | Ответ в дизайне |
|---|---|---|
| Раздувание охвата | четыре подсистемы в одном продукте — классический способ не выпустить ничего | M0–M2 полезны сами по себе, остальное за флагом |
| Бюджеты не выдержаны | если myc медленнее grep, агенты перестанут его звать | бюджеты в CI, регрессия p95 > 15 % ломает сборку |
| Память деградирует незаметно | база выглядит здоровой, но полна мусора | И2: деградация в поле строки узла, а не только в `doctor` |
| Рой учится на шуме | мало данных, отложенные и косвенные сигналы | иерархические приоры, пропенсити, контрольная группа, забывание с полураспадом 60 суток |
| Сигналы исхода отсутствуют | без git-хуков рой слепнет | состояние сигналов — часть `doctor`, отсутствие видно, а не молчит |
| Дублирование graft | соблазн «доделать своё» | И3 и правило неудвоения MCP-инструментов |
| Утечка через L0 | транскрипты содержат чужие секреты | редакция на записи, `private` по умолчанию, ретеншн 14 суток |

## 14. Решения, которые нужны от заказчика

Три вопроса, где выбор продуктовый, а не инженерный. Дизайн собран под
рекомендованный вариант и работает при любом из них.

| Вопрос | Варианты | Рекомендация |
|---|---|---|
| **Контрольная группа роутера.** Чтобы доказать, что роутинг экономит деньги, часть задач должна идти мимо него | 10 % постоянно · 10 % первые 90 дней, затем 3 % · только на пилоте | 10 % первые 90 дней после `init`, затем 3 %. Это осознанная плата за доказуемость: без контроля любое «стало дешевле» объясняется тем, что роутер сам выбирал себе задачи полегче |
| **`effort` в ключе руки бандита.** Уровень усилий — часть ключа или поправка к нему | в ключе (504 руки, точнее при больших данных) · поправкой (168 рук, учится втрое быстрее) | Начать с 504 и через 30 дней пилота измерить долю рук со слабой статистикой. Если она велика — схлопнуть в поправку; обратный переход дешевле прямого |
| **Автозахват L0.** Пишем ли весь диалог агента автоматически или только явно | автоматически · только явно (`myc session`, хук `PreCompact`) | Только явно. Автозахват всего диалога — это транскрипты с чужими секретами и чужим кодом на диске рядом с git; редакция секретов снижает риск, но не отменяет его. Хук `PreCompact` и так ловит главный момент потери контекста |
