# memory-2shvpjay4nx6 — `myc init --global --force` больше не сносит ~/.myc

## Что было

`packages/cli/src/commands/init.ts`, ветка `--global`:

```ts
if (force && existsSync(status.dir)) rmSync(status.dir, { recursive: true, force: true });
```

Одна строка сносила личный ярус целиком: базу с оплогом, её журнал и всё
остальное, что лежит под `~/.myc` — включая установленный бинарь
`~/.myc/bin/myc`, который `wire.ts` прописывает в хуки всех репозиториев.

## Что восстановимо в личном ярусе, а что нет

Проектный `--force` отличает одно от другого по git: `.myc/graph` и
`workspace.toml` коммитятся, поэтому стёртое возвращается из репозитория
(`FORCE_KEEP`). У личного яруса такого признака нет вовсе — он не коммитится
никуда, и «восстановимо» здесь значит ровно одно: **пересчитывается из оплога,
который остаётся на месте**.

| Что | Класс | Почему |
|---|---|---|
| `projections/`, `state.json`, `bootstrap.cache.json` | восстановимо | кеш; S42 — в git только оплог, проекции пересобираются |
| `myc.db` | НЕУСТРАНИМО | оплог личной памяти; в git его нет ни у кого |
| `myc.db-wal`, `-shm`, `-journal` | НЕУСТРАНИМО | в `-wal` лежат зафиксированные, но не слитые транзакции: снести журнал отдельно от базы = потерять последние записи, оставить журнал без базы = ловушка для следующего открытия |
| `graph/` | НЕУСТРАНИМО | выгрузка оплога, если её сделали руками |
| всё прочее (`bin/`, чужие файлы) | не наше | не стираем |

Отсюда **умолчание для неизвестного файла обратное проектному**. В репозитории
`--force` стирает всё, кроме перечисленного: чего myc не знает, то либо в git,
либо создастся заново. Под `~/.myc` стирается ТОЛЬКО перечисленное: у файла
здесь нет ни одного источника, из которого он вернётся, и «я его не знаю» —
не основание его убить.

Мера потери — строки **оплога**, а не узлы: узлы это проекция (S42).
Считаются оба числа, в сообщение идут оба.

## Как выглядит явное подтверждение без терминала

Флаг `--wipe-memory`, а не вопрос в stdin. Агент запускает команды без
терминала — вопрос, которого некому увидеть, превращается в вечное ожидание,
а `yes | myc ...` превращает подтверждение в декорацию. Флаг же виден в
истории команд, в логе агента и в code review.

`--wipe-memory` без `--force` — ошибка (`usage`, exit 2): разрешение без
действия почти наверняка опечатка в разрушительной команде, и додумывать за
человека `--force` нельзя именно здесь.

## Что делать, если пользователь ВСЁ РАВНО хочет снести

Отказ без выхода — тупик, поэтому в отказе три вещи: что стоит на пути (путь и
цифры), почему это не вернуть (нет git) и как всё-таки сделать задуманное:

```
$ myc init --global --force
myc: precond.personal_memory: /home/u/.myc: 1 узел, 10 операций оплога. Личный ярус
не коммитится в git — восстановить его будет неоткуда, поэтому --force стирает здесь
только восстановимое и на память не распространяется
  hint: сначала копия: cp -R /home/u/.myc /home/u/.myc.bak · стереть насовсем:
        myc init --global --force --wipe-memory
```

exit 5 (`precond`), `--json` даёт тот же `error.code` — агент ветвится кодом, а
не разбором текста. Про `--wipe-memory` человек узнаёт и раньше отказа: строка
идемпотентного `myc init --global` теперь говорит «память переживёт; стереть и
её — добавить `--wipe-memory`» вместо прежнего неверного «удалит данные».

Разрушительный путь честный: стирает по-настоящему (копии внутри не остаётся),
но говорит, чего это стоило: `! память стёрта 1 узел, 10 операций оплога —
восстановить неоткуда, копии не осталось`.

## Правила по классам

| Случай | Поведение |
|---|---|
| `--force`, в ярусе есть память | ОТКАЗ, exit 5, на диске **ничего** не изменено (кеши тоже) |
| `--force`, база нечитаема | ОТКАЗ: чего не смогли прочесть, того не знаем — стирать по незнанию нельзя |
| `--force`, ярус пуст (0 узлов, 0 операций) | как раньше: пересоздаёт |
| `--force --wipe-memory` | стирает базу, журнал, `graph/` и кеши; чужое (`bin/`) не трогает |
| `--wipe-memory` без `--force` | usage, exit 2 |

Решение принимается ДО первой записи на диск. Полумера «кеши стёр, базу не
тронул, вышел с ошибкой» оставила бы человека гадать, что с ним произошло.

## Мутации — на каждую защиту своя

Мутация вносится, прогоняется весь `packages/cli`, затем откатывается.

| # | Что снимаем | Упало |
|---|---|---|
| M1 | гейт отказа целиком (`if (force && plan.hasMemory && !wipeMemory)`) | **5** |
| M2 | fail-closed на нечитаемой базе (`!counted.readable`) | **1** |
| M3 | `graph/` как память (`graphNotEmpty`) | **1** |
| M4 | `wipePersonalWorkspace` сносит каталог целиком (старое поведение) | **1** |
| M5 | проверка «`--wipe-memory` без `--force`» | **1** |
| M6 | порядок: стереть, а потом решать (запись раньше гейта) | **3** |
| M7 | `-wal`/`-shm`/`-journal` вынесены из класса «память» | **1** |

M1 и M6 — про главное: M1 возвращает исходную дыру, M6 доказывает, что тест
«при отказе на диске ничего не изменилось» проверяет факт, а не код возврата
(при мутации отказ остаётся, но кеш уже снесён — и тест падает).
M7 сначала ВЫЖИЛ (0 падений) — пришлось дописать тест про осиротевший `-wal`.

Проверка «ничего не изменилось» — слепок SHA-256 каждого файла каталога, а не
байты одного `myc.db`: свежие записи живут в `-wal` до чекпойнта, и сравнение
одной базы прошло бы даже там, где память успели потерять.

## Что проверено живьём

Настоящий CLI (`bun run packages/cli/src/main.ts`), подставной `MYC_HOME`,
свой `~/.myc` не трогался (его на этой машине и нет — проверено `ls` после).

1. `init --global` + `remember --global "…"` → `nodes=1 ops=10`.
2. `init --global --force` → **exit 5**, отказ с цифрами и подсказкой.
   `myc.db` и `myc.db-wal` побайтно те же (SHA-256 совпал). Изменился только
   `myc.db-shm` — это mmap-индекс WAL, его переписывает любое ОТКРЫТИЕ базы
   на чтение (в т.ч. обычный `myc init --global`), данных в нём нет.
3. `init --global --wipe-memory` (без force) → **exit 2**.
4. `init --global --force --json` → `error.code=precond.personal_memory`, exit 5.
5. `cp -R ~/.myc ~/.myc.bak` по подсказке, затем
   `init --global --force --wipe-memory` → **exit 0**, `nodes=0 ops=0`,
   `bin/myc` цел и исполняем, в выводе `не тронуто bin`.
6. Восстановление из копии → `nodes=1 ops=10`, заголовок узла на месте:
   подсказанный путь действительно работает, а не только упомянут.

## Что осталось нерешённым

- **`myc export`/`import` не умеют `--global`.** Честная копия личного яруса
  сегодня — только `cp -R`, и именно её советует подсказка. Оплог-выгрузка
  для личного яруса (`myc export --global`) дала бы и текстовый бэкап, и
  восстановление в ту же базу; отдельная задача, за границей этой.
- **`myc.db-shm` переписывается при каждом чтении.** На отказ это не влияет
  (данных в нём нет), но формально «на диске ничего не изменилось» верно про
  файлы с данными, а не про mmap-индекс. Убрать это можно только отказавшись
  считать узлы для сообщения — цена выше пользы.
- **Проектный `--force` остался с прежним умолчанием** («стираю всё, кроме
  перечисленного»). Для репозитория это обосновано git, но неизвестный файл в
  `.myc/`, которого нет в git, он по-прежнему снесёт молча. Не трогал: за
  границей задачи.
- **`bd`/`myc doctor` не проверяют наличие копии личного яруса.** Напоминание
  «сделай бэкап» живёт только в подсказке отказа.
