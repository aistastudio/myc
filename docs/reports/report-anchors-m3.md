# Якоря код↔знание: `myc anchor`, хук post-edit, трёхуровневый детект

Связка задач memory-3afmdwe7bwyp (таблица anchors и запрос по file:line),
memory-rw885z6nvatt (хук post-edit) и memory-ehmatz79210p (детект протухания).

## Что сделано

**Движок был, входа не было** — подтвердилось. `packages/code-intel` (3652 строки)
уже умел `listDefs`/`classifyCode`/`findBlockEnd`, таблица `anchors` уже стояла в
схеме со всеми колонками (`file_hash`, `span_hash`, `crux`, `crux_norm`, `state`,
`drift`, `mtime_ms`, `size_bytes`), индекс `ix_anchors_file` уже был. Не хватало
ровно команды. Схему я не трогал, миграций не добавлял.

### 1. `packages/code-intel/src/anchors.ts` — движок якорей (новый файл)

* `bindAnchor` — что якорь запоминает: спан, wyhash файла, хеш нормализованного
  спана, сырой crux (≤24 строк / ≤400 символов, для человека) и `crux_norm`
  (ключ поиска).
* `normalizeStream` — нормализованный ПОТОК файла: без комментариев, без
  содержимого строковых литералов, без переносов строк, плюс отображение
  символ → номер строки.
* `checkAnchor` — лестница §7.2 целиком, с параметром `maxLevel` для мутаций.
* `findNormalized` — поиск переехавшего спана, из дублей выбирается ближайший.

### 2. `packages/cli/src/commands/anchor.ts` — команда (новый файл)

`add`, `rm`, `of`, `check`, `touch`. Модель данных — та, что УЖЕ читает очередь:
якорь это отдельный узел `kind='anchor'`, строка в `anchors` с его id и ребро
`touches` от задачи к нему (ровно так его читает `ready`, ANCHOR_SUBQ).

### 3. `packages/cli/src/commands/wsfind.ts` — поиск воркспейса (новый файл)

Четыре функции вынесены из `store.ts` и ре-экспортируются оттуда: хуку нужен
подъём к `.myc`, а не граф модулей @myc/core + bun:sqlite.

### 4. `packages/cli/src/commands/attempt.ts` — починен `anchorPathsOf`

Стояло `WHERE anchors.node_id = <id задачи>`. Якорь — отдельный узел, поэтому
выборка не находила НИ ОДНОГО привязанного якоря, и `scope` класса задачи
оставался `unknown` у всех задач разом. Теперь запрос идёт через ребро `touches`.

## Цена хука — числом

**Собственная работа команды: p50 0.176 мс, p95 0.217, p99 0.252, max 2.547 мс.**
500 настоящих процессов собранного бинаря `dist/myc`, число печатает сама команда
(`--json`, `data.took_ms`). Бюджет задачи 2 мс, бюджет записи И1 5 мс — уложено
и по p99, и по одиночному худшему случаю.

Разложение полного процесса (чередующийся A/B, 400 троек, собранный бинарь):

| | p50 | p99 |
|---|---|---|
| `myc --version` — пол любого запуска | 19.8 мс | 25.0 мс |
| `myc anchor touch` без пути | 26.5 мс | 32.8 мс |
| `myc anchor touch <файл>` | 26.4 мс | 34.1 мс |

Полезная работа = 26.42 − 26.45 ≈ **0 мс на фоне запуска процесса**. Всё, что myc
может здесь потратить, он уже не тратит.

**Почему не база.** Замер в одном процессе, 500 вызовов подряд:

| | p50 | p99 | max |
|---|---|---|---|
| открыть базу + `jobs.enqueue` + закрыть | 1.045 мс | 19.511 мс | 37.219 мс |
| `appendFileSync` в журнал | 0.023 мс | 0.123 мс | 12.702 мс |

p99 первого — 19.5 мс, вчетверо больше ВСЕГО бюджета записи. Тратит не вставка
(0.03 мс), а открытие соединения (WAL, PRAGMA, схема) в процессе, живущем одну
строчку, плюс писательский замок в очередь к absorb и эмбеддеру.

Журнал `.myc/anchor-dirty.log` — не вторая очередь: у него один потребитель
(`anchor check`), он не хранит состояния и не знает ни аренды, ни приоритетов.
Потеряв его целиком, система теряет очерёдность и ничего больше — `check` и без
него обходит якоря по `checked_at`.

Побочно замерено: статический против динамического импорта `store.ts` внутри
`anchor.ts` в собранном байткод-бинаре — всего **0.36 мс**. Импорты всё равно
оставлены внутри обработчиков (правило дешёвое), но приписывать им экономию
нельзя, и в шапке файла это записано.

## Протухание — проверено настоящим рефакторингом

Подделки mtime нет ни в одном тесте. Файл реально переформатируется, реально
уезжает вниз и реально переписывается.

| что сделали с файлом | состояние | уровень | спан |
|---|---|---|---|
| ничего | fresh | 1 | 4-9 |
| перезаписали тем же текстом (mtime новый) | fresh | 2 | 4-9 |
| переформатировали: отступ 4, сигнатура на 5 строк, висячая запятая, комментарии | **fresh** | 3 | 4-9 → 5-10 |
| над функцией добавили 40 строк кода | **fresh** | 3 | 5-10 → 46-51 |
| правка в другом конце файла | fresh | 3 | 4-9, moved=false |
| тело переписано целиком | **stale** | 3 | 4-9 |
| файла нет | stale | 0 | — |

Главное открытие: **построчная нормализация не переживает настоящее
переформатирование**. Первая реализация сравнивала строку со строкой и объявила
якорь протухшим на файле, где не изменилась ни одна инструкция — prettier
разносит одну сигнатуру на пять строк. Работает поток без переносов: пробел
выживает только между двумя словесными символами (`const x` остаётся `const x`,
`f( a , b )` сводится к `f(a,b)`), на стыке строк пробел ставится (иначе
ASI-перенос `return\n x` склеился бы в `returnx`), висячая запятая перед
закрывающей скобкой снимается.

`drifted` не ставится нигде: он означает «нашли в другом месте с известным
сходством», а меру сходства считает нечёткая ре-привязка (memory-5c03r9t5n472).
Ставить его без числа значило бы врать числом. Колонка `anchors.fp` этим модулем
не заполняется по той же причине.

## Тесты и мутации

Здоровое дерево: **97 pass / 0 fail** в `packages/code-intel`,
**739 pass / 0 fail** в `packages/cli`. Три файла якорей — **49 pass / 0 fail**.

Мутации прогонялись по этим трём файлам (здоровый прогон 49/0):

| мутация | упало |
|---|---|
| 1. детект по содержимому снят (уровень 3 не выполняется) | **5** |
| 2. уровень 1 снят (mtime+size не сверяются, файл читается всегда) | **2** |
| 3. нормализация не съедает висячую запятую и переносы строк | **5** |
| 4. хук открывает базу и ставит работу в jobs вместо журнала | **5** |
| 5. запрос `of` теряет `ix_anchors_file` | **2** |
| 6. `anchorPathsOf` снова читает `anchors` по `node_id` задачи | **2** |

Мутация 1 — обязательная по заданию: якорь начинает врать в обе стороны.
Переформатирование объявляется протуханием, а переехавший на 41 строку код
теряется молча — спан остаётся на 4-9, где теперь лежит чужой `pad3`. Обе
половины проверяются отдельными тестами.

Мутация 5 с первого прогона дала **0 упавших** — тест мерил СВОЮ копию SQL.
Исправлено: запрос импортируется из команды, после чего мутация ловится.
