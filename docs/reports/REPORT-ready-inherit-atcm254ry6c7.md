# `ready` наследует блокеры вниз по `parent` — решение, цена, сверка

Задача: **memory-atcm254ry6c7**. Замеры и сверки — 2026-09-08, macOS 14 ядер.

---

## 1. Решение: НАСЛЕДОВАТЬ, и материализованно

`ready` = `open_blockers = 0 AND anc_blockers = 0`, где `anc_blockers` —
число предков узла по `parent`, держащих открытый блокер. Счётчик ведут
триггеры в той же базе, что и `open_blockers`. Обход предков на выдаче
отвергнут — измеренно, см. §3.

### Почему наследовать — довод не про совместимость с beads

Совпадение с `bd ready` тут следствие, а не цель. Решающее — **что именно
делал блокер на эпике при старом правиле**. Числа со снимка `~/src/cherry`
(796 задач, 972 зависимости):

| | |
|---|---|
| рёбер `blocks` всего | 558 |
| из них нацелены в узел, **у которого есть дети** | 12 |
| из этих 12 блокер ещё открыт | 12 |
| различных «виновных» предков | 11 |
| из них **контейнеров** (есть дети) | **11** |
| из них листьев (есть своя работа) | **0** |

Все 11 — `issue_type = epic`, вехи M2–M5. У контейнера собственной работы нет.
Значит при старом правиле блокер на эпике убирал из очереди **ровно один узел,
который работой не является**, а все его дети выдавались как готовые. Блокер,
не блокирующий ничего, — это неверное определение очереди, а не вопрос вкуса.

Хуже того, часть таких блокеров — **порядок внутри вехи**: `cherry-zgak.2`
(«M5/D — Делегированный API») заблокирована `cherry-zgak.1` («M5/O — OIDC-ядро»).
Старое правило предлагало агенту делать часть D, пока не сделана часть A.
Человек посмотрит вокруг и заметит; агент, разбирающий очередь, — нет.

Довод против («наследование прячет 51 задачу из 195, 26 % очереди») принят и
взвешен: это ровно те задачи, которые собственный трекер заказчика не считал
готовыми всё это время. Очередь не пустеет — остаётся 144.

### Краевой случай, который решён явно

Правило: «предок держит открытый блокер», **без** условия на статус самого
предка. Причина — простота инварианта: счётчик тогда зависит ровно от двух
событий (`open_blockers` предка пересёк ноль; изменилось `parent_closure`), и
третьей пары триггеров на смену статуса предка не нужно. На данных cherry оба
варианта дают одно и то же: закрытых узлов с открытым блокером — 2, открытых
потомков у них — 0, и правило «предок обязан быть открыт» даёт те же 144.

## 3. Цена: числа до и после

### Чтение очереди — наследование не стоит НИЧЕГО

Стенд `ready.inherit-latency.test.ts`: 100 000 узлов, 4 000 открытых задач,
400 эпиков по 9 детей, 40 эпиков заблокировано. Две схемы (9 и 10) с
идентичными данными, меряются **чередуясь в одном процессе**.

| вариант | p50 | задач в очереди |
|---|---|---|
| прежнее правило, наследования нет (схема 9) | **8.78 мс** | 3 960 |
| наследование СЧЁТЧИКОМ (схема 10) | **8.04 мс** ×0.92 | 3 600 |
| наследование ОБХОДОМ по `parent_closure` | **12.71 мс** ×1.57 | 3 600 |

Счётчик дешевле прежнего правила: 360 скрытых задач не доходят до скоринга.

Соперник взят **честный**: прежняя схема со своим `ix_nodes_ready`, поверх
которого `NOT EXISTS (… parent_closure …)`. «Обход без индекса» даёт 26 мс, но
так альтернативу никто бы и не писал, и мерить её было бы чучелом.

Обход стоит **+32 % и +4.6 мс** — почти весь бюджет И1 (5 мс) целиком, потому
что `NOT EXISTS` считается для КАЖДОГО кандидата до `LIMIT`: очередь считает
score всем и режет top-k уже после сортировки. Цена обхода растёт вместе с
очередью, цена счётчика — нет. На узкой выдаче (фильтр репозитория S59, ~1/17
очереди) обход стоит ×1.33 (0.85 против 0.64 мс) — тоже не бесплатно.

### Бюджетный тест И1 не сдвинулся

`ready.repo-latency.test.ts` (тот самый, на который ссылается задача):

| | до (записано в тесте) | после (два прогона подряд) |
|---|---|---|
| p50 | 1.21–1.37 мс | 1.52 / 1.54 мс |
| p99 | 1.33–1.65 мс | 1.87 / 1.88 мс |
| отношение к сопернику | ×3.80 / ×3.87 / ×3.89 | **×3.83 / ×3.88** |

Абсолютные числа выросли вместе с загрузкой машины (load1 5.3–5.5 против
свободной при записи эталона), **отношение не изменилось вовсе** — именно оно
и есть проверка, переживающая нагрузку (методика @myc/bench). План запроса
прежний: `SEARCH nodes USING INDEX ix_nodes_ready_repo`, скана таблицы нет.

### Запись — вот где материализация платит

Блокировка эпика раскладывает ±1 по всему поддереву одним `UPDATE` по
`ix_pc_desc`:

| потомков у эпика | `addEdge(blocks)` p50 |
|---|---|
| 0 (лист) | 0.098 мс |
| 10 | 0.119 мс |
| 100 | 0.28–0.31 мс |
| 1 000 | 1.96–2.13 мс |
| 5 000 | **9.37 мс — мимо бюджета записи 5 мс** |

Цена линейна (×6.8 при росте поддерева в 10 раз; квадратичная дала бы ×70) —
это утверждает тест. Порог 5 000 — тот же, на котором design doc §риск 14 уже
предписывает уводить работу с `parent_closure` в `jobs`; в коде этого выноса
нет до сих пор, поэтому `addEdge(parent)` на широком дереве стоит столько же
уже сегодня. Заведена задача **memory-sj70gctz88y1** — решить одним решением
для обоих.

## 4. Граница воркспейса

`parent_closure` живёт внутри одной базы — как и `open_blockers`. Предок из
чужого воркспейса не наследуется никак (тест: строка замыкания без узла даёт
`anc_blockers = 0`, а не «предок заблокирован»).

Но появилась новая дыра, и она закрыта: **`parent` перестал быть ребром,
которому можно пересекать границу**. Узел, уехавший из-под заблокированного
эпика, в приёмнике насчитал бы ноль и встал бы в очередь готовым — тот же
класс молчаливой лжи, что и `cross_boundary` для `blocks`. `planMove` теперь
отказывает кодом `cross_boundary_parent`, и `--with-blockers` эту защиту не
снимает (утащить сам эпик значило бы разорвать наследование у ОСТАВШИХСЯ его
детей). Докстрока `packages/core/src/move.ts`, утверждавшая обратное,
исправлена. Тест «ВРЕД, который снимает эта защита» показывает состояние,
которого отказ не даёт создать.

## 5. Мутации — каждая с числом

| мутация | что ломается |
|---|---|
| терм `anc_blockers = 0` убран из очереди | очередь снова предлагает обе подзадачи заблокированного эпика: `readyIdsWithoutInheritance().length − readyIds().length === 2` |
| `DROP TRIGGER trg_anc_block` | счётчик остаётся нулём, `ancBlockersDrift()` даёт **2** узла с `actual = 1`, очередь = 3 задачи вместо 1 |
| жёсткий `DELETE` ребра `blocks` (триггерами не покрыт by design) | `ancBlockersDrift()` = 1, `recountOpenBlockers()` возвращает **2** и чинит оба счётчика |
| «actual» в `anc_blockers_drift` читался бы из `nodes.open_blockers` предка | разъехавшийся `open_blockers` маскировал бы разъехавшийся `anc_blockers` — поэтому сверка идёт с ГРАФОМ, не с соседним счётчиком |
| 400 случайных мутаций (parent/blocks/статусы, с отказами по циклам) | оба счётчика сходятся с пересчётом, минимум ≥ 0 |
| `--with-blockers` как способ обойти `cross_boundary_parent` | отказ остаётся (тест) |
| наследование считается обходом вместо счётчика | ×1.57 медленнее, +4.6 мс (тест роняет при отношении < 1.2) |
| раскладка счётчика стала бы квадратичной | ×6.8 → ×70, тест роняет при > 20 |

## 6. Что произойдёт с ЭТИМ проектом

**Ничего не изменится в выдаче.** На живой базе `~/src/memory` (361 узел,
139 строк `parent_closure`):

```
ready сейчас                                50
ушло бы наследованием                        0
```

Ни у одной открытой задачи нет предка с открытым блокером. Миграция нужна
техническая, не смысловая.

**Миграция автоматическая и forward-only.** Схема 10 добавляет колонку,
заполняет её из `parent_closure` при накате (без этого шага старые базы
получили бы нули и наследование включилось бы только для будущих изменений),
пересоздаёт два ready-индекса и заводит четыре триггера. Накат идёт при первом
открытии базы на запись.

**Одно предупреждение:** база сейчас на схеме 9, а глобально установленный
`myc` 0.1.0 знает миграции до 9. После наката схемы 10 старый бинарь на ту же
базу ответит `schema.newer` (это штатный контракт, а не поломка) — то есть
обновление бинаря и наката схемы должны приехать вместе.

утверждают. На данных cherry расхождение было бы 195 против 144.

раньше (только свои блокеры); наследованное число называет подвал `myc ready`.
Если нужно — свести в отдельной задаче.
