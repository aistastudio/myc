# myc-nxtnbwpjqfhw — очередь фоновых работ `jobs`

Решение S7: одна таблица `jobs` с арендой и классами приоритета; демона нет
(S8), поэтому все инварианты обязаны держаться **между процессами**. Числа ниже
замерены, а не рассчитаны.

## API

```ts
enqueue(db, kind, { entityId, scope, priority, runAfter, payload, maxAttempts, now })
  → { id, inserted, row }         // идемпотентно по ux_jobs_dedup, когда есть entityId
claim(db, kinds[], holder, { leaseMs, limit, now }) → JobRow[]   // атомарно, под аренду
complete(db, id, holder?) → boolean          // снимает строку; holder ограждает от зомби
fail(db, id, error, { holder, now }) → { attempts, maxAttempts, dead, runAfter }
sweep(db, nowMs) → { released, dead, ids }   // брошенные аренды обратно в очередь
stats(db, nowMs) → { total, waiting, ready, leased, dead, byKind[] }
```

Имена полей — camelCase (соглашение пакета: `WalGuardOptions.hardLimitBytes`),
колонки в возвращаемых строках — как в схеме (`entity_id`, `run_after`).

**Состояния** выражены колонками, отдельного `status` в схеме нет:

| Состояние | Условие |
|---|---|
| ждёт | `attempts < max_attempts`, `lease_expires <= now`, `run_after <= now` |
| отложена | то же, но `run_after > now` (экспоненциальный откат) |
| в аренде | `lease_holder <> ''` и `lease_expires > now` |
| мертва | `attempts >= max_attempts` — терминально, **строка сохраняется** |
| выполнена | строки нет (`complete` удаляет) |

Граница «мертва» выбрана не мной: ровно так `packages/web/src/health.ts:194-204`
считает `jobs.pending`/`jobs.failed`, и так же устроен `enqueueWarmJob` в CLI.
Отдельный тест сверяет `stats()` с дословными запросами health.

**Приоритеты** (S7: эмбеддинги > дистилляция > пересчёт приоров роя), числа
согласованы с уже стоящими в коде: `embed` 3 (`remember.ts`), `absorb`/`distill` 5,
`anchor_check` 6, `compact` 7 (`WAL_JOB_PRIORITY`), `rescore` 9.

**Совместимость с checkpoint.ts.** `enqueueWalCheckpointJob` / `dropWalCheckpointJob` /
`walCheckpointJobPending` продолжают работать: это частный случай той же таблицы
и того же индекса. Тест гоняет их вперемешку с общим API в обе стороны.

## Как держится «убитый процесс не теряет и не дублирует задачу»

1. **Захват — один стейтмент.** `UPDATE ... WHERE id IN (SELECT ...) RETURNING *`.
   Пара «SELECT кандидатов, потом UPDATE» в автокоммите даёт двойную выдачу —
   ровно этот класс дефекта дважды стоил репозиторию молчаливой потери записей
   (S38, S40) и ни разу не был виден однопоточному тесту.
2. **`lease_expires <= now` в предикате.** Единственное, что мешает соседу
   забрать работу, которую кто-то уже делает. Ноль в колонке = «не в аренде»,
   поэтому один предикат покрывает и свободные строки, и брошенные.
3. **Отбор просроченной аренды засчитывается попыткой**
   (`attempts + (lease_holder <> '') < max_attempts`, проверка по значению
   ПОСЛЕ инкремента). Иначе работа, роняющая процесс, каталась бы вечно;
   при `max_attempts = 1` выдача ровно одна.
4. **`fail` не удаляет строку.** Исчерпав попытки, работа перестаёт выдаваться,
   но остаётся с `last_error` — иначе диагностировать нечего, а health
   показывает ноль вместо аварии.
5. **Ограждение арендой** в `complete`/`fail`: зомби, у которого аренду уже
   отобрали, не закроет работу, которую в этот момент делает другой.

Откат после провала: `base * 2^attempts`, база 1 с, потолок 5 мин.
Аренда по умолчанию 60 с.

## Приёмка: настоящие процессы

Оба теста поднимают отдельные процессы `Bun.spawn` против одной базы; события
пишутся в общий журнал через `appendFileSync` (настоящий `write(2)`, переживает
SIGKILL). **Дубли считаются по выдачам, а не по успешным снятиям**: снятие
огорожено арендой и молча вернуло бы `false` у второго исполнителя, то есть
спрятало бы ровно тот дефект, ради которого тест написан.

**Конкурентность — 6 процессов, 300 работ, батч 8:**

```
[concurrency] процессов=6, работ=300; выдач=300, уникальных=300, дублей=0;
              по процессам: w0=48, w1=48, w2=48, w3=52, w4=56, w5=48
```

**Аварийное завершение — SIGKILL посреди аренды:** барьер в два шага (жертва
берёт работу первой, соседи выходят на дорожку, пока её аренда ЖИВА, затем
`kill -9`), иначе тест сам был бы гонкой и сценарий не наступал бы.

```
[crash] работа 1 была в аренде у убитого процесса; подобрана процессом w0
        через 701 мс (аренда 700 мс, kill +4 мс); выдач=41, исполнений=40, работ=40
```

Проверяется: работа исполнена (не потеряна), исполнена **ровно один раз**,
повторная выдача единственная во всём прогоне и произошла **не раньше
`lease_expires`** (а не «через ~аренду» — точка отсчёта сама аренда, журнальная
строка пишется на миллисекунду позже), `attempts` подобранной работы = 1,
очередь пуста, выход жертвы — `signalCode = SIGKILL`.

4 прогона подряд: 28/28, разброс подбора 700–703 мс.

## Мутационное тестирование

Три мутации применялись скриптом к `jobs.ts`, после каждой — полный
`bun test packages/store-sqlite/src/jobs.test.ts`, затем откат.

### Мутация 1 — `claim` без атомарности (SELECT кандидатов, затем UPDATE)

Мутант отличается ТОЛЬКО разъятием стейтмента: предикат и порядок те же, строки,
исчезнувшие между SELECT и UPDATE, молча отбрасываются.

```
error: expect(received).toBe(expected)      // выдач против работ
Expected: 300
Received: 324
(fail) настоящая конкурентность … ровно одна выдача на работу, ноль потерянных

error: expect(received).toHaveLength(expected)   // исполнений против работ
Expected length: 40
Received length: 42
(fail) аварийное завершение (SIGKILL посреди аренды) …

 26 pass, 2 fail    → мутант пойман
```

24 лишние выдачи из 300 и 2 двойных исполнения в crash-тесте.

### Мутация 2 — `claim` без проверки `lease_expires`

```
(fail) захват под аренду > аренда проставлена, второй захват под живой арендой ничего не даёт
       Expected length: 0 / Received length: 1
(fail) захват под аренду > фильтр по видам и limit
       Expected length: 3 / Received length: 5
(fail) настоящая конкурентность …   Expected: 300 / Received: 1252
(fail) аварийное завершение …       Expected length: 40 / Received length: 43

 24 pass, 4 fail    → мутант пойман
```

1252 выдачи на 300 работ: без аренды процессы разбирают одно и то же по кругу.

### Мутация 3 — `fail` удаляет строку вместо инкремента `attempts`

```
(fail) fail НЕ удаляет строку: попытка засчитана, ошибка сохранена, аренда снята
       TypeError: undefined is not an object (evaluating 'row.last_error')
(fail) откат экспоненциальный и с потолком
(fail) исчерпав попытки, работа мертва: не выдаётся, но строка с ошибкой на месте
(fail) fail с чужой арендой не проходит         (ограждение исчезло вместе с предикатом)
(fail) повторная постановка после провала не плодит строк и не теряет ошибку
       Expected: false / Received: true         (дедупликация перестала работать)
(fail) сводка очереди > по видам …              Expected: 7 / Received: 6

 22 pass, 6 fail    → мутант пойман
```

Три мутации из трёх покраснели; чинить тесты не потребовалось.

## План запроса

`EXPLAIN QUERY PLAN` захвата: `SEARCH jobs USING INDEX ix_jobs_pull (kind=?)`
плюс `USE TEMP B-TREE FOR ORDER BY` — сортировка идёт по строкам, уже отобранным
индексом по виду работ, и при очереди в тысячи строк это единицы сотен
микросекунд. Если очередь вырастет до сотен тысяч строк одного вида, это первое
место, куда смотреть.

## Что осталось нерешённым

- **Разгребатели очереди (D28)** — `myc worker`, idle-время MCP-процесса, хвост
  CLI-команд с бюджетом 50 мс. Это отдельная задача; здесь только механизм.
- **Возврат мёртвой работы в строй.** Сейчас снять `attempts >= max_attempts`
  можно только руками (UPDATE). Для `myc doctor --retry-dead` нужна функция —
  не делал, в задаче её нет.
- **`stats()` не показывает возраст** самой старой ждущей работы; для R4
  («очередь стоит месяцами») это пригодится, но нужен явный потребитель.
- **Продление аренды** (`renew`) для долгих работ не сделано: длинная работа
  обязана просить длинную аренду сразу. Если появится дистилляция на минуты —
  понадобится.
- Статус задачи в трекере не менял: закрытие за координатором.
