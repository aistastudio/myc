# Отчёт W3 — задачи в интерфейсе (memory-snm42rbgehmm)

## Что сделано

Полный цикл работы человека с задачей в просмотрщике: завести, изменить любое
поле, посмотреть карточку со связями, взять в работу с арендой, отпустить,
закрыть с причиной, вернуть, отменить.

**Сервер (`packages/web/src/`):**
- `card.ts` (новый) — `GET /api/nodes/<id>/card`: то же, что печатает `myc show`:
  родитель («входит в»), состав с детьми и прогрессом («состав N из M закрыто»),
  blocked-by/blocks со статусами, links, аренда, видимый тип. Ребро `parent`
  разбирается в ту же сторону, что в show.ts (родитель — по исходящим рёбрам,
  состав — по входящим). Только SELECT.
- `server.ts` — маршрут карточки; POST на `/card` отвечает 404.
- `mutate.ts` — `type` в правке существующего узла отвечает 501
  `unsupported.field` с объяснением зазора движка (ниже). Создание уже несло
  `--kind` в общий движок — не тронуто.
- `db.ts` — исправлен найденный при проверке баг: база в WAL без `-wal/-shm`
  (чистый выход последнего писателя) не открывалась readonly-соединением
  (SQLITE_CANTOPEN на первом prepare), и `loadTables` молча проглатывал это →
  просмотрщик показывал «0 узлов / schema missing» на живом воркспейсе. Теперь
  после открытия идёт пробный запрос; при CANTOPEN соединение пересоздаётся
  читаемым handle-ом с `PRAGMA query_only = 1` (запрет записи держится), а
  если query_only не поддержан — громкий `VizDbError`, не тишина. End-to-end
  проверено на реальном сломанном воркспейсе: до фикса `nodes: 0,
  schema_ready: false`, после — `nodes: 2, schema_ready: true`, карточка
  отдаётся.

**Клиент (`client/app.ts`, css, index.html):**
- Форма «завести задачу» в панели очереди: заголовок, тип (task/bug/epic/chore),
  тело, приоритет («по умолчанию» не отправляется вовсе), теги, оценка,
  исполнитель, «входит в» (id эпика). Тот же `POST /api/nodes`, что у любого
  клиента; пустые поля не отправляются — операция совпадает с командой,
  которую человек ввёл бы в терминале.
- Редактор свойств: добавлены строки заголовка и тела (любое поле из
  `UPDATE_FIELDS` теперь правится); в заголовке панели и в карточке тип
  показывается рядом с видом: «epic (task)» — без иллюзии отдельной сущности.
- Карточка графа: операции полного цикла (claim с выбором аренды
  30m/1h/2h/4h, release, close, reopen, cancel — причины через отдельное
  подтверждение) + связи с сервера карточки: «входит в», «состав N из M
  закрыто, отменено K» с отметками ×/—/·, blocked-by/blocks, links, теги.
  Один и тот же бар операций используется очередью ready и карточкой.

## Приёмка (oplog, не состояние)

`tasks.test.ts` (новый, 7 тестов, движок — настоящий процесс `myc`):
1. bug из интерфейса: оплог = `myc create --kind bug`, состав узла
   `kind='task'`, `attrs.type='bug'`.
2. epic с родителем: оплог = `create --kind epic --parent`; вид task, тип epic.
3. Полный цикл (завести → править title+body → claim → release → close):
   оплог совпадает операция в операцию; claim/close дают 2 lease-записи,
   release виден как `action:"release"`. Нюанс: `closed_at` нормализуется в
   сравнении как «время, а не решение» (как `expires` у W1).
4. Эпик с 4 детьми (2 closed, 1 cancelled, 1 open): `progress = {done: 2,
   cancelled: 1, total: 4}` — отмена НЕ в сделанных; у задачи без детей
   `progress: null`, `parent` заполнен.
5. Карточка показывает аренду (`holder`, `expires`) и блокировки.
6. Смена `type` существующего узла: 501 `unsupported.field`, узел не тронут.
7. Выдуманный `--kind` отвергается движком (400 `usage.invalid`), не UI.

## Нерешённое и найденное (названо прямо)

1. **Смена типа существующего узла невозможна во всём движке**: у `myc update`
   нет флага `--type` (проверено на живом CLI: `unknown flag --type`), в MCP
   тоже. Тип выбирается только при создании. Интерфейс показывает тип везде,
   на попытку смены отвечает 501 с объяснением. Чтобы дать менять тип на
   живом узле, нужен флаг `--type` в `packages/cli/src/commands/tasks.ts` —
   за моей границей. Вывод записан через `myc remember`. Координатору
   отправлялся вопрос (msg_0fbbd435b068) — ответа за 10 минут не пришло,
   реализовано по самому честному из возможных вариантов.
2. **Флакующий тест вне границы**: `packages/cli/src/drain.test.ts:190`
   («бюджет дренажа», `budgetMs: 35` против 5 мс/работа) падает ~1 раз из
   4–6 полных прогонов под нагрузкой. Воспроизводится и без моих изменений
   (drain не трогает web). Координатору — свести с владельцем cli.
3. **Фикс db.ts без юнит-теста**: состояние «WAL-база без сайдкаров» внутри
   bun-процесса воспроизводится недетерминированно (bun лениво держит
   соединения, sidecar-семантика различается между `bun test` и `bun -e`),
   тест, зелёный при обеих реализациях, — плохой тест, поэтому он снят.
   Фикс проверен end-to-end на реальном воркспейсе (см. выше).
4. Пакет `packages/web` не закоммичен в git вообще (`??`), правки поверх
   рабочей копии W1/W2 — коммиты вне моей компетенции.
