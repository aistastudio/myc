# memory-7kk9vpa8x3en — четвёртый блокер импорта cherry: столкновение идентичностей

Дата: 2026-09-07. Данные: снимок `bd export --include-memories` из `~/src/cherry`
(796 задач, 265 заметок, 41 память, 972 зависимости). В `~/src/cherry` не записано
ничего — работа шла на снимке и на копии `ch2`.

## Что было

```
$ myc import-beads cherry-snap.json
myc: internal.unexpected: UNIQUE constraint failed: nodes.scope, nodes.kind, nodes.content_hash
```

## Решение по существу: идентичность ввезённого узла — ссылка, а не текст

Уникальный индекс `ux_nodes_content(scope, kind, content_hash)` запрещал два узла
с одинаковым `(kind, title, body)`. Правило написано под ПАМЯТЬ и там верно:
одинаковый текст — один и тот же факт.

У записи чужого трекера это неверно, и на настоящем cherry неверно буквально:

| столкновение | что это на самом деле |
|---|---|
| `cherry-ys5o` / `cherry-xxc9` | две ЖИВЫЕ задачи, одна `in_progress`, другая `open` |
| `cherry-bkrm.1.1/.1.2/.1.3` | три закрытые задачи под одним родителем |
| **11 групп заметок `bd note`, 108 лишних узлов** | «Agent: general-purpose» у двух десятков задач — заметка КАЖДОЙ из них |

Заметки в описании задачи не назывались, а их в 36 раз больше, чем задач: любое
решение, чинящее только `kind='task'`, оставило бы импорт лежать.

**Миграция 9** (`packages/store-sqlite/src/migrations/009-nodes-external-id.ts`)
разводит ДВА способа быть уникальным, и выбирает не `kind`, а происхождение узла:

```sql
-- своё (myc завёл сам): идентичность по содержимому — прежний индекс дословно
CREATE UNIQUE INDEX ux_nodes_content ON nodes(scope, kind, content_hash)
 WHERE deleted_at IS NULL AND json_extract(attrs,'$.external_ref') IS NULL;

-- ввезённое: идентичность по ссылке на источник
CREATE UNIQUE INDEX ux_nodes_external ON nodes(scope, kind, json_extract(attrs,'$.external_ref'))
 WHERE deleted_at IS NULL AND json_extract(attrs,'$.external_ref') IS NOT NULL;
```

Второй индекс не только снимает запрет — он ДОБАВЛЯЕТ гарантию: на `external_ref`
стоит идемпотентность повторного импорта, и до сих пор её держал только прикладной
код `import-beads`; ошибка в нём удваивала бы граф молча.

### Почему не два других варианта из описания

- **Ребро `duplicates` на столкновении.** Одна из двух задач тогда не ввозится
  вовсе. `cherry-xxc9` — открытая задача, `cherry-ys5o` — в работе; дубликатом
  объявили бы живую работу. Плюс 108 заметок, каждая из которых висит на своей
  задаче, слились бы в 11 и приписали бы чужую работу чужой задаче. `myc ready`
  разошёлся бы с `bd ready` уже по составу, а не только по правилу.
- **`external_ref` внутрь `content_hash`.** `content_hash` производный: любой сайт
  обязан получить тот же хеш из `(kind, title, body)` — на этом стоит сходимость
  реплик. `attrs` приезжают отдельными `set`-операциями, поэтому до их приезда
  реплика материализовала бы узел с ДРУГИМ хешем, чем на исходном сайте, и
  уникальный индекс развалился бы на репликации. Правка CRDT-уровня ради формы
  данных.

## Отказ обязан быть именованным — и не обрывать ввоз

Три починенных до этого блокера были ОДНОЙ ошибкой: одна строка из 796 давала ноль
ввезённых. Поэтому в `import-beads` появился `createGuarded` с двумя рубежами:

1. **предполётная проверка** по индексу содержимого локальных узлов — сообщение
   называет обе стороны (`cherry-x: задача не ввезена — в myc уже есть свой узел
   <id> с тем же заголовком и телом …; разведите тексты либо удалите локальный
   дубль`);
2. **`catch` на нарушении уникальности** — сеть под сетью: любой иной отказ стора
   тоже остаётся ОДНОЙ пропущенной записью.

Обе ветки пишут в `data.skipped` и поднимают `WARN import.skipped`. Импорт идёт
дальше, счётчики честные.

## Пункт 5: «972 зависимости без цели» — ложная тревога сухого прогона

Независимый подсчёт по снимку: 972 зависимости, недостающих целей **ноль**.
Причина расхождения найдена: в сухом прогоне узлы не создавались и **имён не
получали**, поэтому `resolveRef` не разрешал НИ ОДНОЙ ссылки, и все 972 попадали в
`missing_refs`. Ровно то сообщение, по которому потом ищут потерю графа связей.

Починено: в сухом прогоне узел получает имя-заглушку `dry:<external_ref>`, и сухой
прогон считает то же, что сделает настоящий (тест это и проверяет — сверяет четыре
счётчика сухого и настоящего прогонов).

**Связи не теряются.** В базе после импорта: `blocks 558`, `parent 410`,
`derived_from 3`, `supersedes 1` — сумма 972, ровно столько же, сколько в снимке;
плюс 265 `replies_to` у заметок.

## Заодно: 4 зависимости, которые молча не ввозились

`discovered-from` ×3 и `supersedes` ×1 попадали в «ссылки без цели» — под чужое
сообщение. У обоих есть точное ребро myc:

- `discovered-from` → `derived_from` (src = задача, dst = то, из чего нашли);
- `supersedes` → `supersedes` (src = замена, dst = заменённое; направление сверено
  по `bd show cherry-cme` / `cherry-phl`).

Тип, которому ребра нет, теперь называется отдельной строкой
`unknown_dep_types` и `WARN import.unknown_dep_types`: «цель есть, выразить нечем»
— не то же самое, что «цели нет».

## `myc ready` против `bd ready`: 195 против 144 — и это НЕ потеря связей

`bd ready ⊆ myc ready`, в обратную сторону **ни одной** задачи. Разница 51.

Причина — разные определения «готова», и она воспроизведена ПО САМОМУ СНИМКУ, без
базы myc (`scratchpad/explain51.ts`):

| правило | сколько |
|---|---|
| открыта и нет открытого блокера **у неё самой** (правило myc) | 195 |
| открыта и нет открытого блокера **у неё или любого предка по parent-child** | 144 |
| настоящий `bd ready` | **144**, совпадение поимённое, разности в обе стороны пусты |

Все 51 «лишних» — потомки эпиков, у которых блокер висит на предке (например,
`cherry-jrq6.1` открыта, её родитель `cherry-jrq6` зависит от открытого
`cherry-w1f6`). То есть импорт довёз ВСЁ, а расходится определение очереди.

Наследование блокеров вниз по `parent` — решение уровня продукта для ВСЕХ
воркспейсов и упирается в бюджет И1 (`ready` 5 мс на 100k: наивный подъём по
предкам идёт до `LIMIT`). Менять это в задаче про импорт я не стал —
**заведена `memory-atcm254ry6c7` (P1, bug)** с числами, воспроизведением правила и
эскизом материализации.
