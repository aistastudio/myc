# Пул разбора в СОБРАННОМ БИНАРЕ: почему падал и что сделано

## Что видит воркер в бинаре (замер, не гипотеза)

Первое, что я сделал, — вывел в `w.onerror` настоящее сообщение вместо
`воркер разбора ${i} упал`. Оно одно и то же у всех восьми, каждый прогон:

```
[DBG worker 0..7] error: Cannot find package 'web-tree-sitter'
                  from '/Users/egortaranin/src/memory/packages/code-intel/src/symbols.ts'
```

Падают ВСЕ ВОСЕМЬ, а не один. Плавающий номер («упал воркер 3» / «упал воркер 7»)
— это не недетерминизм падения, а гонка за то, чей необработанный отказ первым
убьёт процесс. Отсюда же и exit=0 в одном прогоне из двух.

Две независимые причины, обе — резолвинг за границей потока:

1. **`bun build --compile` НЕ вшивает воркеров.** Конструкцию
   `new Worker(new URL("./code_index_worker.ts", import.meta.url))` бандлер не
   видит (`bundle 205 modules` — воркера среди них нет; в бинаре строка
   `code_index_worker.ts` встречается ровно один раз, как текст URL).
   `import.meta.url` в собранном бинаре сохраняет ИСХОДНЫЙ абсолютный путь
   сборочной машины. Проверено отдельным стендом: если убрать .ts с диска,
   воркер даёт `ModuleNotFound resolving ".../w.ts" (entry point)`. На машине
   сборки файл на месте — поэтому пул «работал» ровно у того, кто собрал.
2. **Standalone-рантайм не резолвит node_modules.** Даже найдя .ts на диске,
   воркер не может импортировать `web-tree-sitter` — это и есть сообщение выше.

Плюс третья беда, уже в нашем коде: `pool.parse()` возвращал промис, обработчик
на который вешался ПОЗЖЕ, в цикле ожидания. Падение воркера отклоняло разом три
сотни промисов, до которых очередь не дошла, — Bun убивал процесс необработанным
отказом. Отсюда стек резолвера в выводе и случайный код возврата.

## Сделано

**1. Воркер вшивается в бинарь вторым входом.** `bun build --compile <main>
<worker>` кладёт в bunfs самодостаточный бандл воркера (web-tree-sitter внутри).
Имя фиксируется явно — `--entry-naming "[name].[ext]"`: по умолчанию бандлер
считает путь от ОБЩЕГО ПРЕДКА входов, и воркер получал имя
`code-intel/src/code_index_worker.js`, то есть зависящее от места ЧУЖОГО входа.
Я на это наступил: первая версия искала `packages/code-intel/src/...`, не
находила, пул молча не заводился, команда рапортовала успех. Обе константы
(`PARSE_WORKER_SOURCE`, `PARSE_WORKER_IN_BINARY`) живут в
`packages/code-intel/src/parse_worker_entry.ts` — модуле без импортов, который
читают и `scripts/build.ts`, и рантайм.

**2. Воркер НИЧЕГО не резолвит.** Каталоги wasm он получает от главного потока
через `MYC_TREE_SITTER_DIR` / `MYC_TREE_SITTER_GRAMMAR_DIR` (опция `env` у
`new Worker`); главный поток находит их один раз в `treeSitterDirs()`. Если
переменных нет — воркер падает СРАЗУ и с названной причиной, а не ищет.
Это принципиально: на сборочной машине резолвер иногда всё-таки попадает в чужой
node_modules по путям, впечённым в бандл, — ровно это и делало поломку невидимой.
`runtimeDir()` теперь, как и `grammarDir()`, называет причину вместо стека.

**3. Падение воркера — отказ команды.** Разделены два исхода, которые раньше
были одним: сторож (`WATCHDOG_MS`) гасит пул молча — это законная перегрузка;
`onerror` запоминает причину, и `drainCodeIndex` бросает её ПОСЛЕ того, как
очередь разобрана в своём потоке. Файлы не теряются, но «готово» про неисправную
сборку не говорится. Обработчик отказа вешается в момент посылки (`settle`), так
что необработанных отказов больше нет.

**4. Отчёт различает пул и главный поток.** `DrainStats.pooled` и строка
`разобрано 413 (пулом 413)`: по `parsed` пул, который не завёлся, неотличим от
пула, который отработал, — так он и жил.

## Тест на собранном бинаре

`packages/code-intel/src/code_index.binary.test.ts`: собирает бинарь рецептом
`scripts/build.ts`, кладёт корпус `PARSE_POOL_MIN_FILES + 16 = 80` файлов ВНЕ
дерева репозитория (рядом нет node_modules, резолвер не может «случайно найти»)
и гоняет `dist/myc code index` с cwd в нём. 5 тестов, 2.1 с.

Мутации доступны через `MYC_PARSE_POOL_MUTATION` — флага у этой развилки нет, а
дотянуться до неё в бинаре надо:

| мутация | что возвращает за границу потока | бинарь |
|---|---|---|
| `entry-from-source` | резолвинг МОДУЛЯ (`import.meta.url`) | exit 1, `воркер разбора 4 упал: … Cannot find package 'web-tree-sitter'` |
| `resolve-in-worker` | резолвинг КАТАЛОГОВ wasm | exit 1, `воркер разбора запущен без каталогов tree-sitter…` |

## Числа

`myc code index` на этом репозитории, 818 файлов, 413 на разбор, индекс
сбрасывается перед каждым прогоном, `MYC_DRAIN=0`, 14 ядер:

| | разбор, мс | wall, с | пулом |
|---|---|---|---|
| бинарь, 3 прогона | 689 / 537 / 608 | 1.02 / 0.62 / 0.68 | 413 / 413 / 413 |
| исходники, 3 прогона | 469 / 536 / 513 | 0.59 / 0.64 / 0.59 | 413 / 413 / 413 |

Бинарь медленнее исходников примерно на 10–25 % по разбору: каждый воркер в
бинаре разбирает свою копию бандла. До правки бинарь на этом корпусе не
завершался вовсе.

Размер `dist/myc`: 72.2 → 73.0 МБ (+0.76 МБ — вшитый воркер).

Тесты: `bun test` — 2553 pass, 16 skip, 0 fail, 0 errors, 230 с. `bun run
typecheck` — 14 пакетов, все 0.
