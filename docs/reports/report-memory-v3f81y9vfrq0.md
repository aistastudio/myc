## 1. Что отдаёт orca (числами, замер 2026-09-07, orca 1.4.197)

Проверено шесть команд, ключи считались по всему JSON вместе с конвертом.

| команда | различных ключей | ключей token/cost/usage | строк `"pid"` |
|---|---|---|---|
| `orchestration worker-show --json` | 91 | 1 (`launch_token_hash`) | 0 |
| `orchestration worker-list --json` | 31 | 0 | 0 |
| `orchestration dispatch-show --json` | 24 | 1 (`launch_token_hash`) | 0 |
| `terminal show --json` | 25 | 0 | 0 |
| `terminal list --json` | 28 | 0 | 0 |
| `diagnostics memory --json` | 33 | 0 | **27** |

**Расхода нет нигде.** Единственные два совпадения на слово «token» — хеш
поручения, не потребление.

**Pid есть ровно в одной команде** — `diagnostics memory --json`: 27 сессий,
у каждой `pid`, `cpu`, `memory`, ключ `sessionId` (= `ptyId` из
`terminal list`) и `paneKey`. Но это pid **ведущего процесса
псевдотерминала**, а не агента. Проверено на живом процессе:

```
81259  /usr/bin/login … orca-tcc-login   ← это и отдаёт orca
81260  -/bin/zsh -l
81610  claude --model claude-opus-5      ← а интересен этот
```

**Что orca даёт полезного:** `worker-show` — `assignee_pane_key`,
`process_incarnation` (`<ptyId>:<incarnationId>`), `start_options` с
`launch.effective.model`; `worker-list` — единственное место, где `ctx_*`
стоит рядом с `term_*` (174 мс на вызов).

**Главная находка: искать было не нужно.** В окружении агентского процесса
уже лежит всё:

```
CLAUDE_CODE_SESSION_ID=b1b7b2cd-9322-4ad5-ad7f-adf39cbb68d6   ← uuid стенограммы
CLAUDE_PID=81610                                              ← pid АГЕНТА
ORCA_TERMINAL_HANDLE=term_7de4e77c-…                          ← ключ к оркестратору
ORCA_PANE_KEY=ab4038fc-…:6b78775f-…                           ← ключ к pid у orca
AI_AGENT=claude-code_2-1-263_agent
```

`ctx_*` в окружении **нет ни у одного харнесса** (проверено полным `env`
внутри dispatch-нутого агента) — он берётся по терминалу из `worker-list`.

## 2. Что сделано

Половина, которая была, не тронута: `swarm_attempt`, `myc report models`,
формула качества, заморозка цены — как были.

**Миграции 006/007** (`packages/swarm/src/migrations/`): таблица
`swarm_attempt_run`, 1:1 к попытке, FK на `swarm_attempt` (барьер при
`PRAGMA foreign_keys=ON`), частичный индекс по `session_id`.
`db/schema.sqlite.sql` НЕ правился: таблицы `swarm_*` в нём отсутствуют по
устройству — у роя своя нумерация и своя таблица учёта, а
`schema-parity.test.ts` сверяет только миграции store-sqlite (проверено,
тест зелёный).

Отдельная таблица, а не колонки в `swarm_attempt`, потому что **у запуска
другое время жизни**: попытка кончается вердиктом, процесс — нет. Пока это
одна строка с одним `finished_at`, «работает» и «завершено, но живо»
неразличимы.

**`packages/swarm/src/launch.ts`** — чистые функции: `launchContext(env)`,
`overrideLaunch`, `parsePid`, `liveStateOf`, `pidAlive`. Ни одного `kill`:
myc смотрит (сигнал 0 по записанному pid) и записывает, снимает тот, кто
запускал. Проба вынесена параметром, поэтому классификация проверяется без
процессов.

**Пять состояний** — пересечение двух независимых вопросов:

| | работа открыта | работа закрыта |
|---|---|---|
| pid жив | `working` | **`orphan`** ← то, что съело 380 МБ на 6 ч 52 мин |
| pid мёртв | `lost` | `done` |
| pid не записан | `unknown` | `unknown` |

`unknown` сознательно не сводится к `done`: это спрятало бы ровно те
строки, ради которых всё писалось.

**Команды:**

- `myc attempt start <id>` — **без единого флага** пишет сессию, pid,
  терминал, pane, диспетчера (по терминалу у orca) и `git_head`. Нет
  сессии → WARN `launch.no_session`; orca не ответил → WARN
  `launch.no_dispatch`. Флаги `--session/--dispatch/--pid/--no-orca` —
  запасной путь.
- `myc attempt list --live` — **одна команда** на «что сейчас работает и
  сколько висит»; отделяет `orphan` от `working`, печатает `kill <pid>`
  подсказкой и прямо говорит, что снимает не он. Здесь же (и только здесь)
  наблюдение записывается: `running → exited` + `proc_exited_at`. Обычный
  `list` остаётся чтением и не пишет ничего.
- `myc attempt finish` и `myc close --verdict` — расход **по записанной
  сессии**, без перебора файлов. `spendVia`: `recorded|flags|transcript|none`.
- `myc attempt link … --found` — запасной путь: находку перебором можно
  записать, и она помечается `session_source='search'`, отличимо от
  записанного при старте.

**Источник каждой связи хранится рядом с ней** (`session_source`,
`dispatch_source`, `pid_source`): `env`/`flag`/`lookup` — записано,
`search` — угадано. Ровно потому, что старый вывод по строке
`Задача myc: <id>` ломался молча.

`scripts/attempt-cost.ts` оставлен и переименован в запасной путь: печатает
теперь `myc attempt link … --found` перед `finish`.

## 6. Что осталось / на что смотреть

1. **`git diff` не различает агентов.** «Тронуто 15 файлов» на живой
   проверке включает файлы второго агента, работающего в том же worktree.
   Иначе и не может быть при общем дереве; для класса задачи это шум.
   Если нужна точность — считать по worktree на агента или фильтровать по
   границам файлов из брифа.
2. **Автоопределение сессии есть только у Claude Code.** Для `opencode` и
   `kimi` работает `MYC_SESSION_ID`/`MYC_AGENT_PID`; имена их собственных
   переменных не выдумывались — не проверено, не записано.
3. **Переиспользование pid.** Живость — это `kill(pid, 0)`; если система
   успела выдать номер заново, запись покажет чужой процесс живым. Для
   6-часовых висяков это не проблема, для многодневных записей — да.
   Лечится сверкой `paneKey` с `orca diagnostics memory`, если понадобится.
4. **`ctx_*` берётся запросом к orca (174 мс на `attempt start`).** Исчезнет
   сам, если оркестратор начнёт выставлять `ORCA_DISPATCH_ID` — переменная
   уже читается.
5. **Коммит 839fb33 «0.1.1: fix the package name in the no-Bun message»
   подмёл файлы этой задачи** (`launch.ts`, `run.test.ts`, миграции 006/007,
   `attribution.ts`, `index.ts`) вместе с чужими. Ничего не потеряно, но
   история перепутана; git я не трогал.
6. `myc attempt list --live` на настоящей базе сейчас показывает мою же
   открытую попытку `att_d69528cd24f4` — она закроется штатно при
   `myc close memory-v3f81y9vfrq0 --verdict …`, и расход посчитается сам.
