# memory-spwaw50jxcpw — кеши результатов, эмбеддингов и гидратации (M2)

## Статус задачи в трекере

`myc claim memory-spwaw50jxcpw` **не прошёл**: `precond.blocked` — задача
заблокирована открытой `memory-eb91mperrr2k` (digest_cache и инвалидация по
oplog.seq). Работа сделана по прямому наряду координатора; закрывать бид сам
не стал. Мой модуль с digest_cache не пересекается: тот кеш табличный
(`digest_cache(scope, profile, seq, payload)` в БД), мои — in-process LRU.
Общий у них только источник версии — хвост оплога.

## Что сделано

Три кеша §2.6, каждый — не «оптимизация», а конструкция вокруг одного
инварианта: **попадание обязано быть неотличимо от повторного запроса к базе.**

| Кеш | Где | Ключ | Инвалидация |
|---|---|---|---|
| Результаты поиска | `packages/retrieval/src/cache.ts` → `SearchResultCache`, подключён в `hybridSearch` | sha1(запрос + скоупы + слои + limit + vector_mode + **вызывающий** + эффективный конфиг) | `MAX(oplog.seq)` + TTL 60 с |
| Эмбеддинги запросов | `packages/embed/src/cache.ts` → `CachedEmbedder` поверх `EmbedQueryCache` | sha1(norm_query) + отпечаток пространства | отпечаток в ключе |
| Гидратация узлов | `packages/retrieval/src/cache.ts` → `NodeHydrationCache` | node_id | **точечно**: список узлов, менявшихся после запомненного seq |

Ключевые решения (каждое закрыто мутацией, см. ниже):

1. **Версия базы — `SELECT MAX(seq) FROM oplog`, а не `myc_meta.last_seq`.**
   `oplog.seq` — INTEGER PRIMARY KEY AUTOINCREMENT, MAX берётся одним спуском
   по правому краю B-дерева. `last_seq` — счётчик локального сайта: операция,
   приехавшая репликацией, двигает оплог, не трогая его, и кеш её бы не увидел.
2. **Вызывающий входит в ключ.** Таблица §2.6 перечисляла в ключе
   norm_query + scopes + layers + profile + limit — этого не хватает: ACL
   фильтруется внутри SQL, значит один запрос от разных вызывающих даёт разные
   выдачи. В долгоживущем процессе такой ключ — утечка чужих узлов через кеш,
   а не промах производительности. Доку поправил.
3. **Ключ поиска НЕ понижает регистр** (в отличие от ключа эмбеддингов):
   `isAnchorToken` разбирает форму токена, `ENOENT` и `enoent` ведут к разным
   решениям триггера вектора.
4. **Ключ включает эффективный конфиг целиком**, а не перечисленные руками
   поля: список полей ржавеет при добавлении параметра, и это молча портит выдачу.
5. **Деградированный ответ отдаётся, но не кешируется** (`degraded` непуст или
   вектор `unavailable`/`degraded`): заморозить его на TTL значит продлить
   деградацию после того, как она кончилась (И2).
6. **Вектор из кеша эмбеддингов отдаётся копией**: потребители правят его на
   месте (`normalizeInPlace`, `quantizeInt8`), ссылка травила бы кеш навсегда и молча.
7. **Гидратация инвалидируется точечно.** Сбрасывать 4096 тел из-за одной
   правки — кеш, который в рабочей сессии не попадает никогда. Запасной путь —
   полный сброс при списке длиннее 512 id или при уехавшем назад seq (`cleared`).

Попадание и промах **видны**: `mode_used.cache` = `hit` | `miss` | `off` (тот
же образец, что `cache hit`/`cache miss` в подвале `myc prime`),
`EmbedResult.cached` у эмбеддера. При `hit` `roundTrips` = 1 — единственный
statement запроса это чтение хвоста оплога.

## Числа

Проверка: `bun test packages/retrieval packages/embed` — **259 pass, 0 fail,
15 skip** (было 220 pass, 0 fail, 15 skip). Типизация: retrieval, embed, cli,
mcp, web, server, distiller, code-intel, anchors — все OK.

### Цена попадания (корпус 2000 узлов, `cache.test.ts`)

| | промах | попадание | во сколько раз дешевле |
|---|---|---|---|
| Поиск | 1.31–1.35 мс | 0.0066–0.0084 мс | **162–198×** |
| Эмбеддинг запроса | 23.3 мс (замер координатора, WASM p50) | 0.0009 мс | **~25 000×** |

### Доля попаданий на сценарии сессии (60 запросов, каждый 5-й — новая формулировка)

| Сценарий | Попаданий | Комментарий |
|---|---|---|
| без записей | **40/60 (67%)** | 12 новых + 8 холодных + 40 повторов; каждый повтор — попадание |
| запись каждые 20 запросов | **24/60 (40%)** | 16 записей сброшено как устаревшие — цена честной инвалидации |

Второе число специально в отчёте: seq-валидация глобальная, любая запись
сбрасывает весь кеш поиска. Это плата за то, что устаревший ответ невозможен.

### Память

- Кеш поиска: 512 ответов по 12 узлов = **0.66–0.72 МиБ** (~1400 Б/запись).
  Мерилось `heapTotal` до/после с `Bun.gc(true)`; `heapUsed` под JSC — константа.
- Кеш эмбеддингов: 1000 × 384 float32 = **1.46 МиБ** векторов.
- Итого на процесс ~2.2 МиБ.

### Качество не изменилось

запроса** (совпадение средних можно получить и перемешав выдачу):

  on      |           0.867 |          0.867 |   0.800 | 0.800 |                0

**cold_start — не моя регрессия, проверено двумя способами:**
1. Чередующийся A/B на `scripts/coldstart.ts`: с моим модулем p50 **22.21 мс**,
   без него — **22.40 мс** (то есть разницы нет, а бенч в тот же момент
   показывал 22.1 и 24.3 на одном и том же коде — разброс хоста).
2. Размер бандла: `bun build --target=bun --minify packages/cli/src/main.ts` —
   **1 092 891 Б** с кешем против **1 092 154 Б** без = **+737 байт (+0.067%)**.
   При `--bytecode` парс бандла и вовсе предвычислен.

Машина при замерах была под нагрузкой параллельного агента (load average
6.6–12.7 на 14 ядрах); базовая линия cold_start снималась на другой нагрузке.
Бюджет 60 мс не нарушен (p99 = 34.3 мс), падает именно проверка регрессии
относительно baseline.

Кросс-процессная приёмка (`cache.race.worker.ts`, настоящий `Bun.spawnSync`):
процесс с горячим кешем (`miss` → `hit`) не видит собственных записей, потом
второй процесс пишет узел + операцию оплога в тот же файл — следующий тот же
запрос даёт `miss`, содержит новый узел, `staleDrops` = 1. Под M6 этот тест
падает.

Стабильность новых тестов: 5 прогонов подряд, 49 pass / 0 fail каждый.
Один прогон полного набора из пяти дал 1 падение, которое я не смог
атрибутировать (имя ушло из вывода); четыре последующих прогона чистые, мои
файлы в 5 отдельных прогонах не падали ни разу. Наиболее вероятный источник —
перф-тесты соседних файлов (`federation.latency.test.ts`, `vector.test.ts`,
`fts.test.ts`) на загруженной машине.

## Что осталось (за границами моих файлов)

1. **`packages/cli` — подвал и владение кешем.** `mode_used.cache` уже есть в
   ответе, но CLI его не печатает. Нужно: в `search.ts`/`retrieve.ts` вывести
   `cache hit`/`cache miss` в подвал по образцу `prime.ts`, и завести
   `SearchResultCache` на процесс (в one-shot вызове кеш бесполезен — он
   окупается в MCP-сервере/демоне).
2. **`packages/cli/src/commands/retrieve.ts:551` — кеш эмбеддингов сейчас
   почти не работает.** `resolveQueryEmbedder` создаёт эмбеддер на КАЖДЫЙ
   вызов, вместе с ним рождается и умирает кеш. Ради этого случая
   `EmbedderConfig.queryCache` принимает готовый `EmbedQueryCache`: достаточно
   держать один экземпляр на процесс и передавать его —
   `createEmbedder({ backend: "local", queryCache: processCache })`.
   Без этой правки 25 000× экономии остаются на бумаге в долгоживущем процессе.
3. **`NodeHydrationCache` не подключён к гидратации.** Запросы `hydrate_full`/
   `hydrate_light` живут в `packages/cli/src/commands/retrieve.ts` (граница).
   Метод `hydrate(db, ids, fetch)` подставляется туда одной строкой:
   `cache.hydrate(driver, ids, (miss) => driver.all(QR.hydrate_full, [JSON.stringify(miss)]).map(r => [r.id, r]))`.
4. **`digest_cache` (memory-eb91mperrr2k)** — соседняя задача; `readOplogSeq`
   и `cacheQueries.cacheOplogSeq` готовы к переиспользованию, чтобы источник
   версии в проекте был один.
5. **Прогрев для prime** из формулировки бида относится к digest_cache и
   инстанцированию эмбеддера при старте MCP — обе точки в `cli`/`mcp`.
