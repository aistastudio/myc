## 1. `--db` — это база И её воркспейс (memory-dyjt6fafz8j9 P1, memory-h0d5p1smqb5v P2)

**Было.**
- CLI (`store.ts`, `openStore`): при `--db` конфиг `workspace.toml` читался из каталога
  `-C`/cwd. Слаг — а с ним id и scope каждого нового узла — приходил от воркспейса, из
  которого позвали: `myc --db <cherry>/.myc/myc.db -C <cherry>/messaging-server task …`
  давал `myc-…` в scope `''`, а из чужого воркспейса — его слаг (`local-…`).
- MCP (`command.ts`): при `--db` сервер отдавал `wsDir = cwd`, и прямой стор (myc_link,
  myc_update note/extend/release) открывал `<cwd>/.myc/myc.db`. Команды CLI того же сервера
  шли в базу из `--db`, заметки и связи — в базу воркспейса вокруг cwd. `instructions`
  собирались со слагом cwd (`ws=local` вместо `ws=cherry`).

**Стало.** Одно правило для CLI и MCP: конфиг — `workspace.toml` **рядом с базой**
(`dirname(--db)/workspace.toml`; для `<dir>/.myc/myc.db` это `<dir>/.myc/workspace.toml`,
ровно как без флага и как уже искал `findMycDir` в bootstrap). Конфиг чужого воркспейса
вокруг `-C`/cwd не подставляется никогда.
- MCP: `mcpWorkspace` при `--db` отдаёт `dbPath` самой базы; прямой стор открывает ровно
  этот файл (`openMcpStore(…, { dbPath })`), слаг — из `workspace.toml` рядом. Файла нет —
  сервер без инструментов, в stderr `no database at <путь> (--db)` (прежде — «no myc
  workspace at <cwd>», путь базы не назывался).
- CLI: рядом с базой конфига нет — умолчания базы; если прежняя подстановка дала бы ДРУГОЙ
  слаг (воркспейс вокруг `-C`/cwd со своим `workspace.toml`) — `WARN ws.db_config` с обоими
  путями и слагами.

**Решение по «иначе отказ вслух».** Отказ — там, где правило выполнить нельзя: базы по
`--db` нет (CLI: `ws.not_initialized: no <путь>`, MCP: 0 инструментов с путём в stderr), и
MCP больше не может молча писать в другую базу. Для «конфига рядом с базой нет» я выбрал
WARN, а не отказ: база без `workspace.toml` — это воркспейс с умолчаниями (так её открывает и
обычный путь), а жёсткий отказ в этой ветке ломает 6 тестов вне моих границ — замер
мутацией «throw вместо WARN» в изолированной копии с базой в корне (как у рабочего дерева):
`drain.test.ts` ×2 («8 параллельных CLI: 40 работ», «приёмка S8 end-to-end») и
`reindex.test.ts` ×4 (SIGKILL-догон, «неизменённое не переэмбеддится», «расхождение
отпечатка — ОТКАЗ», watch) — они открывают `<tmp>/myc.db` с cwd = корень этого
репозитория, у которого свой `workspace.toml` (прежде они молча брали слаг `memory`).
Если нужен именно отказ — это одна строка в `warnBorrowedConfig` (`ctx.warn` → возврат
`CommandFailure`) плюс `-C <tmp>` в этих шести тестах.

**Воспроизведение** (падают на `HEAD`): `store.db-flag.test.ts` — 4 из 5 (узел в слаг базы
из подкаталога, из чужого воркспейса, копия файлом с конфигом рядом, WARN при отсутствии
конфига); `mcp/src/db-flag.test.ts` — 2 из 3 (заметка/связь/аренда в базу `--db`;
причина с путём при несуществующей базе). Третий MCP-тест (копия файлом вне `.myc`)
добавлен после мутации M1d.

**Мутации:** M1a конфиг снова из `-C`/cwd → 4 падения; M1b снят `WARN ws.db_config` → 1;
M1c MCP-стор снова `<cwd>/.myc/myc.db` → 2; M1d `openMcpStore` игнорирует `dbPath` → 1
(сначала выжила: для `<dir>/.myc/myc.db` путь совпадает — добавлен тест на копию файлом).

## 2. `myc_prime` отдаёт `prime`, а не `bootstrap` (memory-rkmcfqmaw4sc P1)

**Было.** `toolPrime` (`dispatch.ts`) звал `myc bootstrap`: агент через MCP получал второй
раз блок, уже приехавший в `initialize.instructions`, и не получал ни очереди, ни «в
работе», ни ядра/решений — в отличие от агента с хуком (`prime --format agent`).

**Осознанной разницы нет.** В дизайне (03 §4.4) `myc_prime` — схема prime (ready,
in_progress, core, decisions, counts); в ARCHITECTURE решения «MCP-prime = bootstrap» нет;
`bootstrap.ts` в шапке прямо говорит «это НЕ `myc prime`»; единственное упоминание — отчёт
memory-7j8zgjnd0bjz, где это записано как наблюдение («закреплено тестом»), а не решение.

**Стало.** `myc_prime` = `myc prime --budget N`: структура из `--json`, текст — дословный
вывод prime; последовательно (второй прогон берёт дайджест из кеша первого; отказ первого
не зовёт второй). Правила работы (bootstrap) остаются в `instructions` — они переживают
сжатие контекста сами. Описание инструмента приведено к §4.4 («ready queue, work in
progress, core and recent decisions»), бюджет описаний (`index.test.ts`) соблюдён.
Параметры `role`/`focus` из §4.4 не добавлял (бюджет токенов профиля; отдельное решение).

**Воспроизведение:** `dispatch.test.ts` 2 теста и `e2e.test.ts` (текст содержит задачу,
`ready_total = 2`, нет `MYC BOOTSTRAP`) падают на `HEAD`. `pending-review.test.ts`
переписан: теперь кандидат проверяется в настоящем пакете prime.
**Мутация:** M2a `argv = ["bootstrap", …]` → 3 падения.

## 3. Расход попытки — только исполнителя (memory-1s8dcfkfz20r P1)

**Было** (attempt.ts `recordedSpend`): стенограмма — по `run.sessionId`, записанному
`attempt start` ИЗ ОКРУЖЕНИЯ ТОГО, КТО НАБРАЛ КОМАНДУ; `isSelfAttributed` не спрашивался;
модели стенограммы не сверялись; `transcriptPath` на старте не писался, на финише файл
искался только в `~/.claude/projects/<слаг cwd финиширующего>`. Воспроизведение механизма
аудита на `HEAD`: попытка sonnet, заведённая координатором из своей сессии, закрывается с
`spend_via: recorded` и `cost_usd = 498.69` (токены opus по ставкам sonnet); агент из
worktree — `notfound.session`, расход не взят.

**Как теперь определяется сессия исполнителя** (`executorSession`, `launch.ts`, рядом с
`isSelfAttributed`): подтверждена, если диспетчер известен (`dispatch_source` ∈
env/flag/lookup) ИЛИ сессия привязана явно (`session_source` ∈ flag/search: `--session`
при старте, `attempt link`). `session_source='env'` при `dispatch_source='none'` — сессия
того, кто набрал `attempt start` (так легли все три строки аудита), — не подтверждена.

**Как находится его стенограмма:** (в) на старте путь пишется в `swarm_attempt_run.transcript_path`
(`locateSessionTranscript`: сначала каталог проекта cwd, затем `<uuid>.jsonl` во ВСЕХ
каталогах `$CLAUDE_CONFIG_DIR/projects` — uuid уникален, ~170 stat); на финише — записанный
путь, если файл на месте, иначе тот же поиск по uuid, не по cwd финиширующего. Попутно
исправлен слаг каталога проекта: Claude Code меняет на `-` всё не буквенно-цифровое
(`…/docs/.claude/worktrees/x` → `…-docs--claude-worktrees-x`, проверено по
`~/.claude/projects`), прежний код менял только `/`. `attempt link` с другой сессией
перезаписывает путь (иначе финиш читал бы стенограмму прежней сессии). Явный
`--from-session` ищет так же.

**Защиты на автоматическом пути** (финиш и `close --verdict`):
- (а) сессия не подтверждена → расход не берётся, `WARN spend.not_executor` с подсказкой
  `myc attempt recost <att> --from-session <uuid> --apply`;
- (б) модели стенограммы (без служебной `<synthetic>`) должны принадлежать модели попытки
  (`checkTranscriptModels`: все слова семейства или хвоста id — среди слов имени;
  `claude-sonnet` ⊂ `claude-sonnet-5`, но не ⊂ `claude-opus-5`) → иначе не берётся,
  `WARN spend.model_mismatch`. Явный `--from-*` сверяется тоже, но только WARN: его назвал
  человек.

**(г) `myc attempt recost [<att>] [--task] [--from-session|--from-transcript] [--apply [--clear-foreign]]`.**
По умолчанию dry-run. Те же правила, что у финиша; стенограмма исполнителя читается до
момента финиша (`readTranscriptUsage(path, { until: finished_at })` — сессия могла работать
после приёмки); цена — та же строка, что на `started_at` (`Attribution.recostAttempt`;
инвариант «стоимость заморожена» запрещает менять исход правкой ЦЕНЫ, здесь меняются токены,
взятые не из той стенограммы). Действия: `recost` / `unchanged` / `foreign` / `refused` /
`skipped`. Стенограмму исполнителя не найти или она чужой модели — `refused` (для одной
названной попытки — отказ команды, `notfound.session`, exit 3), ничего не пишется.
`foreign` — записанный расход ДОКАЗУЕМО взят из неподтверждённой сессии: какой-то
**префикс** её файла даёт ровно те же четыре суммы (`findUsagePrefix`); снимается только
явным `--clear-foreign`.

Почему префикс, а не срез по времени финиша — найдено на копии базы: финиш читал файл
без ответа «в полёте» (того, чей вызов инструмента и запустил `myc close`), а его записи
легли позже, но с отметкой времени до финиша. У att_696c6767c557 срез по `finished_at`
больше записанного ровно на один ответ (+2 in, +837 out, +816 747 чтений кеша, +861 записей);
префикс, совпадающий по всем четырём полям, — `2026-09-07T19:56:04.086Z`.

## 4. `close --verdict` по уже закрытой задаче (memory-swbmm4qhqkeh P1)

**Было.** `tasks.ts ~1661`: `{ok:true, already:true}` раньше разбора вердикта — вердикт
пропадал молча; это ровно ретро-сценарий (83 задачи за 09-08…14 без попыток, §4.1).

**Стало** (`verdictOnClosed`): задача не трогается; вердикт идёт в попытку тем же путём, что
при закрытии (`applyAttribution` → `finishWithFact`): открытая попытка задачи (последняя) или
названная новым флагом `--attempt <att>`; открытой нет, попыток нет, `--model` назван — ретро-
попытка. Записать некуда — отказ `attribution.not_recorded` (exit 5) с подсказкой
`myc close <id> --verdict … --model <roster model id>`; у задачи уже есть закрытая попытка и
нет открытой — отказ `conflict.finished` (exit 4): повтор той же команды не заводит второй
исход. `--attempt` чужой задачи — `usage.attempt`, закрытой попытки — `conflict.finished`;
работает и на незакрытой задаче. Без `--verdict` — прежнее тихое `already`.

**Воспроизведение:** 5 из 6 тестов `close --verdict по закрытой задаче` падают на `HEAD`
(шестой — сторож прежнего `already` без вердикта).
**Мутации:** M4a вернуть ранний `already` → 5; M4b без проверки записанного исхода → 2;
M4c «некуда записать» не отказ → 1; M4d `--attempt` чужой задачи принят → 1.

## 5. `myc model update` не сбрасывает явные ставки кеша (memory-s4t6yzs3kxz7 P2)

**Было.** Недостающая ставка кеша выводилась долей от цены входа ВСЕГДА: `update --price-in 4
--price-out 20` без флагов кеша превращал явные 0.5/6 в 0.4/5 (10 %/125 % от 4), `update
--price-cache-read 0.45` сбрасывал явную запись 6 → 5. Подмена ложилась в историю цен и во
все будущие заморозки.

**Стало.** Недостающая ставка берётся из строки цены, действующей на ту же дату. База хранит
только числа, поэтому явное от выведенного отличается по самому числу: ставка, равная доле
от входа СВОЕЙ строки, — умолчание (или совпадающее с ним явное — пропорция та же) и
пересчитывается от новой цены входа вслух (`WARN price.cache_defaulted`, как прежде); любая
другая — явная и переносится. Откуда каждая ставка — в `meta.cacheRates` (`flag|kept|default`).
Ставки 0/0 (явно «не заведено», `cacheUnpriced`) тоже переносятся.

**Воспроизведение:** «update без флагов кеша сохраняет явно заданные ставки» падает на `HEAD`
(0.4/5 вместо 0.5/6); «умолчание остаётся умолчанием» — сторож обратной стороны.
**Мутации:** M5a всегда доля → 1; M5b всегда перенос → 1.
