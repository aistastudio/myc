# Бенчмарки памяти агентов: что проходит supermemory и как туда попасть myc

Задача `memory-p4vnbe7jex4r` (P1, эпик M2). Исследование, не правка кода.
Все проверки сделаны **2026-09-09** на `darwin-arm64`, bun 1.3.14, бинарь
`dist/myc` (сборка от 22:39). Каждая цифра ниже помечена: **[изм]** — снято
здесь, командой из приложения; **[пуб]** — опубликованное число со ссылкой на
строку; **[слов]** — заявление без опубликованной методики.

**Короткий ответ.** У supermemory нет ни одного воспроизводимого результата на
бенчмарке. Есть заявление «#1 на LongMemEval, LoCoMo и ConvoMem» в README и
отдельно — **свой** открытый харнесс MemoryBench (MIT), который эти бенчмарки
гоняет, но ни одного прогона не публикует. То есть их «#1» — это `[слов]`, а
`[пуб]` у них ровно одно: код харнесса. Зато существует то, чего у них нет и
что бьёт ровно в myc: **LongMemEval-V2** (UCLA, Apache-2.0) — публичный
лидерборд памяти агентов, где метрика — интеграл точности по **логарифму
латентности**, и он **сегодня пуст**.

Собственное измерение (главный факт отчёта): myc, как есть, поставленный
на LoCoMo, даёт **hit@10 = 0.671, MRR@10 = 0.364** на 82 размеченных вопросах
`[изм]`. При этом **лексическая ветка не сработала ни разу**: в режиме `bm25`
79 запросов из 82 вернули пусто. На английских вопросах-предложениях весь
результат даёт вектор.

## 2. MemoryBench: что их харнесс на самом деле делает

Это самая полезная часть их работы, и её стоит разобрать честно, потому что
именно через неё лежит самый дешёвый путь myc к сопоставимому числу.

**Конвейер** (`src/orchestrator/`): `ingest → indexing → search → answer →
evaluate → report`, каждая фаза с чекпойнтом и резюмом.

**Интерфейс провайдера** ([`src/types/provider.ts`](https://github.com/supermemoryai/memorybench/blob/main/src/types/provider.ts)) — шесть методов:

```ts
interface Provider {
  name: string
  prompts?: ProviderPrompts
  concurrency?: ConcurrencyConfig
  initialize(config: {apiKey: string, baseUrl?: string}): Promise<void>
  ingest(sessions: UnifiedSession[], opts: {containerTag}): Promise<{documentIds: string[]}>
  awaitIndexing(result, containerTag, onProgress?): Promise<void>
  search(query: string, opts: {containerTag, limit?, threshold?}): Promise<unknown[]>
  clear(containerTag: string): Promise<void>
}
```

Что из чтения кода следует, а из документации — нет:

1. **Контейнер на каждый вопрос.** `containerTag = ${questionId}-${dataSourceRunId}`
   (`phases/ingest.ts`, `phases/search.ts`). Хайстек переливается заново под
   каждый вопрос. Для полного LoCoMo это **55 014 вызовов `ingest`** на
   уровне сессий (вместо 272 уникальных сессий) и 1 194 140 сообщений, если
   провайдер хранит по сообщению `[изм: подсчёт по locomo10.json]`. Плюс
   `RATE_LIMIT_MS = 1000` в батчере. Полный прогон — это часы, и документация
   честно это признаёт («Ingestion can take hours»).
2. **Поиск всегда с `limit: 10, threshold: 0.3`** — жёстко зашито в
   `phases/search.ts`, флагом не меняется.
3. **Три вызова LLM на вопрос**: answer (`DEFAULT_ANSWERING_MODEL = "gpt-4o"`),
   judge, и ещё один — судья релевантности в `phases/retrieval-eval.ts`,
   который считает Hit@k/MRR/nDCG. Итого для полного LoCoMo ≈ **5 958**
   платных вызовов.
4. **Тихая деградация метрик извлечения.** В `retrieval-eval.ts` при любой
   ошибке парсинга ответа судьи возвращается «всё нерелевантно» (`relevant: 0`)
   — прогон не падает, а retrieval-метрики молча обнуляются.
5. **Встроенный провайдер supermemory ходит в их облако.** `initialize()`
   создаёт `new Supermemory({apiKey})` без `baseUrl`
   (`src/providers/supermemory/index.ts:24-27`) — то есть проверка их
   собственного результата стоит денег им же.
6. **Каждый провайдер может подсунуть свой промпт ответа**
   (`prompts?: ProviderPrompts`). Размеры файлов промптов: supermemory 6 543 Б,
   zep 5 469, rag 3 054, filesystem 2 459, mem0 1 693 `[изм: git tree]`. Это
   не доказательство подкрутки, но это ось свободы, которая у автора харнесса
   больше, чем у пришедшего.
7. **`-l N` — это `slice(0, N)`, а не выборка** (`benchmarks/locomo/index.ts`).
   «Быстрая проверка на 20 вопросах» из их же документации берёт первые 20
   вопросов первого диалога, а не случайные 20.
8. **Их справочник врёт про их же датасеты.** `skills/memorybench/references/benchmarks.md`
   пишет «LoCoMo: ~100 questions, LongMemEval: ~150, ConvoMem: ~80» — загрузчик
   LoCoMo кладёт **1 986** вопросов `[изм]`, LongMemEval — 500 `[пуб]`. Там же
   LongMemEval описан как бенчмарк «длинных документов, RAG, академических
   статей» — это неверно, LongMemEval построен на истории чата.

**Ключевой факт для нас:** ни одна фаза не требует, чтобы *провайдер* ходил в
сеть или имел ключ. Ключи нужны **харнессу** — для ответа и суда. Наш инвариант
И1 (нет сети в горячем пути) MemoryBench не нарушает: myc в этой схеме — только
`search()`.

## 3. Ландшафт: что вообще считается ориентиром

Только память агентов и долгий контекст, не общий RAG. Колонка «лидерборд» —
есть ли место, где результат публикуется и его видно рядом с чужим.

| Бенчмарк | Что меряет | Корпус | Метрика | Лицензия | Лидерборд | Язык |
|---|---|---|---|---|---|---|
| **[LoCoMo](https://github.com/snap-research/locomo)** (Snap, ACL'24) | факты в многосессионном диалоге; 5 категорий (расшифровка «single-hop / multi-hop / temporal / world-knowledge / adversarial» — не из README LoCoMo, а из кода memorybench, `benchmarks/locomo/index.ts`) | `locomo10.json`, 2.8 МБ: **10 диалогов, 272 сессии, 5 882 сообщения, 1 986 вопросов** (кат. 1: 282, 2: 321, 3: 96, 4: 841, 5: 446) `[изм]`. Это **подвыборка**: изначально было 50 диалогов, оставили самые длинные с хорошей разметкой; **изображения не выкладывались** — только URL и подписи `[пуб: README.MD:24-26]` | F1/BLEU в оригинале; на практике все считают LLM-judge accuracy | **CC-BY-NC-4.0** (`LICENSE.txt`) `[изм]` | **нет** | en |
| **[LongMemEval](https://github.com/xiaowu0162/LongMemEval)** (ICLR'25) | долговременная память ассистента: извлечение, мультисессионность, обновление знания, темпоральность, воздержание | 500 вопросов; `_s` 277.4 МБ (~115k токенов истории), `_m` 2 737 МБ (~500 сессий), `_oracle` 15.4 МБ `[изм: HF API]` | QA-accuracy, судья GPT-4o (`evaluate_qa.py`); отдельно session/turn-level recall по `answer_session_ids` | MIT | **нет** (только скрипт оценки) | en |

### Насколько этим бенчмаркам можно верить

Прежде чем идти, стоит знать, во что вкладываешься.

* **LoCoMo: 6.4% ключа ответов сломано.** Аудит Penfield Labs (2026-04-04,
  код [`dial481/locomo-audit`](https://github.com/dial481/locomo-audit)):
  проверено 1 540 вопросов (это ровно 1 986 − 446 adversarial `[изм: сходится
  с нашим подсчётом]`), найдено **99 ошибок (6.4%)** — галлюцинации в ключе,
  неверная темпоральная логика, перепутанные говорящие (24 случая). Отдельно:
  судья `gpt-4o-mini` принял **62.81%** намеренно неверных, но тематически
  близких ответов. То есть шум метода сопоставим с разницей между
  соревнующимися системами.
* **LoCoMo: результаты уже переигрывали.** Zep (2025-05-06) перемерил свою
  систему в постановке Mem0 и получил **75.14% ± 0.17** против **65.99%**,
  которые Mem0 опубликовал за него; расхождение объяснили тремя ошибками
  интеграции (обе стороны диалога записаны как user, таймстемпы в тексте
  вместо поля `created_at`, последовательные вместо параллельных поисков —
  из-за чего у Zep и латентность вышла завышенной: 0.778 с вместо 0.632 с).
  Вывод не «Mem0 жулики», а «на LoCoMo цифра конкурента, посчитанная
  конкурентом, ничего не стоит».
* **Категория 5 LoCoMo (446 вопросов, 22% датасета) частью команд просто
  выбрасывается** как непригодная. У memorybench она загружается наравне
  с прочими.

## 4. Измерение: myc как есть на LoCoMo

Это не «прогон бенчмарка» — LLM не участвовал вообще. Это проверка **того
единственного, за что в бенчмарке отвечает myc: извлечения**. Никакого адаптера
не писалось: только CLI, который уже есть.

**Постановка.** Диалог `conv-26` из `locomo10.json`: 19 сессий, 419 сообщений,
199 вопросов. Каждое сообщение записано отдельным узлом
(`myc remember "<speaker> (<дата>): <текст>" --tag dia-<id> --reach project
--no-absorb`). Взяты 82 вопроса категорий 1–3 (single-hop 32, multi-hop 37,
temporal 13); категория 4 (world-knowledge) и 5 (adversarial) отброшены как не
проверяющие извлечение. Успех: среди top-10 выдачи `myc recall --json --limit 10`
есть узел с тегом одного из `evidence`-сообщений.

**Стоимость постановки** `[изм]`: `myc init` 56 мс; загрузка 419 сообщений
через CLI **29.3 с** (≈70 мс на сообщение — это почти целиком старт процесса:
холодный старт бинаря p50 21.9 мс, сама запись p50 0.258 мс по
`site/measurements.json`); `myc reindex` — **521 мс**, 419 векторов,
отпечаток `local:onnx-wasm:multilingual-e5-small-q8:384:l2`.

**Результат** `[изм]`:

| Режим | n | hit@10 | MRR@10 | пустых выдач | латентность recall, p50 |
|---|---:|---:|---:|---:|---:|
| `hybrid` (по умолчанию) | 82 | **0.671** | **0.364** | 0 | 353.9 мс |
| `vec` | 82 | 0.671 | 0.364 | 0 | 375.1 мс |
| `bm25` | 82 | **0.000** | 0.000 | **79** | 11.9 мс |

По категориям (hybrid): single-hop 0.594 / 0.260, **multi-hop 0.865 / 0.531**,
temporal 0.308 / 0.147.

**Что из этого следует — включая неприятное.**

1. **Лексическая ветка на этом корпусе мертва.** `bm25` вернул пусто на 79
   запросах из 82. Диагностика самого myc: «ни один из 419 видимых узлов не
   совпал с запросом (строгое И и 2 ступ. отката, 9 терминов — не совпало ни
   на одной)». Вопрос бенчмарка — предложение на 6–9 значимых слов, узел —
   реплика на 10–20 слов; строгое И не выполняется никогда. `hybrid` и `vec`
   дают **побайтово одинаковые** числа: гибридности в этой постановке нет.
   Это не «плохо настроено» — это политика поиска, которая хорошо работает на
   нашем корпусе (короткие запросы агента к базе знаний) и не работает на
   чужом (длинные вопросы к диалогу).
2. **Темпоральные вопросы — 0.308.** Дата лежит в тексте узла строкой
   («7 May 2023»), отдельного временного измерения при извлечении нет. Это
   ровно та категория, на которой LongMemEval и LoCoMo делают акцент.
3. **Multi-hop 0.865 выше single-hop 0.594** — контринтуитивно и, скорее
   всего, артефакт разметки: у multi-hop в `evidence` перечислено больше
   сообщений, значит попасть хоть в одно легче. Честная метрика для multi-hop —
   покрытие всех evidence, а не одного; я его не считал.
4. **Латентность 354 мс — это не латентность myc, это латентность CLI.** В
   каждом вызове заново поднимается процесс и прогревается ONNX
   (`--embed-timeout 3000`; штатно `--embed-timeout 0`, и первый запрос идёт
   вообще без вектора — WARN «холодный ONNX стоит ~184 мс при бюджете recall
   25 мс»). Внутрипроцессные числа из `site/measurements.json`: гибридный
   поиск p99 10.354 мс на корпусе 100 000 узлов, эмбеддинг запроса промах
   23.3 мс / попадание 0.0009 мс. Для бенчмарка адаптер обязан быть
   долгоживущим процессом, иначе мы меряем `fork()`.
5. **Найден дефект.** `--reach project` даёт 40 попаданий; `--reach
   project,session` — 0, все 40 отброшены с причиной `session` `[изм]`.
   По коду: `packages/cli/src/commands/recall.ts:525-531` рядом с
   `reach: reachFilter` дополнительно ставит `reachSession = <текущая сессия>`,
   как только в списке встретилось `session`; а `dropMaskOf`
   (`packages/cli/src/commands/retrieve.ts:1004-1005`) роняет любую строку с
   другим `reach_session` — включая строки с `reach: project`, у которых
   `reach_session` пуст по определению. Комментарий в коде объясняет намерение
   («сессия сужает выдачу ТОЛЬКО вместе с `--reach session`»), но композиция
   вышла И вместо ИЛИ: расширение списка сужает выдачу до нуля. Первый прогон
   этого исследования из-за этого дал ровный ноль по всем 82 вопросам, и я
   чуть не записал его в отчёт как результат myc.

## 5. Что нужно сделать myc, чтобы прогнаться

По кандидатам, от дешёвого к дорогому. «Есть» — работает сегодня, проверено;
«нет» — надо писать.

### 5.1 MemoryBench (LoCoMo / LongMemEval / ConvoMem) — самый дешёвый вход

Нужен один файл `src/providers/myc/index.ts` в их репозитории плюс три строки
регистрации (`providers/index.ts`, `ProviderName`, `utils/config.ts`).

| Метод интерфейса | Что требуется | Что у нас есть | Чего нет |
|---|---|---|---|
| `initialize({apiKey, baseUrl})` | подготовить клиент | `myc init` — 56 мс, каталог с `myc.db` `[изм]` | ничего. `apiKey` игнорируется — это и есть наш аргумент |
| `ingest(sessions, {containerTag})` | залить сессии в изолированный контейнер | `myc remember`, запись p50 0.258 мс `[пуб: measurements.json]` | **изоляции по `containerTag` нет**. Ближайшее — каталог на контейнер (`myc -C <dir>`). 55 014 воркспейсов на полный LoCoMo — рабочая, но грубая схема; правильнее поле-скоуп в схеме БД |
| `awaitIndexing()` | дождаться индексации | `myc reindex` — 521 мс на 419 узлов `[изм]`; очередь `jobs` embed'ит и сама | тонкость: `remember` кладёт embed в очередь, `reindex` её досушивает. Синхронного «готово» нет — нужен опрос очереди |
| `search(query, {containerTag, limit, threshold})` | вернуть top-10 | `myc recall --json --limit N` — **готовый программный вход**, плюс MCP `myc_recall` | `threshold` в recall нет (игнорировать — допустимо). Формат строк наш, не их — подойдёт: тип `unknown[]` |
| `clear(containerTag)` | снести контейнер | `rm -rf <dir>` | ничего |
| `prompts?` | свой промпт ответа | — | не нужен: пусть работает дефолтный, это честнее |

**Объём работ.** Адаптер — ~150 строк TS, шелл-аут на бинарь. Плюс:

* **долгоживущий процесс** вместо `fork()` на вызов — иначе латентность
  меряется мимо. Варианта два: (а) `myc serve`/сокет — уже есть `myc embedd`,
  который держит эмбеддер на сокете; (б) импорт `@myc/*` прямо в их bun-проект
  — но наши пакеты не опубликованы отдельно (`exports: ./src/index.ts`,
  `workspace:*`), нужен git-чекаут. **Это главная неочевидная работа, не адаптер.**
* **починить лексическую ветку на длинных запросах**, иначе гибридность в
  отчёте будет фикцией: 79 из 82 пустых `[изм]`.
* **прогрев эмбеддера один раз на прогон**, не на вопрос.
* деньги и ключи **у нас** для answer+judge: ≈5 958 вызовов LLM на полный
  LoCoMo (3 на вопрос × 1 986). Инвариант И1 не нарушается — сеть нужна
  харнессу, не myc; но «прогнать бенчмарк без ключа к модели» невозможно, и
  это надо сказать вслух.
* корпуса **только английские** — все три датасета `language: en` `[изм: HF API]`.
  Наш `multilingual-e5-small` (384) против их `bge-base-en-v1.5` (768) на
  чистом английском — заведомо не наша сильная сторона. Двуязычность,
  ради которой мы его выбирали, здесь **не измеряется вообще**.

**Оценка:** 2–3 дня на адаптер + прогон на 20 вопросах; ещё 2–3 дня на
долгоживущий процесс и лексику; полный LoCoMo — часы машинного времени и
несколько десятков долларов API.

### 5.2 LongMemEval-V1 напрямую (без memorybench)

Интерфейс проще: скормить историю, выдать `jsonl` из `question_id` +
`hypothesis`, прогнать `src/evaluation/evaluate_qa.py gpt-4o`. Нужен свой
цикл ответа (LLM) — то есть всё равно ключ. Плюс: результат сравним с числами
из статьи ICLR'25 напрямую. Минус: **лидерборда нет**, публиковать некуда,
и это ровно наша сегодняшняя ситуация, только на чужом корпусе.

**Оценка:** 1–2 дня. Ценность — внутренняя (регрессия), не репутационная.

### 5.3 LongMemEval-V2 — единственный настоящий лидерборд

| Требование | Что у нас есть | Чего нет |
|---|---|---|
| Python-класс `Memory` с `insert(trajectory)` / `query(query, query_image) -> list[{type: "text"\|"image", value}]` | логика есть в TS | **Python-обвязки нет вообще.** Нужен мост: подпроцесс к бинарю или FFI |
| `save_memory` / `_load_backend`: состояние памяти сохраняется и грузится, конфиг обязан совпасть побайтово | `myc.db` — файл, копируется | сериализация конфига в их формате `memory_config.json` |
| Мультимодальность: до 5.9 ГБ скриншотов, `query_image` | — | **у myc нет обработки изображений вообще**. Можно вернуть только `type: "text"` — тогда часть evidence недостижима |
| Фиксированный reader `qwen3.5-9b` | — | локальный запуск 9B-модели: GPU или очень терпеливый CPU |
| Фиксированный судья `gpt-5.2` | — | ключ OpenAI; проверяется валидатором пакета (`leaderboard/README.md`) |
| Хайстеки 25–115 млн токенов, до 500 траекторий | запись 0.258 мс, поиск p99 10.4 мс на 100k узлов `[пуб]` — на порядок больший корпус мы не мерили | замер на 10⁶–10⁷ узлах; неизвестно, где ломается |
| Пакет сабмита: 2 домена × ≥1 latency operating point, `SYSTEM_DESCRIPTION.md`, один файл кода, tar.gz, Google Form | — | вся упаковка |

**Оценка:** 3–6 недель, и это оптимистично. Из них большая часть — не myc, а
инфраструктура вокруг (Python-мост, reader, скриншоты, железо).

**Но именно здесь метрика совпадает с тем, ради чего myc существует.** LAFS —
интеграл точности по log-латентности от 1 до 200 секунд. Фронт сегодня:
0.2 с → 51.0%, 26.9 с → 58.6%, 108.3 с → 74.9%. Система, которая на
низколатентном конце даёт заметно больше 51% при ~1 с, двигает фронт там, где
его сейчас держит примитивный RAG. Это единственная площадка, где «поиск
за 10 мс» — не самореклама, а координата на графике.

### 5.4 Чего делать НЕ надо

Не строить «свой публичный бенчмарк памяти». Их уже минимум 13 (таблица
LongMemEval-V2 перечисляет 12 плюс себя). Ещё один, автором которого будем мы,
имеет ровно тот же вес, что «#1» у supermemory.

## 7. Стоит ли туда идти

Разложу по кандидатам, потому что общего ответа нет.

**MemoryBench — да, но не ради «#1», а ради дефектов.** Проверка на 82 вопросах
LoCoMo (раздел 4) — даже без харнесса, без LLM и без адаптера — уже дала больше
знания о myc, чем неделя внутренних бенчмарков: мёртвая
лексическая ветка на длинных запросах, провал на темпоральных вопросах, дефект
`--reach`. Это дёшево (2–3 дня), это чужая разметка, и это ломает нашу главную
слабость — что мы меряем себя по своей линейке. Побочный эффект: строка
«myc есть в MemoryBench» стоит дороже, чем любая наша цифра, потому что её
может перепроверить кто угодно одной командой.
**Но заявлять по итогам «мы обошли supermemory» нельзя**: LoCoMo с 6.4%
битого ключа и судьёй, принимающим 62.81% неверных ответов, не различает
системы на нашем масштабе различий.

**LongMemEval-V1 — нет.** Публиковать некуда, работа та же, что и по
MemoryBench, ценность только внутренняя. Если нужен регрессионный корпус на
английском — дешевле взять `longmemeval_oracle.json` (15.4 МБ) как ещё один
`bench/*.ts`, без всякой публикации.

**ConvoMem — нет.** CC-BY-NC-4.0. Мы MIT-проект, который собирается быть
инструментом; тащить некоммерческий корпус в свои бенчмарки — заводить
лицензионную мину ради датасета, чью метрику никто не ведёт (и чей код-репозиторий
по ссылке из README supermemory отдаёт 404).

**Отдельно про лицензии.** **Два из трёх** датасетов, на которых строится
заявление «#1» — LoCoMo и ConvoMem — под **CC-BY-NC-4.0**, то есть
некоммерческие `[изм: LICENSE.txt и карточка HF]`. Это ничего не говорит о
добросовестности supermemory (исследовательский прогон под NC обычно допустим),
но для нас это ограничение прямое: числа, полученные на этих корпусах, нельзя
класть на лендинг рядом с ценой. На LongMemEval (MIT) и LongMemEval-V2
(Apache-2.0) такого ограничения нет — ещё один довод в пользу именно их.

**LongMemEval-V2 — да, но не сейчас.** Это единственная площадка, где метрика
(LAFS) меряет ровно то, ради чего myc существует: полезность памяти **при
бюджете латентности**. Пустой лидерборд — редкое окно. Но вход стоит недель,
требует Python-моста, локального Qwen3.5-9B, ключа к gpt-5.2 и работы с
изображениями, которой у нас нет вовсе. Это отдельный эпик, а не задача, и
браться за него до того, как закрыт M3, — значит подменить продукт витриной.

**Чего бенчмарки НЕ померяют, и это надо знать заранее.** Все четыре — про
диалог и веб-траектории. Ни один не меряет: двуязычный корпус (все `en`),
код-якоря, очередь задач, оплог, работу без ключа, размер дистрибутива,
холодный старт. То есть **лучшая версия myc по нашему собственному замыслу и
лучшая версия myc по LoCoMo — это разные системы**. Идти туда стоит как на
внешнюю проверку извлечения, а не как за подтверждением продуктовой правоты.
Если из бенчмарка вернётся вывод «надо переделать поиск под длинные английские
вопросы к диалогу» — это вывод про бенчмарк, а не про myc, и принимать его
надо ровно в этом объёме.

## 8. Задачи, которые из этого следуют

Названы, не заведены.

**Прямые дефекты, найденные по дороге** (эти стоят своих денег независимо от
всей бенчмарк-темы):

1. `--reach` списком сужает выдачу вместо расширения: `project,session`
   роняет все `project`-строки фильтром `reachSession`
   (`packages/cli/src/commands/recall.ts:525-531` +
   `packages/cli/src/commands/retrieve.ts:1004-1005`). Нужен тест на
   «список reach — это ИЛИ».
2. Лексическая ветка возвращает пусто на запросах длиннее ~6 значимых слов:
   строгое И + 2 ступени отката не срабатывают. Нужна третья ступень —
   покрытие по доле терминов — и бенч на длинных запросах.
3. Темпоральные запросы: даты живут строкой в тексте узла, отдельного
   временного измерения при ранжировании нет.

**Вход в MemoryBench:**

4. Долгоживущий режим myc для внешних харнессов (сокет/сервер), чтобы
   латентность мерилась без `fork()` на вызов.
5. Изоляция корпуса внутри одной БД (`containerTag`/scope) вместо каталога
   на контейнер.
6. Провайдер `myc` для MemoryBench: адаптер + PR в их репозиторий.
7. Прогон LoCoMo на 20 и на полном наборе; отчёт с их же числами и нашими.

**Внутреннее использование чужих корпусов:**

8. `bench/locomo-eval.ts` — LoCoMo как постоянный регрессионный корпус
   извлечения (без LLM, только hit@k/MRR по evidence), рядом с
   `boost-eval.ts` и `graph-eval.ts`. **Датасет в репозиторий не класть**:
   CC-BY-NC-4.0 против нашего MIT — скрипт должен качать `locomo10.json`
   сам, как это делает memorybench.
9. Замер поиска на 10⁶ узлах: сегодняшний потолок замеров — 100 000.

**Дальний прицел:**

10. Эпик «LongMemEval-V2»: Python-мост, `Memory`-класс, reader, упаковка
    сабмита. Не начинать до закрытия M3.

## Приложение. Как повторить

```bash
# 1. Корпус LoCoMo (2.8 МБ, публичный)
curl -sSL -o locomo10.json \
  https://raw.githubusercontent.com/snap-research/locomo/main/data/locomo10.json

# 2. Состав корпуса (10 диалогов / 1986 вопросов / 5882 сообщения)
python3 -c "import json,collections;d=json.load(open('locomo10.json'));\
print(len(d), sum(len(i['qa']) for i in d), collections.Counter(q['category'] for i in d for q in i['qa']))"

# 3. Стенд: 419 сообщений conv-26 в свежий воркспейс
myc init && for each message: \
  myc -C lc remember "<speaker> (<date>): <text>" --tag dia-<id> --reach project --no-absorb
myc -C lc reindex                       # 521 мс, 419 векторов

# 4. Замер (82 вопроса категорий 1-3, hit@10 / MRR@10 по evidence)
myc -C lc recall "<question>" --json --limit 10 --budget 40000 \
    --embed-timeout 3000 --mode hybrid|vec|bm25

# 5. Наши опубликованные числа
bun run scripts/bench-latency.ts        # latency
bun run bench/boost-eval.ts             # boost
bun run bench/graph-eval.ts             # graph
bun run pack:npm                        # размер пакета

# 6. Их числа
curl -sS https://api.github.com/repos/supermemoryai/supermemory/releases  # размеры бинарей
curl -sS https://api.npmjs.org/downloads/point/last-week/supermemory      # скачивания
```

Скрипты стенда (`prep_locomo.py`, `ingest.py`, `eval_locomo.py`) — во временном
каталоге сессии; они на 60 строк и восстанавливаются из описания выше. В
репозиторий не клались намеренно: их место — будущий `bench/locomo-eval.ts`
