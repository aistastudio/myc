# memory-2shvpjay4nx6 — `myc init --global --force` снова работает

## Что было сломано

`countPersonalMemory` (store.ts) открывала личную базу единственным способом —
`new Database(path, { readonly: true })`. База в WAL, из которой писатель вышел
начисто, остаётся БЕЗ `-wal`/`-shm`, и такому соединению негде построить индекс
WAL: первый же prepare падает с `SQLITE_CANTOPEN`. Дальше `!readable` шло в
`hasMemory`, и `--force` отказывал ВСЕГДА — включая пустой ярус, где терять
нечего. Безопасный путь был мёртв, работал только `--wipe-memory`.

Воспроизведение из тикета, после правки (тот же `main.ts`, что в бою):

```
MYC_HOME=$H bun packages/cli/src/main.ts init --global      # exit 0
MYC_HOME=$H bun packages/cli/src/main.ts prime              # exit 0
sqlite3 $H/.myc/myc.db 'SELECT count(*) FROM oplog'         # 0, спутников нет
MYC_HOME=$H bun packages/cli/src/main.ts init --global --force
  → личный воркспейс на месте, стёрто только восстановимое
  → · память не тронута  0 узлов, 0 операций оплога · myc.db
  → exit 0                                     (было: precond.personal_memory, 5)
```

## Что сделано

**packages/cli/src/commands/store.ts**

1. `countPersonalMemory` — вторая ветка чтения. Лечение из просмотрщика
   (`packages/web/src/db.ts`, `openReadOnly`: пересоздать соединение читаемым
   handle-ом под `PRAGMA query_only`) я взять НЕ смог и объясняю числами —
   замер на подставном `~/.myc`, четыре способа на одном и том же файле:

   | состояние базы | способ | числа | каталог до/после |
   |---|---|---|---|
   | писатель вышел начисто (нет `-wal`/`-shm`) | `readonly` | **падает**: unable to open database file | совпал |
   | то же | writable + `query_only` (рецепт web) | ops 0 | **изменился**: появились `myc.db-shm:32768`, `myc.db-wal:0` |
   | то же | writable + `locking_mode=EXCLUSIVE` + `query_only` | ops 0 | **изменился**: появился `myc.db-wal:0` |
   | то же | `file:…?immutable=1` | ops 0 | **совпал** |
   | живой журнал (`-wal` 477952, `-shm` 32768) | `readonly` | ops 10 | совпал |
   | то же | writable + `query_only` (рецепт web) | ops 10 | **изменился**: `myc.db` 4096 → 274432, `myc.db-wal` 477952 → **0** (чекпойнт на закрытии) |
   | то же | `immutable` | **падает** громко: no such table: oplog | совпал |

   Рецепт просмотрщика для просмотрщика верен, но здесь он бы означал: функция,
   решающая, СТИРАТЬ ЛИ память, сама переписывает её файлы, а принятый пункт
   «отказ не пишет на диск» перестаёт быть правдой (477 КБ журнала уезжают
   в базу при каждом отказе). Поэтому вторая ветка — `immutable=1`.

2. Условие включения второй ветки: журнала нет вовсе (`-wal`, `-shm`,
   `-journal`) — проверяется ДО чтения и ещё раз ПОСЛЕ (писатель мог стартовать
   в промежутке). immutable игнорирует журнал, и читать им базу с журналом
   значило бы решать судьбу памяти по её прошлому. Во всех прочих случаях
   fail-closed сохранён дословно: чего не прочли, того не стираем.

3. `wipePersonalWorkspace(plan, { memory })` — разрешение доезжает до
   исполнителя параметром. Без `--wipe-memory` стирается ровно восстановимое,
   `myc.db` остаётся — в том числе на пустом ярусе. «Пустая» и «которую не
   жалко» — разные вещи: у пустой базы есть `site_id`, под которым уже
   подписаны операции.

4. `createPersonalWorkspace` сохраняет существующий `site_id` (и `slug`): база,
   пережившая `--force`, теперь не создаётся заново, а открывается, и менять
   ей личность сайта нельзя.

**packages/cli/src/commands/init.ts** — передаёт `{ memory: wipeMemory }`; в
конверт добавлено `wiped.memoryKept`; человеческий вывод больше не говорит
«создан» там, где база осталась на месте («личный воркспейс на месте, стёрто
только восстановимое» + строка «память не тронута  N узлов, M операций»).

**packages/cli/src/commands/init.test.ts** — один внутрипроцессный тест и новый
многопроцессный `describe` (Bun.spawn того же `main.ts`).

## Почему баг прожил под зелёными тестами

Две причины сразу, и обе снимаются только настоящим процессом:

1. внутри процесса `-wal`/`-shm` переживают закрытие соединения — состояние
   «писатель вышел начисто» в тестах не наступает;
2. под `bun test` предзагружается кастомная libsqlite3 (`bunfig.toml` →
   `runtime-preload.ts`), и она такую базу readonly открывает БЕЗ ошибки
   (и попутно создаёт пустой `myc.db-wal`). Боевой CLI работает на встроенной
   в Bun сборке, где тот же вызов падает.

Поэтому приёмочные тесты — многопроцессные.
