# `--anchor` привязывает; `anchor_check` разбирается фоном

Задачи **memory-m3xkayb4rhay** (`--anchor` не привязывает, а откладывает) и
**memory-h9ckxqdztf93** (фоновый прогон `anchor_check` без потребителя). Взяты
связкой: первая наполняла очередь, вторая её разбирает.

## Что было

`myc remember --anchor` и `myc task --anchor` писали в `attrs.anchors` запись
`{path, start, end, state:'pending'}`, печатали «якорь отложен до `myc anchor
bind`» — и всё. Отложен он был навсегда: разбирать `attrs.anchors` не умеет
ничто, `myc anchor of` такого якоря не находит, лестница §7.2 его не проверяет,
`ready` (ANCHOR_SUBQ идёт по рёбрам `touches` к узлам `kind='anchor'`) не видит
вовсе. Команды `myc anchor bind` при этом не существует — она `add`.

Класс работ `anchor_check` ставился (хук `absorb-session`, `remember --anchor`),
а исполнителя не имел: лестницу гонял только ручной `myc anchor check`. Журнал
грязных файлов `.myc/anchor-dirty.log`, который пишет хук post-edit, снимался
тем же ручным вызовом — то есть рос до первого.

## Что сделано

**1. Одна функция привязки на все входы.** `bindAnchorAt` в
`packages/cli/src/commands/anchor.ts` — узел `kind='anchor'`, строка `anchors`,
ребро `touches`. Её зовут `myc anchor add`, `myc remember --anchor` и
`myc task --anchor`; трёх копий одного правила больше нет, и мутация в ней
ломает все три входа сразу (мутация 11 ниже — 15 упавших).

Неудача привязки — не отказ записи, а громкая деградация (И2): узел записан,
намерение остаётся в `attrs.anchors` со `state='pending'` (оттуда его читает
`anchorPathsOf`, и ось `scope` класса задачи не теряется), причина уходит в
`WARN anchor.unbound` и в строку вывода. При успехе `attrs.anchors` НЕ пишется:
вторая копия дала бы `show` две строки об одном якоре.

Разборщик пути тоже стал один — `parseTarget`. Побочно исправлено: `--anchor
src/x.ts` без номеров строк теперь берёт **файл целиком**, а не строку 1.

Заодно закрыта дыра, которую нашла проверка личного яруса: `myc remember
--global --anchor src/fuse.ts` писал в `anchors` путь `../demo/src/fuse.ts` —
он резолвится только на этой машине и только из этого каталога, а `anchor of`
по нему не найдётся никогда (запрос идёт по паре `repo_id+path`). Теперь путь
выше корня отвергается: `usage.outside_repo` у `anchor add`, деградация с
причиной у `--anchor`.

**2. Устаревшая строка `myc anchor bind` → `myc anchor add`** — во всех
найденных местах, а не в трёх: `remember.ts`, `tasks.ts`, `mcp/src/format.ts`
(названы в задаче), плюс `core/src/graph.ts:326` (`writtenBy` ребра `touches`)
и таблица рёбер в `docs/design/01-core-data-model.md`. В `remember`/`tasks`
строка теперь собирается одной функцией `anchorFlagLine`.

**3. Фоновый потребитель `jobs(kind='anchor_check')`** — шаг в `drain.ts`,
§7.5 целиком:

* **период 300 с** на воркспейс, отметка в `myc_meta.anchor_swept_at` (durable,
  общая для процессов, ни файла, ни демона). Работа в очереди период пробивает:
  ждать 300 с после правки не надо;
* **дебаунс 2 с** — файл, изменённый только что, фон не трогает: якорь,
  проверенный посреди правки, честно объявился бы `stale` по недописанному
  тексту, а `ready` понизил бы задачу на ровном месте. Ручной `anchor check`
  дебаунса НЕ знает — спросили про сейчас;
* **батч ≤ 256 по `checked_at ASC`** среди `state <> 'lost'`, грязные пути
  (журнал + payload снятых работ) первыми. Батч режется в SQL (`LIMIT`), а не
  `.all()` по таблице, как было в ручной команде;
* **журнал `.myc/anchor-dirty.log` снимается фоном** — расти до ручного вызова
  ему больше нечем.

`anchor_check` намеренно НЕ в `INLINE_JOB_KINDS`: класс батчевый, строка очереди
— подсказка «посмотри сюда», а не единица работы. Все её строки снимаются разом,
payload'ы сливаются с журналом, прогон случается ОДИН.

Лестница у ручного и фонового вызова одна — `sweepAnchors`; различаются только
аргументы (дебаунс и бюджет).

## Класс задачи: до и после

Класс мерился на живом воркспейсе (`myc attempt start … --model`) и через
`myc ready --why`.

**Класс `intent:scope` был `fix:local` и до, и после.** Заявленного в задаче
`*:unknown` я не воспроизвёл: `anchorPathsOf` (`attempt.ts:509`) читает и
объявленные пути из `attrs.anchors` — это уже почищено предыдущей задачей
якорей. Ось `scope` держалась на обещании, и это работало.

Что действительно менялось — **всё остальное, что считается по настоящему
якорю**. Одна и та же команда, две сборки, один воркспейс:

```
myc ready --why
demo-xw13b3jp456p  --anchor на НОВОЙ сборке
  score 0.41 = P2(0.13) + unblocks 0(0.00) + свежесть(0.14) + якоря fresh(0.10) + task(0.05)
demo-ctqf51x4zc6r  --anchor на СТАРОЙ сборке (запись pending в attrs)
  score 0.36 = P2(0.13) + unblocks 0(0.00) + свежесть(0.14) + якоря нет якорей(0.05) + task(0.05)

myc anchor of src/fuse.ts
  ДО:    якорей нет: src/fuse.ts · запрос 0.055 мс
  ПОСЛЕ: src/fuse.ts:1-3
           demo-xw13b3jp456p  task open  Исправить падение fuse ещё раз
```

Терм якорей в `ready`: **0.05 → 0.10** (норма 0.5 → 1.0). Обратный ход код →
знание: **0 узлов → 1**. Лестница §7.2 такой якорь теперь проверяет и двигает —
после правки файла спан сам переехал `1-3 → 2-4`, состояние осталось `fresh`.

## Цена фона — числами

Замерено на этой машине (14 ядер), 300 якорей в базе.

| что | число |
|---|---|
| **период закрыт** (99 вызовов CLI из 100) | **+0.007 мс p50** к дренажу (0.390 против 0.383) |
| полный батч 256, уровень 1 (файл не читается) | **9.2 мс** p50, **0.036 мс** на якорь |
| полный батч 256, уровень 2, файлы по 167 КБ | 45.8 мс, 0.179 мс на якорь |
| он же под бюджетом по умолчанию **20 мс** | 20.7 мс, проверено 128 из 256, `budget_hit` |

Бюджет прогона — 20 мс, меньше половины бюджета дренажа (50 мс, §12.2 D28):
даже упёршийся в потолок прогон оставляет absorb'у больше, чем тот тратит на
одну работу (~8 мс). Недоразобранный батч не теряется: `checked_at` этих якорей
не сдвинулся, и следующий прогон берёт их первыми.

**Выключатель — `MYC_ANCHOR_CHECK`**, отдельный от `MYC_DRAIN` и внесён в
`BACKGROUND_SWITCHES` (`packages/core/src/test-env.ts`). Отдельный потому, что
механизм читает ФАЙЛЫ репозитория: тесту, который правит файлы под собой, нужно
гасить именно его, оставив разбор очереди. Тест на исчерпывающность —
4 pass / 0 fail.

## Цена `--anchor` в горячем пути записи

`myc task`, 120 прогонов на вызов, время всего `run()`:

| | p50 | p95 | p99 |
|---|---|---|---|
| без `--anchor` | 1.19 мс | 4.40 мс | 5.38 мс |
| `--anchor`, файл 200 строк (~7 КБ) | 1.57 мс | 2.93 мс | 3.55 мс |
| `--anchor`, файл 4000 строк (~140 КБ) | 4.96 мс | 8.61 мс | 10.86 мс |

Типичный файл стоит **+0.4 мс**. Файл на 140 КБ стоит **+3.8 мс** и подводит
p50 к границе бюджета записи (И1, 5 мс), а p99 переходит её. Это ровно цена
`myc anchor add`, которую проект уже принял, и платится она только когда
`--anchor` назван; альтернативой было «отложить», то есть не привязать никогда.
Ускорять тут нечего без отказа от уровня 3: 140 КБ надо прочитать и
нормализовать. Если граница окажется важной — резать по размеру файла, но это
отдельное решение и отдельная задача.

## Мутации

Здоровый прогон пяти файлов (`anchor-sweep`, `anchor`, `tasks`, `memory`,
`drain`) — **150 pass / 0 fail**.

| мутация | упало |
|---|---|
| **1. фон не разбирает очередь** (шаг якорей снят целиком) | **12** |
| 2. дебаунс 2 с снят | 1 |
| 3. бюджет прогона не проверяется | 1 |
| 4. период 300 с снят (лестница на каждый вызов CLI) | 1 |
| 5. батч не ограничен 256 | 1 |
| 6. порядок не `checked_at ASC`, а по `node_id` | 1 |
| 7. `--anchor` снова только откладывает | 5 |
| 8. ребро `touches` не заводится | 9 |
| 9. строка «якорь отложен до `myc anchor bind`» вернулась | 3 |
| 10. журнал грязных файлов не снимается | 3 |
| 11. строка `anchors` не пишется (только узел и ребро) | **15** |
| 12. защита «файл вне корня репозитория» снята | 1 |

Мутация 1 — обязательная по заданию. Мутация 6 с первого прогона дала **0
упавших**: тест сортировки проверял пять якорей при батче 256, где порядок не
решает ничего. Переписан на десять якорей и батч 3 — ловится.
