# memory-fqcxrktkqvcr — методика бенчмарков и ночные прогоны

Дата: 2026-09-07. Стенд: 14 ядер, darwin-arm64.

## Коротко

Бюджетный тест теперь состоит из ТРЁХ утверждений, и абсолютное из них — самое
слабое. Под нагрузкой (load1 46–55) семь бюджетных замеров дали p99 24–67 мс при
бюджетах 3–25 мс, и прогон остался зелёным: **68 pass, 0 fail**. Под той же
нагрузкой четыре мутации все покраснели — по относительному утверждению, которое
загрузку машины не замечает. Полный прогон: было **2002 pass / 1 fail**, стало
**2126 pass / 0 fail**.

## 1. Методика

Оснастка — новый пакет **`@myc/bench`** (`packages/bench`). Он подключается
тестами как devDependency и импортируется из `scripts/`.

**Что мерим.** Одну операцию горячего пути за раз, ТЕМ ЖЕ текстом запроса, что
исполняет команда.

**Чем.** Прогрев отбрасывается; перцентили p50/p95/p99 берутся как МЕДИАНА по
трём независимым прогонам (`trials`, по умолчанию 3).

**При каких условиях.** Рядом с полезной операцией, ЧЕРЕДУЯСЬ с ней в одном
цикле, крутится ЭТАЛОН — чисто процессорный цикл, подогнанный под ту же
длительность. `ref.p99 / ref.p50` («дрожание») — измеренный ответ на вопрос «во
сколько раз машина сейчас растягивает работу такого размера».

| длительность | покой (load 5.9) | 20 занятых процессов (load 9–15) |
|---|---|---|
| 0.05 мс | ×1.66 ×1.63 | ×4.09 ×2.29 |
| 0.3 мс | ×1.19 ×1.19 | ×2.31 ×1.39 |
| 1 мс | ×1.20 ×1.17 | ×6.64 ×23.84 |
| 5 мс | ×1.17 ×1.13 | ×10.25 ×10.58 |
| 20 мс | ×1.23 ×1.26 | ×3.07 ×4.79 |

`JITTER_MAX = 2.5` выбран по этим числам (`scripts/bench-jitter.ts` —
воспроизводимая калибровка). Условия печатаются в одной строке с числом и, если
задан `MYC_BENCH_LOG`, пишутся JSON-строкой в файл.

**Что считается регрессией.**

1. **Структурное** — план запроса, реальность отсева. От машины не зависит,
   обязательно всегда.
2. **ОТНОСИТЕЛЬНОЕ** — здоровый против СОПЕРНИКА (заведомо деградировавшего
   близнеца) либо против ЭТАЛОННОЙ СОСЕДНЕЙ операции, если близнеца не
   существует. Меряются чередуясь → отношение переживает нагрузку.
   **Обязательно всегда, это главная проверка.**
3. **Абсолютное** — бюджет в мс. Роняет прогон только при годных условиях
   (дрожание ≤ 2.5) либо в строгом режиме (`MYC_BENCH_STRICT=1`). Иначе печатает
   `НЕДОСТОВЕРНО` с причиной.

**Условия записываются вместе с числом и в базовой линии.** `bench/baseline.json`
теперь разложен ПО МАШИНАМ (`darwin-arm64-14`, …) и каждая запись несёт `load1`,
`cpus`, `jitter`. 15 % от числа, снятого на другом железе, не значат ничего:
секции для текущей машины нет — сравнение не проводится, и это сказано вслух, а
не подразумевается. Прежняя плоская линия сохранена как `неизвестная-машина` —
она условий не несла.

### Почему p99 по 60 замерам не годится (найдено в общем прогоне)

Первая версия методики оставила ready-тест на одном прогоне: он упал с p99 3.115
при пороге 3 — **при дрожании ×1.10**, то есть машина была свободна и проверка
условий не помогала. p99 по 60 замерам — это 60-й элемент, один сосед по
процессору (ровно довод S63 про cold_start). Медиана трёх прогонов на том же
стенде даёт p99 1.66 / 1.78 / 1.82.

### Лимит теста — тоже стенное время

Трейлы сделали замеры втрое длиннее, и под 20 занятыми ядрами два ЗДОРОВЫХ
бюджетных теста упали по лимиту `bun test` **5 с по умолчанию** — тот же класс,
что myc-dze.3. Всем бюджетным тестам проставлен явный лимит 120 с с подписью,
что это потолок «что-то зациклилось», а не бюджет.

## 3. Утверждения против отчётов

`эксперимент myc-dze.3 > ОТЧЁТ` разведён на два теста. Исходы (нашлось /
подключился ли вектор) от числа повторов не зависят вовсе — `runMode` заполняет
`per` только на первом проходе, повторы нужны лишь распределению времени в
таблице. Поэтому:

* **утверждения** — один повтор, **0.56 с**, обычный лимит, все `expect`;
* **отчёт** — пятнадцать повторов, **7.25 с**, лимит 120 с, ни одного `expect`.

## 4. Ночные прогоны

`scripts/bench-nightly.ts` — один вход: бюджетные тесты (каждый в своём
процессе), `bench:latency`, `boost-eval`, `graph-eval`.

* Перед стартом меряется ГОТОВНОСТЬ машины на трёх длительностях; на занятой
  машине скрипт отказывается работать (код 2), если не дан `--force`.
* **Строгий режим включается измерением, а не флагом**: машина прошла проверку →
  `MYC_BENCH_STRICT=1` и абсолюты обязательны; не прошла → числа снимаются,
  относительные утверждения обязательны как всегда, абсолюты только печатаются.
* Бюджетные тесты **не перечислены списком** (списки забывают пополнять), а
  находятся по признаку «файл импортирует `@myc/bench`». Проверено: обнаружение
  уже подхватило `anchor.latency.test.ts` и `anchor.test.ts`, написанные вторым
  агентом.
* Результат — JSONL с условиями (`MYC_BENCH_LOG`), в CI выгружается артефактом
  на 90 дней, в том числе при падении.

**Отдельно от `ci.yml`, а не внутри** — `.github/workflows/nightly-bench.yml`,
`cron 17 3 * * *` + `workflow_dispatch`, `concurrency: nightly-bench`. Обоснование:
(1) абсолюту нужна незагруженная машина, а в `ci.yml` бюджетные тесты идут внутри
общего `bun test` вместе с двумя тысячами других; (2) прогон стоит минуты — стенды
по 100k строятся заново в каждом файле, и платить это на каждом коммите в PR не за
что; (3) семантика падения разная: красный PR блокирует слияние, красная ночь
заводит разбор и никого не блокирует; (4) числа для README и для базовой линии
обязаны сниматься в одинаковых условиях, а не в тех, какие достались коммиту.

В `ci.yml` ничего не удалено: `bun test` и `bun run bench:latency` остались,
комментарии объясняют, что там обязательно, а что нет.

## 5. Границы

* Разрешено координатором по ходу: заведён пакет `packages/bench` (`@myc/bench`),
  подключён как **devDependency** в `packages/cli`, `packages/retrieval` и в
  корневой `package.json` (для `scripts/`). `rootDir` нигде не снят.
* Исходники команд (`packages/cli/src/**` кроме тестов, `packages/swarm/**`) не
  тронуты.
* **Корневой `package.json`** — одна строка devDependency; формально он не был в
  списке «можно», но без него `scripts/` не видит новый пакет. Прошу подтвердить.

## 6. Что осталось

1. **`cycle.latency` в store-sqlite остаётся флакающим** — измерено: p99 5.107 мс
   при бюджете 5 под 20 занятыми процессами (изолированно 0.231 мс, запас ×21).
   Починить нечем: `scripts/deps-check.ts` собирает зависимости пакета в том числе
   ИЗ ТЕКСТА тестовых файлов (`collectImportedDeps` глобит `src/**/*.ts`), поэтому
   правило «store-* may only depend on @myc/core» запрещает и тестовую оснастку.
   То же у `core` (нельзя ни одного `@myc/*`) и `swarm` (только core) — три пакета
   из четырнадцати не могут иметь методики. **Заведено `memory-p1v756t1jc1z`** с
   тремя вариантами решения.
2. **README не генерируется** — таблица бюджетов в `README.md:68` вбита руками
   (`prime 0.70 / read 0.011 / search 9.1 / write 0.5 / cold start 24`), сегодняшний
   прогон даёт `0.728 / 0.0091 / 9.72 / 0.431 / 28.9`. `README.md` вне моих границ;
   заготовка есть — ночной прогон уже пишет JSONL с условиями, дальше нужен шаг,
   который перерисовывает таблицу из него. Это часть исходной приёмки задачи
   («числа в README сгенерированы»), поэтому задачу закрытой не считаю.
3. **Синтетика 1M и 200 размеченных запросов** из исходного описания задачи не
   построены: сейчас 44 запроса у myc-dze.3, по 25 у boost-eval и graph-eval, 68
   пар у absorb-calibrate. Гейт «recall@10 упал больше чем на 2 п.п.» тоже не
   заведён — eval-скрипты сверяются с записанными числами точно, а не с допуском.
4. **Выделенного раннера нет.** На общем раннере GitHub строгий режим включаться
   почти не будет, и абсолютные бюджеты в CI останутся печатью. Это честно
   сказано и в `nightly-bench.yml`, и в §2.10 дизайн-документа.
5. **Секции `ubuntu-*` в `bench/baseline.json` нет** — её нужно снять на раннере
   один раз, иначе регрессионная сверка в CI не проводится (скрипт говорит об
   этом вслух).
