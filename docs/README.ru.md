# myc

Локальный, быстрый слой задач и памяти для кодовых агентов: очередь задач,
оплог фактов и решений, гибридный (лексика + вектор) поиск по памяти проекта и
встроенный индекс кода — без собственных сетевых вызовов и без обязательного
ключа к модели. В сеть myc ходит только по вашей просьбе: `myc models fetch`,
`myc code fetch`, `myc version --check` (или `MYC_UPDATE_CHECK=1` — фоновая
проверка версии не чаще раза в сутки из `init` и `wire`).

Агенты забывают. `myc` — та часть, которая нет: решения переживают сжатие
контекста, работа переживает смерть процесса, и то и другое переезжает между
машинами обычным git.

Дизайн — в `docs/design/` (начать с `docs/design/00-brief.md`), рабочие
измерения по конкретным задачам — в `docs/reports/`; числа ниже повторяются
скриптами из `bench/` и `scripts/`.

**Сайт: <https://aistastudio.github.io/myc/>** — каждая возможность с релизом,
в котором появилась, и командой, которой её видно, дорожная карта и замеры в
графиках, по-русски и по-английски, и рядом с каждым числом — команда, которой
его повторяют. Это единственный источник чисел: `bun run site/build.ts` сверяет
каждое число сайта с артефактами замеров в репозитории, числа этого README и
английского — с `site/measurements.json` сайта, а каждую команду и флаг `myc`
на сайте и в обоих README — со справкой `--help` этой сборки; расхождение
роняет сборку.

## Требует Bun — это не мелкий шрифт

Рантайм жёстко завязан на `bun:sqlite` (SQLite и `sqlite-vec` встроены в Bun,
без нативных биндингов на стороне Node). **На голом Node.js или Deno проект не
запустится.** Нужен Bun ≥ 1.3.0 (зафиксировано в `package.json` →
`engines.bun`).

Установка Bun: https://bun.sh

## Установка

Одна команда:

```bash
bun install -g @aistastudio/myc   # 3.40 МБ сжатый, 12.53 МБ распакованный, 13 файлов; модели не качаются
myc --version                     # myc 0.3.7 (schema 1)
```

Работает на macOS и Linux. На Windows — через WSL, Bun и myc ставятся внутри
неё: в cmd и PowerShell лаунчер `myc` не стартует, и установка через npm на
Windows об этом говорит.

Модель эмбеддингов при установке **не** скачивается. Семантический поиск
включается явно: `myc models fetch` (129 МБ, ~7 с). До этого поиск лексический
и говорит об этом в каждом ответе (`WARN degraded.embeddings`). Грамматики для
индекса кода скачиваются так же, один раз: `myc code fetch`.

Чтобы работать с кодом свежее опубликованного релиза — собрать из исходников:

```bash
git clone https://github.com/aistastudio/myc && cd myc
bun install
bun run build          # собирает один бинарь: dist/myc (dist/ не в git)
./dist/myc --version
```

Положите бинарь туда, где его найдёт `myc wire`, — `MYC_BIN`,
`node_modules/.bin`, `~/.myc/bin/myc` или `PATH`. Если не найдёт, `wire` скажет
об этом вслух, а не запишет конфиг, который молча не стартует.

## Быстрый старт

Две команды настраивают проект; остальное — цикл, в котором живёт агент. (При
сборке из исходников — `./dist/myc` вместо `myc`.)

```bash
myc init                        # .myc/ + SQLite + миграции в этом репозитории
myc wire                        # хуки и MCP для Claude Code, Codex, opencode и Kimi
myc ready --claim               # взять следующую задачу
myc show <id>                   # всё, что о ней известно
myc close <id>
myc remember "почему X, а не Y" # записать факт или решение
myc recall "как устроен ретривал"
myc prime                       # стартовый пакет контекста сессии (зовёт агент)
myc code fetch                  # грамматики языков этого репозитория, один раз
myc code index                  # символы, вызовы, поиск по коду
myc doctor                      # схема, счётчики, хуки — где не знает, так и говорит
```

Полный список команд: `myc --help`, детали каждой — `myc <command> --help`.

## Подключение агентов

`myc wire` пишет целиком только свои файлы, а JSON-конфиги сливает по узлам с
`.myc.bak` рядом; `CLAUDE.md` не трогает никогда. Повторный запуск ничего не
меняет. Всё сверх голого `wire` — только по флагу:

```bash
myc wire --dry-run              # показать всё, ничего не писать
myc wire --agents claude,codex  # только часть агентов
myc wire --status-line          # + строка статуса myc под приглашением Claude Code
myc wire --queue-hook           # + тяжёлые команды по очереди (ниже)
myc wire --agents-md            # + блок myc в AGENTS.md
myc wire --scope user           # то же для агентов в git worktree (пользовательский слой Claude Code)
myc unwire                      # снять то, что поставил wire
```

**Агенты в git worktree.** `myc wire` пишет в проект: `.claude/settings.json`,
`.mcp.json`. Агент, которого orca запускает в git worktree вложенного
репозитория (`~/orca/workspaces/<repo>/<ветка>`), живёт в дереве командного
репозитория, и этих файлов там нет, хотя сам `myc` из worktree находит
воркспейс основной копии. `myc wire --scope user` ставит то же в
пользовательский слой Claude Code, который читает любая сессия:
`~/.claude/helpers/myc-hooks.mjs`, хуки SessionStart/PreCompact/PostToolUse и
правила `Bash(myc <команда>:*)` в `~/.claude/settings.json` (слиянием по узлам,
чужие хуки orca, herdr и других инструментов остаются байт в байт), навык
`~/.claude/skills/myc`, MCP-сервер через `claude mcp add --scope user`. Helper
этого слоя сначала сам, без запуска myc, проверяет, есть ли здесь воркспейс
(git worktree — через основную копию), и молчит, если его нет или проект
проводит myc сам, — в проектах без myc хук стоит один старт node, а prime не
приходит дважды. MCP-сервер вне воркспейса отдаёт ноль инструментов и ни
строки инструкций. `--hook-mode replace` здесь запрещён. Журнал —
`~/.myc/wire-user.json`; `myc unwire --scope user` возвращает настройки к
прежним по узлам и снимает MCP-сервер.

С `--status-line` в пользовательский слой встаёт и строка статуса myc — `myc
statusline --scope user`: в воркспейсе myc (и в его git worktree) это полная
строка, вне воркспейса она не печатает ничего своего. Строка, стоявшая до неё
(у orca — ничего не печатающая, она шлёт ввод в orca), записывается в журнал, а
не в нашу команду, и на каждой отрисовке получает тот же stdin, её не ждут:
orca считает своей строку, в команде которой есть её
`agent-hooks/claude-statusline.sh`, и при снятии удаляет её (чужую не трогает),
поэтому слова `claude-statusline` в нашей команде нет. Проект со своей
строкой myc её сохраняет, и она отдаёт ввод той же записанной строке. Заменит
пользовательскую строку другой инструмент — `myc doctor --hooks` это скажет;
`myc wire --scope user --status-line` поставит нашу обратно, а новая станет
прежней; `myc unwire --scope user` вернёт прежнюю байт в байт. `myc doctor
--hooks` сверяет весь пользовательский слой с журналом: наши хуки и правила на
месте в `~/.claude/settings.json`, helper'ы — ровно то, что пишет эта сборка
(устаревший назван вместе со сборкой, которая его записала), строка статуса,
MCP-сервер.

## Тяжёлые команды — по очереди

Несколько агентов на одной машине — в одном дереве или в соседних проектах —
гоняют тяжёлое одновременно: полный прогон тестов, сборки, бенчмарки — и мешают
друг другу: прогоны идут вдвое дольше, бюджеты задержек падают из-за соседа, а
не из-за кода. `myc run` ставит такую команду в общую для всех репозиториев
пользователя машины очередь (`~/.myc/queue.db`), ждёт свободный слот (кто
первым пришёл, того первым и обслужат) и выполняет её с тем же терминалом и тем
же кодом выхода:

```bash
myc run -- bun test              # ждёт очереди (по умолчанию --max-wait 5m), потом выполняет
myc run --max-wait 15m -- make   # ожидание дольше — под более длинный таймаут инструмента
myc queue                        # кто выполняется, кто ждёт и сколько
```

```
$ myc queue
heavy · slots 1 · 1 running · 1 waiting · ~/.myc/queue.db
  running #1      4s  bun test  ~/src/api  session 6468c59d · orca term_efe4850f · pid 44815 · command pid 44827
  waiting #2      3s  bun run build  ~/src/web  session 6468c59d · orca term_efe4850f · pid 44850 (#1 in line)
```

Ждущий пишет в stderr, кого ждёт, а после `--max-wait` сдаётся с кодом 9 и
называет, кто впереди:

```
myc run: waiting for a 'heavy' slot (1/1 busy, 1 waiting ahead), waited 0.0s of max 3s — held by 'bun test' in ~/src/api, session 6468c59d, orca term_efe4850f, pid 44815, running 13s
```

Упавший держатель (даже по `SIGKILL`) слот освобождает; вложенный `myc run`
идёт сразу, в слоте предка. По умолчанию один слот на полосу,
`MYC_HEAVY_SLOTS=2` — два. `.env` и `bunfig.toml` проекта myc не читает:
команда получает окружение вызывающего как есть.

**Помнить об этом агенту не нужно.** `myc wire --queue-hook` ставит Claude
Code хук `PreToolUse`, который переписывает тяжёлую Bash-команду в
`myc run -- <та же команда>` до её запуска. Тяжёлое — полный прогон тестов и
сборка: `bun test` без путей, `bun run build` / `typecheck`, `npm` / `pnpm` /
`yarn` `test` и `build`, `cargo test` / `build`, `go test ./...`, `pytest` без
путей, `make`. Точечный `bun test <путь>`, уже обёрнутое в
`myc run`, фоновое и вложенное не трогается. `MYC_QUEUE_HEAVY` заменяет список
(`+…` дополняет, `off` выключает хук). Только по флагу: `wire` без него такого
хука не пишет, а `unwire` его снимает. Хук дешёвый, потому что стоит на каждом
вызове Bash: лёгкую команду отпускает сам shell хоста, не запуская ни bun, ни
node, — 3.4 мс медиана и 4.3 мс p99 в прогоне 2026-09-11 при бюджете prime-хука
30 мс p99 (`bun test packages/cli/src/hooks/queue-hook.multiprocess.test.ts`).

**`myc run` — не обход прав.** Он исполняет что угодно, поэтому команда в
очереди проходит без вопроса, только если ваши правила пропустили бы исходную
(`Bash(bun test:*)` оставляет `bun test` без вопроса и в очереди); иначе Claude
Code спрашивает, и в вопросе видна вся команда, а deny/ask-правило исходной
команды действует как прежде. Так же судится `myc run -- <команда>`, набранный
агентом. По той же причине `wire` не пишет широкое `Bash(myc:*)`: он разрешает
подкоманды myc по одной, а `run`, `statusline --then`, `wire` и `unwire`
спрашивают.

## Код-интеллект

Код-интеллект встроен, и движок у него тот же, что у альтернатив: tree-sitter,
грамматики качаются по требованию, а не лежат в пакете. Символы, вызовы и поиск
по коду — для TypeScript, TSX, JavaScript (js, jsx, mjs, cjs) и Python: для них
есть правила разбора определений. В пакете грамматик их 36, но язык
добавляется парой — правило и строка каталога, поэтому грамматика, которая не
дала бы ни одного символа, не предлагается. Остальным файлам доступны
`code grep`, якоря и протухание.

`myc code fetch` скачивает ровно те грамматики, что нужны файлам этого
репозитория, со сверкой sha256 — это единственный шаг, который ходит в сеть;
индексация туда не ходит никогда, а язык без грамматики пропускается и
называется. `myc code index` строит индекс инкрементально: повторный прогон по
неизменному дереву не читает ничего, дальше индекс обновляется в фоне. Читают
его — из CLI и через MCP одинаково:

```
myc code symbol <имя>    где определено и какое знание к этому привязано
myc callers <имя>        кто зовёт; --direction out, --depth all
myc code search "…"      по смыслу, когда имя неизвестно
myc code grep "<лит>"    все вхождения; --in <путь> сужает область
myc code map             ориентация: кластеры каталогов, их хабы, кто от них зависит
myc skeleton <файл>      API файла — и во сколько раз это дешевле, чем читать его целиком
```

Перечень файлов — от самого git (`git ls-files`, то есть с `.gitignore`;
дерево без git обходится, и команда об этом говорит). Поверх любого перечня
файлы с секретными именами не индексируются никогда, что бы ни было в
`.gitignore`: `.env` и `.env.*` (шаблоны вроде `.env.example` индексируются),
`*.pem`, `*.key`, хранилища ключей, приватные ключи SSH, `.npmrc`, `.netrc` и
другие файлы учётных данных — `code index` называет их число, но не имена, а
`code grep` читать такой файл отказывается.

**Вложенные репозитории и git worktree.** Воркспейс может быть экосистемой:
корень — git-репозиторий, внутри него самостоятельные репозитории (не
подмодули). Код-индекс у такого воркспейса один, из корня: строка на файл,
пути вида `messaging-server/server/src/x.ts`. Изнутри вложенного репозитория
любая код-команда отвечает из его части индекса корня, и пути в ответе — от
корня того репозитория, где вы стоите; из корня ответы не меняются.
`myc code index`, запущенный во вложенном репозитории, обновляет его часть
индекса корня, а не строит вторую копию тех же файлов. Индекс и сам следит
за свежестью: после любой команды myc, если его последний прогон старше
15 минут (`MYC_CODE_INDEX_PERIOD_MS`), в очередь ставится один фоновый
`code index` на воркспейс, и он идёт отдельным процессом с пониженным
приоритетом, не задерживая команду; строка статуса и код-команды говорят,
когда индекс обновляется, стоит в очереди или устарел. Из git worktree (в том числе вынесенного за дерево
воркспейса) ответ берётся из индекса основной копии: отдельного индекса на
ветку нет. Если worktree стоит на другом коммите или в нём есть правки
отслеживаемых файлов, каждый ответ несёт `WARN code_index.worktree_divergent`
с обеими ветками: строки и спаны могут не совпасть с вашими файлами.
`code grep` читает файлы worktree (номера строк — ваши, владельцы — из
индекса); `skeleton`, когда ваша копия файла разошлась с индексом, показывает
объявления основной копии и говорит об этом. Если репозиторий не покрывает
ни один индекс, подсказка — команда для корня воркспейса
(`myc -C <корень> code index`), а не та, что построила бы дубль. Якоря,
поставленные из корня и изнутри репозитория, лежат под разными ключами;
`code symbol` читает оба.

Якоря привязывают знание к участку кода и следуют за ним при правках; эта
половина от языка не зависит и проверена на Python так же, как на TypeScript.

## Миграция с beads

```bash
cd <проект-с-beads>
myc init
myc import-beads --dry-run   # посчитать, что приедет, ничего не менять
myc import-beads             # снимок соберёт сам: bd export --include-memories
```

Повторный запуск — синхронизация, а не вторая копия: поля, изменённые в beads
(статус, приоритет, метки, причина закрытия, parent, блокеры), применяются
обычными изменениями графа, а локальные правки в myc молча не затираются
никогда — односторонние сохраняются и называются, двусторонние называются
конфликтами и остаются нетронутыми. Между машинами то же переносит файл
снимка: `bd export --include-memories > snapshot.json`, потом
`myc import-beads snapshot.json`.

**Это настоящая миграция, а не демонстрация.** Живой проект, ввезённый в
пустой воркспейс за 889 мс: 796 задач, 972 зависимости, 265 заметок,
41 память — незнакомые типы задач переносятся дословно и называются,
приоритеты вне шкалы прижимаются и называются, вместо того чтобы одна странная
строка роняла весь импорт. Эти числа — с первого релиза (0.1.1, 2026-09-07), и
тот прогон молча потерял комментарии той же выгрузки, отчитавшись, что все
заметки ввезены; это нашли на следующий день на живом проекте и исправили в
0.2.0 (`git show aac5d1f`). Что импорт везёт теперь:

- комментарии — в нить узла, с авторами; незнакомые поля верхнего уровня
  называются, а не выбрасываются (0.2.0);
- критерии приёмки и дизайн — в тело задачи между управляемыми маркерами, и
  даты, автора и владельца из источника (0.3.3);
- статусы, которых в myc нет, вроде `deferred`, — как `blocked` с сохранённым
  исходным словом, и никогда как `open` (0.3.3);
- вложенные репозитории общего воркспейса — каждый со своим охватом; пустой
  источник — отказ с подсказкой, а не молчаливый ноль (0.3.3).

На том же графе обе очереди готовых задач теперь дают одни и те же 152 задачи.
Так было не всегда: myc предлагал 195 против 144 у beads, потому что beads
наследует блокеры вниз по цепочке parent, а myc смотрел только на собственные
блокеры задачи. Те 51 задача лежали внутри ещё заблокированного эпика, и beads
был прав, что их прятал; `memory-atcm254ry6c7` закрыта, `anc_blockers`
материализуется триггером, и очередь теперь пишет
`281 blocked (51 through an ancestor)`, а не молча их предлагает.

## Чем отличается

**Скорость — ограничение, а не оптимизация.** У каждого горячего пути есть
бюджет, и бюджетный тест утверждает три вещи: структурную (план запроса,
предфильтр), относительную (здоровый путь против заведомо деградировавшего
соперника, замеренные вперемешку, так что железо сокращается) и абсолютную. На
каждом пуше CI проверяет первые две. Абсолютные бюджеты и порог регрессии p95
в 15% откалиброваны на darwin-arm64-14 и держатся на ней; CI и ночной прогон
идут на 4-ядерных раннерах GitHub, которые не эта машина и объявлены
неоткалиброванными (`MYC_BENCH_ABSOLUTE=0`), поэтому там абсолютные числа
печатаются и пишутся в журнал, но не проверяются. Замер на 100 000 узлов
2026-09-11, darwin-arm64-14, myc 0.3.6, с тех пор не переснимался
(`bun run scripts/bench-latency.ts`):

| операция | p99 | бюджет |
|---|---|---|
| `prime` — пакет контекста сессии | 0.608 мс | 30 мс |
| `read` — чтение узла | 0.010 мс | 3 мс |
| `search` — гибридный поиск | 8.215 мс | 25 мс |
| `write` — запись | 0.327 мс | 5 мс |
| `cold_start` — холодный старт бинаря | 21.337 мс | 60 мс |

**Ранжирование измерено, а не заявлено.** Два размеченных корпуса с
градуированной релевантностью, и в каждом *контрольная группа, которой
становится хуже*, когда функция работает, — выигрыш нельзя изготовить подгонкой
корпуса (оба перемерены 2026-09-10):

- бусты (приоритет, свежесть, ярус): MRR@10 **0.520 → 0.867** (`bench/boost-eval.ts`)
- расширение по графу на 2 хопа: MRR@10 **0.193 → 0.422** (`bench/graph-eval.ts`),
  а группа запросов, недостижимая за один хоп, идёт 0.000 → 0.333

**Кеш, который не может устареть молча.** Кеши результатов, эмбеддингов и
гидратации инвалидируются по `MAX(oplog.seq)`, прочитанному *из базы*, поэтому
запись другого процесса их тоже сбрасывает. Попадание в кеш на два порядка
дешевле промаха — 252× в прогоне 2026-09-07, ≈27 000× для эмбеддингов;
отношение — стенное время и зависит от машины. Ранжирование — нет: тот же MRR
до третьего знака, ноль расхождений в рангах.

**Память переживает сжатие контекста.** `myc wire` ставит хук PreCompact:
перед тем как контекст агента сожмут, эпизод сессии пишется на диск — сырым,
`L0`, `acl private`, с замаскированными секретами, — а в выживший контекст
печатается спасательный пакет. Дистилляция ставится в очередь и никогда не
идёт на пути записи. Эпизод на диске раньше всего остального, поэтому
превышение таймаута хука стоит выжимки, а не записи:

```
$ myc absorb-session --reason manual --transcript … --agent claude
# myc: context is being compacted — here is what must not be lost
episode sess-5jh8je4g050m saved (265 B)
NEXT     myc show sess-5jh8je4g050m · myc ready --claim
```

**Решения из сжатия — кандидаты, а не факты.** Тот же хук вытаскивает из
стенограммы строки «решили / потому что» и пишет их кандидатами (`state
pending_review`): recall, search, prime и MCP их не отдают, пока кто-то не
подтвердит. `prime` называет их в подвале — `N pending review hidden — myc
review`, — а `myc review` показывает их списком, своя сессия первой, чтобы
человек или агент разобрал. Подтверждённый кандидат становится знанием так же,
как рождается новая заметка (эмбеддинг и классификация absorb — в очереди);
отклонённый отзывается, причина остаётся в узле. Агент делает то же через MCP:
`myc_ready` с `review` — список, `myc_update` с `confirm` или `reject` —
разбор; в вебе, в базе знаний, у строки кандидата — две кнопки.

```
$ myc review
PENDING REVIEW 2 · 1 in this session's prime · 1 from other sessions · session 3f9c21aa
$ myc review confirm memory-6k2x…
$ myc review reject memory-9x1q… --reason "пересказ задачи, а не решение"
```

Отозванная заметка — и отклонённый кандидат среди них — не попадает ни в один
путь выдачи, как и заменённая версия: заменённое, отозванное и отменённое — один
список на recall, prime и строку статуса.

**Строка статуса с тем, чего агент не видит.** `myc wire --status-line` ставит
одну строку под приглашением Claude Code — заполненность контекста, очередь
задач, индекс кода, память проекта и сколько обращений этой сессии к myc
действительно что-то вернули:

```
myc │ ctx 42% │ 61 ready · 34 blocked │ 612 files · 4268 symbols · 1h ago │ 101 notes │ 600/653 useful calls
```

«Полезные» считаются по транскрипту самого хоста, а не на глаз: ошибка, отказ
или пустой ответ — это обращение, но не полезное. Только по флагу — `wire` без
него `statusLine` не трогает — и прежнюю строку не вытесняет: прежняя команда
(строка статуса, на которую рассчитывает другой инструмент) получает тот же
ввод, её не ждут и не убивают. Отрисовка заняла 34 мс по медиане в прогоне
2026-09-10.

**Память разделена по сессиям, и разделение видно.** У каждой заметки есть
охват: `session` (этот разговор) или `project` (все). Автоматический пакет
контекста — `prime` — несёт только заметки текущей сессии; сессия другого
агента в вашу не протекает. Явный `myc recall` находит и их, потому что
спрятать знание — не то же, что ограничить его охват, и помечает каждую строку:
`ses` своя сессия, `ses*` чужая, `prj` весь проект.

```
$ MYC_SESSION_ID=s1 myc recall "retries"        $ MYC_SESSION_ID=s2 myc recall "retries"
… prj  project note: retries use jitter          … prj  project note: retries use jitter
… ses  session note: retries back off…           … ses* session note: retries back off…
3 of 3 · bm25 only · …                           3 of 3 · bm25 only · … · 2 from other sessions
```

**У памяти три независимые оси**, и поверхность говорит, что скрыла: ярус
(проектный или личный), охват сессии, охват репозитория. `prime` печатает
`N from other sessions hidden` и `N notes from other repos hidden`, а не молча
сужает выдачу.

**Деградация громкая.** Молчаливых откатов нет: если векторная ветка
недоступна, вывод говорит об этом и помечает ответ как лексический; если
превышен бюджет, он назван числом. Инвариант: ухудшенный ответ не имеет права
быть неотличимым от здорового. С `--strict` ухудшенный ответ ещё и выходит с
кодом 6 вместо 0, а строка `WARN` печатается по-прежнему.

**Синхронизация между машинами через обычный git, слиянием по полям.** В git
идёт только оплог. Две машины, правившие один узел, сходятся: одна меняла
заголовок и приоритет, другая заголовок и теги — после обмена у обеих поздний
заголовок, приоритет первой и теги второй. Ничего не теряется на
«последний пишущий побеждает» по целым записям.

**Сторожа доказаны мутациями.** Каждый отказ и каждый инвариант сопровождается
мутацией, которая его убирает; сторож, чьё удаление не роняет ни одного теста,
считается отсутствующим. Полный прогон: 3501 pass / 0 fail / 16 skip
(`bun test`, 2026-09-11).

## Что умеет myc

Задачи с арендой, зависимостями и блокерами, наследуемыми вниз по цепочке
parent; память, которая переживает сжатие и разделена по сессиям и
репозиториям; ранжированный гибридный поиск; индекс кода выше; хуки и MCP для
четырёх агентов; общая для машины очередь тяжёлых команд; строка статуса;
импорт из beads; локальный веб-интерфейс (`myc viz`: граф, очередь, доска,
карточки, поиск, здоровье — правки идут тем же путём записи, что у CLI); git
worktree и вложенные репозитории; синхронизация через git и `doctor`, который
сверяет заявленное с пересчётом.

Полный список — у каждой возможности релиз, в котором она появилась, и
команда, которой её видно на вашей машине, а каждая команда при сборке сайта
сверяется со справкой `--help` этой сборки, — на сайте:
<https://aistastudio.github.io/myc/#features>.

## Дорожная карта

Где стоит каждая веха — закрытые/все подзадачи каждого эпика из трекера самого
проекта и каждая задача, ещё открытая внутри него, без дат, — на сайте:
<https://aistastudio.github.io/myc/#planned>. Числа не вписаны руками:
`bun run site/roadmap.ts` читает их из myc перед релизом, а сборка сайта не
пропускает план, описывающий задачу, которая в трекере уже не открыта.

Коротко: ядро, память, семантика и интерфейс человека (M0–M2, M7) сделаны или
почти сделаны, как и английский вывод каждой строки CLI и MCP; код-интеллект
(M3, вместе со встроенной заменой graft) и очередь тяжёлых команд вышли, и
открытые задачи у них ещё есть; командная веха (M4: `myc serve`, ACL, сетевая
синхронизация, Postgres) — в основном дизайн; самообучение роя (M5: роутинг
моделей по цене и исходу, с общим пулом статистики агентов) и дистилляция (M6)
не начаты.

Что это значит на практике: **сегодня myc — однопользовательский локальный
инструмент поверх файлов в git.** Сервера, ACL и командного режима нет. Они
спроектированы (`docs/design/03-interfaces-and-integration.md`,
`docs/design/04-swarm-learning-and-routing.md`) и заведены задачами, но не
реализованы.

## Синхронизация между машинами

В git идёт только оплог (`myc export` → `.myc/graph`, `myc import` при клоне) —
не производные проекции и не кеши. `.myc/workspace.toml` и оплог в
`.myc/graph` коммитятся намеренно; `.myc/myc.db*`, локальные кеши и рантайм-
состояние — нет (см. `.gitignore`).

Merge-драйвер регистрируется один раз на клон:

```bash
git config merge.myc-oplog.driver "myc merge-driver %O %A %B %L %P"
```
