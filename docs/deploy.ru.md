# Развёртывание командного сервера myc

Один бинарь и один Postgres. На сервере живёт воркспейс команды; у каждого
человека и каждого агента свой локальный воркспейс, а обмен идёт командой
`myc sync`.

Прежде чем планировать работу вокруг этого, прочтите
[чего пока нет](#чего-пока-нет): сервер — место, где реплики **встречаются**,
а не пока ещё место, где живёт весь рабочий цикл.

## Что нужно

- Хост с Docker и доменное имя, указывающее на него.
- Postgres 17 с [pgvector](https://github.com/pgvector/pgvector) ≥ 0.7 —
  схеме нужны `halfvec` и HNSW. Образец compose поднимает его сам; управляемый
  Postgres тоже подойдёт, если у него есть это расширение.
- Обратный прокси для TLS. Сервер говорит по обычному HTTP намеренно и
  сертификат не держит.

## 1. Поднять сервер

```bash
git clone https://github.com/aistastudio/myc && cd myc
cp deploy/compose.yml deploy/compose.prod.yml
```

В `deploy/compose.prod.yml` до первого старта поменяйте три вещи. Именно они
отличают образец от установки:

1. **Пароль** — в трёх местах: `POSTGRES_PASSWORD`, пароль внутри
   `MYC_PG_URL` и `deploy/initdb/10-app-role.sql`. Берите его из секрета
   оркестратора, а не из файла.
2. **Опубликованный порт** — оставьте на `127.0.0.1`, чтобы до него доставал
   только прокси.
3. **`MYC_BOOTSTRAP_TENANT` и `MYC_BOOTSTRAP_TOKEN`** — оставьте на первый
   старт и уберите обе строки после. Они существуют, чтобы `up -d` давал
   сервер, в который можно войти; первый секрет они печатают **в журнал
   контейнера**, а это не то место, где ему жить постоянно.

```bash
docker compose -f deploy/compose.prod.yml up -d
docker compose -f deploy/compose.prod.yml logs server | grep -A2 'bootstrap token'
```

На пустом томе Postgres накатывает схему сам: сперва роль со входом
(`10-app-role.sql`), затем `db/schema.postgres.sql`. Схема создаёт таблицы,
триггеры и политики RLS, а прав на это у прикладной роли намеренно нет —
поэтому её накатывает суперпользователь, а сервер дальше живёт ролью
`myc_app`.

Секрет из журнала запишите. Он показывается один раз: в базе хранится только
его sha256.

## 2. Поставить TLS перед сервером

Выдавать ли куке сессии флаг `Secure`, сервер решает по `X-Forwarded-Proto`,
поэтому прокси обязан его ставить. У Caddy это две строки:

```caddyfile
myc.example.com {
	reverse_proxy 127.0.0.1:8080
}
```

Caddy ставит `X-Forwarded-Proto` сам. В nginx — руками:

```nginx
location / {
	proxy_pass http://127.0.0.1:8080;
	proxy_set_header X-Forwarded-Proto $scheme;
	proxy_set_header Host $host;
}
```

Проверка снаружи:

```bash
curl https://myc.example.com/v1/health
# {"ok":true,"ver":"0.4.0","uptime_s":…,"pid":…}
```

`/v1/health` — единственный маршрут без токена. Всё остальное отвечает 401,
пока токена нет.

## 3. Арендаторы и токены

**Арендатор** — это организация; токены выпускаются под ним, а строки разных
арендаторов изолированы политиками RLS. Большинству команд нужен ровно один.

```bash
alias myc-srv='docker compose -f deploy/compose.prod.yml exec -T server myc serve'

myc-srv --add-tenant acme:Acme
myc-srv --add-token acme:anna --role owner
myc-srv --add-token acme:boris --role member
myc-srv --add-token acme:reviewer-bot --role agent
myc-srv --tokens          # у кого какой и когда пользовались
myc-srv --revoke-token tok_…
```

По токену на человека и на агента — общий не заводите. Тогда отзыв стоит
одной строки и никому больше не стоит доступа.

**Роли и права.** Роли: `owner`, `maintainer`, `member`, `agent`, `viewer`;
права: `read`, `write`, `claim`, `sync`, `admin`. Роль — это набор прав по
умолчанию, а `--scopes read,sync` сужает его явно.

`sync` по умолчанию есть только у `owner` и `maintainer`, и это не
осторожность, а то, чем реплика является. Обмен везёт **оплог**, который не
фильтруется предикатом видимости: реплика полна по построению, иначе она не
сходится. Значит право забрать реплику — это право видеть в воркспейсе всё,
включая чужие приватные заметки. Давайте `sync` тем, у кого такой доступ и
так есть, остальным — `member`, который читает через API под ACL.

**Админка** — `https://myc.example.com/v1/admin`. Она спрашивает у браузера
токен формой и держит его в HttpOnly-куке с `SameSite=Strict`. Нужно право
`admin`.

## 4. Что делает каждый в команде

Имя воркспейса на сервере и **слаг** воркспейса на машине обязаны совпасть:
слаг входит в id каждого узла, и обмен воркспейса `cherry` с воркспейсом `web`
переселил бы узлы туда, где их не ждёт ни одна из сторон. `myc sync` такое
отвергает, а не сливает.

```bash
# один раз на машину, в каталоге проекта
myc init --slug acme          # или: слаг уже лежит в .myc/workspace.toml

export MYC_SERVER=https://myc.example.com/acme   # воркспейс — в пути
export MYC_TOKEN=myc_…                            # не в командной строке
myc sync
```

**Имя, которым человек подписывает работу, обязано совпасть с тем, на кого
выпущен его токен.** `myc init` берёт его из git — той же подписи, что стоит
в коммитах, — записывает в воркспейс и печатает:

```
  ✓ actor                Анна Петрова (from git; override with $MYC_ACTOR)
```

Выпускайте токен этого человека ровно на это имя
(`--add-token acme:"Анна Петрова"`) или задайте у него `MYC_ACTOR` тем, что
написано в токене. Совпасть они обязаны потому, что приватный узел
принадлежит автору ПО ИМЕНИ: при расхождении заметка доезжает и локально
автору видна, а на сервере принадлежит имени, на которое токена нет ни у
кого, — и не видна никому. Ничего не утекает, но и не находится.

У воркспейса, созданного myc до 0.4.0, записанной личности нет — там
умолчание остаётся прежним, `$USER`, и это не недоделка: сменить личность
молча в базе с накопленной историей значит осиротить каждую аренду и каждое
назначение. Посмотрите `actor` любого узла, чтобы узнать, каким именем
подписан тот воркспейс, и либо выпустите токен на него, либо задайте
`MYC_ACTOR`.

`MYC_TOKEN` живёт в окружении потому, что аргументы видны в `ps`, в истории
оболочки и в журналах хуков. Положите оба экспорта в профиль оболочки или в
`.envrc` проекта, который не коммитится.

Дальше — обычный локальный цикл: `myc prime`, `myc ready --claim`,
`myc recall`, `myc remember`, `myc close` — всё по локальной базе, на местной
скорости, а `myc sync` тогда, когда нужно отдать своё и забрать чужое. Обмен
идемпотентен: оборванный продолжается повторным запуском.

## 5. Резервное копирование

Том Postgres — единственное состояние сервера: бинарь его не имеет, а админка
и токены лежат в той же базе.

```bash
docker compose -f deploy/compose.prod.yml exec -T db \
  pg_dump -U postgres -Fc myc > myc-$(date +%F).dump
```

У каждой машины к тому же лежит полная реплика воркспейса, поэтому потерянный
сервер стоит сервера, а не знания, — но только для тех воркспейсов, которые
кто-то действительно синхронизировал. Копии всё равно делайте.

## 6. Обновление

Образ собирается из репозитория, поэтому обновление — это пересборка:

```bash
git pull
docker compose -f deploy/compose.prod.yml build server
docker compose -f deploy/compose.prod.yml up -d server
curl -s https://myc.example.com/v1/health   # «ver» обязан стать новым
```

**У релиза, меняющего схему Postgres, автоматической миграции сегодня нет.**
`--apply-schema` пишет схему в **пустую** базу и отказывается от населённой
намеренно: накат DDL поверх живых данных — это миграция, у неё свой порядок,
свои проверки и свой откат, и делать её молча при каждом старте контейнера —
верный способ потерять базу. Перед обновлением смотрите заметки к релизу; если
номер схемы сдвинулся, считайте это плановой операцией.

## Чего пока нет

**С сервером разговаривает лишь ЧАСТЬ CLI.** Удалённо сегодня работают
`create`/`task`/`bug`/`epic`/`msg`, `update`, `claim`, `list`, `ready`,
`show`, `prime` и `sync`. Остальные — `close`, `remember`, `recall`,
`comment`, `link`, `dep`, `attempt`, `search`, `code` — отказывают
`precond.no_remote`, а не уходят молча в локальную базу: увидеть чужие задачи
и принять их за общие хуже, чем получить ошибку.

Поэтому работающая форма такая: у каждого локальный воркспейс, а обмен идёт
через сервер. Указать `MYC_SERVER` и работать «в нём» — не тот режим, вокруг
которого сегодня стоит строить процесс.

Ещё нет: гибридного поиска на Postgres (у серверного `recall` нет ни
лексической, ни векторной ветки — лексический источник заработал, векторному
нечего искать), SSE-дельт для веб-интерфейса и массового ввоза существующего
воркспейса из SQLite в Postgres.

## Когда что-то отказывает

| Что видно | Что это значит |
|---|---|
| `401 denied.no_token` | нет `MYC_TOKEN`, либо прокси срезает заголовок `Authorization` |
| `denied.scope: this token has no 'sync' scope` | токен выпущен как `member`; выпустите с `--role owner` или `--scopes …,sync` |
| `usage.ws_mismatch` | локальный слаг и воркспейс сервера разные — в сообщении названы оба |
| `precond.no_remote` | у этой команды нет удалённого режима; выполните её локально |
| health отвечает `ok`, остальные маршруты — `500 Something went wrong!` | контейнер жив, но до Postgres не достаёт. Проба живости намеренно ничего не знает о базе; сама пятисотка — голая страница без кода и причины (известный дефект, memory-3h980j79swnh), причина при этом лежит в журнале контейнера |
| `/v1/readyz` отвечает `401` | готовность сообщает состояние системы, поэтому тоже требует токена; для пробы живости оркестратора берите `/v1/health` |
